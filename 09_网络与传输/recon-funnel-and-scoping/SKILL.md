# 侦察漏斗与漏洞面收敛

## R — 原文 (Reading)

> “黑客在入侵之前，都会进行踩点以收集相关信息，然后扫描系统的相关漏洞，最后就可以利用相关攻击手段攻击目标。”
>
> — 网络安全技术联盟 编著，第3章「网络踩点侦察与系统漏洞扫描」章首

---

## I — 方法论骨架 (Interpretation)

- 侦察不是“打开扫描器扫一遍”，而是一条有先后依赖的流水线：前一步的产出是后一步的输入。
- 第一问不是“有什么漏洞”，而是“目标是否可达”；没有存在性，后面的系统、端口与漏洞都无从谈起。
- 确认存在之后才粗判操作系统，再枚举端口与服务，再用 WHOIS/DNS 与路由跳数还原归属和边界。
- 最后才把“系统 + 服务 + 拓扑”交给漏洞扫描器，由它给出候选范围，而不是判决书。
- 每一步都可能失败；失败时先拆竞争假设（地址错、未开机、ICMP 被过滤、ACL、NAT），再设计能区分假设的补充探测。
- “ping 不通”只否定了“当前 ICMP 探测可达”，不能否定主机存在；端口“关闭”同理只说明该类探测没有回应。
- 任何单点信号（TTL、banner、扫描器标签）都只是候选证据，至少要有第二类独立证据才能升级为结论。
- 收敛的终点不是“扫到了什么”，而是“哪些暴露面已被证实、哪些仍未验证、下一步验证什么”。

## A1 — 书中的应用 (Past Application)

### 案例 1: 用 ping 的 TTL 初判 Windows 主机
- **问题**: 需要确认 192.168.0.135 是否在线，并粗略判断它属于哪类操作系统。
- **方法论的使用**: 先 ping 确认有回包，再读取 TTL=128，按默认初值把目标归入 Windows 候选；同节的对照目标 192.168.0.100 返回“无法访问目标主机”。
- **结论**: 135 在线且很可能是 Windows；100 的失败不能直接判“不存在”，还可能是未开机或过滤了 ICMP。
- **结果**: 作者把 135 作为后续选择工具与攻击路径的前提，但 TTL 只给出了候选范围，并未做进一步确认。

### 案例 2: 用 Zenmap 摸清网段端口与拓扑
- **问题**: 需要知道 192.168.0.1–150 中哪些主机在线、分别开放了哪些服务。
- **方法论的使用**: 选择 Intense scan，实际执行 `nmap -T4 -A -v 192.168.0.1-150`，逐条读取开放端口（如 445/tcp、139/135），再用“主机/拓扑/主机明细”标签补全系统与设备信息。
- **结论**: 得到一份“主机—端口—服务”清单，可据此挑选下一步要验证的对象。
- **结果**: 扫描结果缩小了范围，但仍是候选，具体服务与版本仍需人工确认。

### 案例 3: 用流光把漏洞范围收敛到 1433 端口
- **问题**: 网段内是否存在可直接进入的 SQL Server 弱口令入口。
- **方法论的使用**: 用流光的高级扫描针对 1433 端口猜解 sa 口令，扫描日志按主机、端口、账号、口令逐条记录。
- **结论**: 192.168.0.16 的 sa 口令为空、192.168.0.7 的 sa 口令为 123，属于可直接验证的具体暴露面。
- **结果**: 两台主机被拿到数据库管理员入口；说明收敛必须落到“主机 + 端口 + 账号”的粒度，而不是停留在“网段有高危”。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新接手一个网段或办公网，资产台账缺失，需要知道哪些主机在线、分别开了哪些服务。
2. 同事说某业务系统明明在线，但你 ping 或 telnet 不通，需要判断是主机不在、网络不通，还是被过滤。
3. 扫描器一次吐出几十条“高危”，需要判断哪些是真暴露、先验证哪几条。
4. 授权渗透或攻防演练开始前，需要界定范围、确认目标可达，并留下可复核的侦察记录。
5. 自有系统上线前自查暴露面，想知道“外面能看到什么”。

### 语言信号 (用户的话里出现这些就应激活)

- “先踩点”“帮我扫一下这个网段”“目标到底在不在线”
- “ping 不通是不是主机没开”“是不是防火墙拦了”
- “nmap 扫出来一堆端口，哪些要管”“扫描结果怎么收敛”
- “recon this subnet”“is the host up”“port scan results are noisy”“scope the assessment”

### 与相邻 skill 的区分

- 与 `hidden-account-hunt` 的区别: 该 skill 处理入侵后主机上“有没有隐藏账号”，靠命令行、图形界面、注册表与审核日志跨视图核对；本 skill 处理入侵前目标网络“有什么暴露面”，不进入主机账号层。侦察中若通过 IPC$ 拿到用户列表，只把它当作线索，账号核实交给该 skill。
- 与 `identity-deception-detection` 的区别: 该 skill 解释 ARP/DNS/URL 的身份映射被替换；本 skill 遇到探测失败时先考虑可达性与过滤，不把“没回应”直接归因于欺骗。若发现解析结果与可信 DNS 不一致，转该 skill。
- 与 `usb-autorun-hardening` 的区别: 该 skill 封可移动介质入口；本 skill 只做网络侧侦察，不处理 U 盘 autorun。
- 与 `malware-triage-order` 的区别: 该 skill 是已感染主机的处置顺序；本 skill 是感染前的目标发现。若目标已确认失陷，先处置再谈侦察。
- 与 `data-backup-recovery-discipline` 的区别: 该 skill 管备份与恢复；本 skill 不涉及数据恢复，也不把“扫描前先备份”当作替代。
- 与 `wireless-security-grading` 的区别: 该 skill 评估 WEP/WPA/WPS 与无线管理面；本 skill 可以发现无线设备暴露，但不做加密分级。问“Wi-Fi 密码够不够强”走该 skill。
- 与 `buffer-overflow-defense-layering` 的区别: 该 skill 针对已确认的溢出漏洞设计防御；本 skill 只负责找到暴露的服务与版本。若问题已经变成“这个漏洞怎么防”，转该 skill。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行:

1. **锁定授权与边界**
   - 完成标准: 写下目标清单（IP/域名/网段）、时间窗、允许的探测强度、排除资产与联系人；没有明确授权就停止，不发出任何探测包。
   - 判停条件: 若目标不在授权范围，跳到步骤 5，只输出“未执行”和所需授权。

2. **确认目标存在，优先收集两类独立证据**
   - 动作: 先 ping/ICMP，再用 TCP 端口（如 80/443/22/445）、ARP 或邻居表、traceroute 末跳、DNS 解析、业务方实际访问记录交叉。
   - 完成标准: 至少两类独立证据指向同一目标，或明确列出“当前所有手段均不可达”。
   - 判停条件: 若两类证据都不可达，不要把结论写成“不存在”；进入步骤 3 拆假设，或记录“当前探测方式不可达”。

3. **拆解失败原因，逐条排除竞争假设**
   - 动作: 对“地址不在本网段 / 主机未开机 / ICMP 被过滤 / ACL 丢包 / NAT 或跳板 / 域名解析错”分别设计区分实验（换协议、换端口、查路由、对比可信 DNS、找旁路信号）。
   - 完成标准: 每个假设都有“支持 / 排除 / 仍未知”的状态和对应证据。
   - 判停条件: 若证据指向解析或身份被替换，转 `identity-deception-detection`；若主机已确认失陷或异常，先转 `malware-triage-order`。

4. **判操作系统、端口与拓扑，只给候选**
   - 动作: TTL 粗判（注意每跳递减、可伪造）→ 端口扫描并记录 open/closed/filtered → banner/服务/版本 → WHOIS/DNS → traceroute 还原边界。
   - 完成标准: 操作系统有候选且至少两类佐证；每个开放端口有服务/版本或“未知”标记；拓扑有边界节点。
   - 判停条件: 若只有 TTL 一个信号，只能写“候选”，不得写“确认 Windows/Linux”。

5. **把结果收敛成漏洞候选并人工验证**
   - 动作: 用“服务 + 版本 + 配置”匹配候选漏洞；按影响与可达性排序；对高优先级做最小化验证（banner、版本、非破坏性验证），记录未验证项。
   - 完成标准: 输出一张表，每条含“主机 / 端口 / 服务 / 候选漏洞 / 证据 / 状态（已证实、可能、未证实）/ 下一步”；没有一条只写“扫描器说高危”。
   - 判停条件: 若任务转为“怎么防”，转 `buffer-overflow-defense-layering`；若需要实际利用，交给获得额外授权的利用验证流程，不在本 skill 内扩大动作。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 目标不在书面授权范围内，或授权边界含糊：侦察本身就是发包行为，可能触发告警或影响业务。
- 只是要利用某个已知漏洞：本 skill 不提供利用链，收敛到候选后应转授权验证流程。
- 只问某个工具的参数、安装或菜单路径：这是工具用法，不是侦察方法论。
- 已有完整资产台账与监控，只需核对一条记录：不必重跑整个漏斗。
- 生产高峰或脆弱工控环境：主动扫描可能造成中断，应改用被动流量、日志与配置核查。

### 作者在书中警告的失败模式（warning_signs）

- **把 ping 不通当“不存在”**：书中明确列出“不在网络、未开机、存在但过滤 ICMP”三种可能；否定结果只排除当前探测方式。
- **把 TTL 当精确指纹**：约 128 指向 Windows、约 64 指向 Linux/UNIX 只是候选；多跳会递减，也可被伪造。
- **把扫描器输出当结论**：SuperScan、Nmap、X-Scan 给出的是主机、端口与“可能漏洞”清单，仍需回到具体主机/端口/账号确认。
- **跳步**：没有确认存在就去判系统、扫漏洞，后面所有判断都建立在未验证的前提上。
- **用单点现象判成败**：ping 超时也可能只是防火墙，不等于目标不存在，也不等于攻击失败。
- **越出授权边界**：书中演示都在自有局域网；把同一动作搬到公网或他人网络就是未授权扫描。

### 作者的盲点 / 时代局限

- 默认同一局域网、可 ping、可直连；现代环境有 NAT、CDN、云 WAF、网络分段与零信任，漏斗需要更多旁路信号。
- 工具与菜单路径老旧（SuperScan、流光、旧版 Zenmap），照抄命令会失效；应抽取“先存在、再系统、再端口、再拓扑、再漏洞”的顺序与判据。
- 重操作、轻验证：书中很少给出“扫描结果如何复核”的步骤，容易把工具输出当结论。
- 默认单机管理员视角，缺少资产台账、CMDB、日志与流量侧证据。

### 容易混淆的邻近方法论

- `identity-deception-detection`：都处理“看到的和实际不一致”，但该 skill 针对 ARP/DNS/URL 身份替换；本 skill 的“不通”先按可达性与过滤解释。
- `malware-triage-order`：都从现象出发，但该 skill 是已感染后的处置顺序，本 skill 是感染前的发现。
- `wireless-security-grading`：都可能“发现无线设备”，但该 skill 评加密与旁路，本 skill 只做暴露面定位。
- `buffer-overflow-defense-layering`：本 skill 找“哪里可能有问题”，该 skill 决定“怎么防”。
