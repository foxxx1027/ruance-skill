# 08 中间件与Web容器

这一层测的是应用跑在哪个容器里、这个容器配错没有：IIS/Apache/Nginx/Tomcat/JBoss/WebLogic 的版本、默认页、管理面与配置项。典型被测物是 Server 头与指纹、alias/location 配置、readonly 与 WebDAV 开关、CDN 边缘与源站的不一致。很多问题没有 CVE，纯粹是配出来的。

## 这一层最常见的四类问题

- 拿到一个站点，不知道它跑的是什么，也就不知道该查哪张检查表。
- alias 穿越、autoindex、`$uri` 解码 CRLF、fix_pathinfo 这类纯配置问题，扫描器一条都报不出来。
- 管理面 7001/4848/9060 暴露在外，默认口令没改、管理路径没收敛。
- 已经确认是配置问题，却不知道该先删组件还是先改配置，改完也没做回归。

## 这一层的 skill

| skill | 作用 | 什么时候会用到 |
| --- | --- | --- |
| middleware-fingerprint-and-triage | 从 Server 头、默认页与端口判断中间件种类与版本，再分派对应检查表。 | 「这个站跑的是 Tomcat 还是 WebLogic」 |
| middleware-misconfig-audit | 审无 CVE 的配置型漏洞：alias 穿越、autoindex、CRLF、readonly、WebDAV 与配置漂移。 | 「nginx 的 alias 能不能穿越」「autoindex 开着吗」 |
| middleware-remediation-layering | 在删组件、改配置、打补丁之间排修复顺序，评估副作用并做回归验证。 | 「这几个中间件漏洞先修哪个」 |
| web-minimal-exposure | 收敛自建站点与云服务器的暴露面：目录权限、库文件位置、上传目录可执行、错误回显。 | 「网站只开 80 够不够」「数据库文件能被下载」 |

## 跨层可复用

- java-deserialization-entry-enumeration（06_接口与协议）— 判清是 WebLogic/JBoss 之后，下一步就是枚举它的反序列化入口。
- upload-parser-bypass-audit（05_后端业务逻辑与权限）— 上传目录能否执行，往往由容器的解析配置决定。
- cloud-and-container-baseline（11_云与容器）— 镜像与 K8s 入口的基线检查，与容器层配置同源。
- recon-funnel-and-scoping（09_网络与传输）— 先把端口与资产摸清，再来判中间件。
- supply-chain-and-dependency-security（12_构建产物与依赖）— 组件版本对应的已知 CVE 由它比对。
- web-minimal-exposure 之外的代码层注入见 non-memory-vulnerability-analysis（06_接口与协议）。

## 和相邻层的分界

- 与 06 接口与协议：08 看容器的配置与行为（没有业务代码参与的那部分），06 看应用报文与接口逻辑。同一个目录穿越，来自 alias 配置归 08，来自代码拼路径归 05/06。
- 与 12 构建产物与依赖：08 看运行时的版本与配置，12 看交付物里的组件清单与完整性。
- 与 11 云与容器：08 的对象是 Web 容器/反向代理本身，11 的对象是云资源、镜像与编排层。
