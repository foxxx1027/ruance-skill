# 中间件修复分层决策

## R — 原文 (Reading)

> “1. 不需要 http-invoker.sar 组件的用户可直接删除此组件。... 2. 或添加如下代码至 http-invoker.sar 下 web.xml 的 security-constraint 标签中，对 http invoker 组件进行访问控制。”
>
> — lyxhh，《Web中间件常见漏洞总结》JBoss 节

---

## I — 方法论骨架 (Interpretation)

修复不是“有补丁就打补丁”，而是按四层排序，并逐层评估副作用：

1. **删组件**：业务不使用就直接移除攻击面。最快、不依赖厂商，但可能破坏依赖——尤其是一级应用包（书中明确说删除 `wls-wsat.war` 可能有未知后果，Oracle 不建议）。
2. **改配置/加访问控制**：保留组件但收紧入口，例如 `readonly=true`、`cgi.fix_pathinfo=0`、`security.limit_extensions=.php`、T3 连接筛选器、仅本地绑定管理页。
3. **打补丁**：依赖厂商发版；要认识到很多补丁只是黑名单，可能被下一次等价语法绕过。
4. **应用层兜底**：WAF、上传目录禁执行、站库分离；只能降低概率，不能替代前三层。

排序原则是：**先问“这个组件业务真的用吗”，再问“能不能不依赖厂商”，最后才问“补丁什么时候来”**。每层落地后都要做回归验证：原漏洞请求是否失效、业务功能是否正常、是否引入新的暴露面。

## A1 — 书中的应用 (Past Application)

### 案例 1：JBoss 的三层修复

- **问题**：`http-invoker` 反序列化入口可被利用，但不同用户的使用情况不同。
- **方法论的使用**：作者给出三层：不需要就删 `http-invoker.sar`；需要就在 `web.xml` 加 `security-constraint`；或者等待/安装补丁。
- **结论**：修复顺序由“是否使用组件”决定，而不是由“补丁是否发布”决定。
- **结果**：删除后访问 404；加访问控制后仍保留功能但需认证。

### 案例 2：WebLogic 删除组件的副作用

- **问题**：`wls-wsat` 漏洞可删可补丁。
- **方法论的使用**：作者列出删除 `wls-wsat.war` 的多处路径，同时引用 Oracle 的提醒：它属于一级应用包，移除或更名可能造成未知后果。
- **结论**：删除不是无条件最优；要先确认业务不依赖，再承担副作用。
- **结果**：作者同时保留“安装补丁”作为备选，并指出黑名单补丁不可长期依赖。

### 案例 3：Tomcat/Nginx 的配置层修复

- **问题**：不依赖厂商补丁，能否消除利用条件。
- **方法论的使用**：Tomcat 把 `readonly` 设为 `true`；Nginx/PHP 把 `cgi.fix_pathinfo` 设为 0、限制 `security.limit_extensions`、禁止上传目录执行。
- **结论**：配置层修复往往比补丁更快，但必须验证不会破坏业务（例如某些框架依赖 `fix_pathinfo`）。
- **结果**：书中给出对应配置与验证结果；`readonly=true` 后 PUT 写入失效。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 已经确认漏洞，但厂商补丁未发布或无法立即停机。
2. 安全团队与运维在争“删组件还是打补丁”，需要给出排序依据。
3. 需要写修复方案/风险接受文档，要求列出每层的副作用与验证方法。
4. 修完之后要确认“原利用链是否真的失效”。

### 语言信号 (用户的话里出现这些就应激活)

- “这个漏洞怎么修 / 修复顺序”
- “能不能直接删组件 / 删了会不会出问题”
- “补丁还没出，有没有 workaround”
- “remediation / mitigation / compensating control”
- “修完怎么验证”

### 与相邻 skill 的区分（定稿）

- 与三个检测 skill（`upload-parser-bypass-audit`、`java-deserialization-entry-enumeration`、`middleware-misconfig-audit`）：本 skill 以它们的可复现证据为输入，不自行做检测；没有证据时退回对应检测 skill。
- 与“风险接受”的区别：本 skill 输出技术修复路径；接受风险是治理决策，需要另行签字。
- 与“打补丁”的区别：补丁只是四层中的一层，不等于修复完成。

## E — 可执行步骤 (Execution)

1. **确认漏洞证据与影响面**
   - 完成标准：有可复现的请求/响应或配置证据；明确受影响组件、版本与入口。
   - 判停条件：没有证据时停止，回到检测 skill。

2. **判断组件是否被业务使用**
   - 完成标准：查路由、访问日志、依赖清单或业务确认，给出“使用/不使用/未知”的结论。
   - 判停条件：若“未知”，不能直接删除，先选访问控制。

3. **按四层排序并评估副作用**
   - 完成标准：为每一层写出“是否可行、副作用、停机需求、验证方法”；删除一级应用包必须标注风险。

4. **落地最高可行层**
   - 完成标准：配置或补丁已应用，且有变更记录与回滚方案。

5. **回归验证**
   - 完成标准：原利用请求失效；关键业务功能正常；没有新增暴露面（例如为了绕过限制而放宽了目录权限）。

6. **记录残余风险**
   - 完成标准：写明未能修复的部分、依赖的补偿控制（WAF、监控）与复查时间。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没有确认漏洞，只是“听说这个版本有问题”；先做检测。
- 目标是 0-day 且没有任何官方或配置层缓解；此时只能做临时隔离与监控。
- 组织决定接受风险；本 skill 不能替代风险接受流程与责任人签字。

### 作者在书中警告的失败模式

- 删除或改名 `wls-wsat.war` 一级应用包可能造成未知后果，Oracle 不建议（ce04）。
- 黑名单补丁不可长期依赖，下一次等价语法可能绕过（ce03、p40）。
- 配置修复可能破坏业务：例如某些应用依赖 `cgi.fix_pathinfo`，关闭前要确认（p21）。
- 改完配置未重启/未回收进程，验证结论无效（ce09）。

### 作者的盲点 / 时代局限

- 修复建议以“单点关闭”为主，缺少纵深防御与持续配置管理。
- 未讨论变更管理、灰度发布与回滚演练；生产环境的修复成本被低估。
- 默认测试者可以停机重启，真实业务往往不允许。

### 容易混淆的邻近方法论

- “打补丁”只是四层中的一层，不等于修复完成。
- “WAF 拦截”是补偿控制，不是根因修复；不能用来关闭漏洞工单。
