# 身份鉴别与口令安全

## R — 原文 (Reading)

> "避免鉴别过程被绕过……避免在处理身份鉴别的过程中透露多余信息……避免使用过于严格的账户锁定机制（账户锁定保护机制过于严格且容易被触发，就允许攻击者通过锁定合法用户的账户来拒绝服务合法的系统用户）。"
>
> — GB/T 38674-2020, 5.3.1 h)、5.3.1 i)、5.3.1 m)

---

## I — 方法论骨架 (Interpretation)

评估任何认证设计，固定从三个方向发问，三类的修法互不相同，不能互相替代。

第一类是绕过面：是否存在第二条通往系统的通道？鉴别是否只在客户端做？是否省略或跳过了算法关键步骤？是否把可伪造的东西当身份依据——cookie 里的字段、反向 DNS 解析出的主机名、请求头里带过来的用户标识？证书是否只看了"能连上"而没验状态、有效期与实际持有者？

第二类是信息泄露面：所有鉴别请求的处理耗时是否一致（用户不存在时若提前返回，时间差就是账号枚举的侧信道）；登录、注册、找回的失败文案是否统一；响应体大小、状态码、跳转地址是否随账号存在性变化；反馈里是否夹带了敏感数据。

第三类是穷举面：有没有频率限制与失败阈值？限频是否只按账号计数（那样成本被转嫁给账号所有者）？

这三类会互相冲突。锁定越严越抗爆破，也越容易被用来锁死他人账号，所以锁定参数不是"越严越好"，而是要同时给出解锁路径（时限自动解锁、自助或人工申诉）、按账号与来源双维度计数、渐进延迟、告警，并且锁定状态本身不能向未认证方确认账号存在。

实现层面还有两条硬约束：鉴别逻辑只应有一处实现、只应在服务端执行，多入口（Web、API、移动端、管理后台、SSO）必须收敛到同一处，收敛不了就要做等价性核对；会话建立后仍需在长周期与关键操作前重新鉴别，因为鉴别是某个时刻的事件，会话是一段时间的凭据。

口令侧是同一套思路的延续：不明文存、不明文传、只存加盐的单向散列值；默认与初始口令强制首登修改；重置走与创建、鉴别同级的控制，确认信息走独立信道且不含鉴别信息。

## A1 — 书中的应用 (Past Application)

### 案例 1: 建立 SSL 连接却不校验服务器证书（附录 A.2.3.1.3）

- **问题**: 邮件客户端只开启了"走 SSL"，没有开启服务器身份校验；部分 SSL 库默认不验证证书。
- **方法论的使用**: 归入第一类绕过面——鉴别对象是"对面这台服务器"，而证书校验才是这一步的鉴别动作。只加密不验证书，等于把身份判定交给了任何持有证书的人；攻击者用一张任意域名证书即可完成冒充。
- **结论**: 加密与认证是两件事，必须显式开启主机名与证书链校验，并检查状态、有效期与实际持有者一致；不能因为"库默认不校验"就沿用默认值。
- **结果（防住什么）**: 不修时任何证书都被接受，中间人可解密与篡改全部"加密"流量；开启校验后证书或主机名不匹配即握手失败。

### 案例 2: 用网络传来的明文口令直接连库（附录 A.2.3.2.4）

- **问题**: 从请求参数取出明文口令，直接用于获取数据库连接；相邻示例还有 null 口令与空口令直连。
- **方法论的使用**: 归入口令侧的两条硬约束——禁止明文传输、禁止把用户口令当作系统凭据；同时 null/空口令绕过了一切鉴别语义。这里要问的不是"有没有加密"，而是"这个口令从哪来、以什么形态存在、谁还能读到它"。
- **结论**: 连接凭据只能来自受保护的配置或密钥管理并在可信环境解密；空与 null 一律拒绝；用户口令只用于鉴别，不参与建立后端连接。
- **结果（防住什么）**: 不修时口令在链路与日志中明文暴露，配置泄露即失守；改造后凭据以密文形态存在，空/null 无法建立连接。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 登录或短信验证码接口被刷，产品提出"加个图形验证码"，需要判断这是否足够。
2. 安全评审要求"登录失败要提示得友好一点"，而团队想区分"用户不存在"和"密码错误"。
3. 设计或调整账户锁定策略，需要在抗爆破与"被用来锁死他人账号"之间取舍。
4. 系统有多套登录方式（Web、App、开放 API、管理后台、SSO、内部服务互调），怀疑其中一条没走统一鉴别。
5. 口令存储与重置流程评审：加盐散列是否到位、默认口令是否强制改、重置确认走哪条信道。

### 语言信号 (用户的话里出现这些就应激活)

- "登录接口被爆破 / 要不要加验证码"（login brute force / captcha）
- "用户不存在要不要提示 / 提示语能不能区分"（user enumeration / invalid credentials）
- "锁定几次合适 / 锁了会不会被恶意利用"（account lockout threshold / lockout DoS）
- "时序攻击 / 响应时间不一致"（timing attack / constant time）
- "口令怎么存 / 加盐够不够 / 能不能明文传"（password hashing / salt / plaintext password）

### 与相邻 skill 的区分

- 与 `authorization-and-least-privilege` 的区别：本 skill 回答"你是谁"，后者回答"你能做什么"；登录成功后的每个请求仍要授权判定。
- 与 `network-transport-and-session` 的区别：会话标识的生成强度、超时、登录后重建、并发登录限制更偏会话侧，本 skill 只负责"鉴别时刻"的判定与重鉴别时机。
- 与 `sensitive-data-lifecycle` 的区别：口令的存储形态重叠，但本 skill 关注鉴别流程的完整性与可绕过性，后者关注数据暴露面与密钥管理。

## E — 可执行步骤 (Execution)

1. **枚举全部鉴别入口与旁路**
   - 完成标准: 列出 Web 登录、App、开放 API、管理后台、SSO、内部服务互调、口令重置、验证码校验等所有入口，每个标注"是否走同一实现"。
   - 判停条件: 若存在无法纳入统一实现的入口（遗留协议、第三方回调），标记为高风险，跳到步骤 4 为该入口单独设计限频与监控。

2. **用三重威胁模型逐入口检查**
   - 完成标准: 每个入口在"能否被绕过 / 是否泄露元信息 / 能否被穷举"三栏各至少有一条结论，并附代码或配置位置作为证据；空栏视为未完成。

3. **收敛实现并清除可伪造的身份依据**
   - 完成标准: 只有一处鉴别入口且运行在服务端；cookie 字段、反向 DNS、客户端传来的用户标识都不再作为身份依据；证书校验包含状态、有效期、主机名与实际持有者；长会话有周期性重鉴别，改口令等不可逆操作前有再次鉴别。

4. **统一失败反馈并给出限频与锁定方案**
   - 完成标准: 用户不存在与口令错误走等价计算路径与同一文案，响应体大小、状态码、跳转目标不随账号存在性变化；限频按账号与来源双维度计数并有渐进延迟；阈值、锁定时长有书面理由，配有时限自动解锁或申诉通道，锁定事件进告警。

5. **落实口令的存储、传输与重置**
   - 完成标准: 只存加盐的单向散列值且不可逆；无明文口令出现在链路、日志、配置与报错中；默认与初始口令强制首登修改；重置操作与创建、鉴别同级防护，确认信息走独立信道且不含鉴别信息。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 判断登录后某个用户能否读取某条记录：这是授权问题，鉴别通过不等于有权访问。
- 设计 TLS 套件、会话标识随机源、Cookie 属性、登出与超时参数：属于传输与会话侧，本 skill 只界定鉴别时刻。
- 只想"让登录页更好用"的交互需求：表单提示、自动填充、记住我属于体验范畴，安全判定仍在服务端。
- 生物特征识别、硬件令牌、FIDO 的协议与密码学实现细节：超出本标准覆盖范围，需要专门规范。

### 作者在书中警告的失败模式

- **ce09 只在登录那一刻鉴别，之后一路放行**：鉴别是时刻事件，会话是一段时间的凭据；会话不过期、不重建、不随权限变更失效，一次窃取即可长期复用；拦截器只覆盖已知路径时，未被拦截的接口等于裸奔。
- **ce10 失败信息与响应时间泄露账号存在性**：账号枚举本身不是终点，而是把用户名空间缩小后再集中爆破的前置步骤；即使文案统一，用户不存在时跳过散列计算的提前返回仍会形成可测量的时间差。
- **ce11 锁定策略的两难**：按账号计数把成本转嫁给账号所有者；阈值过低、锁定过长且匿名可触发时，攻击者用错误口令批量锁定已知账号即可让合法用户登不进去；不区分来源、没有渐进延迟与解锁通道，就没有中间档位。

### 作者的盲点 / 时代局限

- 只提到"高安全要求建议多因素"，完全没有讨论 MFA 自身的失效模式：短信与邮件通道可被劫持、推送可被轰炸骚扰、恢复码与备用通道是最软的环节、可降级的 MFA 等于没有 MFA。落地时必须单独设计"如何证明第二因素失效"。
- 没有给出任何密码学参数。口令散列只说"不可逆算法或单向杂凑并加变量"，未涉及 Argon2/bcrypt/scrypt 的成本因子、内存参数与升级策略，也未涉及 passkey/WebAuthn；照字面实现容易落成"单次 SHA-256 加盐"，在离线爆破面前几乎无成本。

### 容易混淆的邻近方法论

- 授权与最小权限：认证解决"是谁"，授权解决"能做什么"，把两者混为一谈会出现"登录即可访问一切"。
- 敏感数据生命周期：口令存储属于它的一个实例，但重置信道的选择与确认信息的内容属于鉴别流程设计。
