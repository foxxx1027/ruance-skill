# 授权与最小权限

## R — 原文 (Reading)

> "将访问控制作为集中化程序框架的一部分，建立统一的访问控制策略。……对每个用户交互都要检测访问控制状态。……确保访问控制策略检查了用户访问或操作的数据。"
>
> — GB/T 38674-2020, 5.3.3 c)、5.3.3 d)、5.3.3 e)

---

## I — 方法论骨架 (Interpretation)

把"能不能做"拆成四个依次收紧的问题，任何一个越权漏洞都能定位到其中一个失效。

第一问：默认给多少。服务账户、对外系统对接账户、数据库账户，都只应持有完成该任务所必需的最小权限，并且尽可能细化。给的是"能读这张表的所有行"还是"只能读属于当前租户的行"，差别就是一次拖库和一次越权的差别。

第二问：策略写在哪里。集中成一处统一策略，而不是每个接口里各写一段 if。散落的实现意味着必然有遗漏点，而且没人能回答"这个系统一共有多少条权限规则"。

第三问：什么时候查。每一次用户交互都查，不是登录时查一次就把角色缓存在会话里一路放行。权限被收回、角色被调整之后，旧会话必须立即失去相应能力。

第四问：查到什么粒度。检查对象必须是"用户这次要访问的那条数据/那个功能"，不是"这个用户有没有某个角色"。只判定功能入口，等于允许任何持有该角色的人用任意 ID 访问全部记录。

数据库层是第五道保险，不是可选项。应用账户不用默认角色与默认口令、按信任级别分角色、开启行级访问控制、连接与游标用后即释放、关闭不必要的存储过程与组件。这条要求的前提是承认"应用层授权可能被绕过或被写漏"，所以在数据出口再拦一次。

账户生命周期也要收口：明确最长闲置期、强制失效长期不用的账户、停用时终止会话、权限变更留审计。离职人员与遗留集成账号是最常见的后门。

## A1 — 书中的应用 (Past Application)

### 案例 1: 文件权限掩码取自系统属性导致越权（附录 A.2.3.3.2）

- **问题**: 程序从系统属性读出一个权限字符串，直接当作文件权限应用。
- **方法论的使用**: 这是第一问与第四问同时失效——权限的粒度被交给了外部输入，而系统属性未必可信；更深一层，代码把"决定权限"这个动作本身开放给了攻击者，等于让人自己给自己发许可。
- **结论**: 权限只能从预定义的白名单集合中选取，输入与某一项完全相等才应用；用户输入永远不直接决定权限值。
- **结果（防住什么）**: 不修时把属性设为过宽权限即可读写本不应访问的文件，甚至触及系统文件；白名单后无法通过输入提权。

### 案例 2: 只按单据 ID 查询，缺少属主条件（附录 A.4.3.3）

- **问题**: 查询用了参数化绑定，但语句里只有单据 ID 一个条件，ID 直接取自请求参数。
- **方法论的使用**: 参数化只解决"注入"，不解决"该不该看"。用第四问检验——检查对象是"这条单据"，而代码检查的只是"能不能调用这个查询"；属主条件缺失，任何通过鉴别的用户都能遍历他人记录。修法是让访问范围进入查询本身：从服务端上下文取当前用户，把属主条件与 ID 一起绑定，或在数据访问层统一做行级授权。
- **结论**: 对象级授权必须落到"数据 + 主体"的联合条件上，且主体身份来自服务端状态，不能来自请求参数。
- **结果（防住什么）**: 不修时改一个 ID 就能读取或修改他人账单，属于典型水平越权；加上属主条件后非本人记录查不到。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 接口用资源 ID 直接查询，评审时有人问"换个 ID 会怎样"，需要判断是注入问题还是越权问题。
2. 设计多角色后台或多租户 SaaS，要决定权限规则写在哪、按功能还是按数据授权。
3. 系统对外暴露一个统一入口（GraphQL 单端点、网关统一路由、RPC 泛化调用），需要判断"按路由做权限中间件"是否足够。
4. 服务账户、数据库账户、第三方对接账号的权限长期只增不减，需要做一次收敛与审计。
5. 有人离职或某个集成下线，需要确认账号、令牌与旧会话是否都已失效。

### 语言信号 (用户的话里出现这些就应激活)

- "改个 ID 就能看到别人的数据 / 这算不算越权"（IDOR / horizontal privilege escalation）
- "这个接口要不要加权限 / 有角色判断就够了吗"（is role check enough / authorization）
- "行级权限 / 租户隔离怎么做"（row-level security / tenant isolation）
- "数据库账户给多大权限 / 服务账号能不能用 root"（least privilege / db account privileges）
- "权限收回后旧会话还能用吗 / 僵尸账号怎么清"（stale session / dormant account）

### 与相邻 skill 的区分

- 与 `input-validation-output-encoding` 的区别：参数化查询、SQL 注入、编码归它；本 skill 只管"查到之后该不该返回"。案例 2 那种"用了参数化仍然越权"的情形要明确落到本 skill。
- 与 `authentication-and-passwords` 的区别：鉴别回答"你是谁"，本 skill 回答"你能对哪个对象做什么"；登录成功不构成任何授权结论。
- 与 `trust-boundary-mapping` 的区别：边界 skill 关心数据能否被信（例如请求头里的用户标识不可信），本 skill 关心主体与对象的对应关系；两者在"身份从哪来"这一点上交界。

## E — 可执行步骤 (Execution)

1. **画出主体—对象—动作矩阵并写清默认值**
   - 完成标准: 每一行是"某类主体（匿名用户/普通用户/管理员/服务账户/数据库账户）× 某类对象 × 允许的动作"，未列出的组合默认拒绝；服务账户与数据库账户单独成表。
   - 判停条件: 若某类对象无法枚举（如动态资源、用户上传文件），改用"对象归属规则 + 拒绝兜底"描述，并进入步骤 3 逐个访问路径核对。

2. **把策略收敛到一处，并列出所有判定入口**
   - 完成标准: 权限规则集中定义、业务代码只调用不实现；入口清单覆盖 HTTP 端点、GraphQL 字段与 resolver、消息消费者、定时任务、文件下载、内部 RPC，每一项都指向同一判定函数。
   - 判停条件: 若存在不经过该函数的入口，先记录为缺口再进入步骤 3，不得因为"内部调用"而豁免。

3. **把检查下沉到被访问的对象**
   - 完成标准: 每条涉及单条记录的路径都带属主或租户条件，且该条件取自服务端上下文而非请求参数；抽查三个"换成他人 ID"的请求，结果必须是拒绝或空结果，而不是他人数据。

4. **在数据库层叠加最小权限与行级控制**
   - 完成标准: 应用账户非默认账户、无默认口令、无 DDL 与超级权限；按信任级别分角色；行级访问控制在库侧生效；连接与游标在异常路径上也被释放；不必要的存储过程、服务与组件已关闭。
   - 判停条件: 若数据库不支持行级策略，跳到步骤 5，在数据访问层强制统一拼接属主条件并加自动化用例守住。

5. **做账户审计与生命周期收口**
   - 完成标准: 每个账户有明确归属人与用途；设定最长闲置期并支持强制失效；停用账号时同步终止其会话与令牌；权限变更留有审计记录并有定期复核结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 处理 SQL 注入、命令注入、XSS 与编码：参数化与转义属于输入验证与输出编码，本 skill 不重复覆盖，也不要拿"加了权限"当作不修注入的理由。
- 判断登录是否可靠、口令如何存储、验证码是否够用：属于身份鉴别范畴。
- 设计会话超时、令牌随机性、并发登录限制：属于传输与会话侧，本 skill 只消费"会话里的主体是谁"。
- 上传文件的类型校验与路径规范化：属于文件安全范畴，与本 skill 的行级控制不是同一层。

### 作者在书中警告的失败模式

- **ce06 信任隐藏字段与客户端状态**：把角色、用户 ID、审批状态、价格放进隐藏字段或本地存储，服务端直接采信；hidden、前端路由守卫都只是 UI 约定，改包即可绕过，等于把授权判定交给攻击者。
- **ce09 只在登录时鉴别，之后一路放行**：只在登录时查一次角色并缓存，权限变更后旧会话仍然有效；拦截器只匹配已知路径，未被拦截的接口与消息入口等于裸奔。安全检查若只覆盖已知路径，就等于没有覆盖。
- **ce16 共享可变状态造成跨会话串数据**：单例的请求处理对象用实例字段保存当前用户数据，A 用户的身份或记录会出现在 B 用户的响应里，既是并发缺陷也是越权泄露；防御只能靠请求作用域、不可变对象与快照，而不是"再检查一次"。

### 作者的盲点 / 时代局限

- 标准默认"应用层做集中授权就够了"，对微服务、网关终止鉴权、GraphQL 单入口这些形态缺乏讨论：网关只判定"能否调用端点"，字段级与对象级仍需每个 resolver 自查；服务之间传递的用户标识若不重新校验，前端的授权结论会被下游无条件继承。
- 没有给出默认拒绝（deny by default）的明确表述，也没有讨论属性级授权、策略即代码、租户隔离在多库多服务下的落地形态；实际工程中还需要一套能回答"这条规则覆盖了哪些入口"的覆盖证明，否则"集中化"只是一句口号。

### 容易混淆的邻近方法论

- 输入验证与输出编码：它修"数据怎么进来"，本 skill 修"进来之后能碰什么"；参数化查询属于前者，属主条件属于后者。
- 身份鉴别与口令安全：认证通过是授权判定的前提条件，但不是结论；把两者合并会导致"登录即全权"。
