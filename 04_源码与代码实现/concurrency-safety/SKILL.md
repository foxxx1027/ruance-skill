# 并发安全（concurrency-safety）

## R — 原文 (Reading)

> 确保所有的全局变量、线程间的共享可变数据是线程安全的。……所有执行读或写操作的线程都应在同一个锁上同步……确保同步对象上的锁按相同的顺序获得和释放，以避免当两个或多个线程互相等待时被阻塞进而发生死锁。……禁止在一个表达式中两次访问同一个原子变量。
>
> — GB/T 38674-2020, 6.2 a) b) c) k)

---

## I — 方法论骨架 (Interpretation)

并发缺陷不是"忘了加锁"这么简单，而是一组可以被逐项排查的结构性问题。

第一问是"这块数据谁都能改吗"：共享可变状态要么变成不可变，要么所有读写路径都在同一把锁上同步。用不同的锁保护同一份数据等于没锁，因为可见性和互斥都不成立。

第二问是"锁对象本身安全吗"：锁靠对象身份工作，因此不能拿 Boolean、包装类型、字符串常量池、getClass() 返回值这些会被复用的对象当锁，也不能拿非 final、可被重新赋值的字段当锁。

第三问是"多把锁会不会互相等"：所有线程按同一顺序获取、按相反顺序释放；临界区里不做阻塞调用；异常路径也要释放锁。

第四问是"线程和任务的生命周期谁管"：线程池限制并发以抗 DoS，池内任务不得等待同池任务，任务必须可中断、异常必须上报；线程专有对象及时释放，不重复 join/detach，不用异步取消。

第五问是"原子性到底覆盖了多大范围"：原子变量只在单次操作上原子，一个表达式里读两次就有窗口；同理，跨会话共享的单例字段会把 A 用户的数据带给 B 用户。

## A1 — 书中的应用 (Past Application)

### 案例 1: 用 Boolean.FALSE 作锁对象（附录 A.3.2.2、A.3.2.3）
- **问题**: 类里声明 private final Boolean initialized = Boolean.FALSE，然后 synchronized(initialized) 保护初始化逻辑。
- **方法论的使用**: 按 6.2 b) e) 检查锁对象的身份是否唯一、是否受控：Boolean 只有两个实例且被 JVM 共享，别处一旦也锁 Boolean.FALSE，两段无关代码就在争同一把锁。
- **结论**: 锁会被重用，出现失去响应或死锁；非 final 的锁字段被重新赋值后同样失效。规范做法是用 private final 的专用 Object，或显式 new 一个包装类型实例（附录 A.3.2.2、A.3.2.3）。
- **后果/防住什么**: 不修则临界区互斥被破坏、并发下随机死锁；修后锁唯一且不可变，同步语义可靠。

### 案例 2: 用实例锁保护共享静态数据（附录 A.3.2.7）
- **问题**: 一个可被创建多个实例的类，用 synchronized(this) 保护一个 static 计数器。
- **方法论的使用**: 按 6.2 b) 追问"读写的线程是否在同一把锁上"：每个实例的 this 都不同，实例锁对静态数据没有任何互斥作用。
- **结论**: 多实例并发进入时共享状态完全未被保护。规范做法是把锁改为该类的静态锁对象，保证所有实例竞争同一把锁（附录 A.3.2.7）。
- **后果/防住什么**: 不修则计数丢失、状态错乱且难以复现；修后静态数据只有一把锁，可见性与互斥同时成立。

### 案例 3: 双重检查锁定的"性能优化"（附录 A.3.2.19）
- **问题**: 延迟初始化写成先判 instance 是否为 null，为 null 再加锁并二次判断，实例字段没有 volatile。
- **方法论的使用**: 用 6.2 a) b) 检查可见性与发布安全：instance 的赋值与对象构造可能被重排，别的线程可能先看到非 null 再看到未初始化完的字段。
- **结论**: 这是错误的优化，会拿到半成品对象。规范做法是使用 volatile 加双重检查、静态内部类持有，或直接由框架管理单例（附录 A.3.2.19）。
- **后果/防住什么**: 不修则偶发空指针或读到默认值，测试环境几乎不复现；修后对象安全发布。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 压测或线上出现偶发超发、计数偏小、缓存串数据，代码"看起来没问题"。
2. 服务偶发卡死、线程 dump 显示互相持有对方需要的锁。
3. 正在写线程池、定时任务、异步回调，纠结池大小、拒绝策略、任务取消。
4. 用 AtomicInteger/AtomicLong 做限流或计数，怀疑"原子类应该没问题"。
5. 代码评审发现 synchronized 里包着网络调用、数据库操作或 sleep。

### 语言信号 (用户的话里出现这些就应激活)

- "并发 / concurrency / 多线程 / multithreading"
- "死锁 / deadlock / 卡住 / 线程 dump"
- "竞态 / race condition / 偶发 / 压测才出现"
- "线程池 / thread pool / 队列满了 / 拒绝策略"
- "原子变量 / atomic / compareAndSet / 超发"
- "可见性 / volatile / happens-before"
- "会话串数据 / 单例里的成员变量"

### 与相邻 skill 的区分

- 与 `object-design-immutability` 的区别: 后者通过"不给可写入口"从结构上消除共享可变状态；本 skill 处理不得不共享时的同步、锁与生命周期。
- 与 `memory-and-resource-safety` 的区别: 后者管内存与句柄的配对释放、越界与 double free；本 skill 管线程安全语义，尽管线程泄漏会表现为资源耗尽。
- 与 `logging-security` 的区别: 后者管日志内容与完整性；本 skill 管多线程下日志/会话上下文不串数据。

## E — 可执行步骤 (Execution)

1. **列出共享可变状态**
   - 完成标准: 标出所有 static 字段、单例的实例字段、被多个线程传入的对象、缓存与计数器，并为每条注明"谁写、谁读、在哪个锁下"。
   - 判停条件: 若某状态可改为不可变或改为请求内局部变量，直接改掉并跳过后续同步设计。

2. **审计锁对象、锁范围与锁顺序**
   - 完成标准: 每个锁都是 private final 的专用对象；不存在 Boolean、包装类型、字符串常量、getClass() 作锁；不存在非 final 锁字段；读写用同一把锁；没有用实例锁保护静态数据；多锁场景画出加锁顺序表并统一，释放顺序与获取相反；临界区内无网络、数据库、sleep、回调；异常路径通过 finally 释放锁。
   - 判停条件: 若使用 ReentrantLock 等高层并发对象，确认只用其 lock()/unlock()，不以对象内置锁同步；若无法统一多锁顺序，改为单锁、锁分段或消息传递，不要靠超时重试掩盖。

3. **检查原子性与表达式**
   - 完成标准: 每个"读—判断—写"复合操作要么在锁内，要么用 CAS 循环；同一原子变量在一个表达式里只读一次；限流计数说明单进程还是跨进程。
   - 判停条件: 若状态需跨进程一致，标注"本 skill 不覆盖"，转外部一致性存储或分布式协调。

4. **审计线程池与任务生命周期**
   - 完成标准: 池有界且拒绝策略明确；任务可中断、能响应取消；池内任务不等待同池任务的结果；任务异常有上报通道；线程专有对象有释放路径；无重复 join/detach、无异步取消。
   - 判停条件: 若使用虚拟线程或异步运行时，确认没有在事件循环线程上做阻塞调用后，可跳过线程数调优部分。

5. **做并发回放**
   - 完成标准: 用多线程压测或确定性调度工具复现关键路径，确认计数、会话隔离、锁顺序在压力下稳定；死锁检测工具无告警。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单线程程序、无共享可变状态的服务、纯函数式处理管线：加锁只会引入复杂度与死锁面。
- Actor、CSP、消息传递或协程模型下没有共享可变状态：应换用"所有权/消息"推理，逐条套锁规则会失真。
- 需要跨进程、跨节点的互斥与一致性：单机锁、synchronized、原子类都不保证，必须用外部一致性存储与租约机制。
- 读多写少且粗锁成为瓶颈：此时需要无锁结构、分片或副本，但必须另行证明内存序与线性化点，不能照搬本 skill 的锁细则。
- 问题实际是内存越界、double free 或 GC 行为：属于内存与资源安全，不是线程同步。

### 作者在书中警告的失败模式

- **ce17 看似能提升性能的并发优化**：Boolean/字符串作锁会被跨代码复用；非 final 锁被换对象后同步失效；无 volatile 的双重检查锁定让半初始化对象逸出——三者都"单线程正确、只在并发压力下暴露"。
- **ce16 共享可变状态**：Servlet 是单例，实例字段被所有会话共享，A 用户的数据出现在 B 用户的响应里；校验与使用之间重读可变变量还会形成 TOCTOU。
- **ce13 依赖 GC 或退出钩子释放资源**：线程专有对象、连接、句柄不及时释放，在 GC 触发前就被耗尽，少量并发即可打满池造成拒绝服务。

### 作者的盲点 / 时代局限

- 停留在单进程多线程模型：未覆盖分布式锁与租约、Actor/协程、异步运行时（事件循环上禁止阻塞）、以及跨服务的一致性问题。
- 未展开内存序：只提"在同一个锁上同步"，没有讲 happens-before、volatile 语义、无锁结构的线性化点，读者容易把"原子类"当成万能。
- "释放锁时通知所有等待线程"在高并发下会引发惊群，标准只给了这一条，没有给出条件变量分组、公平锁或信号量式的替代。
- 未涉及现代运行时：虚拟线程的 pinning、结构化并发、任务取消传播、优先级反转与公平性都不在条目内。

### 容易混淆的邻近方法论

- `object-design-immutability` 的防御性复制：它消除"可写入口"，但两个线程仍可能同时调用副本生成逻辑，不能替代同步。
- `memory-and-resource-safety` 的配对释放：线程与句柄泄漏在现象上都是资源耗尽，但根因一个是生命周期管理、一个是并发控制，排查入口不同。
