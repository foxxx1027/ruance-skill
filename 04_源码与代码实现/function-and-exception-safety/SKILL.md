# 函数契约与异常处理（function-and-exception-safety）

## R — 原文 (Reading)

> 函数需要对传入的参数进行合法性、安全性验证，包括但不限于对参数数量、顺序、类型、值的验证。……避免在越过执行边界时抛出异常。……异常处理时保持数据的状态一致性。……精确捕获异常，并对捕获的异常进行恰当的处理，避免在捕获异常后不做任何处理。……向用户展示通用的错误提示信息。
>
> — GB/T 38674-2020, 6.3 a)；6.4 b) d) f) g)

---

## I — 方法论骨架 (Interpretation)

函数是信任边界落地的最小单位：调用方说什么、函数就信什么，是最常见的破口。

先把契约写清楚：参数的数量、顺序、类型、取值各自允许什么；不符合预期时不是"尽力处理"，而是明确拒绝或返回可判定的失败。不可信字符串永远只能作为数据，不能充当格式化串、命令模板或查询片段。返回值是"操作是否真的发生"的唯一证据，忽略它就等于默认成功。

再把异常当作与正常路径并列的第二条执行路径来设计：异常不跨执行边界（进程、模块、线程、跨语言调用），不在静态对象构造与线程存储期抛出；一旦抛出，先保证数据状态一致，再释放已占资源；捕获要精确到具体类型，捕获后必须有动作，空 catch 是把失败伪装成成功。

最后是信息面：对外只给通用提示与追踪号，堆栈、会话标识、账号信息、绝对路径只进受保护的内部日志。

一句话判断：把每个可能失败的调用当成一个分叉，分别问"谁负责处理""状态还一致吗""资源放了吗""外面看到了什么"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 用 %1$tm 探测被校验的日期（附录 A.3.3.2）
- **问题**: 提示语写成"用户输入 + 固定后缀"拼成的格式化字符串，用户输入直接进入格式串。
- **方法论的使用**: 按 6.3 c) 检查"来自不可信数据源的格式化字符串"是否只被当作数据；再追问格式符能否反过来读取程序内部值。
- **结论**: 攻击者提交 %1$tm、%1$te、%1$tY，程序分别打印出月份、日、年份，泄露本应保密的信用卡有效期；不匹配的转换符还可抛异常造成拒绝服务。规范做法是格式串写死，用户输入只作为参数传入（附录 A.3.3.2）。
- **后果/防住什么**: 不修则格式化串成为读取内部状态与制造异常的双重入口；修后格式符永不被用户控制。

### 案例 2: 异常反复上抛完整路径（附录 A.3.4.3）
- **问题**: 路径由请求参数拼成，文件不存在时 FileNotFoundException 原样向上抛出，最终出现在响应里。
- **方法论的使用**: 按 6.4 g) 检查异常对象携带的信息是否会到达用户：异常消息里有什么、栈帧暴露了什么、不同失败原因是否可区分。
- **结论**: 反复提交猜测的文件名，攻击者可依据报错差异逐层重建内部文件系统结构。规范做法是先规范化路径并校验根目录，不合法统一返回"Invalid file"，异常不外泄路径（附录 A.3.4.3）。
- **后果/防住什么**: 不修则错误信息成为目录测绘的旁路；修后所有失败对外同形，内部细节只进受保护日志。

### 案例 3: I/O 流与连接不在 finally 释放（附录 A.4.1.2）
- **问题**: 方法里创建文件流与数据库连接后只在 try 内使用，正常结束与异常路径都不关闭，指望垃圾回收。
- **方法论的使用**: 按 6.4 e) 走一遍异常路径：抛异常时已打开的资源由谁释放？再按 6.3 d) 检查 close 的返回值/异常是否被忽略。
- **结论**: 反复请求会耗尽文件句柄或连接池，其他合法用户无法访问。规范做法是资源变量先置空，在 finally 中判空逐个关闭，或用 try-with-resources（附录 A.4.1.2）。
- **后果/防住什么**: 不修则形成资源耗尽型拒绝服务；修后每条执行路径（成功、异常、提前返回）都释放资源。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计对外 SDK、开放 API、插件接口，需要确定参数校验、错误码与异常策略。
2. 代码里出现 catch 后什么都不做、只打印、或把异常包装成 RuntimeException 继续抛。
3. 出现"操作失败了但界面显示成功""删除没成功却提示已删除"这类静默失败。
4. 日志或响应里出现堆栈、绝对路径、SQL 片段、会话标识。
5. 使用 String.format、日志模板、shell 命令拼接，输入部分来自请求。

### 语言信号 (用户的话里出现这些就应激活)

- "参数校验 / parameter validation / 入参要不要判空"
- "返回值要不要检查 / ignore return value"
- "格式化字符串 / format string / %s 拼接"
- "异常处理 / exception handling / try-catch / 空 catch"
- "错误信息 / error message / 堆栈能不能给前端"
- "抛异常还是返回错误码 / Result / error code"
- "这个函数在旧版本行为不一样"

### 与相邻 skill 的区分

- 与 `input-validation-output-encoding` 的区别: 后者是系统级的入口验证与输出编码策略；本 skill 关注单个函数的契约与失败语义，是它在函数粒度上的落地。
- 与 `memory-and-resource-safety` 的区别: 后者管申请/释放配对、越界与 double free；本 skill 只在异常路径上要求"已占资源被释放"。
- 与 `logging-security` 的区别: 后者决定日志记什么、如何防注入；本 skill 决定错误文本对内外分别暴露到什么程度。

## E — 可执行步骤 (Execution)

1. **列出函数契约**
   - 完成标准: 每个对外函数写明参数的数量、顺序、类型、取值范围与非法输入的处理方式；标明哪些参数来自信任边界之外；标明返回值/错误码的语义。
   - 判停条件: 若参数由类型系统在编译期完全约束且不跨信任边界，可只标注"编译期保证"，跳过运行时校验设计。

2. **检查数据与语法的隔离**
   - 完成标准: 不可信字符串不作为格式串、不作为命令/查询/模板片段；所有拼接点已改为参数化或固定模板；跨版本行为不一致的函数（含解析、编码、排序）已列出并替换或锁定版本。
   - 判停条件: 若必须保留旧函数，记录版本约束并加回归用例，防止运行环境升级后行为漂移。

3. **逐个检查返回值与失败分支**
   - 完成标准: 每个可能失败的调用都有判断；权限设置、删除、关闭、写入、读取结果均被验证；失败分支不会继续走成功路径；无空 catch、无只打印不处理。
   - 判停条件: 若失败可安全忽略（如尽力而为的清理），必须写明理由并保证不影响安全判断。

4. **按异常路径重走一遍并统一错误出口**
   - 完成标准: 每个抛出点都回答四个问题——是否越过执行边界、状态是否一致（有无半更新）、已占资源是否释放、对外提示是否泄露内部信息；静态构造与线程存储期不抛异常；捕获按具体类型排序；对外响应只有通用文案 + 追踪号，堆栈、路径、SQL、会话标识、账号信息不出现在响应与前端，内部日志可按追踪号还原细节。
   - 判停条件: 若异常必然跨进程/跨语言边界，改为返回错误码或 Result，并在边界处转换。

5. **写失败用例**
   - 完成标准: 至少覆盖缺参、多参、类型错、越界值、空值、超长输入、下游失败七类，验证全部被安全拒绝且无信息泄露。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯内部工具函数、参数全是同模块常量：逐项运行时校验只增加噪音，收益接近零。
- 语言已用类型系统消除非法状态（Rust newtype、TypeScript 严格模式、依赖类型）：重复运行时校验价值低，但跨 FFI、反序列化、配置解析边界仍需补。
- 语言没有异常机制（Go、Rust）：不要硬套 try/catch 条款，应映射为 error 返回、Result、panic 边界与 recover 策略。
- 需要给内部调用方保留详细错误（SDK 开发者调试）：可以分层保留，但对最终用户仍须脱敏，不能因此取消通用提示。
- 问题是资源配对释放或缓冲区越界：那是内存与资源安全的范围，本 skill 只覆盖"异常路径上的释放"。

### 作者在书中警告的失败模式

- **ce15 用异常/错误信息泄露内部结构**：堆栈暴露框架与版本，SQL 报错暴露表结构，路径报错让人逐字符重建目录树，会话标识可直接被盗用。
- **ce20 吞掉异常、忽略返回值**：空 catch 与丢弃 delete/close/mkdirs/权限设置的返回值，让程序把失败当成功继续执行，审计与告警也看不到失败。
- **ce02 把不可信数据拼进格式化串或命令**：用 String.format 把用户输入格式化进查询/命令模板，数据与语法同层，格式化符或分隔符即可改写语义。

### 作者的盲点 / 时代局限

- 未区分"可恢复错误"与"编程错误"：现代实践用 Result/Either 表达前者、用 panic/abort 暴露后者；标准把所有失败都塞进异常，导致该断言的错误被吞、该恢复的错误被终止。
- 未展开跨语言 FFI 边界：C++ 异常穿过 C ABI、JNI 中的 Java 异常、WASM 与宿主间的错误传播，规则与同语言调用完全不同。
- 未涉及异步错误传播：Promise rejection 未处理、结构化并发中的取消传播、回调里抛异常无人接收，都是当代高频失陷点。
- 只要求"精确捕获"，未讨论错误码空间设计、重试与幂等、错误分类对可观测性的影响。

### 容易混淆的邻近方法论

- `input-validation-output-encoding` 的入口验证：它决定"数据能不能进系统"，本 skill 决定"函数拿到不合规数据时怎么失败"。
- `logging-security` 的审计事件选择：本 skill 只规定错误文本的暴露面，日志该记哪些安全事件由前者决定。
