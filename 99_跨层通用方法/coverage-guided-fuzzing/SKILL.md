# 覆盖率引导模糊测试

## R — 原文 (Reading)

> 在主模糊测试循环中，模糊器反复选择一个有趣的种子，用于后续的突变和测试用例生成。然后驱动目标程序在fuzzer的监控下执行生成的测试用例。收集触发崩溃的测试用例，并将其他有趣的用例添加到种子库。
>
> — 魏强、武泽慧，第7章 7.4.2 基本流程

---

## I — 方法论骨架 (Interpretation)

它不是“多跑一些随机输入”，而是一个由执行反馈驱动的闭环：种子库 → 变异生成 → 在监控下执行 → 判断哪些用例“有趣” → 按调度策略决定下一轮选谁。五环缺一，测试就退化成撞库。

输入构造的标准是“足够有效”，不是“越畸形越好”：必要标识和大部分数据保持合法，只让少数关键字段非法，程序才愿意走进深层逻辑，而不是在解析入口丢弃样本。

格式与校验和是前置门。先定位校验算法并在变异后回填，或按语法规范生成合法骨架，再谈变异；否则绝大多数样本死在门口。

变异前必须回答两个问题：在哪里变、怎么变。真正影响控制流的只有长度、类型、魔数、分支条件等少数关键字节，均匀翻字节是把能量倒在无关区域。

覆盖反馈要记边而不是只数基本块，否则走过同一些块的不同路径无法区分。调度按适应度分配能量：前期偏“新”，优先能发现新路径片段的种子；后期偏“深”，优先路径更深、经过基本块更稀有的种子；并对低频路径加权，避免能量挤在热门路径上。

覆盖率只是近似指标，不是漏洞概率。覆盖提升只说明代码被执行过，还要看危险状态是否可达、异常能否被判定。

崩溃不是终点。先按模块偏移、函数偏移、调用栈、异常码去重分组，把“崩溃数”还原成“缺陷数”；再判可利用性，核心是 EIP 能否被控制，同时把任意地址写、指定地址写、任意地址读、指定地址读映射为可用、可能可用、可能不可用、未知，并把基址泄露等信息泄露单列为价值依据。

覆盖停滞是最重要的信号：若卡在复杂条件或魔数比较，加大变异次数没有意义，应切到 concolic 求解该分支约束，再把解出的输入交回 fuzzer 继续变异。

## A1 — 书中的应用 (Past Application)

### 案例 1: 用 AFL 对 gif2png 做覆盖率引导模糊测试
- **问题**: 需要在一个真实的文件转换程序上跑通“插桩—种子—边覆盖—崩溃收集”的完整闭环，并拿到可分析的崩溃样本。
- **方法论的使用**: 用 `apt-get source` 取源码，以 `afl-clang-fast` 并开启 ASan 重新编译；准备一个合法 GIF 作为初始种子启动 `afl-fuzz`；运行中跟踪边覆盖，保留到达新边的用例，监控崩溃并写入 `out/crashes`；结束后用 `triage_crashes.sh` 遍历崩溃文件做初步分类。
- **结论**: 覆盖率引导的最小闭环可以落地为“插桩编译 + 合法种子 + 边覆盖反馈 + 崩溃目录”；崩溃文件必须再做去重与分类，不能直接当缺陷清单。
- **结果**: 约 12 小时运行检测到 28 个唯一崩溃，并完成初步分类。

### 案例 2: 用 Peach 对 WDScanner 登录接口做 HTTP 模糊测试
- **问题**: 要对 HTTP 登录接口做模糊测试，手工构造畸形请求成本高，且不清楚哪些字段才是值得变异的输入向量。
- **方法论的使用**: 先用 Wireshark 抓取登录 GET 请求，据此编写 Peach 的 pit 文件；在 DataModel 中把 `HTTP/1.1`、`\r\n` 等协议关键字段标为可变，Publisher 用 TcpClient 指向 `10.211.55.2:80`，变异策略选 Sequential；执行 `peach.exe` 并用抓包与 `-debug` 观察生成结果。
- **结论**: “抓包 → 协议建模 → 标记可变字段 → 执行”是基于生成的 fuzz 的最小路径；变异点应落在协议关键字段，而不是整包随机改字节。
- **结果**: 自动生成大量畸形请求并在抓包与调试输出中可见；书中未报告漏洞命中，说明“能生成合法畸形输入”不等于“能挖到漏洞”。

### 案例 3: Driller 在覆盖率停滞时切换选择性 concolic
- **问题**: 目标存在复杂校验条件，纯模糊测试长期无法跨过，覆盖率停在某条分支之前。
- **方法论的使用**: 先用轻量级模糊测试打底铺覆盖；当检测到覆盖率因某个特殊条件无法继续提升时，用选择性 concolic 执行收集该分支的路径约束并求解出可跳转的输入；新输入再交回 fuzzer 继续变异。
- **结论**: 两种技术按“何时需要”组合，而不是二选一或全程符号执行；fuzz 负责吞吐量，concolic 只负责啃下卡住的分支。
- **结果**: 在 CGC 自动网络攻防竞赛中取得良好效果；但受符号执行瓶颈限制，难以扩展到大程序。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 手上有一个二进制或程序，以及一个可送达的文件/协议/命令行输入通道，目标是挖缓冲区溢出、UAF 等内存破坏类漏洞。
2. fuzzer 已经跑了一段时间（例如两天），覆盖率不涨、没有新路径，用户问“下一步改什么”。
3. 种子只有一个或种子与目标格式不匹配，变异长期停在解析入口和错误处理层。
4. 目标带校验和、哈希、严格格式检查或运行环境依赖，变异样本全被拒绝。
5. 崩溃样本太多，用户需要去重分组，并判断哪些 crash 值得继续做 exploit 分析。

### 语言信号 (用户的话里出现这些就应激活)

- “跑了两天覆盖率不涨 / coverage plateau / no new edges”
- “只有一个样本能用 / only one seed / corpus 太小”
- “变异全被校验和拒了 / checksum rejects every mutation”
- “崩溃太多怎么去重 / crash triage / dedup crashes”
- “AFL 怎么配 / edge coverage / fuzzer 怎么选种子”
- “这个 crash 能不能利用 / is this crash exploitable”

### 与相邻 skill 的区分

- 与 `fuzzing-strategy` 的区别: 后者决定 Blind Fuzz 还是 Smart Fuzz、选哪类工具；本 skill 决定已经选定 fuzz 后，闭环每个参数怎么配、什么时候停。
- 与 `symbolic-execution` 的区别: 后者讲符号化、路径条件、约束求解的内部流程与失败边界；本 skill 只在覆盖停滞时把 concolic 当作补分支的组件。
- 与 `directed-memory-kernel-fuzzing` 的区别: 后者处理已知目标点的定向测试、闭源内存 fuzz、内核/驱动接口与反 Fuzz 对抗；本 skill 处理常规输入通道下的覆盖率引导。
- 与 `file-format-vulnerability-reversing` 的区别: 后者从畸形样本反推格式解析入口、构造最小 POC；本 skill 用格式知识提升 fuzz 的通过率与变异命中率。

## E — 可执行步骤 (Execution)

1. **定目标与输入通道**
   - 枚举所有可到达程序的输入：文件、协议字段、消息头、文件名、环境变量、注册键值、命令行参数。
   - 完成标准: 得到“输入通道清单 + 可复现的启动命令 + 异常判定 oracle（崩溃/ASan 报告/断言）”，并确认目标处理的是内存破坏类逻辑。

2. **建种子库**
   - 收集目标真实支持的合法样本、官方测试集、公开 PoC 或抓包报文；只保留格式良好且能走到较深路径的样本，并做最小化。
   - 完成标准: 每个主要格式/协议分支至少有一个合法种子，且空跑时能越过入口解析。

3. **处理校验与格式门槛**
   - 定位校验和/哈希/长度字段与校验点，在变异后重算回填；强格式目标先建立语法模型，在合法骨架上做定向变异。
   - 完成标准: 抽样变异能稳定通过前置校验，执行路径进入解析主体而非错误处理。
   - 判停条件: 若校验机制无法定位或无法重算，且无格式规范可用，停止本条路线，改走内存 fuzz 或人工逆向。

4. **选覆盖信号与调度策略**
   - 用边覆盖位图而非基本块计数；按阶段选适应度：前期“新度”优先，后期“深度”优先，并对低频路径加权；为每个种子设定能量上限。
   - 完成标准: 能读出新增边数、种子命中分布与单种子执行频率，调度策略有明确参数而非默认值。

5. **运行并监控**
   - 记录 exec/s、新增边、崩溃数、超时数、路径分布；用 ASan/UBSan 等消毒器补充崩溃判定。
   - 完成标准: 有连续时间序列数据，能判断“无新边”是暂时波动还是真实停滞。

6. **处理覆盖停滞**
   - 先排查种子多样性、校验门槛与关键字段是否未覆盖；仍无新边时，定位卡住的分支条件。
   - 完成标准: 明确停滞原因是“输入没到”“条件跨不过”还是“目标已测尽”。
   - 判停条件: 若停滞由复杂条件/魔数比较造成且目标可符号化，转 concolic 求解后回灌；若无结构线索且目标是已知深层点，转 directed fuzz；若输入通道根本不可达，转内存/内核 fuzz 路线。

7. **崩溃去重分组**
   - 用模块名 + 模块偏移 + 函数偏移 + 调用栈 + 异常码作稳定特征，不用绝对地址；按启发式重复识别、路径/调用栈聚合、异常签名三类方法归并。
   - 完成标准: 产出“样本组—疑似缺陷”映射，报告中区分 crash 数与去重后的缺陷数。

8. **可利用性初判**
   - 看崩溃点 EIP 是否可控、是否可形成任意地址写/指定地址写/任意地址读/指定地址读，并检查是否存在基址或敏感数据泄露。
   - 完成标准: 每个样本组标注“可用 / 可能可用 / 可能不可用 / 未知”及依据；把高价值样本移交 exploit 分析，而不是继续盲目扩量。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **目标是逻辑漏洞、权限绕过、会话/状态机缺陷**: 这类问题不破坏内存、不触发崩溃，基于崩溃信号的 fuzz 看不到；应改用人工审计、污点分析或带语义断言的测试。
- **需要用“没崩溃”证明“没有漏洞”**: fuzz 只能证明“在给定种子、时间与 oracle 下未发现”，不能证明不存在漏洞。
- **输入通道不可达**: 目标不接收外部文件/协议输入，或关键数据只在内存中生成；此时应转内存模糊测试、内核/驱动 fuzz 或定向 fuzz。
- **目标有强反 Fuzz 且尚未处理**: 反调试、反插桩、输入获取阻断、异常吞掉会让覆盖率与崩溃信号同时失真；先解决对抗前提，再谈闭环。
- **漏洞需要多字段、多请求或时序组合才能触发**: 单维变异无法凑齐组合条件，应转多维 fuzz 或定向测试。

### 作者在书中警告的失败模式

- 把崩溃数量等同于漏洞数量，未做调用栈/偏移归并就按 crash 数汇报（ce-C01）。
- 用“没有崩溃”证明“没有漏洞”，漏掉逻辑漏洞与信息泄露（ce-C02）。
- 把覆盖率当漏洞概率或测试完成标准，覆盖停滞即收工（ce-C03）。
- 初始种子质量差，样本长期卡在浅层解析与错误处理（ce-C04）。
- 盲目均匀变异，不定位长度、类型、魔数等关键字段（ce-C05）。
- 忽视输入验证、校验和与格式门槛，样本全部在入口被拒后误判目标安全（ce-C06）。
- 用单因素 fuzz 处理多点触发漏洞，长期无 crash 就判定安全（ce-C08）。

### 作者的盲点 / 时代局限

- 成书于 2022 年，fuzz 工具生态变化极快；书中对 AFL、BAP、KLEE 等的描述偏原理，具体版本、脚本与工程流水线很快过时（今天更常见 AFL++、LibFuzzer、honggfuzz 等）。
- 案例规模偏小：gif2png 约 12 小时、28 个崩溃，Peach 案例是本地搭建的登录页，不能直接外推到大型真实系统。
- 示例以 32 位 x86 为主，ARM64、Apple Silicon 与 JIT/动态生成代码场景需另行补课。
- 假设分析者能获得可插桩或可符号化的目标；加壳、反调试、JIT 会让这一前提失效。
- 假设漏洞可由“一条路径/一个崩溃”解释；真实漏洞常涉及多线程竞争、跨请求状态与环境组合。

### 容易混淆的邻近方法论

- `fuzzing-strategy`: 负责 Blind/Smart 选型与工具选择，本 skill 负责闭环参数与停止条件。
- `symbolic-execution`: 负责约束求解内部机制，本 skill 只把 concolic 当停滞时的补充分支手段。
- `directed-memory-kernel-fuzzing`: 负责定向/内存/内核路线与反 Fuzz，本 skill 负责常规覆盖率引导。
- `file-format-vulnerability-reversing`: 负责格式解析逆向与最小 POC 构造，本 skill 借用格式知识提升变异通过率。
