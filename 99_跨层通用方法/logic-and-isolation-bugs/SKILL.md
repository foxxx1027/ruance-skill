# 逻辑与隔离类缺陷：竞争条件、类型混淆与沙盒逃逸

## R — 原文 (Reading)

> "竞争条件的本质是检查（Check）与使用（Use）之间存在时间窗口，攻击者在这个窗口内改变被检查的对象。"
>
> — 林桠泉，《漏洞战争：软件漏洞分析精要》第 11 章 11.4.2

类型混淆的界定（第 11 章 11.2.2）：

> "类型混淆不只是编程概念上的数据类型错误，还包括类对象、数据结构布局层面的错配。"

---

## I — 方法论骨架 (Interpretation)

这类缺陷不是"越界写"式的内存破坏，而是**逻辑或隔离边界被绕过**。作者给出三个可复用的判定/枚举模型。

**模型 1：竞争条件 = Check/Use 时间窗**
- 把任何竞态抽象为"程序在 T1 时刻**检查**某状态，在 T2 时刻**使用**该状态，中间存在窗口"。
- 可统一解释差异极大的场景：银行存取款（余额检查与扣款之间）、文件 IO（`stat` 与 `open` 之间）、网络访问（先判权限后用资源）。
- 利用的关键不是"抢跑"（提高并发数碰运气），而是**主动撑开窗口**——在窗口内用可控动作阻塞 Use 侧。典型手法：对共享对象加锁/占用（如 Windows 的 `OpLock`：锁定文件后，Use 侧会挂起，攻击者借"解锁回调"把文件重定向动作精确塞进 Check 与 Use 之间）。
- 历史印证：Therac-25 事故（关闭硬件互锁）也是同一"检查—使用"缺失。

**模型 2：类型混淆的判据是"布局错配"，不是"用法灵活"**
- 判定问句：**解析引用时用的类型，是否与实际对象的类型/内存布局不符？**
- 若引擎以"字典布局"去读一个"数组对象"的内存，导致读到越界字段 → 成立。
- 若只是语法糖、底层仍是同一布局 → 不成立。
- 覆盖面分两级：基础类型级（如 Uint 被当 String 用）+ 类对象级（A 类对象被当 B 类处理）；可用 union 类 + 反射把不同宽度的域混用（如 int 域与 8 字节域的混用）。

**模型 3：沙盒逃逸 = 攻击面枚举清单**
把 IE 沙盒逃逸归纳为 6 类，用于"面对陌生沙盒时的检索序"：
1. Broker 接口漏洞（低权限进程调用 broker 暴露的接口）；
2. 策略检查绕过（绕过完整性级别/令牌检查）；
3. 策略设置不当（如本应以 Low 启动却以 Medium 启动）；
4. IPC 通信问题（共享内存/消息中夹带主进程敏感指针）；
5. 沙盒权限限制不严（可访问本不该访问的资源）；
6. 内核提取（借内核漏洞跃出沙盒）。

要点：清单里有"策略设置不当""IPC 夹带敏感信息"这类**非漏洞型的配置/设计缺陷**——这是差异化的视角：逃逸未必需要"另一个漏洞"。

## A1 — 书中的应用 (Past Application)

### 案例 1: CVE-2014-9150（Adobe MoveFileEx）— 用 OpLock 撑开窗口
- **问题**: 竞态 PoC 成功率依赖运气，窗口太窄。
- **方法论的使用**: 用 `OpLock` 锁定目标文件使 Use 侧挂起；借解锁回调把文件重定向动作塞进 Check 与 Use 之间。
- **结论**: 不是提高并发数，而是**人为撑开窗口**。
- **结果**: 成功率由"运气"变为"可控"。

### 案例 2: CVE-2013-2423（Java Applet）— union + 反射混用域标签
- **问题**: 需要让引擎把一类对象当作另一类解析。
- **方法论的使用**: 用 union 类 + 反射，把 int 域与 8 字节域混用，制造布局错配。
- **结论**: 类型混淆发生在**布局**层面而非语法层面。
- **结果**: 形成可控的越界访问。

### 案例 3: CVE-2014-0257（dfsvc）— 沙盒逃逸的 broker 接口面
- **问题**: 需要从低完整性进程跃出。
- **方法论的使用**: 按 6 类清单逐项试探，命中"Broker 接口漏洞"这一面。
- **结论**: 攻击面枚举让"从哪下手"变成清单检索。
- **结果**: 完成沙盒逃逸。

### 案例 4: Therac-25 事故（第 11 章 11.4.1）— 检查—使用缺失的历史实例
- **问题**: 讲述竞争条件的本质。
- **方法论的使用**: 把放射治疗机的"硬件互锁被关闭"归入同一 Check/Use 缺失模型。
- **结论**: 竞态模型跨越软件与物理系统。
- **结果**: 为模型提供非软件证据（加强 V1）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **判定缺陷类别**
   - 竞态 → 步骤 2；类型混淆 → 步骤 3；沙盒逃逸 → 步骤 4。
   - 完成标准: 明确写出属于哪一类（或哪几类并发）。

2. **（竞态）画 Check/Use 时间窗并撑开**
   - 方法: 标出 Check 点与 Use 点、两者共享的对象；不要只堆线程数，而是找/造一个能在窗口内阻塞 Use 侧的动作（加锁/占用/OpLock 式回调）把窗口拉长。
   - 完成标准: 窗口由"概率"变为"可控时长"，成功率可测量。
   - 判停条件: 找不到任何可阻塞 Use 侧的手段 → 退回概率法并明确其不可靠性。

3. **（类型混淆）用"布局错配"判据裁决**
   - 方法: 问"解析引用时的类型是否符合实际对象的内存布局"；检查是否存在越界字段读取；注意基础类型级与类对象级两个层次。
   - 完成标准: 给出"成立/不成立"的判定及依据（布局是否错配，而非用法是否灵活）。

4. **（沙盒逃逸）按 6 类清单枚举攻击面**
   - 逐项试探: ① broker 接口 ② 策略检查绕过 ③ 策略设置不当 ④ IPC 共享内存夹带敏感指针 ⑤ 权限限制不严 ⑥ 内核提取。
   - 完成标准: 对每一类给出"命中/不命中"，宁可有遗漏清单项也要逐项过一遍。

5. **串联到利用/评估**
   - 方法: 若形成可控原语，交给 `exploit-chain-construction` / `kernel-exploitation` 续接；若仅做评估，记录每类面命中情况。
   - 完成标准: 明确下一步归属。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **缺陷本质是内存破坏**（越界、UAF、双释）→ 走定位/堆利用 skill。
- **只是普通业务逻辑 bug、无安全边界被绕过** → 不属本 skill 范畴。
- **需要精确证明"可用"的场合**：本 skill 中类型混淆/沙盒逃逸为 V1 partial（单章证据），不宜作为唯一依据下强结论。

### 作者在书中警告的失败模式

- 竞态 PoC 只靠提高并发碰运气、不做窗口构造（g05-ce07）。
- 把"语法灵活"误判为"类型混淆"（判据应是布局错配而非用法灵活）。

### 作者的盲点 / 时代局限

- **单章覆盖、样本有限**：类型混淆与沙盒逃逸仅第 11 章展开（V1 partial），其枚举清单源自 IE 沙盒，未必完整适用于 Chrome/Firefox 的现代沙盒（站点隔离、MutipartitionAlloc、Win32k lockdown）。
- **未涉及 Spectre/Meltdown 之后的隔离模型**：现代"隔离"已扩展到微架构侧信道，本 skill 的清单不覆盖此类。
- **竞态模型偏文件/句柄场景**：现代用户态/内核态更细粒度锁与无锁数据结构的竞态形态未覆盖。

### 容易混淆的邻近方法论

- "多线程 bug"≠"竞争条件漏洞"：只有"检查与使用之间存在可被攻击者利用的窗口、且影响安全边界"才构成本 skill 的对象。
