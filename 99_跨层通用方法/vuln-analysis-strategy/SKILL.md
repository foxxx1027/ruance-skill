# 漏洞分析策略选择（动手前的元决策）

## R — 原文 (Reading)

> "如果只是为了分析某个函数的功能，定向地静态分析会比较直接高效，但如果想弄清楚不同函数之间的关系，以及变量、返回值或相互传递的参数，可能就需要结合动态调试执行程序去跟踪分析。"
>
> — 林桠泉，《漏洞战争：软件漏洞分析精要》第 1 章 1.4.1 / 1.4.2

配套引文（作者对重型方法的定调，第 1 章 1.4.5）：

> "污点追踪犹如'七伤拳'一般，'先伤己，再伤人'，开发污点追踪工具，不仅费时费力，而且开发完成后，运行比较大的工具往往需要运行很长时间。"

---

## I — 方法论骨架 (Interpretation)

分析漏洞最大的浪费不是"读不懂汇编"，而是**在错误的方法上花掉一天**。作者把"选方法"这件事本身上升为方法论，其骨架有四层判断，必须按顺序做：

1. **先判类型，再选方法。** 崩溃若发生在 `free/delete` 路径，或地址经 `!address` 查为 `MEM_FREE`，优先按"释放后使用 / 双重释放"处理；崩溃在 `rep movs`/`memcpy` 上则按"越界写"处理。类型判错，后面所有工具选择都会跟着错（书中原话：漏洞类型无法穷举，但分析思路可迁移）。
2. **再判层次。** 目标运行在哪一层决定了你能用哪些手段：脚本/框架层（有符号、有日志、可反编译）↔ Native 层（要靠反汇编）↔ 内核层（要靠双机调试、符号表、驱动开发功底）。先分层，再选锤子。
3. **再选方法，且要认成本。** 五种通用方法（静态分析、动态调试、源码分析、补丁比较、污点追踪）没有一个是万能的。作者给出的隐性排序是：**有源码就别逆向；只有补丁就从差异反推（性价比最高）；污点追踪是最后手段**，只在漏洞位置隐蔽、其他方法失效时使用。
4. **工具服从场景。** IDA 通用反汇编；OllyDbg 用于破解/协议/病毒；Immunity Debugger(+mona) 专用于漏洞调试；WinDbg 用于微软自家产品与内核；GDB 用于非 Windows；JEB 用于 Android。选错调试器 = 选错切入点。

贯穿其中的是**止损纪律**：当延续当前路径不再产生新的可验证假设（崩溃函数只是"触发"而非根因），立即换切入点，优先换到"输入侧"（PoC/样本构造处），而不是继续在"输出侧"死磕。

## A1 — 书中的应用 (Past Application)

### 案例 1: CVE-2013-2551（IE VML 整数溢出）— 从"输出侧"退回"输入侧"
- **问题**: 作者在 `vgx!COALineDashStyleArray::get_item` 上跟了很久，栈回溯显示它是崩溃函数，但继续跟没有新信息。
- **方法论的使用**: 判定"当前分支不再产生新假设" → 触发止损；换切入点到 PoC 源码本身，逐行看它构造了什么对象、哪个数值异常。
- **结论**: `get_item` 只是"触发异常"的末尾一环；真正写入异常值的是 `put_length`（数组长度被设为 -1）。
- **结果**: 从输入侧一眼锁定真正的漏洞函数，比在输出侧继续硬钻快得多。

### 案例 2: 第 3 章 MDAC / MSHTML 案例 — "只有补丁"时的选择
- **问题**: 部分案例（MS10-055、MS12-037）手上只有官方补丁，没有 PoC，成因从单向调试推不出来。
- **方法论的使用**: 走"方法选择"的排除法——无源码 → 源码分析不成立；无 PoC → 动态调试缺靶点；污点追踪成本过高。剩补丁比较。
- **结论**: 用 Turbodiff/BinDiff 比对修补前后二进制，直接读出差异指令（如多出的 `and bl,7Fh`）。
- **结果**: 补丁的差异形状直接暴露根因（偏移量未做掩码截断），并同时得到修复方案。

### 案例 3: 第 6 章 CVE-2010-3974（fxscover 双重释放）— 先判类型
- **问题**: 程序在 `free` 路径上触发异常，但成因不明。
- **方法论的使用**: 按"崩溃位置 → 漏洞类型"先定性：free 路径 + 栈回溯到对象析构 + `!address` 显示内存为 `MEM_FREE`。
- **结论**: 确认为双重释放；随后利用思路直接锁定"占坑、控虚表指针"方向。
- **结果**: 避免按堆溢出去推演堆结构这条弯路。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 拿到一个崩溃样本/漏洞公告/补丁，以及一句"帮我看看这个漏洞"，但没有任何分析方向提示。
2. 在多个可选手段之间犹豫：要不要开污点追踪？要不要先逆向？没有 PoC 是不是没法分析？
3. 已经在某个思路上投入很久却毫无产出，需要判断"该继续还是该换"。
4. 需要选调试器/工具，或跨平台（Windows / Linux / Android）分析，不确定工具是否匹配。
5. 面对一个新领域（移动端、云、IoT）或一种没见过的漏洞类型，需要决定从哪一层切入。

### 语言信号 (用户的话里出现这些就应激活)

- "这个漏洞该怎么分析 / 从哪下手 / 没思路"
- "只有补丁没有 PoC，怎么办"
- "我用 IDA 跟了半天没进展，还要继续吗"
- "该用 WinDbg 还是 Immunity / GDB"
- "which approach should I use / where do I start / no PoC available"

### 与相邻 skill 的区分

- 与 `crash-to-root-cause` 的区别: 本 skill 只做"选哪条路"的判断，**不展开具体定位步骤**；一旦方法选定（如"走栈回溯"），交给 `crash-to-root-cause` 执行。
- 与 `patch-diff-and-source-analysis` 的区别: 只有在本 skill 判定"补丁比较是当前最优路径"之后，才进入后者；后者不负责路径比较。
- 与 `vuln-essence-classification` 的区别: 后者回答"这个漏洞属于程序缺陷还是策略缺陷"（是什么），本 skill 回答"该用什么手段分析它"（怎么做）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **判漏洞类型（先定性后定量）**
   - 完成标准: 给出一个初步类型（栈溢出 / 堆溢出 / 整数溢出 / UAF / 双重释放 / 数组越界 / 竞态 / 类型混淆 / 策略缺陷）。
   - 方法: 看崩溃指令形态（`rep movs` → 越界写；`mov ecx,[eax]; call [ecx+N]` → 虚调用 + 可能 UAF）、看崩溃是否在 `free/delete` 路径、用 `!address` 判断目标地址是否为已释放区。
   - 判停条件: 若连类型都无法初判且手上没有可复现样本 → 跳步骤 5（先补样本）。

2. **判目标所处层次**
   - 完成标准: 明确落在 脚本/框架层、Native 层 还是 内核层（Windows 还要区分 ring3/ring0）。
   - 依据: 崩溃栈里出现的模块（`jscript.dll`/`mshtml.dll` → 浏览器内核与脚本层；`ntoskrnl.exe`/`.sys` → 内核层；`libwebviewchromium.so` → Android native）。

3. **按"成本刻度"选方法（按序排除）**
   - ① 有源码 → 源码比对 / 源码级调试（成本最低，信息最全）。
   - ② 只有补丁 → 补丁比较（差异直接暴露根因与修复方式）。
   - ③ 有可复现样本 → 动态调试 + 栈回溯（最直接）。
   - ④ 样本不可复现/过于稳定 → 先改造样本制造崩溃，再回到 ③。
   - ⑤ 以上都不通且漏洞位置隐蔽 → 才考虑污点追踪。
   - 完成标准: 写出"选定方法 + 排除理由"，并明确该方法的前置条件是否已满足。

4. **选工具并确认前置条件**
   - 完成标准: 调试器与目标匹配；断点通用性已处理（模块未加载用 `sxe ld:`、堆地址会变则用"符号+偏移"、复合进程用 `.childdbg 1`）。
   - 判停条件: 若前置条件不满足（如目标模块尚未加载），先补前置配置再下断点。

5. **建立止损判据并执行**
   - 完成标准: 明确"什么情况下换路径"的可核查条件——当前分支不再产生新的可验证假设时即换点。
   - 换向偏好: 优先换到输入侧（PoC / 样本构造），其次换方法（补丁比较 / 源码比对），最后才换目标版本。

6. **产出分析记录（反结论式）**
   - 完成标准: 记录"遇到什么现象 → 为什么这样排查 → 每个断点想验证什么 → 走不通时如何换向"，而不是只贴漏洞代码。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **已经明确知道该用哪种方法、只缺执行细节** → 直接用执行型 skill（`crash-to-root-cause` / `patch-diff-and-source-analysis`），不要在这里空转做比较。
- **没有可复现样本、也没有补丁、也没有源码** → 本 skill 的排除法会全部落空；此时应先解决"样本获取"问题，而不是继续比较方法。
- **面对的是配置/策略类缺陷**（未授权访问、弱口令暴露），而非程序缺陷 → 走配置审计，不要套用二进制分析工具箱（见 `vuln-essence-classification`）。

### 作者在书中警告的失败模式

- 对庞大软件做全量静态分析，工作量过大（候选反例 g01-ce02）。
- 本可读源码却按闭源处理（或反之），把分析方式与手上材料错配（g01-ce07）。
- 硬编码跳转地址破坏利用的通用性（g01-ce03）。
- 在频繁调用的函数上直接下断点会不停被断下，说明"方法对但落点错"（g06-ce01）。

### 作者的盲点 / 时代局限

- **全书没有 fuzzing / 符号执行的任何位置**：作者的"方法选择"清单里不存在"先用 fuzzer 找漏洞"，而在今天 fuzzing 已是漏洞发现的主流范式。因此本 skill 的选择空间应补上"先自动化挖掘、再手工分析"这一支。
- **保护机制只覆盖到 GS/DEP/ASLR/沙箱**：CFG/CET/MTE 之后的绕过路径不在讨论范围，若目标环境较新，需自行补足。
- **假设分析者时间近乎无限**：作者把污点追踪这类重型方法与轻量方法并列，未给出严格的成本—收益量化；本 skill 已按成本刻度重排，但该刻度本身是经验值。

### 容易混淆的邻近方法论

- "多种方法结合使用"是常识口号；本 skill 的差异点是**带成本刻度的排序**与**止损判据**，不要退化成喊口号。
