# 日志安全（logging-security）

## R — 原文 (Reading)

> 确保系统在发生重要安全事件时创建日志。……通常重要安全事件包括：重要数据更改、认证尝试（特别是失败的认证）、失败的访问控制、失效或者已过期的会话令牌尝试、系统例外、管理功能行为、失败的后端TLS链接、加密模块的错误。……对日志中的特殊元素进行过滤和验证……避免在日志中保存敏感数据。
>
> — GB/T 38674-2020, 5.4 e) g) i)

---

## I — 方法论骨架 (Interpretation)

日志不是"多写点方便排查"的附属品，而是一条跨越信任边界的输出通道，要按不可信数据的同一套规矩处理。

先把它当成第三个输出上下文：写入前过滤或编码，读出来时按纯文本渲染，任何查看界面都不执行日志内容。

再决定记什么：只记能支撑安全判断的事件——数据变更、认证尝试（尤其失败）、访问控制失败、失效令牌重放、系统异常、管理操作、后端 TLS 失败、加密模块错误；其余交给业务埋点。

然后决定不记什么：口令、令牌、证件号、完整请求体不进日志，宁可记标识符与结果。

存储上要求独立目录、严格权限、摘要或哈希链保完整、每条带可信时间戳；写入接口不接受任意拼接。

最后把日志组件自己当作会失败的基础设施：打日志出异常不能拖垮业务，也不能静默丢失。

一句话：日志的安全属性是"不可被外部改写、不可被当作代码执行、不反过来泄露秘密"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 未净化的用户名写日志造成伪造条目（附录 A.2.4.2）
- **问题**: 登录成功与失败两条分支都用字符串拼接把 username 写进日志，username 直接取自请求，没有任何净化。
- **方法论的使用**: 按 5.4 g) h) 把日志当成输出上下文来审：不可信数据是否原样进入？换行与控制符能否改变"一条记录"的边界？写入接口是否等于允许攻击者写任意数据？
- **结论**: 攻击者提交含回车换行的多行"用户名"，日志中会凭空多出一条"User login succeeded for: administrator"，管理员会把它读成系统行为。规范做法是记录前用字母数字下划线白名单校验用户名，不匹配时只记"login failed for unauthorized user"，原始输入不落日志（附录 A.2.4.2）。
- **后果/防住什么**: 不修则审计被污染、入侵轨迹被掩盖；修后日志行不可被拆分或伪造，攻击者无法借日志误导告警与取证。

### 案例 2: 异常文本把内部路径带进日志与用户界面（附录 A.3.4.3）
- **问题**: 程序把请求参数拼成文件路径直接打开，文件不存在时把含完整路径的异常原样上抛，最终进入错误页与日志。
- **方法论的使用**: 用 5.4 i)（日志不存敏感数据）与 6.4 g)（错误信息只给通用提示）这条同源规则，检查异常文本这条"隐式日志通道"是否泄露内部结构。
- **结论**: 反复提交猜测的文件名，攻击者可依据"存在/不存在"的报错差异逐层重建目录树。规范做法是先用规范化路径与允许根目录比较，不合法统一返回"Invalid file"，细节只写进受保护的内部日志并附追踪号（附录 A.3.4.3）。
- **后果/防住什么**: 不修则错误信息变成目录爆破的旁路信道；修后内外部提示分离，日志承担排查、界面只给通用文案。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 正在给登录、支付、后台管理加日志，纠结"这条要不要记、字段要不要脱敏"。
2. 安全评审或等保测评提出"日志不完整/日志可被篡改/日志里有敏感信息"，需要给出整改清单。
3. 日志接入集中平台或 SIEM 后，看板出现弹窗、字段错位、条目被拆成多条。
4. 怀疑攻击者通过请求头、URL、用户名往日志里写入了伪造内容以掩盖痕迹。
5. 日志文件与 Web 目录同处一地，或被低权限账号可读可删。

### 语言信号 (用户的话里出现这些就应激活)

- "日志注入 / log injection / log forging"
- "日志里出现了我没打过的一行 / 时间戳对不上"
- "这条日志要不要脱敏 / 能不能记手机号、token"
- "审计日志 / audit trail / 等保日志要求"
- "后台日志页面弹窗了 / 日志面板执行了脚本"
- "日志文件被删了 / 怎么证明日志没被改"

### 与相邻 skill 的区分

- 与 `input-validation-output-encoding` 的区别: 后者处理所有入口与网页/CSV/命令等输出上下文；本 skill 只处理"日志"这一输出上下文与"该记哪些安全事件"的选择问题。
- 与 `sensitive-data-lifecycle` 的区别: 后者回答"这个字段算不算敏感、要不要加密、留多久"；本 skill 只回答"它能不能进日志、进日志前怎么处理"。
- 与 `function-and-exception-safety` 的区别: 后者管异常的抛出边界与对外提示；本 skill 管错误文本落到日志后的内容与完整性。

## E — 可执行步骤 (Execution)

1. **盘点日志出口与查看面**
   - 完成标准: 产出一张清单，列出每个写入点、落盘位置、保留时长、可读角色、是否有查看界面（含 SIEM 看板、运维脚本、导出功能）。
   - 判停条件: 若系统是无多用户、无查看界面的单机工具，跳过步骤 4 的权限与摘要，仅执行步骤 3 的注入检查。

2. **对齐"必须记录的安全事件"**
   - 完成标准: 对 5.4 e) 的八类事件逐项标注"已有日志点/缺失/不适用"，缺失项写明补充位置；每个日志点能说出它支撑哪一次事后判断。
   - 判停条件: 若某类事件由上游平台（网关、数据库审计）统一记录，记录该归属并跳过本系统实现，但要确认可关联同一请求标识。

3. **处理进入日志的不可信字段**
   - 完成标准: 每个外部字段要么走白名单/枚举，要么结构化为独立字段；换行、回车、制表、ANSI 转义被移除或转义；口令、令牌、证件号、完整请求体不再写入。
   - 判停条件: 若字段必须保留原文用于排查，改为写入受控的加密附件并只记引用 ID。

4. **加固存储与完整性**
   - 完成标准: 日志目录位于应用目录之外，应用账号只有追加权限；有摘要或哈希链且可抽验；每条带统一时区时间戳并与可信时间源同步；查看端按纯文本渲染。
   - 判停条件: 若日志已托管给云日志服务，确认其不可变存储与访问审计已开启后，本条转为核对配置而非自建。

5. **做故障与攻击回放**
   - 完成标准: 注入含换行、超长、控制符的样本后，日志仍为单行且字段数不变；模拟磁盘满或权限拒绝时业务不失败且有告警；在后台日志页提交脚本载荷不执行、不弹窗。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 目的是做业务埋点、漏斗分析或性能指标：这些日志量大、字段自由，按本 skill 的"只记重要安全事件"会被砍掉，应另设遥测通道。
- 纯本地单机工具、无多用户与远程查看面：独立目录、摘要链、权限分级的成本高于收益，只需保留注入过滤。
- 日志已完全托管且平台承诺不可变存储与访问审计：不要自建摘要链，重点转向字段脱敏、查询侧注入与留存策略。
- 事件流已用严格 schema 的消息总线承载：问题重心是 schema 校验与消费者权限，而非文本日志的换行过滤。
- 需要决定"敏感数据留多久、能否出境"：这是合规与数据治理问题，本 skill 只能给出"不记"这一条，不能替代法务判断。

### 作者在书中警告的失败模式

- **ce14 日志既被注入又被当可信内容渲染**：攻击者用换行拆分记录、伪造"管理员登录成功"；同一份未编码内容若被后台用 innerHTML 渲染，还会从审计污染升级为存储型 XSS，拿到运维会话。
- **ce15 用异常/错误信息泄露内部结构**：堆栈、绝对路径、SQL 片段、会话标识被写进日志并回流到界面，攻击者据此测绘系统；这与日志是同一泄露面。
- **ce24 把标准当合规检查表**：只核对"有没有日志"，不验证日志能否支撑一次真实入侵的定责与定范围，逐条打勾会给出虚假安全感。

### 作者的盲点 / 时代局限

- 未涉及集中式日志平台与 SIEM 的注入面：JSON 字段名污染、查询语句注入（如 Lucene/KQL 拼接）、看板模板注入、日志投毒影响告警规则，都超出"过滤换行"的范围。
- 未讨论日志留存合规：只写"避免保存敏感数据"，没有留存期限、删除机制、跨境传输与个人信息保护法下的最小化义务。
- 未讨论日志量本身成为 DoS 面：攻击者制造海量失败事件可打满磁盘或推高计费，标准没有速率限制与采样要求。
- 默认时间戳可信，未覆盖 NTP 欺骗、容器时钟漂移导致时间线不可用于取证的问题。

### 容易混淆的邻近方法论

- `input-validation-output-encoding` 的"按上下文编码"：本 skill 是它在日志这一特定上下文上的实例，不要反过来用日志规则去替代通用输入验证。
- `data-protection-and-secrets` 式的字段分级：先分级再决定是否入日志，本 skill 不负责分级方法本身。
