# 从修复反推漏洞：补丁比较、源码比对与 1-day 验证

## R — 原文 (Reading)

> "补丁比较：通过比较漏洞修补前后的程序，找出被修改的代码，从而定位漏洞所在。这是在没有源码、没有 PoC 的情况下，效率很高的一种方法。"
>
> — 林桠泉，《漏洞战争：软件漏洞分析精要》第 1 章 1.4.4

> “二进制比较的流程可比作寻宝之旅——只向研究人员提供了关于漏洞（或‘宝藏’）的有限的位置和细节信息。若有适当的技能和工具，研究人员即可定位和识别代码的变化，随后便可着手开发可以工作的漏洞攻击程序。”
>
> “通过逆向工程安全补丁而挖掘出来的漏洞常被称为 1-day 漏洞。”
>
> — Daniel Regalado 等，《灰帽黑客 第4版》第 19 章 19.1、19.1.2（书页 433–434）

---

## I — 方法论骨架 (Interpretation)

这套框架合并自《漏洞战争》的"补丁比较 + 源码比对"双路径与《灰帽黑客》的 1-day 实战流水线：前者给出"从修复反推"的通用判据与两条退路，后者补上"补丁怎么取、基线怎么选、差异怎么分诊、动态怎么三点对齐"的工程细节。合并后的统一主张是——**补丁是厂商主动交出的漏洞答案；有补丁时，补丁比较应排在动态调试之前**，它把"几万条指令里大海捞针"压缩成"看两处差异"，但"看到差异"离"确认漏洞"还有一道可达性门槛。

**第 0 步：判定材料形态，选路径。**
- 有补丁前后二进制 → 路径 A（二进制补丁比较）。
- 有修复前后源码/符号 → 路径 B（源码比对与源码级调试）。
- 两者都没有 → 本 skill 不适用，转 `crash-to-root-cause`。

**路径 A：二进制补丁比较。**

1. **选基线优先于选工具。** 查公告受影响软件表的 Updates Replaced，取被本补丁替换的最近版本，让两侧版本号尽可能接近；基线跨度过大会让差异函数成千上万，真正的安全改动被功能更新与重构掩盖。
2. **把补丁变成可比文件。** 微软链路通常是 MSU→CAB→目标 DLL/驱动；补丁前原件必须留档，并记录版本号、架构与哈希。
3. **函数级对齐。** 用 BinDiff/turbodiff 比较两版 IDB；Matched 按 similarity 排序，Unmatched 找新增/删除，category 看 identical、suspicious+、suspicious++、changed。
4. **分诊不能只看最低分。** 先用公告语义、符号名、导出表与交叉引用，把候选缩到少数有外部输入路径的函数；similarity 只表示"变得多"，不理解语义，也不区分安全修复与普通改动。
5. **读差异的"形状"，而不只是差异本身。**
   - 新增长度/边界比较 → 越界类（栈/堆溢出、整数溢出后的漏检）
   - 新增"释放后置空/计数清零" → UAF / 双重释放
   - 新增类型标记或 vftable 检查 → 类型混淆
   - 改变分配尺寸的计算式 → 整数溢出
   - 无界读取改为有界读取（如 `gets` → `fgets`）→ 栈缓冲区溢出
6. **BinDiff 全失配时的两条退路。** 退路 1：函数数组 + `索引*4` 定位——通过函数指针表下标查被改函数；退路 2：指令序列匹配——用一串特征指令在邻近地址搜索，找到对应函数再看差异。
7. **静态差异必须落到动态语义。** 反汇编只给指令，不给寄存器与结构体含义；关键偏移（如 `rdi+1E8h`）必须靠调试会话落地。

**路径 B：源码比对与源码级调试。**

1. 由公告/更新日志/版本记录确认"修复版本号"，不要猜；取修复前/后两份源码，**先只看 diff，不读全码**，避免全量源码的沉重前置成本。
2. 由 diff 锁定修改点后，再按需读该函数及其调用者；需要理解结构体时沿路径逐层搜索定义。
3. 想动态验证时建立源码级调试（WinDbg 接源码、`--enable-debug` 自编译、gdbserver+gdbclient 等）。
4. **符号失效的三级降级**：官方符号服务器有 → 直接用；没有 → 按对应版本号自行编译 debug 产物（构建工具链版本要接近源码发布时间，否则编译失败）；仍不行 → 退回纯汇编级分析。

**合并后的统一判定阶梯（两条路径共用）：**
"差异是否对应真实缺陷 → 是否可达 → 能否稳定复现 → 是否影响控制流"。任一不成立只能停在"疑似"。终点不是"找到差异"，而是能说明**"补丁加了什么检查、缺了它会怎样、怎样稳定触发"**；到这一步才谈得上 1-day。

配套纪律：打补丁前先留原件；确认修复版本号要看公告/更新日志；**不要把所有改动都当漏洞关键**；补丁常只加检查，不纠正错误的状态迁移，根因可能在更上游。

## A1 — 书中的应用 (Past Application)

### 案例 1: MS10-055（Cinepak 解码器）— 一条掩码指令看穿根因
- **来源**: 《漏洞战争》第 3 章 3.4.4 / 3.5.7。
- **问题**: 有补丁但没有 PoC 细节，需要定位被修的漏洞。
- **方法的使用**: 用 IDA + Turbodiff 对漏洞版与修复版 `iccvid.dll` 做函数对齐，得到一个"多出来了"的函数差异。
- **结论/结果**: 新增的 `and bl,7Fh`（对某字段做 0x7F 掩码）直接暴露根因——原实现对编码值缺少范围限制；补丁比较把定位时间压缩到分钟级。

### 案例 2: CVE-2011-0027（MDAC ADO）— BinDiff 失配后用退路
- **来源**: 《漏洞战争》第 4 章 4.3。
- **问题**: BinDiff 因版本/优化差异导致函数对齐失败，直接比对无结果。
- **方法的使用**: 用"函数数组 + 索引*4"的思路手工缩小范围，再用指令序列特征在邻近地址搜索定位对应函数。
- **结论/结果**: 在工具失效的前提下仍找到被修改函数，证明退路是 BinDiff 的必要兜底。

### 案例 3: 心脏出血（OpenSSL）— 打补丁后沿结构体路径搜定义
- **来源**: 《漏洞战争》第 8 章 8.4.2。
- **问题**: 开源组件有源码，但要快速理解补丁补的是什么。
- **方法的使用**: 取修补前后的源码做比对，再沿被改函数涉及的结构体路径逐层搜索其定义。
- **结论/结果**: 补丁在读取长度前增加了对 `payload_length` 与记录长度的复核；不读全量 OpenSSL 源码即可说明漏洞成因。

### 案例 4: MS14-006（tcpip.sys）— 相邻版本、解包、分诊与三点对齐
- **来源**: 《灰帽黑客 第4版》第 19 章 19.1–19.4（书页 433–434）。
- **问题**: 只有公告（CVE-2014-0254，IPv6 路由通告拒绝服务），手上没有可比较的 `tcpip.sys`。
- **方法的使用**: 按 Updates Replaced 追到 MS13-065；下载 `Windows8-RT-KB2904659-x64.msu`，`expand -F:*` 先解 MSU 再解内层 CAB；取 6.2.9200.16518 与补丁版 6.2.9200.16754 做 BinDiff；按公告语义优先看 IPv6 前缀函数，发现新增 `cmp dword ptr [rdi+1E8h],0Ah`；再用 WinDbg 按 `tcpip!Ipv6pUpdateSitePrefix+112/+156/+13d` 下断，Kali 上用 Scapy 发随机前缀的 ICMPv6 路由通告，`dd rdi+1E8h` 看计数、Wireshark 以 `icmpv6.type==134` 核对前缀字段。
- **结论/结果**: 补丁增加"已存储前缀数量不得超过 10"的检查；根因是前缀计数无上限导致内核池与 CPU 资源耗尽；未打补丁内核连发 10000 次可把 CPU 推到 100%。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 厂商刚发布月度补丁，只有 KB/CVE 公告，想知道它修了什么、能否在补丁与部署的时间差内做出 1-day 验证。
2. 拿到了新旧两个 DLL/驱动，但不知道该取哪个旧版本做基线，一 diff 就是成千上万个变化函数。
3. BinDiff/turbodiff 跑出结果，面对大量低相似度函数和 suspicious++ 标签，不知道先看哪个；或函数一个都对不上。
4. 反汇编里看到新增的比较、计数器或分配检查，却无法判断寄存器指向什么、偏移字段是什么含义。
5. 开源组件出了安全更新，想"先看 diff 再读全码"；或想对某个版本做源码级调试但符号服务器没有对应版本。
6. 想判断某处差异是否真的可达、能否稳定触发，避免把加固性改动或不可达代码当成漏洞。

### 语言信号 (用户的话里出现这些就应激活)

- "只有补丁没有公告 / 只有 KB，怎么反推漏洞"
- "补丁比较 / patch diff / patch diffing / 从补丁反推漏洞"
- "BinDiff / turbodiff 结果太多，先看哪个函数 / 函数一个都对不上"
- "相邻版本怎么选 / Updates Replaced 是什么 / MSU 怎么解包"
- "1-day / n-day 怎么做 / 漏洞复现"
- "源码比对 / source diff / 符号服务器没有这个版本 / 恢复源码级调试"

### 与相邻 skill 的区分

- 与 `crash-to-root-cause`: 本 skill 是**从修复反推**（有补丁/源码，走"看差异"）；后者是**从崩溃现场逆推**（无补丁，走"回溯定位"）。有补丁时优先本 skill。
- 与 `locate-by-known-anchor`: 后者用字符串/符号名/导出表在**单个版本内**跳步定位；本 skill 是**跨版本对齐**找差异。
- 与 `source-and-binary-static-audit`: 后者在没有补丁、直接审源码或二进制找缺陷时使用；本 skill 先有"修复前后"这一对照，再把差异函数交给静态分析确认语义。
- 与 `fuzzing-engineering-peach`: 后者从无到有构造 fuzz 找 0-day；本 skill 在已有补丁时优先正推，也可把差异作为定向 fuzz 的输入。
- 与 `vuln-analysis-strategy`: "该不该走补丁比较"的选择判断在前置 skill；本 skill 是选定后的执行体。
- 与 `vuln-debugging-and-breakpoints`: 后者提供断点/回溯工具方法论；本 skill 负责差异定位与可达性判据。
- 与 `exploit-chain-construction`: 本 skill 只到"漏洞在哪、是什么类型、是否可达、控制流影响多大"；完整利用链构造走后者。

## E — 可执行步骤 (Execution)

1. **判定材料形态并选路径**
   - 有源码/符号 → 路径 B；只有二进制补丁 → 路径 A。
   - 完成标准: 明确写出走 A 还是 B，并列出"修补前/修补后"两个待比较对象。
   - 判停条件: 若补丁前版本或旧二进制拿不到 → 本 skill 不适用，转 `crash-to-root-cause`。

2. **确认补丁与目标范围**
   - 写明目标模块、CVE/KB、受影响系统版本、补丁前后版本号；确认目标版本确实在受影响列表内。
   - 完成标准: 版本号有公告/更新日志出处，不靠猜。
   - 判停条件: 若目标版本不在公告列表，停止，不要用其他版本外推。

3. **选相邻基线并解包、留档**
   - 按 Updates Replaced 找到最近前驱版本；补丁包按 MSU→CAB 解出目标文件；补丁前原件备份并记录哈希、架构、版本。
   - 完成标准: 两个文件版本尽量接近，来源可追溯。
   - 判停条件: 若只能拿到跨度很大的旧版，先预期差异噪声，不要直接逐函数通读。

4. **建立两个 IDB 并做函数级对齐**
   - 两版均完成 IDA 自动分析；用 BinDiff/turbodiff 产出匹配结果。
   - 完成标准: 架构、模块名、函数数量可核对，Matched/Unmatched 列表可读。
   - 判停条件: 若大量函数无法匹配 → 进步骤 5 的退路，不要硬看 similarity。

5. **（路径 A 退路）函数数组 + 索引*4 / 指令序列搜索**
   - 通过函数指针表下标定位被改函数；或取一串特征指令在邻近地址搜索。
   - 完成标准: 至少定位到一个"确实被修改"的函数。

6. **差异函数分诊**
   - 用公告语义、符号名、导出表、交叉引用、调用图、外部输入路径排序。
   - 完成标准: 得到 3–5 个候选函数，每个都附"为什么它可能被外部输入触达"的至少两条理由。
   - 判停条件: 若差异函数过多，先按可达性分诊，不要逐函数通读反汇编。

7. **读差异形状并映射漏洞类型**
   - 按"长度/边界比较 → 越界；置空/清零 → UAF/双释；类型标记检查 → 类型混淆；分配尺寸算式变 → 整数溢出"对号入座；指出新增/删除的具体指令及其调用路径。
   - 完成标准: 给出"补丁修的是 X 类漏洞"的判定，并指向具体被改指令。

8. **（路径 B）先看 diff 再读全码；需要时建立源码级调试**
   - 用 diff 工具比对修复前后源码，只读被改函数及其必要上下文；沿结构体路径补定义。
   - 符号三级降级：官方符号 → 自编译 debug 产物（工具链版本贴近源码发布时间）→ 退回汇编级。
   - 完成标准: 能复述"补丁加了什么检查/改了什么计算"；能在源码窗口下断并停住。
   - 判停条件: 编译反复失败 → 直接降一级，不要死磕工具链。

9. **动态触发并做三点对齐**
   - 隔离网段或 Host-Only 虚拟机；符号已加载；按"模块!函数+偏移"下断，ASLR 下不写绝对地址；构造能到达差异代码的输入；让输入字段、抓包/内存 dump、寄存器变化三者相互印证。
   - 完成标准: 断点命中；输入报文/文件字段与抓包或内存 dump 一致；差异指令执行前后的寄存器/内存变化可解释。
   - 判停条件: 断点始终不命中时，先核对符号版本、模块基址与偏移，再判断代码是否真的不可达；寄存器语义无法确认时必须补调试会话，不要继续靠猜。

10. **判定可利用性并形成 1-day 结论**
    - 按"差异真实 → 可达 → 稳定复现 → 控制流影响"逐级判定，输出"确认/疑似 + 缺陷类型 + 触发条件 + 控制流影响 + 控制难度"。
    - 结论包含受影响版本、补丁版本、可复现步骤、环境前提与未验证项；注明授权范围与实验隔离要求。
    - 判停条件: 若差异只是加固、日志、重构或不可达代码 → 停止，不写 PoC；若需要完整 ROP/信息泄露 → 转 `exploit-chain-construction`。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **拿不到补丁前版本或旧二进制** → 没有可比基线，差异无从谈起，改走 `crash-to-root-cause` 或单版本定位。
- **目标做了强混淆/虚拟化**（VMProtect、Themida 等）→ 二进制 diff 会被壳代码、指令重排和等价变换淹没，退路也可能失效。
- **补丁只是功能更新或版本升级** → 差异主体不是安全修复，相似度排序会把功能改动排到前面；先确认该补丁确实修了漏洞。
- **只有源码、要在无补丁对照下直接找缺陷** → 走 `source-and-binary-static-audit`。
- **没有任何可达输入通道** → 无法构造触发输入时只能做静态推断，不能宣称完成 1-day 验证。
- **目标是生产环境且无法隔离** → 尤其内核/网络类补丁验证（如 IPv6 路由通告）必须在隔离网段进行，避免误伤真实设备。

### 作者在书中警告的失败模式

- **基线跨度过大**：拿数月前的文件直接与最新补丁比较，差异函数成千上万，真正的安全改动被功能更新与重构掩盖（ce133）。
- **只看反汇编、不建调试会话**：反复放大流图仍不知道 `rdi+1E8h` 是什么，根因判断停留在猜测（ce134）。
- **把"变化函数暴增"当成漏洞变多**：指令重排、等价替换和编译器差异会制造大量噪声，不能逐个盲目审计（ce135）。
- **在共享网段发送 IPv6 路由通告**：RA 是链路本地组播，会误伤同网段真实设备；实验必须隔离（ce136）。
- **假设所有 Windows 版本都受影响、都有补丁**：MS14-006 只覆盖 Windows 8/Server 2012，Windows 8.1 出厂已含修复（ce137）。
- **把"相似度低"直接当成"漏洞就在这里"**：similarity 只表示变动幅度，不区分安全修复与普通改动（ce138）。
- **分析前没有备份"补丁前"原件**，事后无法比较（g06-f10、g01-ce05）。
- **直接替换目标文件而不留证据**，破坏了可比对的基线（g04-ce03）。
- **把补丁里全部改动都当漏洞关键**，不做逐处验证（g08b-ce01）。
- **忽略"补丁修的是表面，根因可能在更上游"**：补丁常只加检查，不纠正错误的状态迁移。

### 作者的盲点 / 时代局限

- **缺少自动化补丁比较管线**：《漏洞战争》主要靠 BinDiff/Turbodiff 手工对齐；现代实践会配合 `diaphora`/脚本化 bindiff、符号化差异聚类与批量优先级排序。
- **工具版本已过时**：《灰帽黑客》中的 BinDiff 为 Zynamics 商用版、要求 IDA 5.5+，turbodiff 依赖旧版 IDA；今天的菜单、快捷键与文件格式不能照搬。
- **Windows 更新机制已变化**：书中以 Windows 8.0/8.1 的月度补丁、MSU/CAB 解包为背景；Windows 10/11 大量使用累积更新，"相邻版本"的取法与解包链都不同。
- **样本单一**：《灰帽黑客》主案例是 MS14-006 的 IPv6 DoS，结论不能直接外推到浏览器、Office 或用户态服务。
- **对"补丁被退回/回滚"未讨论**：同一漏洞可能被多个补丁反复修，需甄别哪个才是有效修复。
- **假设差异=修复点**：在带调试信息的 Release 版本或高优化级别下，编译器差异会产生假阳性。
- **实验环境依赖旧组件**：VirtualKD、Windows 8 虚拟机、旧版 WinDbg 与 IPv6 默认行为都带有 2014–2015 年的条件，现代系统需重新验证可达性。

### 容易混淆的邻近方法论

- **源码 diff ≠ 二进制补丁比较**：源码 diff 给增删行；二进制比较给函数匹配、相似度和未匹配项，还要反汇编与调试解释语义。
- **字符串搜索/符号定位 ≠ 补丁比较**：前者在单版本内找锚点（见 `locate-by-known-anchor`），后者跨版本对齐找差异。
- **相似度评分 ≠ 漏洞评分**：低 similarity 只代表"变得多"，不代表"可利用"；必须再过公告语义、可达性与动态验证。
- **补丁比较 ≠ 完整利用开发**：本 skill 的输出是根因、触发条件与可利用性判断，不是绕过现代缓解措施的完整链。
- **`crash-to-root-cause`**：无补丁时从崩溃逆推；本 skill 有补丁时从修复正推，两者方向相反但可串联（先用补丁得候选，再用崩溃确认）。
