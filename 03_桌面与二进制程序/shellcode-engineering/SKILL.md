# Shellcode 工程化：先定载荷形态，再写机器码

## R — 原文 (Reading)

> “首先通过段选择字 FS 在内存中找到当前的线程环境块 TEB……线程环境块偏移位置为 0x30 的地方存放着指向进程环境块 PEB 的指针……第二个链表结点就是 kernel32.dll……从 kernel32.dll 的加载基址算起，偏移 0x3C 的地方就是其 PE 头。”
>
> — 王清 等，《0day安全：软件漏洞分析技术（第二版）》第 3 章 3.4.1

> “如果防火墙能够阻止与用来实施端口绑定shellcode的侦听套接字的连接尝试，那么或许我们可以修改shellcode来绕过这个限制。许多情况下，防火墙对出站流量的限制较少。”
>
> — Daniel Regalado 等，《灰帽黑客 第4版》第 6 章 6.1.3–6.1.5

## I — 方法论骨架 (Interpretation)

这套框架合并自《灰帽黑客 第4版》第 6–7 章的“载荷形态与输入/空间约束”与《0day安全》第 3 章的“接口工程、标识压缩、形式适配、空间压缩”。两者不是并列的两张清单，而是同一条流水线的上下游：**前者决定“要什么样的载荷”，给后者提供硬约束；后者决定“怎么把它写出来”，并把可行性回传给前者。** 因此统一成三段：**定形态约束 → 工程实现 → 验证闭环。**

### 第一段：定形态约束（需求侧）

先问任务，而不是先挑工具：

1. **交互性**：需要持续交互的 shell，还是只执行一条命令、投放一个文件、加一个账号？后者优先选更小、更安静的形态，不要默认 bind/reverse。
2. **网络方向**：目标入站能否到达绑定端口、能否主动出站、攻击者能否控制并预知源端口。入站可达 → bind；入站被阻断而出站可用 → reverse；两者都受限且源端口可控 → findsock；有巡检、需长期驻留 → 系统调用代理或进程注入等低痕迹形态。
3. **注入空间**：完整载荷放不下时，改 staged 或多级接力，第一级只负责“读入后续字节 + 移交控制权”。
4. **字符约束**：由注入路径（`strcpy`/`strcat`/Unicode/网络包/异常处理）决定坏字符集；没有明确约束就不编码。
5. **架构与 OS 范围**：决定能否用 `FS:[0x30]`、`int 0x80` 这一类锚点；跨架构不成立。

这一段的产物是一张约束表：形态、端口/地址、`badchars`、空间上限、目标 OS 矩阵、是否 staged。

### 第二段：工程实现（供给侧）

形态约束直接改写实现预算，不能等写完了再补：

| 形态 | 对实现的直接约束 |
|---|---|
| bind / reverse | 需要完整 socket 调用序列，API 定位链是必需项，长度预算较宽 |
| findsock | 复用已有连接，省掉 socket 创建，但要求源端口可预知 |
| 单命令 / 文件传输 | 追求最短、最少 API，通常不需要交互循环 |
| staged | 第一级极短，瘦身优先级高于功能完整，第二级才承载完整逻辑 |
| 系统调用代理 / 注入 | API 面更大、痕迹更小，但实现与验证成本最高 |

在这个预算内，按《0day安全》的四层工程落地：

- **接口工程**：`CLD` → `FS:[0x30]` → PEB → `[0x0C]` PEB_LDR_DATA → `[0x1C]` 初始化模块链表 → 第二个结点 kernel32 → `[0x3C]` PE 头 → `[0x78]` 导出表 → 名称表/RVA 表，逐级按固定偏移解析 API。链表里没有的 DLL（如 user32）用 `LoadLibraryA` 现装再找。
- **标识压缩**：不存函数名字符串，只存 hash 摘要；遍历导出表时对每个名字做同样运算并比对。摘要可以短到 8 bit，这也是后续瘦身的入口。
- **形式适配**：先实现纯逻辑，再整体编码，最后在头部接十几字节解码器。只要解码器满足字符约束，整段 payload 就满足约束——与软件加壳同构。
- **空间压缩**：短指令、复合指令、hash 压缩函数名、复用栈区做结构体与 NULL 参数、用返回值做循环条件；满足条件时让数据与代码重叠，把恰好等价于“准 NOP”的 hash 摘要直接摆进执行流。

两条纪律必须显式写进实现：使用字符串指令前 `CLD` 清零 DF；编码前在原始 shellcode 末尾补 `0x90`，与解码器的结束约定对齐。

### 第三段：验证闭环

验证不是“弹了 shell 就算过”，而是三层：**字节层**（含解码器的整串无坏字符、长度字段一致）、**注入形态层**（在真实字符串注入路径下不截断、解码器能自定位）、**环境层**（目标 OS/补丁矩阵与网络方向都成立）。失败现象要能回推到具体环节：第二次连接超时 → bind 入站前提不成立；回连无流量 → reverse 的出站/代理/NAT 前提不成立；载荷自身崩溃 → 查栈自覆盖、DF、结束符；换机器才失败 → 查静态 API 地址。

## A1 — 书中的应用 (Past Application)

### 案例 1: 防火墙只放行 Web，bind shell 第二次连接失败（《灰帽黑客 第4版》第 6 章 6.1.3–6.1.5）
- **问题**: 目标的 80 端口有可利用的 Web 服务，但网络只允许 Web、邮件等特定服务。
- **方法论的使用**: 先用 80 端口完成初始攻击，载荷在目标上绑定 4444 端口侦听，攻击者再发起第二次连接；按“入站可达性”检查，绑定端口不在放行列表内。
- **结论**: 初始攻击可达不等于绑定端口可达；bind shell 要求目标侧存在一条新的入站连接。
- **结果**: 初始攻击成功，第二次连接被防火墙拒绝，绑定 shell 始终等不到会话，书中据此引出反向 shell。

### 案例 2: encoder.c 用随机 key 生成不同编码并成功执行（《灰帽黑客 第4版》第 6–7 章）
- **问题**: 主体 shellcode 含需规避的坏字符，固定编码结果又容易被签名或过滤器识别。
- **方法论的使用**: 用时间种子随机生成 XOR key 逐字节编码；结果出现坏字符就换 key 重来；把长度与 key 写回解码器占位，拼接 `[decoder][encoded shellcode]` 后执行。
- **结论**: 解码器必须随长度、key 一起改写；坏字符扫描要覆盖整体，而不是只检查主体。
- **结果**: 三次运行分别使用 key 149、104、96，得到三组不同编码字节，每次都成功弹出 `sh-3.1#`。

### 案例 3: 用 PEB 链 + hash 做出跨平台通用弹窗 shellcode（《0day安全》第 3 章 3.4.3）
- **问题**: 早先的 shellcode 直接写死 `MessageBoxA`/`ExitProcess` 的手工地址，换机器或换补丁就失效。
- **方法论的使用**: 开头 `CLD`，把三个函数名的 hash 压栈并用 ESI 标识位置；从 `FS:[0x30]` 取 PEB，经 `[0x0C]`、`[0x1C]` 和第二个链表结点拿到 kernel32 基址，由 `[0x3C]` 到 PE 头、`[0x78]` 到导出表；遍历名称表算 hash 比对，命中后从 RVA 表取地址；user32 用已定位的 `LoadLibraryA` 装载后再找。
- **结论**: 不依赖静态 API 地址，只依赖结构体固定偏移，就能在任意 Win32 平台调用所需函数。
- **结果**: 得到 `popup_general`，不受 OS 版本与补丁版本限制，成为后续章节反复复用的通用弹窗 shellcode。

### 案例 4: 191 字节的 bindshell（《0day安全》第 3 章 3.6.3）
- **问题**: 可用缓冲区空间极小，一个能绑定端口、接受连接、正常退出的通用 shellcode 必须压到极限长度。
- **方法论的使用**: 选 8 bit 摘要且摘要恰好等价于“准 NOP”的 hash 算法，把 hash 值放在开头实现代码/数据重叠；按调用顺序把函数地址存栈；利用 `bind`/`listen` 成功返回 0，用返回值做循环结束条件；复用栈区同时充当结构体与 NULL 参数；优先选机器码最短的指令。
- **结论**: 空间受限时，“功能正确”和“字节最少”可以同时逼近；压缩的关键是重新组织数据与控制流。
- **结果**: 最终只有 191 字节，能绑定 6666 端口、允许外部连接获得 shell，并可在 NT4/2000/XP/2003 上运行。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 已通过远程服务漏洞控制执行流，正纠结“该用 bind 还是 reverse”，或不知道两者各自还缺哪个网络前提。
2. 目标在防火墙/NAT 之后，只放行 80/443，需要判断回连是否可行、要不要换允许端口或改用 findsock。
3. 输入路径会截断 `\x00`、回车，或只允许字母数字/Unicode，需要确定坏字符集并设计编码器与自解码头。
4. 缓冲区只剩一两百字节，完整载荷放不下，需要判断该 staged、该瘦身，还是该换更短的实现。
5. 手上有现成 shellcode，换一台机器或另一个补丁版本后调用 API 失败，需要把静态地址改成 PEB→导出表的运行时定位。
6. 载荷“执行了但连不回来”“编码后仍被截断”“以前能用现在莫名崩溃”，需要用形态与约束逐项排查。

### 语言信号 (用户的话里出现这些就必须激活)

- “shellcode 该用 bind 还是 reverse / 目标只允许出站 443”
- “bad character / 不能用 0x00 / 只允许可见字符 / alphanumeric”
- “注入空间只有 120 字节 / staged 和 stageless 什么区别”
- “PEB 怎么遍历 / 导出表怎么搜 / 怎么动态找 API”
- “编码器 / 解码器 / encoder / 自解压头 / hash 摘要 / 准 nop”
- “shellcode 换机器就失效 / shellcode 太长 / 怎么把它写短”

### 与相邻 skill 的区分

- 与 `crash-to-root-cause` 的区别：那个 skill 从崩溃现场反推“漏洞在哪个函数、哪个字段被写坏”，不产出可执行载荷；本 skill 假定注入点与执行时机已确定。若还不知道 EIP 能否到达、数据会不会被截断，先走它。
- 与 `win-stack-overflow-exploit` 的区别：后者是“运载”，负责量偏移、找跳板、把 EIP 送到 shellcode 起点；本 skill 是“弹头”，负责 shellcode 内部的形态选择、API 定位、编码与瘦身。
- 与 `windows-exploit-and-mitigation-bypass` 的区别：后者解决“DEP/ASLR/GS 挡住时怎么拿到执行权限”；本 skill 不提供信息泄露、ROP 或内存属性修改。栈不可执行时先走它。
- 与 `exploit-chain-construction` 的区别：那个 skill 关心整条链的缺环，shellcode 只是链尾的一个可选落点；本 skill 只解决“拿到执行权限后执行什么、怎么让它活下来”。
- 与 `metasploit-module-development` 的区别：本 skill 是**手写/改造** payload 的工程方法；只是要给模块选现成 payload、让框架自动编码导出，应走后者。两者可组合：先用本 skill 判断约束与可行性，再用框架生成基线。
- 与 `linux-x86-exploit-and-format-string` 的区别：后者提供栈控制与任意写原语；本 skill 从“已有注入点或执行流控制”开始，不再教漏洞定位。

## E — 可执行步骤 (Execution)

1. **确认授权与执行环境**
   - 明确目标架构（x86/x64/ARM）、OS 版本范围、注入路径、禁用字节、最大长度，并确认书面授权或隔离靶场。
   - 完成标准: 留下一张约束表：`badchars`、`Space` 上限、必须支持的 OS 版本、是否需要跨补丁。
   - 判停条件: 无法确认授权立即停止；目标非 x86 则停止本流程（PEB 偏移与指令集都不同）。

2. **判定是否需要交互式 shell**
   - 列出任务清单（加账号、写公钥、改配置、投放工具、持续操作）。
   - 完成标准: 能回答“需要持续交互，还是只需一条命令/一个文件”。
   - 判停条件: 只需单命令或文件传输 → 直接选最小形态，跳到步骤 5，不要默认 bind/reverse。

3. **核对网络方向三要素，选形态**
   - 分别给出“目标入站是否可达绑定端口”“目标出站是否可达攻击者”“攻击者能否控制并预知源端口”的明确结论。
   - 完成标准: 输出一行选型结论：形态（bind/reverse/findsock/单命令/文件传输/staged/系统调用代理）、端口或地址、理由。
   - 判停条件: 入站可达 → bind 分支；入站被阻断、出站可用 → reverse 分支；两者都受限 → findsock 或低痕迹分支。

4. **验证所选形态的附加前提**
   - bind：确认第二次连接可达、监听端口不显眼；reverse：确认无拦截式代理、NAT 已做端口转发、侦听端已就绪；findsock：确认源端口可控。
   - 完成标准: 三个前提逐条有结论，而不是“应该可以”。
   - 判停条件: 出站被代理阻断 → 放弃该路径，改评 findsock 或系统调用代理；NAT 改写源端口 → findsock 不可用。

5. **测量注入空间并决定是否 staged**
   - 得到从注入起点到被覆盖/截断边界的准确字节数，与候选载荷最终长度（含解码器）比较。
   - 完成标准: 有一份长度预算表，标明功能、解码器与余量各占多少。
   - 判停条件: 空间不足 → 改 staged 或多级接力，第一级只保留“读取后续字节 + 移交控制权”。

6. **确定坏字符集**
   - 通过逆向输入路径与调试观察，列出会被截断、转义或改变语义的字节（NUL、`\x0a`、`\x0d`、字母数字限制、Unicode 限制）。
   - 完成标准: 坏字符清单有实测依据，而不是照抄别人的 `-b` 参数。
   - 判停条件: 没有明确字符限制 → 跳过编码，避免无谓增大体积与失败点。

7. **建立可运行基线**
   - 优先复用成熟 payload；确需手写时，先写“能跑通”的调试版，在汇编首尾加 NOP 标记，并用装载器（`lea eax,shellcode; push eax; ret`）跑起来。
   - 完成标准: 调试器能稳定断在 shellcode 第一条指令，并单步走到目标 API 调用。
   - 判停条件: 基线在装载器里都跑不通 → 先查调用约定、栈平衡、数据是否被截断，不要进入编码阶段。

8. **建立 API 动态定位链**
   - `CLD` → `FS:[0x30]` → `[0x0C]` → `[0x1C]` → 第二个结点 kernel32 → `[0x3C]` → `[0x78]` → 按 `0x1C` RVA 表与 `0x20` 名称表遍历；对每个函数名算 hash 并与目标摘要比较；非默认加载的 DLL 用 `LoadLibraryA` 装载后再找。
   - 完成标准: 在至少两个不同 Windows 版本/补丁上正确解析目标 API 并成功调用。
   - 判停条件: 若模块链表顺序不符合“第二个是 kernel32”，改用 `LoadLibraryA` + `GetProcAddress` 或导入表兜底，不要假设顺序永远不变。

9. **做形式适配：编码 + 自解码头**
   - 先完成纯逻辑，再整体编码；异或 key 不与明文字节相同；原始 shellcode 末尾补 `0x90`；解码器满足同一套字符限制，并明确约定入口时哪个寄存器指向 payload 起始。
   - 完成标准: 编码结果不含任何 `badchars`；解码后逐字节比对与原始 payload 完全一致；在真实注入路径下能自动还原并执行。
   - 判停条件: 解码器自身无法在不含坏字符的前提下编写 → 该编码方案不可行，回到步骤 6 重评约束。

10. **按空间预算瘦身**
    - 优先短指令与复合指令；用 hash 压缩函数名；复用栈区做结构体/NULL 参数；用返回值做循环条件；满足约束时让准 NOP 数据与代码重叠。
    - 完成标准: 总长度落到 `Space` 以内并留出余量；功能回归全部通过，而不是“短了但偶尔崩”。
    - 判停条件: 仍超限 → 回到步骤 5 改 staged，不要靠删功能硬塞。

11. **整体字节检查与注入形态验证**
    - 对最终注入串（含 decoder）逐字节扫描坏字符与 `\x00`，核对总长度与长度字段一致；把操作码放入 char 数组以函数指针执行，或在与目标等价的漏洞环境触发。
    - 完成标准: 无截断、地址无关、解码器可自定位；不是只在独立程序中通过。
    - 判停条件: 独立程序通过而注入形态失败 → 视为未完成，回到步骤 9 检查空字节与解码器。

12. **跨环境回归并用失败现象回推**
    - 在目标 OS 矩阵与真实注入路径上测试；记录 hash 算法与摘要长度、编码 key、结束符、`badchars`、栈顶预留大小。
    - 完成标准: 至少两种环境通过；失败模式（哪个版本、哪类注入、什么现象）有记录。
    - 判停条件: 第二次连接超时 → bind 前提不成立；回连无流量 → reverse 的出站/代理/NAT 前提不成立；端口比对不命中 → findsock 源端口不可控；载荷自身崩溃 → 查自覆盖并调整 esp。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **只是要一个现成 payload 做验证**：框架已封装 payload 库、编码器与导出格式，从零手写是重复造轮子；走 `metasploit-module-development`。
- **注入点、偏移或执行时机尚未确定**：shellcode 写得再通用，不知道 EIP 能否到达也没有意义；先走 `crash-to-root-cause` / `win-stack-overflow-exploit`。
- **目标是 DEP + ASLR 且没有可执行落点**：本 skill 不提供信息泄露、ROP 或内存属性修改；先走 `windows-exploit-and-mitigation-bypass` / `exploit-chain-construction`。
- **非 x86 架构（x64/ARM/MIPS）**：TEB/PEB 偏移、段寄存器、调用约定与指令编码都不同，不能照搬 `FS:[0x30]` 与 `jmp esp`。
- **无需规避任何限制的本地实验**：没有字符过滤、空间约束与网络限制时，直接用最简单载荷即可，编码与 staged 只会增加失败点。
- **目标是内核/驱动漏洞**：内核载荷的稳定性、函数集与用户空间完全不同，应走 `kernel-exploitation`。

### 作者在书中警告的失败模式

- **在 shellcode 中写死 API 地址**：不同 OS 版本影响 DLL 加载基址，不同补丁改变导出偏移；本机调试通过、换机器即失效。
- **异或 key 与明文字节相同**：相同字节异或得 `0x00`，编码结果出现 NULL，被字符串函数截断。
- **编码前忘记给原始 shellcode 末尾补 `0x90`**：解码器以 `0x90` 判停，找不到就继续越界解码。
- **依赖 DF=0 却不显式 `CLD`**：经异常处理植入时标志位可能被改，`LODSD` 方向反转，堆溢出场景里“身经百战的 shellcode 突然出错”常是这个原因。
- **只编码主体而忽略解码器自身的坏字符**：最终注入串仍被截断。
- **入站被过滤时仍用 bind shell**：初始攻击成功，但第二次连接被拒绝。
- **认为 reverse 改走 80 端口就一定能出网**：忽略 HTTP 代理、NAT 转发与侦听端配置，书中明确该做法“仍可能失败”。
- **经 NAT 仍使用 findsock**：源端口被改写，端口比对始终不命中。
- **把 TIME_WAIT/FIN_WAIT 误判为 shellcode 逻辑错误**：反复改坏可用代码。
- **只在独立程序上验证**：跳过字符串注入测试，进入真实利用才暴露问题。

### 作者的盲点 / 时代局限

- **《0day安全》完全基于 32 位 x86 与 2011 年前的 Windows**：x64 用 `GS:[0x60]` 一类不同锚点，PEB 结构与偏移也不同；ARM 没有 `FS` 段，偏移表不能跨架构复用。
- **把“导出表 + 初始化链表顺序”当成稳定契约**：现代 Windows 有 ApiSet 重定向、OneCore 精简模块与不同进程类型的加载差异，“第二个结点必是 kernel32”不再可靠。
- **编码只针对静态字符限制与老式 IDS 特征**：面对内存扫描、API 调用序列监控、CFG/CIG，异或 + 自解码头不足以保证执行。
- **把“手写极致瘦身”当作默认追求**：现代利用更常见的是复用成熟 payload 并只做必要适配，为省几十字节投入大量人工在多数工程场景并不划算。
- **《灰帽黑客》以 32 位 Linux 为主**：以 `int 0x80`、`socketcall(102)`、32 位栈布局讲解，64 位的 `syscall`、寄存器约定与 socket 调用方式不同，操作码不可直接照搬。
- **工具已过时**：`msfpayload` 与 `msfencode` 已被 `msfvenom` 取代，书中管道命令只可作原理参考。
- **实验默认关闭或简化保护**：大量演示依赖可控端口、无代理、无出站审计的环境，结论外推到生产网络必须重新验证前提。

### 容易混淆的邻近方法论

- **把“编码”当成“加密/免杀”**：编码只改变字节形态以通过输入路径，不提供机密性，也不保证绕过检测。
- **把“能执行”当成“形态选对”**：本地弹出 shell 不代表在目标的网络方向、代理与 NAT 条件下可用。
- **把 shellcode 等同于“拿 shell”**：单命令执行、文件传输、staged、系统调用代理、进程注入都属于载荷形态。
- **把 exploitation 与 payload 混为一谈**：控制 EIP、绕过保护属于利用链；本 skill 只处理获得执行机会之后“投什么、怎么塞进去、怎么验证”。
- **`metasploit-module-development`**：它用框架“选弹头、自动编码、导出格式”，本 skill 是“自己造弹头、自己定编码约定”；前者重交付效率，后者重可控与可解释。
- **`win-stack-overflow-exploit`**：它负责运载与控流，本 skill 负责弹头内部实现；混为一谈会导致“偏移对了但 shellcode 一换机器就挂”。
