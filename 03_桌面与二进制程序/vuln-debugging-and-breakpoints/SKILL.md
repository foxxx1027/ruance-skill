# 漏洞调试与断点体系

## R — 原文 (Reading)

> “调试的原则在于确认，调试的目的在于定位。”
>
> “而漏洞调试，因为被调试的程序对于我们来说可能是一个黑盒，可疑代码的位置难以确定，所以下断点就显得比较为难，需要一定的技巧。如果说漏洞调试是一门艺术，那么下断点就是这门艺术的精髓，需要深入的研究和实践。”
>
> — 王清 等，《0day安全：软件漏洞分析技术（第二版）》第 25 章 25.2

---

## I — 方法论骨架 (Interpretation)

1. 漏洞调试不是“跑一遍看结果”，而是用断点把执行切成可确认的片段；确认靠寄存器/内存证据，定位要落到具体函数与指令。
2. 先明确“我要观察什么”：某条指令是否执行、某块数据被谁读写、某次调用是否发生、窗口消息走到哪个过程、还是整条调用链如何形成。
3. 按观察对象选断点：执行用普通/硬件执行断点，数据用内存访问/写入断点，首次触碰用段级一次性断点；硬件断点只有 DR0–DR3 四个，要省着用。
4. 高频 API 不能裸下断，也不能不下：把“我要找的那一次调用”翻译成条件表达式，条件写不出来通常说明目标还没想清楚。
5. 只关心轨迹而不需要暂停时，用条件记录断点：Pause 设为 Never，按 Condition/Expression 记录每次命中，事后回放调用序列与参数分布。
6. UI 程序不要依赖断点向导：在必经的消息循环函数 TranslateMessage 上用 MSG 条件拦截目标消息，再回到主模块，于 DispatchMessage 处跟入，对主模块 .text 下一次性的内存访问断点，让程序自己走回窗口过程。
7. 不知道漏洞函数、常规断点无从下手时，用畸形 RetAddr 断点：把覆盖的返回地址改成非法值，让溢出后必然触发访问异常；这个“人为崩溃”就是断点，停下后读栈找前一次调用。
8. 断点负责定格，回溯负责解释。用栈帧重建调用链，观察每一层的参数；OllyDbg 在无标准栈框架时会退化到 ESP 推算与启发式搜索，栈被破坏时结果必须校验。
9. 需要知道“这次攻击额外执行了哪些代码”时，用指令追踪：静态切指令块、动态标注命中，再把正常流程的追踪设为 filter，只显示漏洞触发时新增的块。
10. 方法选型看当前缺什么：缺现场用动态调试，缺全貌用静态分析，缺差集用指令追踪；单步本身不是目的，“这一步确认了什么”才是。

## A1 — 书中的应用 (Past Application)

### 案例 1: MS06-055——先加载 vgx.dll，再在函数入口下断

- **问题**: IE 解析 VML 时崩溃，怀疑在 `vgx.dll`，但直接启动 IE 时该 DLL 尚未加载，按 IDA 地址下断会落在未映射页。
- **方法论的使用**: 先用合法 VML 页面让 IE 自动加载 `vgx.dll`，再 attach 到 IE 进程；用 IDA 找到 `_IE5_SHADETYPE_TEXT::Text` 的入口（Win2000 为 `0x659D7B46`），在入口下断后刷新页面。
- **结论**: 断点命中后单步，看到页面里的 4 个 “Q” 以 Unicode 形式 `0x0051` 进入栈区，形成“这次调用导致复制”的假设。
- **结果**: 只放大 “Q” 的数量，观察到大量 `0x0051` 冲垮返回地址；再回 IDA 确认真正产生溢出的是 `Ptok`。这说明“模块已加载 + 断在破坏前 + 单变量放大”缺一不可。

### 案例 2: MS09-032——递归中的断点收敛与 SEH 状态观察

- **问题**: POC 通过覆盖 SEH 劫持流程，但不知道具体是哪个函数、哪次调用写坏了 SEH。
- **方法论的使用**: 先在疑似函数入口 `0x59F0D3BA` 下硬件执行断点，入口处 SEH 正常；单步发现 `0x59F0D469` 是函数自调用（递归）。把断点移到该调用点，按两次 F9 才出现异常，说明问题在递归第二轮；再 F7 跟入，在每个候选 CALL 前后观察 SEH 链。
- **结论**: `0x59F0D4D4` 的 CALL 执行后 SEH 被改写，继续收敛到 `0x59F0D74D` 的 `mshtml.Read` 调用；函数本身没问题，是调用参数把 `buff` 传成了 `&buff`。
- **结果**: 定位到 `LEA ECX,[EBP+8]` 这一处参数语义错误，并据此构造畸形 MPEG-2 文件覆盖 SEH。递归导致断点重复命中，在这里是结构证据，不是断点失效。

### 案例 3: Yahoo! Messenger——用畸形 RetAddr 把“无法下断”变成“必然停下”

- **问题**: 只知道超长 `Server` 属性后调用 `Send()` 能触发溢出，不知道 `ywcupl.dll` 内部哪一处溢出；直接用 OllyDbg 跟，网页木马成功弹出计算器，调试器却什么也没看到。
- **方法论的使用**: 把 POC 中填充的 `0x0a0a0a0a` 改成 `0xffffffff`，让溢出后的控制流访问非法地址，制造一次必然发生的内存访问异常；停下后读溢出后的栈，找离溢出点最近的返回地址，其指向指令的前一条通常是 CALL，由此反推所在函数。
- **结论**: 该返回地址落在 `ywcupl.dll` 的一个函数内，记为基址 + 固定偏移；用 IDA 静态分析该函数，确认 `Send()` 内部未校验 `Server` 字符串长度。
- **结果**: 把填充改回 `0x0a`，重新用 OllyDbg 跟踪栈变化验证结论。人为崩溃起到了精确断点的作用，解决了“不知道函数就没法下断”的死循环。

### 案例 4: LNK 漏洞——从结果 API 下断，再用 Call Stack 补回缺失符号

- **问题**: 已知 POC 的最终效果是让 explorer 加载 `C:\DLL.DLL`，但不知道是哪条图标加载路径把它送进 `LoadLibraryW`；OllyDbg 的调用栈还有三层显示不出函数名。
- **方法论的使用**: 直接在 `LoadLibraryW` 下断，浏览 POC 所在目录触发图标加载；断下后从栈窗口确认 `FileName` 为 `C:\DLL.DLL`，再用 Call Stack 回溯，按调用顺序、模块归属与命名规律补出 `GetIconLocationW`、`CExtractIconBase::GetIconLocation`、`CShellLink::GetIconLocation` 三层。
- **结论**: 选择语义最匹配的 `GetIconLocationW` 继续下断，单步到 `PUSH EBX` 时看到 `C:\DLL.DLL,0,`；逗号间值为 0 才进入 `CPL_FindCPLInfo`，最终到 `LoadLibraryW`。
- **结果**: 打通完整调用链，并解释了 LNK 中 `0x9CFFFFFF` 必须改成 0 的原因。若断点不命中，多半是图标缓存，重命名 POC 即可绕过。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 目标是无源码二进制，知道“输入能让它崩”，但不知道该在哪个函数、哪条指令下断，或者断点总是断不住。
2. 高频 API（`CreateFileW`、`recv`、窗口过程）调用太多，只关心“打开某个文件/收到某个包/点击某个按钮”的那一次，需要条件断点或记录断点。
3. UI 程序的按钮响应找不到，OllyDbg 窗口列表里的 WinProc 为空、ClsProc 是 `0xFFFFxxxx`，用向导下消息断点完全无效。
4. 断点停下后需要解释“我是怎么走到这里的”，要读调用栈、每层参数和栈帧，判断栈是否已经被破坏。
5. 想知道攻击输入比正常输入多执行了哪些代码，准备用指令追踪/差集缩小范围。

### 语言信号 (用户的话里出现这些就应激活)

- “断点下在哪儿 / 断不住 / 一断就断在无关调用上”
- “条件断点表达式怎么写 / 怎么只拦这一次调用”
- “按 F9 几百次太累 / 想记录每次调用的参数”
- “消息断点 / WinProc 为空 / 按钮点击的窗口过程在哪”
- “栈被破坏了还能回溯吗 / Call Stack 全是垃圾”
- “指令追踪 / 正常流程和异常流程的差集 / Paimei / breakpoint / conditional breakpoint / message breakpoint”

### 与相邻 skill 的区分

- 与 `crash-to-root-cause` 的区别: 那个 skill 是“从崩溃走到根因”的完整诊断流程，负责判断漏洞类型、根因与可利用性；本 skill 只讲“断点这一工具的方法论体系”，回答“在哪里停、用什么断点、停住后看什么、如何回溯/追踪”。若问题还是“这个崩溃到底是谁造成的、是什么类型”，应先走 `crash-to-root-cause`；若根因方向已明确、卡在“下不住断点/看不清现场”，用本 skill。
- 与 `locate-by-known-anchor` 的区别: 那个 skill 利用字符串、导出表、符号、错误文本等已知锚点直接落到目标函数；本 skill 处理“没有可用锚点，或需要在已知函数内部继续观察”的情况。已有明确锚点时先用 `locate-by-known-anchor` 到达入口，再用本 skill 设计断点、回溯与验证，二者是接力关系。
- 与 `overflow-localization` 的区别: 本 skill 是调试工具层，讲断点类型、条件/记录、消息断点、栈回溯与指令追踪；`overflow-localization` 是面向缓冲区溢出的定位流程，讲受控崩溃、跟 CALL、硬件写断点、偏移实测与溢出条件。前者回答“怎么停、怎么看”，后者回答“漏洞函数、写指令、覆盖长度与触发条件是什么”。

## E — 可执行步骤 (Execution)

1. **先写清本轮要确认的命题**
   - 把问题写成一句话，例如“确认是哪个 CALL 把返回地址改成 `0x41414141`”或“确认按钮消息进入哪个窗口过程”；同时标记观察对象是执行流、数据、消息还是调用链。
   - 完成标准: 能说出“停在哪里、停下来看哪个寄存器/内存、看到什么算证实”。
   - 判停条件: 若命题只是“看看程序怎么跑”，先回到上一步把目标具体化，不要盲目单步。

2. **校准环境与地址，保证断点可命中**
   - 确认目标文件大小/版本/补丁级别；由文档按需加载的 DLL 先用合法输入触发加载，再 attach；所有静态地址换算成“模块基址 + 偏移”，不要照抄书上的绝对地址。
   - 完成标准: 模块列表中存在目标模块，`Ctrl+G` 跳转后的地址落在预期代码/数据上。
   - 判停条件: 若目标模块未加载或断点地址显示无效，停止下断，先修正加载顺序或重新计算基址。

3. **按观察对象选择断点类型**
   - 指令是否执行 → 普通 `INT3` 或硬件执行断点；数据被谁读写 → 内存访问/写入断点；某段首次被触碰 → 段级一次性断点；窗口消息 → `TranslateMessage` 条件断点；不知道漏洞函数 → 畸形 RetAddr 断点。
   - 完成标准: 能用一句话解释“为什么是这种断点”，并预估命中次数与命中位置。
   - 判停条件: 若常规断点无法在破坏前停下，改用畸形 RetAddr 或硬件写断点，不要反复在崩溃点重下断。

4. **用条件/记录断点把噪声收敛到目标调用**
   - 把“哪一次调用”写成表达式：参数等于某路径、消息等于 `WM_LBUTTONUP`、缓冲区指针落在某范围；注意 OllyDbg 裸整数默认十六进制，字符串要加 `UNICODE`/`STRING`，`MSG` 中 `hwnd=NULL` 是线程消息。若只需要轨迹，用 Shift+F4 记录断点，Pause 设为 Never，填写 Explanation/Expression 与解码方式。
   - 完成标准: 条件断点只在目标调用命中，或日志中能读出完整调用序列与参数。
   - 判停条件: 若条件表达式写不出来，说明“要找的东西长什么样”尚未定义；回到步骤 1，不要用频繁断点硬试。

5. **停住后先定格现场，再重建调用链**
   - 记录 EIP、ESP、EBP、关键寄存器、栈顶与参数；打开 Call Stack（Alt+K）逐帧核对返回地址是否落在合法代码段，结合符号确认函数名。若栈已破坏，不要相信自动回溯，改用“最近的返回地址”或畸形 RetAddr 现场。
   - 完成标准: 得到一条每帧都有地址、模块归属和参数证据的调用链，能解释“从入口到当前指令”的路径。
   - 判停条件: 若调用栈出现非法地址、明显不合理跳转或一单步就跑飞，判定栈已破坏，转步骤 3 的受控停下方案。

6. **UI 程序用“必经函数 + 两段式”定位窗口过程**
   - 在 `TranslateMessage` 入口下 `MSG==目标消息` 条件断点；命中后 Alt+F9 回到主模块，F8 到 `DispatchMessage` 调用处，F7 跟入；再对主模块 `.text` 段下一次性的内存访问断点，F9 让程序自己走回窗口过程。
   - 完成标准: 停在主模块中处理该消息的窗口过程入口，且能用 IDA 对应到消息分支。
   - 判停条件: 若向导给出的 WinProc 为空或 `0xFFFFxxxx`，不要使用向导，直接走本步骤的条件断点路径。

7. **需要差集时，用指令追踪而不是继续盲跟**
   - 先用 IDA 反汇编并切分指令块，动态记录正常流程命中块；把这次追踪设为 filter，再记录漏洞触发流程，只保留新增块；对新增块逐块下断验证。
   - 完成标准: 得到“该输入特有”的指令块清单，并至少用一次断点确认其中一块确实执行。
   - 判停条件: 若目标加壳/混淆导致 IDA 静态图不可信，先脱壳或修复，不要直接相信 Paimei 结果。

8. **把断点结论写成可复核的证据链**
   - 记录“断点地址/类型/条件 → 命中时的寄存器与内存 → 对应函数与偏移 → 结论”；换一次运行或换一台同版本环境复跑，确认不是偶然命中。
   - 完成标准: 另一位分析者按记录能复现同一断点、同一现场、同一结论。
   - 判停条件: 若只有“程序跑完了/弹窗了”而没有断点现场，视为没有完成调试，不要输出定位结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **漏洞根因尚未定位、需要完整诊断**: 只知道程序崩了，不知道是栈、堆、SEH、格式化串还是逻辑漏洞；先走 `crash-to-root-cause`，本 skill 只提供调试工具层，不能替代根因分类。
- **已有强锚点，只差到达入口**: 字符串、导出函数、符号、错误文本已经能直接定位目标函数时，先用 `locate-by-known-anchor`；再在本 skill 里设计“到达之后怎么观察”，不要为了用断点而绕远路。
- **内核态调试**: 需要 WinDbg 双机/管道、驱动断点、蓝屏分析时，本 skill 的 OllyDbg 用户态断点与 DR 寄存器模型不适用，应走内核调试/驱动分析 skill。
- **生产环境或高风险远程服务**: 下断会改代码字节、暂停进程、改变时序，可能触发超时、看门狗或二次崩溃；优先用转储、日志、ETW/采样式追踪，除非有快照与回滚。
- **强反调试、加壳、EDR 监控的目标**: `INT3` 与调试寄存器容易被检测，静态指令图也可能被壳破坏；未脱壳/未处理反调试前，断点结论不可信。
- **x64/ARM64 或跨架构目标**: 调用约定、返回地址保存方式、影子空间与异常展开都不同，不能照搬 32 位 x86 的栈帧与断点习惯。

### 作者在书中警告的失败模式

- **在漏洞函数入口直接 step over**: F8 会一次性执行完整个函数，包括溢出写；控制权回来时栈已毁，只能得到“这个函数有问题”，看不到内部过程。应在入口 F7 跟入。
- **用向导设置消息断点**: OllyDbg 枚举到的 WinProc 可能为空、ClsProc 可能是非法的 `0xFFFFxxxx`，断点根本不会命中；应改用 `TranslateMessage` 条件断点 + 主模块 `.text` 一次性内存访问断点。
- **在未加载的模块上下断**: 由文档按需加载的 DLL 尚未映射时，IDA 算出的 VA 是无效页；必须先触发加载再 attach，否则会误以为地址算错。
- **把表达式里的十进制当十六进制**: OllyDbg 裸整数默认按十六进制解释，`10` 是 `0x10` 不是十；写错会让断点永不命中。十进制要写成 `10.`。
- **只在函数入口看一次状态就排除该函数**: 入口处 SEH 正常只能证明“还没发生”，不能证明“不会发生”；必须单步到各候选 CALL 之后再看状态。
- **把递归造成的重复命中当成断点失效**: 同一地址连续中断可能正是函数自调用；要记录命中次数，判断异常发生在第几轮，再决定在哪一层跟入。
- **断点下得太多、太频繁**: 高频 API 上的裸断点会淹没分析，硬件断点又只有四个；应先用条件/记录断点收敛，再保留少量关键断点。
- **只关心“程序是否跑完”而不设停点**: 漏洞利用成功时程序可能不崩溃，调试器一路运行到结束，什么现场也没留下；这类调试等于没做。

### 作者的盲点 / 时代局限

- **工具与平台停留在 2011 年前的 32 位 Windows**: 主要是 Windows 2000/XP/2003、OllyDbg 1.1 与 WinDbg 6.x；符号要手工拷贝 `dbghelp/symsrv` 并用 StrongOD 配置，没有现代符号服务器/自动下载，书中地址都是特定版本实测值。
- **没有 ETW/eBPF/perf/TTD 一类低开销全系统追踪**: 指令追踪依赖 Paimei + IDA + MySQL + Python 2.4，部署脆弱，遇到多线程、异步、JIT、加壳样本容易失真；现代可用的硬件追踪、时间旅行调试、快照回放都不在讨论范围。
- **默认目标可 attach、可暂停、单进程、交互式**: 未系统讨论反调试、EDR、受保护进程、沙箱、子进程、竞争条件与远程不可暂停服务；这些场景下“先 attach 再下断”往往根本不成立。
- **只覆盖 x86 32 位用户态**: x64 的寄存器传参/影子空间、ARM 的 LR、CFG/CET 等现代控制流保护都没有进入断点与回溯模型；跨架构必须重新建模。
- **断点实现语义偏旧**: `INT3` 会改写代码字节，硬件断点依赖 DR0–DR3 且可被检测；现代虚拟化/EPT、hypervisor 断点与内核调试的语义不同，不能直接套用。

### 容易混淆的邻近方法论

- **`crash-to-root-cause`（从崩溃到根因）**: 它产出“漏洞类型、根因与可利用性”；本 skill 产出“断点设计与现场证据”。前者是诊断，后者是调试工具方法。
- **`locate-by-known-anchor`（按已知锚点定位）**: 它用字符串/符号/导出表直接到达函数；本 skill 在“没有锚点”或“到达后还要观察”时发挥作用。
- **`overflow-localization`（溢出定位）**: 它面向缓冲区溢出，给出从崩溃到漏洞函数、写指令和覆盖长度的流程；本 skill 的断点/回溯/追踪是它的底层工具，但不负责溢出条件的完整推导。
- **`patch-diff-and-source-analysis`（补丁/源码差异）**: 它从两个版本或源码差异中找候选漏洞点；本 skill 不比较文件，只解决“已知候选后如何在运行时停下来确认”。
