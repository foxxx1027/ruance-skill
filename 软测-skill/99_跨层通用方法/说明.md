# 99 跨层通用方法

这一层不针对某个具体被测对象，放的是两类东西：一是「动手前先决定怎么打」的漏洞分析与工程方法（选型、模糊测试、符号执行、样本分析、授权与流程），二是全部思维与组织方法。典型场景是「手上只有一个崩溃样本 / 一堆扫描结果 / 一份材料 / 一个争论，还不知道该走哪条路」。在这里选定路线后，再回到 01–13 对应的执行类 skill。

## 这一层最常见的四类问题

- 目标是什么类型、在哪一层都没判，就打开 IDA 或扫描器开始动。
- 扫描报告几万条，没人能说清哪条真能利用、哪条是误报，也没人分诊。
- 该 fuzz 还是该静态审计没想清楚，预算全压在错的一条路上。
- 事情一堆、意见一堆、对手一堆，先动哪个、怎么说服人、要不要 all-in 没想明白。

## 这一层的 skill

### 方法选型与分析

| skill | 作用 | 什么时候会用到 |
| --- | --- | --- |
| fuzzing-strategy | 在 Fuzz 与静态审计之间选路线，并决定复杂文件/协议走 Blind 还是 Smart Fuzz。 | 「该 fuzz 还是先静态审」 |
| coverage-guided-fuzzing | 用覆盖率引导模糊测试挖内存破坏，诊断覆盖率停滞、种子质量与崩溃去重。 | 「覆盖率一直不涨怎么办」 |
| fuzzing-engineering-peach | 选目标与输入入口、压缩种子集、编写调试 Peach Pit 并做崩溃 triage。 | 「Peach Pit 怎么写、种子怎么最小化」 |
| directed-memory-kernel-fuzzing | 通用 fuzz 失效时改走定向/内存/内核 fuzz，或先处理反 Fuzz。 | 「没有文件输入、只有函数地址，怎么 fuzz」 |
| kernel-driver-fuzzing | 做驱动 IOCTL Fuzz，设计设备名、控制码与按 Method 位裁剪的参数面。 | 「只有 .sys，不知道设备名」 |
| symbolic-execution | 用路径条件与约束求解生成能到达危险分支的输入，并处理路径爆炸与求解失败。 | 「怎么才能走到那个 if 里面」 |
| vuln-analysis-strategy | 面对陌生崩溃/公告/补丁先判类型与所在层，再选分析方法与工具，并给止损纪律。 | 「这个漏洞该从哪下手」 |
| vuln-essence-classification | 用二元框架判定算不算漏洞、是代码缺陷还是策略缺陷，决定定级与处置路径。 | 「这到底算不算漏洞」 |
| vulnerability-mechanism-identification | 把栈溢出/格式化串/整型溢出/提权/UAF/竞态归到正确机理并写成因链。 | 「这到底是 UAF 还是双重释放」 |
| logic-and-isolation-bugs | 用 Check/Use 时间窗、类型混淆布局错配与沙盒逃逸攻击面模型分析非内存破坏缺陷。 | 「竞态窗口太窄，怎么提高成功率」 |
| appsec-tooling-and-threat-modeling | 做资产与信任边界建模、排 SAST/DAST/IAST 组合，并把扫描结果去重分诊。 | 「扫描报告几万条没人处理」 |
| devsecops-and-vuln-management | 搭 SDL 与 CI 门禁，建漏洞生命周期、SLA、应急监控与合规映射。 | 「上线要不要阻断、漏洞谁来跟」 |
| pentest-engagement-and-disclosure | 确认授权边界与 scope，起草 SOW、交战规则，决定漏洞如何披露。 | 「这次测试的授权到哪为止」 |
| file-format-vulnerability-reversing | 从畸形文件反推格式解析入口、构造最小 POC，为 Smart Fuzz 建格式模型。 | 「一打开这个文档就崩」 |
| malware-sample-analysis | 提取样本、复现第一现场、观察载荷行为并解码 C&C 配置。 | 「样本一跑就结束，来不及断点」 |
| ransomware-safe-dynamic-analysis | 规划隔离环境与防逃逸，用 Procmon/Autoruns 取证、内存解码并提炼 IOC。 | 「勒索样本怎么安全地跑」 |

### 思维与组织方法

| skill | 作用 | 什么时候会用到 |
| --- | --- | --- |
| mass-line | 从一线取意见、加工成方案再回到一线检验，避免闭门造车。 | 「方案怎么听一线的声音」 |
| principal-contradiction | 多任务资源不够时找主要矛盾，决定先集中打哪一个。 | 「事情太多，先干哪个」 |
| two-points-one-focus | 对有功有过的人或有利有弊的事做一分为二评价，再抓主要方面。 | 「该全面肯定还是全盘否定」 |
| investigation-method | 情况不明时先做调查再下结论，判断该不该先花时间摸实情。 | 「要不要先调研再定」 |
| material-refinement | 把访谈、反馈、观察等原始材料按去粗取精、去伪存真、由表及里加工成洞察。 | 「一堆反馈怎么变成结论」 |
| typical-survey-verification | 用解剖一两个典型样本代表整体，并对调查本身做二次检验。 | 「抽几个看看够不够」 |
| quantitative-grasp | 给判断设可核查的数字与上限，避免用「大概」「差不多」拍板。 | 「到底有多少、上限怎么定」 |
| practice-cognition-loop | 复盘行动成败、把经验提炼成规律，判断该继续试还是换做法。 | 「失败是不是说明方向错了」 |
| worst-case-preparation | 为不确定决策做最坏打算与预案，判断现在出手还是再等等。 | 「要不要留后手」 |
| self-reliance | 关键能力依赖单一外部方时，判断要不要自研与被卡脖子时的底线。 | 「关键技术要不要自己做」 |
| unity-through-struggle | 长期合作中被不断越界时，用有理有利有节的方式守住边界又不撕破脸。 | 「一直让步反而被得寸进尺」 |
| united-front-three-tier | 立场分裂时争取多数、对待摇摆者，把可团结的面尽量放大。 | 「怎么争取中间的大多数」 |
| narrow-target | 一次性处置一批问题时收窄打击面，区别对待首恶与可教育者。 | 「要不要全部处理」 |
| committee-work-methods | 主持团队/委员会会议：议程前置、问题摆桌面、兼顾多摊事并抓紧。 | 「会议议而不决怎么办」 |
| lean-organization | 判断组织规模是否与任务匹配，按精简、统一、效能、节约、反官僚验收。 | 「机构是不是太臃肿」 |
| persuasion-technique | 写文章/方案/汇报时先看受众再定内容，删尽可有可无的字句。 | 「方案怎么讲才让人听得进」 |
| strategic-contempt-tactical-seriousness | 面对强敌既要在战略上敢入局，又要在战术上不轻视。 | 「对手太强还要不要上」 |
| favorable-decisive-battle | 判断该不该下重注决战，排除赌上生存的不可逆对撞。 | 「要不要一次定输赢」 |
| layer-switching | 整体弱势时把战略层与战役层分开，局部争取速决与主动。 | 「整体打不过怎么保持主动」 |
| exploit-contradictions | 对手抱团时用正当利益沟通分化，争取多数、孤立少数。 | 「所有人都反对我怎么办」 |
| equivalent-exchange-margin | 设计合作分配与指标时按等价交换，防止白占便宜与层层加码。 | 「指标定多少才不被虚报」 |
| cure-illness-save-patient | 处理内部错误与追责时对事不对人，既分清是非又不一棍子打死。 | 「同事犯错要不要批评」 |
| general-call-individual-guidance | 推新做法时先号召、再选两三个单位突破、最后波浪式推广。 | 「全国推广要不要一刀切」 |
| annihilation-over-attrition | 在铺开占规模与集中打透一点之间取舍，界定「怎么才算赢」。 | 「多做几个功能还是打透一个」 |

## 跨层可复用

- crash-to-root-cause（03_桌面与二进制程序）— 路线选完之后，从崩溃现场回到根因的执行流程。
- heap-exploitation（03_桌面与二进制程序）— 机理判定为堆之后，占坑与控流的具体打法。
- vuln-debugging-and-breakpoints（03_桌面与二进制程序）— 选完方法要真正让程序停下来时用。
- dataflow-analysis-and-code-modeling（04_源码与代码实现）— 静态分析在技术层面的执行细节。
- client-side-and-frontend-security（01_前端与浏览器端）— 判定问题在浏览器侧之后的执行清单。
- middleware-fingerprint-and-triage（08_中间件与Web容器）— 「对象到底是什么」本身就是一个前置判断。
- pentest-engagement-and-disclosure 之外的流程落地见 supply-chain-and-release-hardening（12_构建产物与依赖）。

## 和相邻层的分界

- 与 01–13：99 只回答「用哪种方法、先做哪一步、要不要继续」，具体下断点、布堆、改配置、看日志都回到对应层。
- 判定标准：产出是「路线、判断、组织动作」就放 99；产出是「针对某个具体对象的动作与结论」就放 01–13。
- 与 03：03 里的 `vuln-analysis-strategy` 不在这里，因为它虽然也叫策略，但落点仍是二进制漏洞分析；反过来，`fuzzing-strategy` 不绑定对象，所以留在 99。
