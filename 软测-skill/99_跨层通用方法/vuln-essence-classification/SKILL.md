# 漏洞本质的二元分类

## R — 原文 (Reading)

> "程序世界：由于程序（Web、二进制等）存在安全缺陷，导致攻击者恶意构造的数据进入程序相关处理代码时，会改变程序原定的执行流程，从而实现破坏或获取超出原有权限的能力。"
>
> "安全策略：由于系统（网站、软件、操作系统等）安全策略设置得不够严谨或者未做设置，导致攻击者能够在未经授权的情况下，获得对目标系统原本不应拥有的访问或控制权限。"
>
> — 林桠泉，《漏洞战争：软件漏洞分析精要》第 1 章 1.1.1

---

## I — 方法论骨架 (Interpretation)

行业里"漏洞"这个词被用得太随便，导致处置动作常年错配：把配置缺失当成代码 bug 去等补丁，或把代码缺陷当成"配置问题"去改权限。作者把它拆成两个**并列的**成因面：

- **程序世界（代码面）**：程序存在安全缺陷 → 攻击者恶意构造的数据进入处理代码 → 改变原定执行流程 → 破坏或获取超权限。这一面必须靠代码定位（反汇编 / 源码 / 补丁比较）来修。
- **安全策略（配置面）**：系统/网站的安全策略设置不严谨或未设置 → 攻击者获得本不应拥有的访问或控制权限。典型如"重要管理系统不设密码且暴露外网"。这一面靠配置与权限模型审计来修，**改再多代码也没用**。

关键推论有三条：

1. **两者是并列关系，不是主次关系。** 常识把漏洞等同于"代码 bug"，会整类漏掉策略型漏洞。
2. **分析路径由成因面决定。** 判定属于哪一面，直接决定后续该走"代码定位"还是"配置审计"。
3. **定性的目的是定责与定处置。** 同一现象落在不同面，责任方（开发 / 运维）与处置方式（发补丁 / 改策略）完全不同。

作者在第 12 章把同一思路外推：云平台被攻击的最终目的大多是拿到底层数据，因此"云安全的本质其实是数据安全"——仍是先判断风险落在哪一面再决定投入方向。

## A1 — 书中的应用 (Past Application)

### 案例 1: 重要管理系统不设密码并暴露外网
- **问题**: 系统没有明显代码错误，但可被任意访问并操控。
- **方法论的使用**: 套二元分类——不存在"恶意数据改变执行流程"，风险来自"策略未设置"。
- **结论**: 属于安全策略缺陷，不是程序缺陷。
- **结果**: 作者把它作为策略面的标准实例，与全书大量二进制案例并列，用以说明"策略型漏洞不必有 bug"。

### 案例 2: 第 12 章云平台风险分层
- **问题**: 云平台攻击面分散在 SaaS / PaaS / IaaS 三层，从何下手防护？
- **方法论的使用**: 先定性"最终目标是底层存储数据" → 风险本质落在"数据安全"这一面。
- **结论**: 防护投入应集中到数据加密与数据访问控制，而非平均分配到三层。
- **结果**: 作者据此提出"数据加密往往是最后一道防线"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 判断某个现象"算不算漏洞"，或在漏洞评级/定责时争论不休。
2. 讨论"该修代码还是改配置"，或应急响应中要决定处置动作由开发还是运维承接。
3. SRC / 漏洞报告撰写时，需要给出成因而非只给复现步骤。
4. 面对一个"没有 bug 但就是能被访问"的系统，判断按哪条流程备案。

### 语言信号 (用户的话里出现这些就应激活)

- "这算漏洞吗 / 算不算安全问题"
- "是代码问题还是配置问题"
- "该改代码还是改策略权限"
- "这个漏洞该谁修"
- "is this a vulnerability / is it a code flaw or a misconfiguration"

### 与相邻 skill 的区分

- 与 `vuln-analysis-strategy` 的区别: 本 skill 回答"漏洞是什么、属于哪一面"；策略选择回答"用什么手段分析"。先定性再选手段。
- 与 `locate-by-known-anchor` / `crash-to-root-cause` 等执行型 skill 的区别: 那些服务于"程序世界"这一面；若定性为"安全策略"面，本 skill 会明确把任务**导向配置审计**，不进入二进制流程。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **描述现象，剥离解释**
   - 完成标准: 用一句"未授权者能做什么"描述现象（如"任意人可读写后台配置"），不含成因猜测。

2. **判定是否存在"恶意数据改变执行流程"**
   - 方法: 问"是否需要构造特定输入才能触发"——需要 → 程序世界面；不需要、只要访问就能生效 → 策略面。
   - 完成标准: 得到二选一的初步归属。

3. **双向复核（防止误归）**
   - 程序面复核: 是否存在对应的**缺失的校验/长度检查/类型检查**？能指出具体代码位置吗？
   - 策略面复核: 是否存在**缺失的鉴权/权限配置**？该配置本应存在吗？
   - 完成标准: 至少能指出一个"本该有但没有"的具体东西（一段检查 或 一条策略）。

4. **输出成因面 + 处置路径 + 责任方**
   - 完成标准: 明确写出「成因面 / 处置动作（发补丁·改代码 或 改策略·加鉴权）/ 承接方（开发 或 运维）」。

5. **策略面收尾时给出防线排序**
   - 完成标准: 若定性为策略面且涉及数据暴露，补充"最后一道防线"（如加密、不可逆脱敏）建议，而非只提"加登录"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **已有明确 CVE / 厂商定级** → 不必重新定性，直接用厂商结论。
- **需要技术定位细节**（具体哪一行代码出错）→ 走 `crash-to-root-cause` 等执行型 skill。
- **合规与法律条款判定** → 本框架是技术成因分类，不解决合规归类。

### 作者在书中警告的失败模式

- 把"数组越界"与"溢出"混为一谈（g05-ce01）——同类现象误归，会导致后续方法选错；本 skill 正是要求先分清面再谈细节。
- 厂商为炒作把低危漏洞渲染成严重漏洞（g05-ce04）——定性失真会污染整个处置链。

### 作者的盲点 / 时代局限

- **作者的"策略面"讨论极薄**：全书重心在程序世界（二进制），策略面只有零星举例，缺少体系化的配置审计方法（如 IAM 模型、最小权限、云配置基线）。本 skill 的"策略面"部分因此偏粗，实际使用需补现代配置审计知识。
- **以"单个分析者手工逆向"为中心**：定性结论偏技术视角，未纳入"是否可利用、影响面多大"这类风险量化维度。
- **时代锚定 2016 年**：云/移动/IoT 的策略缺陷形态与今天差异巨大（如容器逃逸配置、CI/CD 凭据泄露），需自行外推。

### 容易混淆的邻近方法论

- "漏洞=缺陷"这类笼统定义；本框架的价值恰恰在于**拒绝**笼统，把两类成因并列并强制二选一。
