# 定向 / 内存 / 内核模糊测试与反 Fuzz

## R — 原文 (Reading)

> 除了上述所说的覆盖率引导的模糊测试，现在模糊测试的发展方向更加多向化，出现了许多其他效果较好的模糊测试，包括定向模糊测试，以及针对特定目标的模糊测试，如内存模糊测试和内核模糊测试，另外，近些年来也出现了一些针对模糊测试的程序保护技术反模糊测试技术。
>
> — 魏强、武泽慧，第7章 7.5（7.5.1–7.5.4 总述）

## I — 方法论骨架 (Interpretation)

这不是又一套 fuzz 算法，而是当“种子 → 变异 → 执行 → 覆盖反馈”的通用闭环不成立时，换输入通道或换导向信号的四条替代路线。

先诊断闭环断在哪：有可达文件/协议输入且覆盖反馈正常，就留在覆盖率引导；没有可达输入，改内存或内核通道；有输入但不知道往哪走，改定向；执行变慢、覆盖率失真或崩溃被吞，先处理反 Fuzz。

定向 fuzz 的前提是把“想去哪里”写成可判定对象——补丁点、敏感函数、深层路径或校验点，再用 CFG/调用图距离把种子和能量向目标倾斜；目标写不清，定向就退化成普通 fuzz。

内存 fuzz 面向闭源、无文件输入、或解析前无关代码开销过大的目标：逆向定位解析例程起止，用变异循环插入或快照恢复，在参数被内部函数使用之前改内存，绕过协议与格式外壳。

内核 fuzz 的输入是系统调用/驱动接口序列，不是文件。知识型路线用 API 模板、参数类型、调用顺序与值依赖保证输入合法（Trinity、IMF）；覆盖率型路线用插桩、虚拟化或硬件跟踪引导探索（syzkaller、TriforceAFL、kAFL）。

反 Fuzz 不修漏洞，而是阻断 fuzz 的三个运行前提：执行足够快、覆盖率可被准确统计并反馈、异常可被捕获且现场可保留。遇到它先判断哪条前提被破坏，再换观测通道或工具，而不是直接放弃。

四条路线共用同一工程纪律：输入通道可验证、导向信号可观测、异常可判定。哪一条缺失，就先补哪一条，而不是先加大变异量。

核心判据：通用覆盖率引导不适用时，先改输入通道与导向信号，再谈跑多久、变异多少次。

## A1 — 书中的应用 (Past Application)

### 案例 1: syzkaller 用系统调用模板 fuzz Linux 内核
- **问题**: Linux 内核代码规模大、文档少，普通用户态文件 fuzz 触达不到系统调用接口；随机生成 syscall 参数大多不合法，内核会在入口直接拒绝。
- **方法论的使用**: 为系统调用定义模板，在模板中声明参数类型并处理调用之间的顺序依赖与值依赖，用知识型模板保证输入格式良好；运行侧把内核放进 QEMU 虚拟机，编译插桩并在一组虚拟机上运行，跟踪覆盖信息与安全违规，形成覆盖率反馈。
- **结论**: 内核 fuzz 的输入通道是系统调用序列而非文件；知识型模板解决“参数合法、顺序有效”，覆盖率型运行环境解决“往哪里继续探索”，两者可以叠加在同一条路线里。
- **结果**: 2015 年开源后发现了多个高价值 Linux 内核漏洞，并被移植到 Android、macOS、Windows 等平台；书中同时把它列为覆盖率型内核模糊器的代表。

### 案例 2: AFLGo 用距离度量做定向 fuzz
- **问题**: 覆盖率引导追求“覆盖更多代码”，但补丁验证、重点函数测试只关心能否到达指定位置；普通 fuzz 不知道目标在哪，资源容易摊到无关路径上。
- **方法论的使用**: 先把易受攻击的代码显式定义为目标位置，书中列出四类：补丁、缺乏足够跟踪信息的程序崩溃、静态分析工具验证的结果、与敏感信息相关的代码片段；再用距离度量优化选择离目标位置更近的测试用例，把更多测试资源分配给感兴趣代码。
- **结论**: 定向 fuzz 的第一动作是定义目标，而不是加变异；距离度量只是把“目标”转成种子排序的手段，目标选得越准，定向效果越好。
- **结果**: 通过适当的定向算法可以把测试资源向目标代码倾斜；但书中也指出 AFLGo 与 QTEP 都严重依赖静态分析的有效性，而静态分析误报率仍高，目标位置不准会削弱定向效果。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 只知道一个函数地址、补丁点、敏感函数或深层路径，想让 fuzz 定向打到那里，而不是继续盲目扩覆盖。
2. 目标是闭源程序，没有可送达的文件/协议输入，或解析前的格式校验与无关代码消耗了大部分执行时间。
3. 要 fuzz 的是驱动或内核接口，但还不知道该走知识型还是覆盖率型、输入通道怎么建模；若设备名与控制码已确定、只问 IOCTL/MITM 的具体配法，走 `kernel-driver-fuzzing`。
4. 目标疑似带反 Fuzz：执行明显变慢、覆盖率反馈与预期不符、崩溃被吞掉或现场无法保留。
5. 通用 AFL/覆盖率引导跑了很久不涨覆盖，用户问“是不是方法不对、该换哪条路线”。

### 语言信号 (用户的话里出现这些就应激活)

- “只知道一个函数地址，怎么让 fuzz 打到那里 / directed fuzzing / target location”
- “闭源程序没有文件输入 / 只能从内存里改 / in-memory fuzzing / snapshot fuzzing”
- “驱动/内核接口该怎么建模输入、走知识型还是覆盖率型 / kernel fuzzing route / syscall fuzzing”（已知设备名与控制码、只问 MITM 具体配置时不激活本 skill）
- “跑了很久覆盖率不涨 / AFL 卡住了 / coverage plateau / no new edges”
- “目标好像有反 fuzz / 崩溃被吞了 / anti-fuzzing / crash suppressed”
- “通用 fuzz 跑不动，下一步换什么 / which fuzzing route should I switch to”

### 与相邻 skill 的区分

- 与 `coverage-guided-fuzzing` 的区别: 后者处理常规文件/协议输入下覆盖率闭环怎么配、何时停；本 skill 处理闭环不成立时，切换到定向、内存、内核或反 Fuzz 对抗路线。
- 与 `fuzzing-strategy` 的区别: 后者做 Blind/Smart 选型与工具选择；本 skill 是在已选定 fuzz 后，判断通用覆盖率路线为何失效并改输入通道/导向信号。
- 与 `kernel-driver-fuzzing` 的区别: 前者讲驱动 IOCTL、设备名、控制码的具体 Fuzz 操作；本 skill 只决定何时该走内核路线、输入通道和知识型/覆盖率型取向。判据：问“该不该走内核路线、输入怎么建模”用本 skill；问“Method 位怎么裁、MITM 怎么配”用 `kernel-driver-fuzzing`。
- 与 `file-format-vulnerability-reversing` 的区别: 后者从畸形样本反推格式解析入口、构造最小 POC；本 skill 只借用格式/解析例程知识建立输入通道与种子，不做格式逆向本身。

## E — 可执行步骤 (Execution)

1. **判断通用 fuzz 为何失效**
   - 逐项检查四件事：输入通道是否可达、是否有明确目标方向、覆盖率信号是否可信、异常是否可观测可判定。
   - 完成标准: 用一句话写出失效点，例如“无文件输入，只有内存中的解析参数”或“覆盖率反馈被目标污染”。
   - 判停条件: 若有正常文件/协议输入且通用覆盖率闭环可跑，停止本 skill，回到 `coverage-guided-fuzzing`；不要为了“更高级”而改路线。

2. **选路线并写明放弃理由**
   - 无输入 → 内存 fuzz；输入是 syscall/ioctl → 内核 fuzz；有输入但只关心特定位置 → 定向 fuzz；信号失真/执行变慢/崩溃被吞 → 先处理反 Fuzz。
   - 完成标准: 选定一条主路线，同时记录另外三条为何不选，以及主路线失败时的回退方案。

3. **建立输入通道或模板**
   - 定向: 准备能到达目标附近路径的种子，标出目标基本块/函数。内存: 逆向定位解析例程的起止位置，确定可注入的内存数据。内核: 编写 syscall/ioctl 模板，声明参数类型、取值、调用顺序与值依赖，准备虚拟机或快照环境。
   - 完成标准: 用一个探针输入证明数据确实到达了目标函数/接口（断点、日志、trace 或驱动返回值均可）。
   - 判停条件: 若经过合理逆向仍无法定位解析入口/接口，且没有替代输入通道，停止并报告“通道不可达”，不要假装继续 fuzz。

4. **设置导向信号**
   - 定向: 用 CFG/调用图距离给种子排序，优先离目标近的用例。内存: 以解析例程内的断点、异常和运行时上下文作为判定信号。内核: 用插桩覆盖（如 KCOV）或硬件跟踪，或知识型的合法调用率/覆盖 API 数。反 Fuzz: 先验证覆盖率与崩溃信号是否仍可信。
   - 完成标准: 信号可测量、可排序或可触发，并记录采集方式与采样开销。

5. **小规模校准**
   - 先短时间运行，观察目标命中次数、覆盖增量、崩溃数、超时数与单次执行开销。
   - 完成标准: 至少出现一次可复现的目标命中/新覆盖/异常，且开销可接受。
   - 判停条件: 若已确认输入到达入口但目标命中与覆盖增量始终为零，回到步骤 3/4 改通道或导向信号，不要用加大变异次数掩盖问题。

6. **正式运行并持续监控**
   - 记录 exec/s、覆盖增长、崩溃/超时、种子分布和资源占用；内存 fuzz 同时保存每次变异的上下文，内核 fuzz 在虚拟机外部保留内核日志与崩溃转储。
   - 完成标准: 有连续时间序列数据，能区分“暂时波动”“真实停滞”和“被反 Fuzz 干扰”。

7. **处理反 Fuzz**
   - 按三前提定位：执行被拖慢、覆盖率被污染/阻断、崩溃被掩盖或现场被破坏；针对被破坏的前提换观测通道（虚拟机退出、内核日志、硬件跟踪、外部调试器、计时）或换工具，并记录对抗行为本身的可观测特征。
   - 完成标准: 至少用一个独立于目标自报的通道交叉验证异常，并归因到具体被阻断的前提。
   - 判停条件: 若三个前提都被阻断且没有可用的独立观测通道，停止并报告“该路线被阻断”；不得据此声称目标没有漏洞。

8. **分诊与收敛**
   - 按模块偏移、函数偏移、调用栈、异常码去重；复现每个 crash；区分 harness/环境错误与目标真实缺陷；把结果映射回代码位置。
   - 完成标准: 每个样本组都有可复现输入、位置与定性，报告中区分 crash 数与去重后的缺陷数；对未覆盖区域明确标注“未测试”，而不是“安全”。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **有正常文件/协议输入且通用覆盖率引导可跑**: 直接用 `coverage-guided-fuzzing`；定向、内存、内核路线会增加逆向与工程成本，收益不成比例。
- **目标只是普通用户态程序、输入通道清晰**: 先用常规 fuzz；内存 fuzz 只在无文件输入、闭源且解析前开销大或需要绕过格式外壳时才值得上。
- **没有权限或环境做内核测试**: 无法加载模块、无法运行虚拟机、无法插桩/跟踪内核时，内核 fuzz 路线不可执行，不要用用户态文件 fuzz 冒充。
- **目标反 Fuzz 无法处理且没有独立观测通道**: 应停止并如实报告阻断，不能把“测不到”写成“没有漏洞”。
- **已确定驱动、设备名与控制码，只问 IOCTL/MITM Fuzz 的具体配置**: 交给 `kernel-driver-fuzzing`；本 skill 只回答“该不该走内核路线、输入怎么建模”，不展开具体驱动操作。
- **只是要在 Blind Fuzz / Smart Fuzz 之间选型或选工具**: 交给 `fuzzing-strategy`，本 skill 不重复选型。

### 作者在书中警告的失败模式

- 把反模糊测试当成不可绕过（ce-C07）：遇到执行变慢、崩溃被吞或覆盖率被干扰就放弃，不尝试检测与对抗。反 Fuzz 主要降低效率、阻断覆盖率统计、隐藏崩溃或干扰污点分析，并没有消除输入面；这些行为会留下可观测特征，针对特定 fuzzer 的保护也常可通过换工具或换监控方式绕开。反过来，也不能因为“可绕过”就忽略它——必须先归因到被阻断的前提，再选择替代通道。
- 定向目标定义不清：只盯着覆盖率而不把目标写成可判定对象，定向会退化成普通 fuzz（p-C13）。
- 闭源目标仍硬套外部输入 fuzz：协议/格式无法重建时，应先考虑进入内存、在参数被内部函数使用前变异（p-C15）。
- 把内核 fuzz 当成“用户态 fuzz 换个目标”：内核在用例生成、输入、运行监控上要求更高，还需处理调用顺序与值依赖，直接套用会大量产生非法调用。

### 作者的盲点 / 时代局限

- 成书于 2022 年，内核与 fuzz 工具生态变化极快：syzkaller 的描述文件、KCOV/KASAN/KCSAN 等机制、kAFL 对 Intel PT 的依赖都在演进，书中的工具能力与版本细节会过时。
- 7.5 节以文献综述为主，教材示例少：syzkaller 案例实际出自 7.1.1 的起源叙述，7.5.3 只给代表性工具与结论，没有端到端命令与可复现实验。
- 内核 fuzz 依赖虚拟化、硬件跟踪与较高权限，书中对其成本、环境搭建与稳定性问题讨论不足。
- 反 Fuzz 部分引用的验证多停留在原型与有限数据集（如 Fuzzification 在 binutils、LAVA-M 上的对比），不能直接外推为“普遍有效”或“普遍不可绕”。
- 定向 fuzz 严重依赖静态分析质量，而书中也承认静态分析误报率仍高；目标位置选错时，距离度量会把资源引向错误方向。

### 容易混淆的邻近方法论

- `coverage-guided-fuzzing`: 常规输入通道下的覆盖率闭环与停止条件；本 skill 是闭环不成立时的路线切换。
- `fuzzing-strategy`: Blind/Smart 选型与工具选择；本 skill 是选定之后的通道与导向改造。
- `kernel-driver-fuzzing`: 驱动 IOCTL 的具体 Fuzz 操作；本 skill 只决定是否走内核路线与如何建模输入。
- `file-format-vulnerability-reversing`: 格式逆向与最小 POC；本 skill 只借用解析例程知识建立内存/定向输入。
- `symbolic-execution`: 约束求解与路径条件构造；本 skill 仅在定向路线需要跨复杂条件时把它当补充分支手段。
