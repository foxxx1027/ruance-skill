# 流程与管理：SDL、CI/CD 门禁与漏洞管理（工程检查清单）

## R — 原文 (Reading)

> SDL 安全开发生命周期
>
> CI/CD 安全门禁、自动化扫描
>
> 漏洞跟踪、修复验证、复测
>
> 应急响应、监控告警、合规检查
>
> 参考标准：OWASP Top 10、CWE Top 25、NIST、等保等
>
> — 用户，《漏洞筛查覆盖框架》第 12 类「流程与管理」，2026-10-19

## I — 方法论骨架 (Interpretation)

1. **先定阶段门禁，而不是先选工具。** 把交付过程拆成需求、设计、编码、构建、发布、运行六个阶段，为每个阶段写清“入口条件、必做活动、退出证据、责任人”。需求阶段看安全需求与数据分级是否进入需求池；设计阶段看威胁建模与架构评审是否留下结论；编码阶段看安全编码规范、代码评审与密钥扫描；构建阶段看 SAST/SCA/镜像扫描是否执行；发布阶段看阻断条件、例外审批与回滚方案；运行阶段看监控、漏洞运营与应急。设计缺陷是“流程里根本没有某个阶段”，实现缺陷是“有活动但没有证据或责任人”，配置问题则是“门禁参数与阈值设置不当”。常见误判是把“买了一个扫描平台”当成“建好了 SDL”。

2. **再定每阶段工具与阻断条件。** 每个门禁只回答三个问题：用什么检查、什么结果算不通过、谁有权批准例外。SAST、SCA、密钥扫描、IaC 扫描、DAST、IAST、容器镜像扫描各自覆盖不同层，不能用一种工具的结果替代另一种。阻断条件要按可利用性与资产重要性分级，而不是按告警数量；对误报要有复核与基线机制，对例外要有到期时间、补偿措施与审批记录。最容易漏的是“只在主分支跑、发布流水线可绕过”“扫描失败被 `|| true` 吞掉”“例外永久有效”。把门禁做成不可绕过的流水线步骤，才算真正落地。

3. **再定漏洞生命周期，确保每个漏洞有唯一身份。** 从发现、去重、定级、派单、修复、验证、复测到关闭，每一步都要有状态、责任人、时间戳和证据。去重要按“资产 + 漏洞类型 + 位置 + 根因”合并，而不是按扫描器告警 ID；定级要结合可利用性、暴露面、数据敏感度与业务影响，不能只看工具给的 severity；派单要落到具体团队与具体负责人；关闭必须经过复测，而不是“研发说修了”。设计缺陷是没有统一台账与状态机，实现缺陷是字段缺失、责任人不明、证据不可追溯，配置问题则是 SLA 阈值与业务不匹配。

4. **再定 SLA 与例外，别让所有漏洞同一个期限。** 按严重度、资产等级、是否互联网暴露、是否有可用利用链分档，给出修复时限、临时缓解时限与复测时限；对无法按期修复的，要求补偿控制（WAF 规则、访问限制、功能下线）、风险接受人和到期复审。SLA 的起点应是“确认漏洞”而不是“扫描发生”，终点应是“复测通过”而不是“工单关闭”。常见误判是把“高危 7 天”写进制度却不区分资产，导致团队批量走例外；另一个盲区是只统计平均修复时间，不看超期率与重开率。

5. **再定应急响应与监控告警。** 应急流程至少包含发现、分级、上报、遏制、根除、恢复、复盘七个动作，并明确值班人、决策人、对外沟通人与证据保全要求；预案必须演练，演练要记录时间线、角色、决策与改进项。监控要覆盖认证失败、权限变更、敏感数据访问、异常出站、管理后台操作、漏洞利用特征与关键业务指标，告警要有阈值、抑制、升级路径与运行手册。设计缺陷是没有预案或没有值班机制，实现缺陷是告警无人接收、阈值噪声过大、日志缺失关键字段，配置问题则是保留期与脱敏策略不当。应急与监控都不能替代漏洞修复，也不能把“有告警”当成“已响应”。

6. **最后做合规映射与度量，把控制点落到证据。** 把 OWASP Top 10、CWE Top 25、NIST 框架与等保要求拆成可检查的控制点，再映射到本组织的阶段门禁、工具、制度与证据，而不是复制一张对照表。每个控制点至少写清“要求—实现方式—证据位置—责任人—复核周期”。度量优先看结果与能力：门禁覆盖率、漏洞超期率、平均确认时间、平均修复时间、复测通过率、重开率、逃逸到生产的漏洞数、应急演练完成率；少看“扫描次数”“告警总数”这类可与风险脱钩的数量指标。常见误判是把合规当安全、把文档当证据、把一次审计当持续运营。

7. **按“建矩阵 → 只读核查 → 小范围试运行 → 证据与改进”收口。** 先建阶段门禁矩阵与漏洞状态机，再核查现有制度、流水线配置、台账字段与监控覆盖；随后选一个非关键项目做小范围试运行，观察门禁是否误伤、例外是否可控、SLA 是否可执行；最后用抽样复测与时间线证据验证流程真的在运转。所有涉及生产流水线、账号权限、应急演练的变更，必须仅在授权范围内进行，并保留回滚方案。

## A1 — 书中的应用 (Past Application)

> 本 skill 为工程清单型，没有单一书籍案例；以下为公开标准条款映射，不虚构事件细节。

### 标准映射 1: OWASP A06:2021 Vulnerable and Outdated Components
- **条款**: OWASP Top 10 2021 A06:2021 Vulnerable and Outdated Components。
- **对应检查**: 真实系统里通常表现为：依赖清单不完整、没有 SBOM、构建时不跑 SCA、已知漏洞组件长期不升级、补丁没有 SLA、镜像与运行时组件漂移；扫描结果存在但没人负责修复。
- **落到本 skill**: 用 I 段第 2、3、4 模块把依赖扫描接入构建门禁，建立“组件—版本—漏洞—责任人—SLA—复测证据”台账，再按 E 段第 2、4、6 步验证阻断与关闭条件。

### 标准映射 2: OWASP A09:2021 Security Logging and Monitoring Failures
- **条款**: OWASP Top 10 2021 A09:2021 Security Logging and Monitoring Failures。
- **对应检查**: 真实系统里通常表现为：关键认证、权限变更、敏感数据访问与异常出站没有日志；日志字段缺失或保留期过短；告警阈值噪声过大、无人值班、没有升级路径与运行手册；出了事件无法还原时间线。
- **落到本 skill**: 用 I 段第 5 模块建立“监控项—日志字段—告警阈值—值班人—运行手册”表，再按 E 段第 7、8 步用演练或抽样告警验证从检测到响应的闭环，证据交由日志完整性类 skill 做取证加固。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队准备落地 SDL，但不知道需求、设计、编码、构建、发布、运行各阶段分别该放什么活动与门禁。
2. CI/CD 里已经接了 SAST/SCA/密钥扫描，但告警没人看、可以手动跳过，想知道怎么设阻断条件与例外审批。
3. 漏洞台账里堆积几十上百条，严重度混乱、责任人不清、修没修无法验证，需要建立生命周期与 SLA。
4. 线上出了安全事件，发现没有预案、没有值班表、不知道谁决策、证据也没保全，需要补应急响应流程。
5. 客户审计或等保检查要求提供 OWASP Top 10、CWE Top 25、NIST 与内控要求的映射和证据。
6. 管理层要安全度量，但目前只有扫描次数和告警数量，想知道哪些指标能反映真实风险与改进效果。

### 语言信号 (用户的话里出现这些就应激活)

- “我们想搭 SDL，每个阶段应该放什么”
- “CI 里扫出来的问题研发不看，怎么让它必须修”
- “漏洞台账怎么去重、怎么定级、怎么派单”
- “这个漏洞修没修，复测要留什么证据”
- “高危漏洞 SLA 定几天合适，修不完怎么办”
- “出了安全事件谁负责，先做什么后做什么”
- “监控告警太多没人看，怎么设阈值和升级”
- “等保要求做应急演练，预案没跑过算不算”
- “客户要 OWASP 和 NIST 的对照表，还要证据”
- “老板只问扫了多少漏洞，这个度量怎么改”

英文关键词：SDL、CI/CD security gate、vulnerability management、incident response、security metrics。

### 与相邻 skill 的区分

- 与 `appsec-tooling-and-threat-modeling` 的区别：后者负责 SAST/DAST/IAST 怎么选、怎么跑、结果怎么分诊，以及威胁建模的具体方法；本 skill 负责把这些能力放进阶段门禁、漏洞生命周期与管理制度。要判断某条告警是不是误报，走前者；要决定“什么级别必须阻断上线、谁来批例外”，走本 skill。
- 与 `middleware-remediation-layering` 的区别：后者回答“多个中间件漏洞先修哪个、补丁与缓解怎么排顺序”；本 skill 回答“漏洞从发现到关闭的流程、SLA 与责任”。单个漏洞的修复技术顺序走前者；台账治理与复测口径走本 skill。
- 与 `log-integrity-and-evidence` 的区别：后者判断日志是否完整、是否被篡改、能否作为证据；本 skill 设计“要记什么、告警怎么发、谁来响应”。怀疑日志被删改，走前者；要补监控覆盖与告警流程，走本 skill。
- 与 `pentest-engagement-and-disclosure` 的区别：后者处理授权、范围、SOW、测试边界与漏洞披露；本 skill 处理渗透结果进入台账之后的修复、复测与关闭。测试前定边界走前者；测试后怎么跟踪到闭环走本 skill。
- 与 `supply-chain-and-dependency-security` 的区别：后者做 SBOM、SCA、依赖投毒与镜像供应链的技术核查；本 skill 把供应链检查接入门禁并定义升级 SLA 与例外。要生成/验证 SBOM，走前者；要规定“构建时不过 SCA 就不能发布”，走本 skill。
- 与 `data-protection-and-secrets` 的区别：后者处理 TLS、存储加密、密钥管理与敏感数据泄露的技术控制；本 skill 负责把这些控制纳入合规映射、审计证据与定期复核。要修密钥硬编码，走前者；要证明密钥扫描已进入门禁并有例外记录，走本 skill。
- 与 `cloud-and-container-baseline` 的区别：后者做容器/K8s/云 IAM 的基线核查；本 skill 负责把基线检查变成发布前门禁与运行期巡检制度。

## E — 可执行步骤 (Execution)

1. **建阶段门禁矩阵**
   - 动作: 按需求、设计、编码、构建、发布、运行六阶段，列出每阶段的必做活动、输入、输出、责任人与证据；标出当前已有、缺失、形同虚设的环节。
   - 完成标准: 形成“阶段 × 活动 × 证据 × 责任人 × 当前状态”矩阵，每个阶段至少有一项可验证的退出条件。
   - 判停条件: 若组织尚未明确交付流程或责任人，先停在流程梳理，不设计无法执行的门禁。

2. **为每阶段选定工具与阻断条件**
   - 动作: 为构建阶段选择 SAST/SCA/密钥扫描/IaC 扫描/镜像扫描，为发布阶段选择 DAST/配置核查；定义“不通过”的判定规则、误报复核路径、例外审批人与到期时间。
   - 完成标准: 每个门禁都有工具、阈值、阻断动作、例外流程与证据留存位置；流水线不能被 `|| true` 或手动跳过静默绕过。
   - 判停条件: 若无历史数据校准阈值，先用观察模式运行一个迭代，记录误报率后再启用阻断。

3. **建统一漏洞台账与去重规则**
   - 动作: 设计字段：唯一 ID、资产、漏洞类型、位置、根因、来源工具、首次发现、严重度、责任人、状态、SLA 截止、修复证据、复测记录；定义按“资产+类型+位置+根因”去重。
   - 完成标准: 同一根因的多条扫描告警能合并为一个漏洞条目，条目能从发现追踪到关闭。
   - 判停条件: 若资产标识不统一（域名/IP/仓库/镜像混用），先完成资产归一，否则台账无法可靠去重。

4. **定级并设定分档 SLA**
   - 动作: 结合可利用性、互联网暴露、数据敏感度、业务影响与补偿控制定级；按级别与资产等级设定修复、缓解、复测时限；定义超期升级与风险接受流程。
   - 完成标准: 每个级别都有可执行的时限、审批人和超期处理规则，且能解释为何不同资产期限不同。
   - 判停条件: 若无资产分级或业务影响数据，先输出临时分级假设并标注，不把假设写成制度。

5. **派单、修复与例外管理**
   - 动作: 把漏洞派给具体团队与具体负责人，附复现步骤、影响与修复建议；例外必须有理由、补偿控制、风险接受人、到期日与复审记录。
   - 完成标准: 每个打开状态的漏洞都有责任人和下一步动作；没有永久例外或无人认领的条目。
   - 判停条件: 若漏洞涉及第三方组件且无可用补丁，转入补偿控制与供应商跟踪，不强行要求“打补丁”。

6. **修复验证与复测**
   - 动作: 按原始复现步骤在修复后的环境复测，优先使用与首次发现不同的独立构造；记录版本、时间、请求/响应、扫描结果与回归范围；未通过则重开并更新 SLA。
   - 完成标准: 关闭条目必须附“修复前失败、修复后通过”的对照证据，且能排除缓存、灰度未覆盖与环境差异。
   - 判停条件: 若无法接触修复后环境，条目保持“待复测”，不得仅凭研发口头确认关闭。

7. **建应急响应流程并演练**
   - 动作: 定义发现、分级、上报、遏制、根除、恢复、复盘的动作与时限，明确值班人、决策人、沟通人与证据保全要求；至少做一次桌面演练或非生产演练并记录时间线。
   - 完成标准: 每个角色知道何时做什么、向谁升级；演练产出改进项、责任人与完成期限。
   - 判停条件: 若演练可能影响生产或真实用户，改用桌面推演；未经授权不得做真实攻击演练。

8. **建监控告警与运行手册**
   - 动作: 列出认证失败、权限变更、敏感数据访问、异常出站、管理后台操作、漏洞利用特征等监控项；为每项定义日志字段、阈值、抑制规则、告警接收人、升级路径与处置手册。
   - 完成标准: 每个高优先级告警都有接收人、响应时限与可执行步骤；告警能关联到资产与责任人。
   - 判停条件: 若日志字段缺失或保留期不足，先补日志与保留策略，不靠调高阈值掩盖盲区。

9. **做合规映射与证据链**
   - 动作: 把 OWASP Top 10、CWE Top 25、NIST 框架与等保要求拆成控制点，映射到阶段门禁、工具、制度与证据；为每个控制点记录实现方式、证据位置、责任人与复核周期。
   - 完成标准: 每个控制点都能指向真实证据（流水线记录、台账、演练报告、审计日志），而不是只有一张对照表。
   - 判停条件: 若标准版本或适用条款未确认，先锁定版本与范围，避免映射到过期要求。

10. **定度量、抽样复核与持续改进**
    - 动作: 选择门禁覆盖率、超期率、平均确认/修复时间、复测通过率、重开率、生产逃逸漏洞数、演练完成率等指标；按月抽样复核台账与证据，定期复盘误报、例外与流程瓶颈。
    - 完成标准: 指标能驱动具体改进项，且不会被“多扫多报”刷高；每项改进都有责任人与验证时间。
    - 判停条件: 无，结束。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 需要判断某个扫描告警是不是真漏洞、如何调规则、如何做威胁建模：走 `appsec-tooling-and-threat-modeling`；本 skill 只处理流程、门禁与台账。
- 需要决定多个中间件漏洞的修复顺序、补丁与缓解如何分层：走 `middleware-remediation-layering`；本 skill 不替代具体修复技术方案。
- 需要判断日志是否完整、是否被篡改、能否作为司法/审计证据：走 `log-integrity-and-evidence`；本 skill 只设计监控与响应流程。
- 需要明确渗透测试授权、范围、SOW 与漏洞披露方式：走 `pentest-engagement-and-disclosure`；本 skill 从测试结果进入台账之后开始。
- 需要生成 SBOM、核查依赖投毒、镜像供应链或许可证风险：走 `supply-chain-and-dependency-security`；本 skill 只定义门禁与 SLA。
- 需要实际修复 TLS、存储加密、密钥硬编码或脱敏问题：走 `data-protection-and-secrets`；本 skill 只做合规映射与证据复核。
- 只有一份制度文档，没有流水线、台账、日志或责任人：只能做差距分析，不能宣称流程已落地或合规。
- 未取得授权，或变更会影响生产发布、账号权限、真实应急响应：不得执行；演练与门禁变更必须限定在授权范围并有回滚方案。

### 作者在书中警告的失败模式

- 本清单未覆盖“买了扫描平台就等于建成 SDL”的误判：没有阶段活动、责任人与证据，工具只会产生更多无人处理的告警。
- 本清单未覆盖“门禁只看告警数量”的失败：不区分可利用性与资产重要性，会逼团队批量走例外或刷低危。
- 本清单未覆盖“工单关闭等于漏洞修复”的失败：没有复测与修复前后对照，关闭只是行政动作。
- 本清单未覆盖“SLA 一刀切”的失败：不区分资产等级与暴露面，期限要么不可执行，要么对真正高危毫无约束。
- 本清单未覆盖“例外永久有效”的失败：没有到期日、补偿控制和风险接受人，例外会变成事实上的默认放行。
- 本清单未覆盖“预案写在文档里但从未演练”的失败：角色、升级路径与证据保全在真实事件中会全部失效。
- 本清单未覆盖“告警很多等于监控有效”的失败：没有接收人、阈值、抑制与运行手册，告警只会被忽略。
- 本清单未覆盖“合规对照表等于合规”的失败：控制点没有证据位置与复核周期，审计时无法自证。

### 作者的盲点 / 时代局限

- 本清单未覆盖不同研发模式（瀑布、敏捷、持续交付、平台工程）下门禁形态的差异，阶段划分需按组织实际交付流程调整。
- 本清单未覆盖 NIST SSDF、OWASP SAMM、SLSA、DORA 等框架的完整条款与成熟度模型，只做控制点映射思路。
- 本清单未覆盖等保具体条款、测评方法与行业监管差异，实际适用版本与证据要求应以最新官方文件为准。
- 本清单未覆盖 AI 生成代码、低代码平台、外包交付与开源维护者等新型供应链场景的治理细节。
- 本清单未覆盖漏洞经济性、风险接受量化与保险转移等管理决策，度量阈值需结合组织风险偏好校准。
- 本清单未覆盖工具链快速演进带来的规则、许可证、数据驻留与误报率变化，门禁参数需定期复核。

### 容易混淆的邻近方法论

- `appsec-tooling-and-threat-modeling`：工具怎么跑、结果怎么分诊、威胁怎么建模；本 skill 是门禁、台账、SLA 与治理。
- `middleware-remediation-layering`：单个/多个中间件漏洞的修复技术顺序；本 skill 是漏洞从发现到关闭的管理流程。
- `log-integrity-and-evidence`：日志完整性与取证；本 skill 是监控项、告警与应急响应设计。
- `pentest-engagement-and-disclosure`：授权、范围与披露；本 skill 是测试结果的跟踪、复测与关闭。
- `supply-chain-and-dependency-security`：SBOM、依赖与镜像供应链技术核查；本 skill 是把检查接入门禁并设 SLA。
- `data-protection-and-secrets`：数据保护技术控制；本 skill 是把控制纳入合规映射与审计证据。
- `cloud-and-container-baseline`：云与容器基线核查；本 skill 是把基线变成发布门禁与运行巡检制度。
