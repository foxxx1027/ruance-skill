# 代码与架构审计工具链：从威胁模型到可利用结论

## R — 原文 (Reading)

> SAST 静态代码扫描
>
> DAST 动态应用扫描
>
> IAST 交互式扫描
>
> 人工代码审计、架构评审、威胁建模
>
> 模糊测试、渗透测试、红队评估
>
> — 用户，《漏洞筛查覆盖框架》第 11 类「代码与架构审计」，2026-10-19

## I — 方法论骨架 (Interpretation)

1. **先建威胁模型，再决定跑什么工具。** 威胁建模的输入不是工具列表，而是资产、数据流、信任边界与攻击者能力。先画清外部入口、身份切换点、数据存储与第三方依赖，再问“谁想拿什么、从哪进、需要什么条件”。产出应是一组可验证的威胁假设与攻击路径，而不是一张架构图。没有威胁模型时，扫描器只能按规则覆盖代码，无法回答“这套系统最该担心什么”。这属于设计层工作，不能由工具替代。

2. **把威胁假设翻译成测试问题。** 每条威胁路径要落到“需要什么证据才能证明或否定”：某个接口是否可越权、某段输入是否进入危险汇点、某个信任边界是否可绕过。测试问题要明确目标、前置条件、观察点和停止条件。这样后续的 SAST/DAST/IAST、人工审计与渗透才有共同靶子。翻译不清会导致工具各扫各的，报告无法合并。常见误判是把“高危规则命中”直接当成“威胁成立”。

3. **按覆盖能力选工具组合，而不是按名气。** SAST 擅长看代码路径与危险汇点，但对运行时配置与第三方交互弱；DAST 擅长看外部行为，但覆盖受爬虫与认证限制；IAST 依赖插桩与测试流量；模糊测试适合有明确输入通道的解析类目标；人工审计适合业务逻辑与权限设计。选型时列出“目标—工具能力—盲区—所需环境”，明确哪些问题必须人工验证。工具组合的目标是互补覆盖，不是数量堆叠。

4. **编排要区分基线、增量与专项。** 基线扫描建立全量视图；增量扫描跟随代码变更，控制噪声；专项测试围绕高风险威胁假设做深度验证。编排时要固定工具版本、规则集、认证方式、扫描范围与时间窗口，避免结果不可比。主动扫描与渗透必须在授权范围内，避开生产高峰，并预设熔断条件。工具版本或规则集变化会让历史结果失真，必须记录。

5. **结果先归一，再去重。** 不同工具对同一问题会给出不同位置、不同名称与不同严重度。归一字段至少包括：资产、入口、代码位置/URL、漏洞类型、证据、可利用前置条件、置信度。去重按“同一根因”而不是“同一标题”：同一未校验输入导致多个接口告警，应合并为一条根因。重复告警会淹没真正需要人工看的少数项，是工具链失败的主要原因之一。

6. **人工验证是分诊的核心，不是可选步骤。** 对每条候选发现，先判断可达性（代码/路由是否可达）、可控性（输入是否受攻击者影响）、影响（能读到什么、改到什么）、前置条件（认证、角色、配置）。验证优先用只读证据与本地复现；需要主动测试时，只用自有账号与合成数据，在授权范围内做最小 PoC。无法复现的项标为“未验证”，不能直接关闭，也不能直接定为高危。

7. **结论要区分设计缺陷、实现缺陷与配置问题。** 设计缺陷需要改架构、权限模型或数据流；实现缺陷需要改代码；配置问题可以快速加固。三者修复责任与周期不同。可利用结论应写清“攻击者需要什么、能达成什么、证据在哪、复现步骤是什么”。只写“存在 SQL 注入风险”而不写入口与影响，无法支撑修复优先级。误报也要记录判断依据，便于规则调优。

8. **修复优先级与复测口径在扫描前就应定义。** 排序依据包括：可利用性、影响范围、暴露面、是否有现成利用、修复成本与业务影响。复测要能回答“原 PoC 是否失效、同类根因是否都修了、是否引入新问题”。工具链的产出不是报告数量，而是“已确认问题—修复—复测”的闭环。若没有复测口径，渗透与扫描会变成周期性重复劳动。

## A1 — 书中的应用 (Past Application)

> 本 skill 为工程清单型，没有单一书籍案例；以下为公开标准条款映射，不虚构事件细节。

### 标准映射 1: OWASP A04:2021 Insecure Design

- **条款**: OWASP A04:2021 Insecure Design。
- **对应检查**: 系统缺少威胁建模与安全设计约束，业务流、权限模型或信任边界本身存在缺陷，靠后期扫描与补丁无法根治。
- **落到本 skill**: 用第 1 至 3 步建资产与信任边界、画攻击路径并把威胁翻译成测试问题；产出威胁假设—测试问题—证据要求表，把设计层问题与实现层告警分开。

### 标准映射 2: CWE-693 Protection Mechanism Failure

- **条款**: CWE-693 Protection Mechanism Failure。
- **对应检查**: 认证、授权、输入校验、隔离等保护机制未覆盖某条路径，或可被绕过，导致同一类攻击在多个入口重复成立。
- **落到本 skill**: 用第 5 至 8 步归一结果、按根因去重并做人工验证；产出“根因—受影响入口—绕过条件—证据”清单，避免逐条修表层告警。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

- 新系统立项或大改版，需要在编码前做架构评审与威胁建模，明确安全测试重点。
- 团队买了 SAST、DAST、IAST 或渗透服务，但报告堆积、重复告警多，不知道怎么落到修复。
- 扫描器报了几百条，研发说都是误报，需要一套可复现的分诊与验证口径。
- 要做年度渗透或红队评估，需要先定范围、攻击路径、工具组合与交付格式。
- 有一套解析类或协议类目标，想判断该用模糊测试还是人工审计，如何编排。
- 想把供应链、云配置、密钥扫描的结果与代码扫描合并成一张风险视图。

### 与相邻 skill 的区分

- 与 `program-analysis-technique-selection`：要在静态、动态、符号执行、模糊测试之间做预算与能力选型时走该 skill；已选定组合，要编排扫描、去重、验证并交付结论时走本 skill。
- 与 `source-and-binary-static-audit`：要对单个代码库或二进制做深度静态审计、追具体数据流时走该 skill；要做系统级威胁建模、工具组合与结果分诊时走本 skill。
- 与 `devsecops-and-vuln-management`：要设计 CI 门禁、漏洞跟踪、SLA 与复测流程时走该 skill；要做一次完整的威胁建模、扫描编排与可利用结论输出时走本 skill。
- 与 `coverage-guided-fuzzing`：已确定目标与输入通道，要搭 Fuzz 闭环、处理种子与崩溃去重时走该 skill；要判断是否该用 Fuzz、如何与其他工具编排时走本 skill。
- 与 `supply-chain-and-dependency-security`：要盘点依赖、SBOM、许可证与组件漏洞时走该 skill；要把 SCA 结果与代码/运行时发现合并分诊时走本 skill。
- 与 `cloud-and-container-baseline`：要按基线核查云资源、容器与 K8s 配置时走该 skill；要把 CSPM/容器扫描结果去重并转成可利用结论时走本 skill。
- 与 `data-protection-and-secrets`：要判断数据级别、密钥轮换与脱敏口径时走该 skill；要把 secret scanning 命中纳入统一分诊与验证时走本 skill。

## E — 可执行步骤 (Execution)

1. **建资产、数据流与信任边界清单**
   - 动作: 列出系统入口、服务、数据存储、第三方依赖与身份体系；画数据流与信任边界，标注跨边界的位置、协议与认证方式。
   - 完成标准: 每个入口与数据存储有归属，信任边界可被指出；未知项单独标注。
   - 判停条件: 关键数据流无法确认时，停止威胁建模，先补架构信息。

2. **画攻击路径并形成威胁假设**
   - 动作: 按攻击者目标（读数据、改数据、提权、横向）列出可行路径，标注前置条件与所需能力；为每条路径写一句可验证的威胁假设。
   - 完成标准: 威胁假设覆盖主要入口与信任边界，且每条都有明确的验证问题。
   - 判停条件: 无，继续。

3. **把威胁假设翻译成测试问题与控制缺口**
   - 动作: 为每条假设定义“需要什么证据、在哪个入口观察、什么算成立、什么算否定”；对照现有控制，标记已覆盖、待验证与明显缺口。
   - 完成标准: 测试问题可分配给具体工具或人工审计，证据要求明确。
   - 判停条件: 无法定义成立条件时，停止排期，先补充设计信息。

4. **选工具组合与授权边界**
   - 动作: 按测试问题选择 SAST、DAST、IAST、人工审计、模糊测试或渗透；列出每个工具的能力、盲区、所需环境与授权范围，明确主动测试的时间窗与熔断条件。
   - 完成标准: 每个测试问题至少有一个主手段与一个交叉验证手段；授权范围与联系人明确。
   - 判停条件: 主动测试未获授权或可能影响生产时，停止该手段，改为只读与本地复现。

5. **编排基线与增量扫描**
   - 动作: 固定工具版本、规则集、认证方式与扫描范围，先跑基线建立全量视图，再对变更做增量扫描；记录每次扫描的配置与时间，确保结果可比。
   - 完成标准: 扫描配置可复现，基线与增量结果能区分；环境与账号信息有记录。
   - 判停条件: 工具版本或规则集无法固定时，停止跨批次比较，只做单次分析。

6. **统一字段并按根因去重**
   - 动作: 把不同工具结果归一为资产、入口、位置、类型、证据、前置条件、置信度；按同一根因合并，保留各工具原始引用。
   - 完成标准: 去重后条目能追溯到原始告警；同一根因不再分散在多个标题下。
   - 判停条件: 无法判断是否同根因时，停止合并，保留两条并标注待验证。

7. **做人工验证与最小 PoC（仅在授权范围内）**
   - 动作: 对高优先级候选逐条判断可达性、可控性与影响；用自有账号与合成数据做最小复现，记录请求、响应与前置条件；不遍历他人数据、不做破坏性操作。
   - 完成标准: 每条候选有“成立/不成立/未验证”结论与证据；成立项有可复现步骤。
   - 判停条件: 复现需要真实用户数据或可能影响生产时，立即停止，改为本地环境验证。

8. **误报分诊与可利用结论**
   - 动作: 对不成立项记录判断依据（不可达、已有校验、框架默认防护、配置未启用等），对成立项写清攻击者所需条件、可达影响与证据位置；把结果按设计缺陷、实现缺陷、配置问题分类。
   - 完成标准: 误报有依据，成立项有可利用结论；分类清晰，未验证项不被混入确定结论。
   - 判停条件: 无，继续。

9. **定修复优先级与复测口径**
   - 动作: 按可利用性、影响范围、暴露面与修复成本排序；为每项定义修复责任人与复测方法，明确“原 PoC 失效、同类根因覆盖、无回归”的通过标准。
   - 完成标准: 修复项可直接分派，复测口径可被第三方复核。
   - 判停条件: 修复方案会改变攻击路径时，停止沿用旧 PoC，重新建模后再复测。

10. **交付证据包与规则调优建议**
    - 动作: 汇总威胁模型、测试问题、扫描配置、去重结果、验证证据与修复建议；记录误报模式，反馈给规则集与工具配置，形成下一轮改进项。
    - 完成标准: 证据包可独立复核，误报原因可转化为规则或流程调整；敏感信息已脱敏。
    - 判停条件: 无，继续。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 要在静态、动态、符号执行、模糊测试之间做技术选型与预算分配，应走 `program-analysis-technique-selection`。
- 要对单个代码库或二进制做深度静态审计与具体数据流追踪，应走 `source-and-binary-static-audit`。
- 要设计 CI 门禁、漏洞跟踪、修复 SLA 与复测流程，应走 `devsecops-and-vuln-management`。
- 要搭建覆盖率引导的 Fuzz 闭环、处理种子与崩溃去重，应走 `coverage-guided-fuzzing`。
- 要处理测试授权、SOW、披露与法律边界，应走 `pentest-engagement-and-disclosure`。
- 未获授权时，不得做主动扫描、渗透、红队演练或任何可能影响生产可用性的测试。

### 作者在书中警告的失败模式

- 本清单未覆盖“先买工具再找问题”的失败：没有威胁模型，工具只能按规则产出噪声。
- 本清单未覆盖“用告警数量衡量安全”的失败：报告条数与真实风险无关，去重与验证才是价值所在。
- 本清单未覆盖“把误报直接关闭”的失败：不记录判断依据，规则无法调优，同类问题会反复出现。
- 本清单未覆盖“只做一次渗透”的失败：没有复测口径与增量机制，修复效果无法证明。
- 本清单未覆盖“为验证漏洞而触碰真实数据”的合规风险；最小 PoC 必须限定在授权范围与合成数据内。

### 作者的盲点 / 时代局限

- 本清单以传统 Web、API 与服务端系统为主，对移动端、桌面端、嵌入式与工控系统的工具链覆盖不足。
- 本清单未展开各商业扫描器的规则差异与许可成本，选型需结合组织实际。
- 本清单未覆盖 AI/LLM 应用、供应链证明与复杂云原生运行时的专门威胁建模方法。
- 本清单不提供渗透测试的法律与合同判断，授权与披露边界需另行确认。
- 本清单未覆盖大规模组织的 AppSec 平台建设与度量体系，偏单系统或单产品线的工具编排。

### 容易混淆的邻近方法论

- 分析技术选型（`program-analysis-technique-selection`）：回答“用哪类分析技术、预算怎么分”，不负责编排与分诊。
- 源码/二进制深度审计（`source-and-binary-static-audit`）：回答“这段代码/二进制到底怎么走”，不做系统级工具组合。
- CI 门禁与漏洞管理（`devsecops-and-vuln-management`）：回答“如何持续阻断与跟踪”，不替代本次威胁建模与验证。
- 覆盖率引导模糊测试（`coverage-guided-fuzzing`）：回答“如何把 Fuzz 跑起来”，不回答“是否值得跑、结果如何与其他工具合并”。
- 授权与披露（`pentest-engagement-and-disclosure`）：回答“能不能测、怎么披露”，不回答“测什么、怎么分诊”。
