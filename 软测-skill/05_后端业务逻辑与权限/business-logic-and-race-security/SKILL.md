# 业务逻辑安全（工程检查清单）

## R — 原文 (Reading)

> 支付、订单、退款、优惠券、积分等流程绕过
>
> 并发请求、重放攻击、竞态条件
>
> 验证码绕过、短信/邮件轰炸
>
> 数据一致性、状态机绕过、审批流绕过
>
> — 用户，《漏洞筛查覆盖框架》第 4 类「业务逻辑安全」，2026-10-19

## I — 方法论骨架 (Interpretation)

1. **先画业务流程状态机，而不是直接找参数。** 把订单、支付、退款、优惠券、积分、审批等对象的状态与允许迁移列出来：待支付→已支付→已发货→已完成、待退款→退款中→已退款、待审批→审批中→已通过/已驳回。标出每个迁移的触发接口、所需主体、所需前置条件、外部回调与补偿任务。没有状态机，就无法判断“跳过某一步”是漏洞还是正常分支。

2. **再列关键不变量，作为后续所有验证的判据。** 典型不变量包括：金额守恒（支付=订单=退款+手续费）、库存非负、优惠券与积分只能按规则抵扣、次数与额度不被突破、资格条件（新用户/会员/地区）成立、时序前置状态必须满足、同一请求只产生一次副作用。每条不变量都要写成可观察的断言，例如“退款总额 ≤ 实付金额”“库存扣减后 ≥ 0”“同一优惠券核销次数 = 1”。

3. **区分设计缺陷、实现缺陷与配置问题。** 状态机本身允许“未支付直接发货”、退款规则允许“退款后仍可再次退款”属于设计缺陷；某个接口漏了前置状态校验、金额只在前端计算、回调不验签属于实现缺陷；限流关闭、风控阈值配错、优惠券叠加规则配置错误属于配置问题。三者修复层级不同，不能一律写成“缺少校验”。

4. **逐条尝试“跳过、乱序、替换、边界值”。** 跳过是直接调用后续步骤接口；乱序是先退款再支付、先发货再付款；替换是改金额、币种、商品 ID、优惠券归属、退款收款方；边界值是 0、负数、小数精度、最大整数、最小单位、超长列表、重复条目。重点看服务端是否重新计算金额与资格，而不是相信客户端传来的计算结果。

5. **重放与幂等要按“请求粒度”检查。** 支付回调、退款申请、优惠券领取、积分兑换、短信发送都可能被重放。确认是否有幂等键、幂等键的作用域是否足够（用户+业务+请求）、重复请求是返回原结果还是再次产生副作用、回调是否验签并校验订单状态。只在前端禁用按钮不构成幂等。

6. **并发与竞态必须用“同时到达”的方式验证。** 顺序执行通过不代表没有竞态：同一优惠券并发核销、最后一件库存并发下单、余额并发提现、积分并发兑换、审批并发通过，都可能在“读—判断—写”之间被插入。检查数据库唯一约束、条件更新、行锁/乐观锁、事务隔离级别、分布式锁与补偿逻辑；分布式环境下还要看锁的粒度、过期与续租。常见误判是“只成功了一单”就认为没有竞态，实际可能是测试没有真正并发或请求被串行化。

7. **频率与滥用要绑定“主体 + 目标 + 动作”。** 短信/邮件轰炸看是否按手机号/邮箱、IP、账号、设备多维限速，是否要求验证码或人机校验，是否可枚举目标；验证码绕过看是否可复用、可预测、可跨动作使用、可被客户端伪造。只按 IP 限速会被代理池绕过，只按账号限速会漏掉“同一号码被多账号轰炸”。数据一致性还要看异步任务、消息重投、对账与补偿是否会造成重复入账。

8. **验证顺序与证据：状态迁移表 → 单请求边界 → 重放 → 并发 → 对账。** 先在授权测试环境按状态迁移表逐条走合法与非法路径，再做金额/数量边界，再做重放，最后用受控并发验证原子性；每一步记录请求、响应、数据库或账务前后值、时间戳与幂等键。涉及真实资金、真实库存或真实短信时必须停在测试环境；无法构造并发时只能标注“未验证”，不能给出确定结论。

## A1 — 书中的应用 (Past Application)

> 本 skill 为工程清单型，没有单一书籍案例；以下为公开标准条款映射，不虚构事件细节。

### 标准映射 1: OWASP A04:2021 Insecure Design
- **条款**: OWASP Top 10 2021 A04:2021 Insecure Design。
- **对应检查**: 真实系统里通常表现为：业务流程没有定义状态机与不变量；退款、优惠券、积分规则允许组合出非预期结果；关键步骤只依赖前端；审批流可跳过或可由同一人自批；对资源消耗与滥用没有业务层限制。这类问题即使每个接口都“有校验”，整体流程仍可能被滥用。
- **落到本 skill**: 用 I 段第 1、2、3 模块产出状态机、不变量清单与设计缺陷判定；用 E 段第 1、2 步把“流程允许什么”固化为可验证断言，再进入实现验证。

### 标准映射 2: CWE-362 Concurrent Execution using Shared Resource with Improper Synchronization ('Race Condition')
- **条款**: CWE-362 Concurrent Execution using Shared Resource with Improper Synchronization（竞态条件）。
- **对应检查**: 多个请求同时读取同一余额、库存、优惠券状态或审批状态，在判断与写入之间没有原子保护，导致超额扣减、重复核销、重复退款或重复审批；常见于“先查询再更新”的实现、缺少唯一约束、锁粒度过粗或过细、异步补偿重复执行。
- **落到本 skill**: 用 I 段第 6 模块和 E 段并发步骤，对关键不变量做受控并发对照，记录成功次数、最终余额/库存、幂等键与事务日志，证明是否存在“判断—写入”窗口。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
- 支付、下单、退款、优惠券、积分、审批流程上线前要做安全评审，需要一份可执行的业务逻辑检查顺序。
- 发现同一优惠券能反复领取、退款金额可改、支付回调重放会重复发货，怀疑流程绕过或重放。
- 库存只剩一件却并发下单成功多单，或余额提现、积分兑换在并发下超额，怀疑竞态。
- 订单状态可以直接从待支付跳到已发货，审批流可以跳过一级，想理清状态机与前置条件。
- 短信/邮件验证码可以被反复触发，或验证码可重复使用、可跨场景使用，需要评估滥用与绕过。
- 财务对账出现差额、异步补偿重复入账，需要从数据一致性角度排查业务流程。

### 语言信号 (用户的话里出现这些就应激活)
- “一分钱支付成功了”
- “退款金额能改成负数”
- “同一张优惠券能反复领”
- “支付回调重放又发了一次货”
- “库存一件，同时下单成功好几单”
- “积分提现并发能超额”
- “订单没支付就能直接发货”
- “审批跳过一级也能提交”
- “验证码用第二次还能过”
- “换个手机号就能一直发短信”

英文关键词：business logic bypass、race condition、replay attack、idempotency、state machine bypass。

### 与相邻 skill 的区分
- 通用 TOCTOU 时间窗模型、类型混淆、沙盒与逻辑隔离：走 `logic-and-isolation-bugs`；本 skill 只处理业务不变量、状态机、重放与并发落点。
- 主体—对象—动作的权限矩阵、IDOR、角色越权：走 `access-control-and-idor`；本 skill 假设“有权操作”，判断“按规则操作是否被绕过”。
- 接口认证、JWT、OAuth/SSO、会话生命周期：走 `auth-session-and-federation-security`；本 skill 不审身份建立，只把验证码/短信通道当作业务流程的一环。
- 接口批量赋值、GraphQL 鉴权、限流与文档暴露：走 `api-and-interface-security`；本 skill 关注业务规则与原子性，接口层清单由它执行。
- 可疑邮件、附件、退信、邮箱分层：走 `email-trust-boundary`；本 skill 只处理邮件/短信作为验证码通道的滥用。
- 注入类漏洞导致的金额或状态被篡改：走 `non-memory-vulnerability-analysis`；本 skill 不把 SQL 注入、命令注入归为业务逻辑缺陷。

## E — 可执行步骤 (Execution)

1. **画业务流程状态机**
   - 动作: 列出订单、支付、退款、优惠券、积分、审批等对象的状态、允许迁移、触发接口、前置条件、外部回调与补偿任务；标出正常分支、异常分支与人工干预分支。
   - 完成标准: 每个状态都有“从哪来、到哪去、谁能触发、需要什么前置条件”，没有孤立状态。
   - 判停条件: 若业务规则或状态定义无法确认，先停在建模阶段，不进入主动验证。

2. **列关键不变量与可观察断言**
   - 动作: 为金额、库存、次数、额度、资格、时序、幂等分别写出断言，例如“退款总额 ≤ 实付”“库存 ≥ 0”“优惠券核销次数 = 1”“同一幂等键只产生一次副作用”。
   - 完成标准: 每条不变量都有对应的数据字段、查询方式与判定阈值。
   - 判停条件: 无，继续。

3. **标注设计缺陷与实现缺陷的候选点**
   - 动作: 对照状态机检查是否存在“设计上允许但业务不应允许”的迁移；对照接口检查是否存在“前端计算、后端信任”“只校验当前步骤、不校验历史步骤”“回调不验签”等实现问题。
   - 完成标准: 形成“候选点 × 缺陷类型 × 预期影响”列表。
   - 判停条件: 无，继续。

4. **做跳过与乱序验证**
   - 动作: 在授权测试环境直接调用后续步骤接口、先退款再支付、先发货再付款、跳过审批节点；观察服务端是否重新校验前置状态。只在测试数据上进行。
   - 完成标准: 每个关键迁移都有“合法路径/非法路径/实际结果”记录。
   - 判停条件: 若操作会触发真实资金、真实库存或真实通知，立即停止，改用测试环境。

5. **做金额、数量与资格边界验证**
   - 动作: 尝试 0、负数、小数精度、最大整数、最小货币单位、重复条目、超长列表；替换商品、币种、优惠券归属、收款方；验证服务端是否重新计算金额与资格。
   - 完成标准: 每个边界值都有“预期拒绝/实际结果”，并记录账务或库存前后值。
   - 判停条件: 无，继续。

6. **做重放与幂等验证**
   - 动作: 重放支付回调、退款申请、优惠券领取、积分兑换、短信发送；检查幂等键是否存在、作用域是否足够、重复请求返回原结果还是再次产生副作用、回调是否验签并校验状态。
   - 完成标准: 每个可重放入口都有“重放次数—副作用次数—幂等键”证据。
   - 判停条件: 若重放会影响真实用户或真实账务，停止并改在隔离环境复现。

7. **做受控并发验证**
   - 动作: 对同一优惠券、最后库存、余额提现、积分兑换、审批节点发起同时到达的请求；记录成功数、失败数、最终余额/库存、数据库约束与事务日志。仅在授权测试环境，使用自己控制的账号与数据。
   - 完成标准: 每条不变量都有并发前后的对照值，能判断是否存在“读—判断—写”窗口。
   - 判停条件: 若无法保证请求同时到达或无法观察最终状态，标注“未验证”，不据顺序测试下结论。

8. **检查频率限制与滥用面**
   - 动作: 验证短信/邮件是否按手机号/邮箱、IP、账号、设备多维限速；验证码是否绑定目标与动作、是否一次性、是否可预测、是否服务端校验；检查目标枚举与资源消耗。
   - 完成标准: 形成“通道 × 限速维度 × 验证码绑定 × 滥用成本”表。
   - 判停条件: 若发送会触达真实号码或产生费用，停止主动触发，改为配置与代码核查。

9. **检查数据一致性与补偿**
   - 动作: 检查异步任务、消息重投、对账任务、补偿逻辑是否幂等；确认重复消费、乱序消费、部分失败是否会造成重复入账或状态回退。
   - 完成标准: 每个异步链路都有“重复/乱序/部分失败”的结果说明。
   - 判停条件: 无，继续。

10. **汇总证据、定性与修复建议**
    - 动作: 把问题归为设计缺陷、实现缺陷或配置问题；给出影响、复现条件、证据、修复层级（规则/状态机/接口原子性/配置）与复测方法。
    - 完成标准: 输出可直接排期的业务逻辑问题清单，每条都对应一条不变量或状态迁移。
    - 判停条件: 无，结束。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill
- 需要通用 TOCTOU 时间窗建模、类型混淆、沙盒逃逸分析：走 `logic-and-isolation-bugs`。
- 问题本质是“无权访问他人对象”：走 `access-control-and-idor`，不要把它写成业务逻辑绕过。
- 登录、会话、JWT、OAuth/SAML 配置问题：走 `auth-session-and-federation-security`。
- 接口批量赋值字段过滤、GraphQL introspection、Swagger 暴露：走 `api-and-interface-security`。
- 可疑邮件内容、附件、退信：走 `email-trust-boundary`。
- 没有测试环境、没有测试账号、不能观察账务或库存最终状态：只能输出待验证清单，不能断言存在竞态或流程绕过。
- 未取得授权，或验证会动用真实资金、真实库存、真实短信通道：不得执行主动测试。
- 目标是实际盗刷、薅羊毛、恶意轰炸：不属于防御性审查范围。

### 作者在书中警告的失败模式
- 本清单未覆盖“每个接口都有校验，所以流程安全”的误判：业务漏洞常来自步骤组合与状态迁移，而不是单个接口。
- 本清单未覆盖“顺序执行通过就没有竞态”的失败：竞态只在同时到达时暴露，且可能被网关或锁偶然串行化。
- 本清单未覆盖“只改前端金额、后端会重算”的假设：必须实际验证服务端是否重算，而不是相信设计文档。
- 本清单未覆盖“重放一次没出问题就认为幂等”的失败：幂等键作用域、重复次数与并发重放都要验证。
- 本清单未覆盖“只按 IP 限速”的失败：代理池、多账号、多目标会绕过单维限速。
- 本清单未覆盖“异步补偿一定可靠”的失败：消息重投、乱序与部分失败都可能造成重复入账。

### 作者的盲点 / 时代局限
- 本清单未覆盖分布式事务、Saga、事件溯源与最终一致性下的完整正确性证明。
- 本清单未覆盖风控与反欺诈模型的绕过评估，这类问题需要业务数据与模型侧证据。
- 本清单未覆盖真实资金链路的清算、结算、通道对账与银行侧差异。
- 本清单未覆盖多租户、多币种、多时区、税务与汇率带来的业务规则组合复杂度。
- 本清单未覆盖业务规则频繁变更导致的回归风险，需配合持续测试与配置管理。

### 容易混淆的邻近方法论
- `logic-and-isolation-bugs`：提供 TOCTOU 与隔离的通用模型，本 skill 提供业务状态机与不变量清单。
- `access-control-and-idor`：判断“谁能操作”，本 skill 判断“操作是否按业务规则发生”。
- `api-and-interface-security`：检查接口层认证、输入输出与限流，本 skill 检查跨步骤的业务一致性。
- `auth-session-and-federation-security`：检查验证码作为认证因子是否可靠，本 skill 检查验证码作为业务动作凭证是否可滥用。
- `email-trust-boundary`：判断邮件是否可信，本 skill 只处理邮件/短信通道的频率与重放。
- `data-backup-recovery-discipline`：处理数据可恢复性，本 skill 处理在线业务的数据一致性与对账。
