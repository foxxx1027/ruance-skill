# C++ 二进制语义还原

## R — 原文 (Reading)

> 在逆向分析过程中，理解一段数据需要首先判断这段数据是有符号整数还是无符号整数。但是仅仅根据数据所在的汇编指令很难确定是有符号整数还是无符号整数。需要查看指令或者已知的函数如何操作此内存地址，根据操作方式或者函数相关定义得出该地址的数据类型。
>
> — 魏强、武泽慧, 第2章 2.3.1 整数

---

## I — 方法论骨架 (Interpretation)

这套方法把反汇编阅读从“逐条指令猜”变成“先认编译器模板，再回填高级语义”。五条还原线：

1. **数据类型**：先定宽度与符号性（最高位/补码、比较与乘除的有符号版本），再判聚合结构——地址连续且元素类型一致才判为数组；字符串先定首地址，再按 ASCII 的 1 字节 0 或 Unicode 的 2 字节 0 找结束。
2. **表达式**：编译器会把慢指令换成等价快指令。乘 2 的幂变 shl，除常量变 magic number 乘法取高位加移位，减法用补码加法，常量表达式在编译期折叠；看到变形要反向映射，而不是照字面读。
3. **控制语句**：数跳转。do 用 1 条条件跳转，while 用 1 条条件加 1 条无条件，for 用 3 条（初始化、步长、回跳）；if 是 1 条条件跳转，if-else 多一条尾部 jmp；分支多且条件线性时，范围检查加间接跳转就是 switch 跳转表。
4. **函数**：按栈帧四段读——保存寄存器并开辟栈空间、初始化局部区（Debug 版常填 CC）、功能指令、恢复并 retn；32 位 cdecl 下 EBP+8 起是参数，eax 是返回值，调用后 add esp 平衡栈。
5. **优化**：识别常量传播、变量替换、代码外提、循环内外层调整等痕迹，解释“源码里的变量为什么消失”，并补回等价表达式。

核心判断：单条指令不携带语义，类型与结构由“谁在如何使用这个地址”决定；先识别编译器模式，再映射回高级语义。

## A1 — 书中的应用 (Past Application)

### 案例 1: 基本数据类型逆向——int、int[]、char、char[] 的栈布局验证
- **问题**: 源码里 int、int 数组、char、char 数组混在一起，二进制中只剩一串 `[ebp-x]` 的内存访问，如何确认各变量的类型、宽度与数组边界。
- **方法论的使用**: 用 OllyDbg 查看赋值指令执行后的栈空间，比较各值的宽度与排列是否连续、元素类型是否一致；再用 IDA 静态反汇编，看它把栈位置自动标注成 var_4、var_10 等变量。
- **结论**: int 占 4 字节、char 占 1 字节；数组元素在内存中连续且类型一致，可据此从内存布局反推变量类型与数组范围。
- **结果**: 验证了“先宽度与符号性、再聚合结构”的类型还原路径，OllyDbg 与 IDA 结果一致。

### 案例 2: 控制语句逆向——if、switch、do、for 的跳转模板
- **问题**: 同一程序同时包含 if、if-else、两个 switch（有/无 break）、do 和 for，如何从跳转指令区分它们并切出各组成部分。
- **方法论的使用**: 逐段数跳转并看位置：if 为 cmp+jnz；if-else 为 cmp+je 加尾部 jmp；switch 分支少时是连续 cmp+je，分支多且条件线性时改为一次查表间接跳转；do 在循环体末尾 cmp+jl，只有 1 条跳转；for 由初始化、jmp、cmp+jge、inc 与回跳 jmp 共 3 条跳转组成。
- **结论**: 跳转指令的条数与位置可以判定控制语句类型，并据此切出条件、循环体、步长与初始化段。
- **结果**: 在 OllyDbg 中逐段得到模板，再用 IDA 控制流图复看，结论一致。

### 案例 3: 函数逆向——average 与 str_copy 的栈帧、传参与返回值
- **问题**: average(a,b,c) 与 str_copy(dst,src) 的参数如何传入、局部空间如何布局、返回值放在哪里、调用后栈如何平衡。
- **方法论的使用**: 按栈帧四段阅读：push ebp / mov ebp,esp / sub esp 建栈帧，用 CC 初始化局部空间；average 从 EBP+8、EBP+C、EBP+10 取三个参数，结果经 eax 返回；str_copy 从 EBP+8、EBP+C 取两个指针并按 `\0` 循环复制；返回后 main 用 add esp 平衡栈。
- **结论**: 32 位 cdecl 从右向左压栈，EBP+8 起依次是参数，eax 承载返回值，调用方负责栈平衡。
- **结果**: 成功还原两个函数的栈帧结构、参数位置、返回值寄存器与调用后的栈平衡操作。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 拿到 Release 版二进制，变量消失、语句顺序改变、代码被内联，逐条读汇编读不出原意。
2. 源码里明明是除法，反汇编却出现 `imul` 加右移，怀疑自己看错或程序被篡改。
3. 分不清一段循环是 do、while 还是 for，或把 switch 的跳转表误判成复杂 if 链。
4. 函数边界被内联、尾调用或代码拆分打乱，不知道该从哪里开始分析一个函数。
5. 变量类型判错（signed/unsigned、宽度、数组长度），导致后续比较、溢出或边界判断全错。

### 语言信号 (用户的话里出现这些就应激活)

- “Release 版反汇编看不懂 / 变量怎么没了”
- “这里明明是除法，怎么变成乘法和移位了”
- “这是 for 还是 while / 跳转表怎么认”
- “函数边界找不到，是不是被内联了”
- “这个变量是 int 还是 unsigned / 数组有多大”
- 英文: "decompile this binary", "magic number division", "signed or unsigned", "jump table", "where does this function start", "stack frame recovery"

### 与相邻 skill 的区分

- 与 `reverse-engineering-workflow` 的区别: 后者在动手前框定分析目标与产出边界；本 skill 是在边界之内，把具体指令序列还原成高级语义。
- 与 `vuln-debugging-and-breakpoints` 的区别: 后者关注在哪里下断、如何单步与观察运行时状态；本 skill 关注静态指令模式的语义解释，动态调试只作为交叉验证手段。
- 与 `crash-to-root-cause` 的区别: 后者从已有崩溃点回溯漏洞根因；本 skill 不预设崩溃，只回答“这段汇编对应什么 C++ 语义”。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **确定分析单元与函数边界**
   - 完成标准: 给出入口地址、出口（retn/尾调用）与调用点列表；边界不清时按连续控制流划成功能代码块。
   - 判停条件: 若目标为强混淆、虚拟化保护或 JIT 动态生成代码，停止本流程，先脱壳/反混淆或改用运行时手段。

2. **读栈帧骨架**
   - 完成标准: 标出 push ebp / mov ebp,esp / sub esp 的范围、局部空间大小与初始化方式（是否填 CC），并记录 esp、ebp 与返回地址的位置。

3. **定参数与局部变量**
   - 完成标准: 列出每个 EBP+8、EBP+C、EBP+10… 的参数位置与调用方压栈顺序；对每个 `[ebp-x]` 给出宽度、符号性、是否为数组/字符串。
   - 判停条件: 若同一地址被不同宽度或不同符号方式访问，标记为类型歧义，跳到步骤 7 用运行时证据裁决。

4. **还原表达式**
   - 完成标准: 对每个结果寄存器写出等价的高级表达式；能解释 shl/add 组合、magic number 乘法加移位、CDQ/idiv、补码减法与常量折叠各自的来源。
   - 判停条件: 若表达式依赖未知函数返回值，先按步骤 7 确认该函数的输入输出约定，再回到本步。

5. **还原控制结构**
   - 完成标准: 按跳转条数标出 do（1 条条件跳转）、while（1 条件+1 无条件）、for（3 条并切出初始化/步长/循环体）；对多分支结构标明是 if 链还是范围检查加跳转表。

6. **标注优化痕迹**
   - 完成标准: 逐项标出常量传播、变量替换、不可达代码删除、代码外提、循环内外层调整；对“源码里有、汇编里没有”的变量给出被消除的解释。

7. **交叉验证**
   - 完成标准: 用调试器核对 esp、ebp、返回地址、关键参数与分支走向，确认静态推断与运行时一致；换一个优化等级或编译器复现同一模式。
   - 判停条件: 静态推断与运行时不一致时，以运行时证据为准，回到步骤 3 重新定类型与参数。

8. **输出语义摘要**
   - 完成标准: 交付变量类型表、表达式映射、控制结构图、函数签名/功能说明、优化痕迹清单与仍不确定的项；不确定项必须显式标注，不得当作已还原。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **有源码或完整符号（PDB/DWARF）**: 直接读源码或符号表即可，按汇编反推类型与控制结构是重复劳动，且容易引入误判。
- **ARM64 或非 x86 调用约定**: 本书的栈帧、EBP+8 参数、eax 返回值、跳转模板都以 32 位 x86 cdecl 为基准；ARM64、x64 SysV/Windows 快速调用、vectorcall 的寄存器传参与栈布局不同，必须重新校准模式库。
- **JIT 或动态生成代码**: 没有稳定的静态函数边界与编译器模板，代码在运行时才生成，静态模式匹配会落空，应改用运行时跟踪或插桩。
- **强混淆或虚拟化保护**: 花指令、代码变形、VMProtect 类虚拟化会破坏跳转结构与栈帧模式；先走脱壳/反混淆流程，再回来做语义还原。

### 作者在书中警告的失败模式

- **只凭汇编指令判断 signed/unsigned（ce-A07）**: mov/add 等指令不携带符号语义，同一段内存可被不同指令解释。若仅凭寄存器宽度或指令形式定型，就会选错 jl/jb、idiv/div，把负数当大整数比较，导致边界检查在负数输入下失效。警示信号：同一地址被不同宽度或符号方式访问、反汇编出的比较指令与源码语义对不上。
- **把优化结果当源码原意**: 把 magic number 乘法误读成乘法或哈希、把常量折叠后的立即数当成源码原本就写死的值、把内联后的代码硬划成独立函数，都会得出错误算法。
- **从函数中间开始读**: 不先读栈帧骨架就从功能指令入手，容易把局部变量与参数位置算错，后续类型与表达式全部偏移。
- **忽略调用约定差异**: 把 stdcall 的栈平衡当成 cdecl，或把 x64 的寄存器传参套到 32 位栈帧上，会错误标注参数个数与返回地址位置。

### 作者的盲点 / 时代局限

- 全书示例以 **32 位 x86 + MSVC（Debug/Release）** 为主；对 x64、ARM64、Apple Silicon 与 GCC/Clang 的代码生成差异未展开，模式库不能直接迁移。
- 教学案例被裁剪成最小可复现程序，真实软件中的宏、模板、内联、异常表、虚表、RTTI 与多编译单元优化被大幅简化；真实 C++ 二进制的语义还原工作量远高于书中示例。
- 编译器版本与优化选项会改变具体指令序列；书中归纳的是模式而非固定字节串，遇到不同工具链必须用“正向构造—逆向验证”重新校准。
- 对 C++17/20 之后的新特性、LTO、PGO 与安全编译选项（CFG、GS）交织后的代码形态覆盖不足。

### 容易混淆的邻近方法论

- `reverse-engineering-workflow`: 管“为什么逆、逆到什么程度”，本 skill 管“这一段具体是什么语义”。
- `vuln-debugging-and-breakpoints`: 管调试动作与断点策略；本 skill 的运行时验证只是辅助，不替代静态模式识别。
- `crash-to-root-cause`: 从崩溃反向定位缺陷；本 skill 不依赖崩溃样本，做的是正向语义翻译。
- `anti-debugging-and-unpacking`: 处理保护与入口恢复；遇到加壳/混淆时先由它清理战场，再进入本 skill。
