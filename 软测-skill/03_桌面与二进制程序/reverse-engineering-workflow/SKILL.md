# 逆向分析的目标、流程与产出

## R — 原文 (Reading)

> 本质上来讲，软件逆向的输入是被逆向的程序，输出是分析的结果。被逆向的程序不一定是完整的可执行程序，可以是程序片段，也可以是常用的库文件，如DLL等。分析结果由分析目标决定，通常由源代码、图表、文档、密钥等关键数据组成，如图1-1所示。
>
> — 魏强、武泽慧，第1章 1.1.1 基本概念

---

## I — 方法论骨架 (Interpretation)

1. 逆向不是“把二进制变回源码”，而是一次有输入、有交付物的信息恢复任务：输入是程序（可执行文件、DLL 或片段）加上分析目标。
2. 目标先决定输出形态——可能是一段类 C 代码、一张调用图、一份行为文档、一个密钥或一个漏洞点；输出确定后，分析深度才有验收标准。
3. 从二进制到结论要经过一条逐级抽象的链：解码/反汇编 → 中间表示（三地址码、SSA 等）→ 数据流分析（数据从哪来、怎么传播）与控制流分析（函数调用、跳转与执行逻辑）→ 高级抽象（类 C 代码、图表、文档）。
4. 链条上每一段都依赖前一段的产物：没有可靠反汇编就没有可用 CFG，没有 CFG 就难以做跨函数数据流；分析不深往往不是工具不行，而是中间产物缺失。
5. 漏洞工作的四个环节对逆向产物的需求不同：挖掘要缩小目标范围（函数清单、攻击面、调用图）；分析要定位成因（危险操作、数据来源、基本块级路径）；利用要定位可利用点（指令地址、可控数据与可达性）；防护要确认修复位置（补丁前后差异、被修改的检查）。
6. 做到哪一层可以用最小充分原则：指令级、基本块级、函数级、模块级、全程序级，选能满足交付物的最浅一层，而不是默认全程序还原。
7. 校准逆向识别能力靠正向—逆向闭环：自己写最小 C/C++ 代码，用相同编译器与优化等级编译，再反汇编对照，记录编译器实际生成的模式；换架构或优化等级时重跑这个闭环。
8. 这个闭环也解释了为什么源码结构不能逐项搬到二进制里：优化后只剩语义等价，不是逐句对应。

## A1 — 书中的应用 (Past Application)

### 案例 1: “Hello, World!”程序的 main 函数定位

- **问题**: 用 Visual Studio 编写的 “Hello, World!” 编译后，OllyDbg 首先断在程序入口点，但入口点并不是 `main`。如果把入口当成 `main`，就会把 CRT 启动代码的初始化误认为用户程序逻辑，也解释不了 `argc/argv` 从哪来。
- **方法论的使用**: 作者先按“目标决定产物”把任务定为“找到 `main` 的反汇编入口”，而不是“还原整个程序”；再梳理 `mainCRTStartup` 的启动链（`GetVersion`、堆初始化、`GetCommandLineA`、`_setargv`、`_setenvp`），据此在 OllyDbg 中从入口点向下找到 `call GetCommandLineA`，其后连续三次压栈后的 `call` 即 `main`；进入该 `call` 查看反汇编，并用 IDA 载入同一程序对照。
- **结论**: `main` 不是程序执行的第一条指令，它前面有调用者；`mainCRTStartup` 负责参数、环境变量、全局数据与浮点寄存器等初始化，再把 `argc/argv/environ` 压栈调用 `main`。因此定位 `main` 应利用启动链的固定特征，而不是从入口逐条盲读。
- **结果**: OllyDbg 与 IDA 两种工具都成功定位到 `main` 并展示了其反汇编代码，结果一致。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 用户手里只有一个 exe、DLL 或程序片段，需求是“逆一下/分析一下”，但没有说明要交付什么，也没有说分析到函数级还是指令级。
2. 用户问“逆向该从哪里开始”“要不要把源码还原出来”“分析到什么程度算够”，需要一个可验收的路线而不是工具清单。
3. 用户在做漏洞工作，需要判断挖掘、分析、利用、防护四个环节各自该向逆向要什么产物，避免一上来就全程序还原。
4. 用户想建立或校验自己的逆向识别能力，愿意用“自己写代码—编译—反汇编对照”的方式做实验。
5. 用户已经拿到反汇编，但不确定当前停留在链条的哪一段、下一步该补中间表示还是直接下结论。

### 语言信号 (用户的话里出现这些就应激活)

- “把这个 exe/DLL 逆一下”“帮我分析这个程序”
- “逆向从哪里开始”“要还原成源码吗”“分析到什么程度算够”
- “漏洞挖掘/分析/利用各需要什么逆向结果”
- “正向写代码再编译逆向验证”“怎么校准汇编识别”
- “reverse this binary”“where do I start reverse engineering”
- “do I need to recover the full source”“how deep should the analysis go”

### 与相邻 skill 的区分

- 与 `vuln-analysis-strategy` 的区别: 对方处理的是**已经有崩溃、补丁或情报线索**之后的取证与排查路线；本 skill 处理**还没有具体线索**时，如何把“逆一下”框定成可交付产物和分析深度。
- 与 `cpp-semantic-recovery` 的区别: 对方负责**具体语义还原**——给定一段汇编，判断它是数组、除法、循环还是虚函数调用；本 skill 只决定“要不要还原、还原到哪一层、产出什么”，不负责逐条语义映射。
- 与 `anti-debugging-and-unpacking` 的区别: 对方负责**保护与入口**——识别反调试、脱壳、找 OEP；本 skill 是总流程与目标框定，遇到加壳或反调试时先转过去恢复可分析代码，再回到本流程。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **把任务改写成一句可验收的问题**
   - 完成标准: 写出“本次要交付什么、给谁用、什么算完成”，例如“找出注册校验使用的常量与比较分支”，而不是“逆一下这个 exe”。
2. **判断任务属于哪类工作与哪个环节**
   - 完成标准: 标注为破解、恶意分析、相似性比对、漏洞挖掘、漏洞分析、利用或防护之一，并列出该环节需要的逆向产物（函数清单、调用图、危险点、指令地址、修复位置等）。
3. **选择最小充分的分析深度**
   - 完成标准: 明确停在指令级、基本块级、函数级还是模块级，并写一句选择理由。
   - 判停条件: 若目标只是拿密钥、常量、字符串或算法片段，则跳过完整控制流还原与高级抽象，定位到数据与相关基本块即停。
   - 判停条件: 若目标只是确认漏洞可利用点，则停在指令级地址与可达性，不要求还原类 C 代码。
4. **检查分析前提是否成立**
   - 完成标准: 确认样本是否加壳、是否有反调试或花指令、能否获得可靠反汇编与 CFG。
   - 判停条件: 若静态结果明显错位或程序拒绝调试，先转到 `anti-debugging-and-unpacking` 恢复入口与可分析代码，再回到步骤 5。
5. **沿“反汇编 → 中间表示 → 数据流/控制流 → 高级抽象”推进，并保留中间产物**
   - 完成标准: 每一步都有可复查的记录（函数边界、调用图、关键数据结构、危险基本块），且能对应步骤 1 的交付物。
   - 判停条件: 若某段语义不影响交付物，标记“未展开”即可，不继续下钻。
6. **对不确定的语义做正向—逆向校准**
   - 完成标准: 写出最小等价 C/C++ 代码，用相同编译器与优化等级编译并对照汇编；差异能解释，或把该模式记入个人样本库。
7. **按交付物验收并记录证据链**
   - 完成标准: 交付物能回答步骤 1 的问题；每条结论附地址、函数或路径证据；列出仍未确定的前提与残余风险。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已有源码或可编译工程: 直接做源码审计或补丁 diff，二进制逆向只会增加噪声。
- 只需要字符串、配置、资源或简单常量: 用 `strings`、资源查看或格式解析即可，不必启动完整逆向流程。
- 目标是纯网络协议或流量分析: 应走协议逆向或流量分析，不以二进制反汇编为主线。
- 只有崩溃日志、补丁或一条情报，没有待框定的二进制分析任务: 走 `vuln-analysis-strategy` 的取证路线。
- 只需观察程序行为（联网、文件、注册表）而不需要静态产物: 动态行为分析更直接。

### 作者在书中警告的失败模式

- **把“还原完整源码”当默认目标**（ce-A04）: 编译丢弃高级语义，优化与加密进一步破坏结构，逐行还原无法验证；表现为没有定义问题、反复重命名变量却不推进结论。正确做法是先定输出形态与验收标准。
- **把 main 当作程序执行的第一条指令**（ce-A06）: 跳过 CRT 启动代码，导致参数来源、全局对象构造、security cookie 等现象无法解释；main 有参数就必然有调用者。
- **直接相信反汇编器输出而不核对解析前提**（ce-A08）: 花指令会让反汇编整体错位，函数边界与 CFG 被破坏而工具不会主动报错；出现无效指令、孤立块或“动态正常而静态图不合理”时应怀疑被干扰。
- **拿源码结构去二进制里逐项对照**（ce-A09）: 优化会折叠常量、删除不可达代码、替换变量，源码与二进制是语义等价而非逐句对应；找不到某个变量不等于分析遗漏。

### 作者的盲点 / 时代局限

- 示例以 32 位 x86 为主，64 位与 ARM64 的调用约定、栈帧和寄存器角色不同，`main` 定位特征不能直接照搬。
- 教学案例被裁剪成最小可复现程序，真实软件中的宏、模板、内联、异常表与优化会显著改变编译器模式。
- 书中假设分析者能获得可靠的反汇编、中间表示或插桩能力；对加壳、JIT、动态生成代码覆盖不足，这些目标要先解决保护与入口问题。
- 静态分析视角偏乐观，低估真实二进制上的建模成本，也较少覆盖多线程竞争、跨请求状态机等难以用单条路径解释的漏洞。

### 容易混淆的邻近方法论

- `vuln-analysis-strategy`: 已有线索后的取证路线，对比本 skill 的“无线索任务框定”。
- `cpp-semantic-recovery`: 具体语义还原，对比本 skill 的“是否还原、还原到哪层”。
- `anti-debugging-and-unpacking`: 保护识别与入口恢复，是本 skill 在步骤 4 的前置分支。
