# 从崩溃到根因：通用逆推与溢出点量化

## R — 原文 (Reading)

> "断下后，查看栈回溯，以定位是哪个函数调用到崩溃函数的。"
>
> — 林桠泉，《漏洞战争：软件漏洞分析精要》第 2 章 2.4.5

> “程序异常发生的位置通常离漏洞函数很远，当溢出发生时，栈帧往往也会遭到严重的破坏，这会给动态调试制造很大的困难。”
>
> “为了定位漏洞函数，我们需要回溯堆栈。如果在溢出前漏洞函数调用过其他的函数，堆栈中就有可能保存着返回地址，找到这个地址也就找到了漏洞函数。”
>
> — 王清 等，《0day安全：软件漏洞分析技术（第二版）》第 25 章 25.3.1；第 31 章 31.3

---

## I — 方法论骨架 (Interpretation)

这套框架合并自《漏洞战争》的六条通用崩溃定位路径与《0day安全》的溢出定位流程：前者回答"崩溃点不是根因时如何逆推"，后者补上"栈已毁、还要精确偏移与触发条件时如何造现场、停下来、量出来"。两者共享同一条主线——**先让崩溃可重复、可观察，再在破坏发生前取得有效中断，最后用可推翻的对照实验把"可疑"变成"必要"**。

统一框架分六层，按顺序推进：

**第 0 层：可复现性与受控崩溃。** 去掉 shellcode 容器与可执行载荷，用可识别字节（`0x41`/`0x24`/`0x0c`）填充，固定输入与环境，让 EIP/EBP/ESP/SEH 至少一项呈现输入指纹。偶发崩溃不算定位起点。

**第 1 层：读指纹分类。** 返回地址被规律字节覆盖 → 栈溢出；SEH 处理函数指针被改写 → SEH 覆盖；破坏对象是块首/空闲链表/虚表 → 堆类问题，转 `heap-vulnerability-locating`。分类决定后续路径，不可跳过。

**第 2 层：在破坏前停住。** 已知候选函数就在入口下断；不知道函数就把填充改成 `0xFFFFFFFF` 一类非法地址，制造畸形 RetAddr 崩溃；仍停不住就对可疑缓冲区下硬件写入断点。配套前置配置：模块未加载用 `sxe ld:<模块>`、复合进程 `.childdbg 1`、地址会变则一律用"符号+偏移"或"模块基址+偏移"、验证字段被覆盖用 `ba w4 <addr>`。

**第 3 层：五条互补定位路径**（按现场可用性选择，不要求全用）：

1. **栈回溯逐层上推**：从崩溃点向上找最近的、落在目标模块代码段的返回地址，换算成"基址+偏移"，确认其前一条是 CALL，再找到该 CALL 所在函数的入口；检查崩溃指令用到的寄存器/内存在本函数内有无初始化，没有就继续上推，直到最初生成异常值的那条指令。
2. **条件记录断点**：当断点会被成百上千次调用淹没（索引分发器、频繁虚表项）时，不中断，改为把关键参数逐次写入日志；**日志中最后一次记录即崩溃那次**。
3. **排除法与状态对照**：按 F7 跟入而不是 F8 跳过；在每个候选 CALL 前后对照 SEH 链、返回地址、关键指针，哪个调用后状态跃变，破坏源就在哪里；"执行完它就要 `POP RETN` 而此前一直正常"是强判据。递归场景要记录命中次数。
4. **硬件写断点直达写指令**：在 `SUB ESP,...`/分配之后对缓冲区附近下写断点，等第一次写命中，命中的 `MOV [EDX],CL` 一类指令就是写点。
5. **消元与反证**：数据流上先剔除来源已知且稳定的分量，只追来源不明者并画传播图；栈已毁时用样本中硬编码的 ROP 指令地址作锚点反向追踪；怀疑某行为根因时做增删对照，删掉即不崩、结构不残留，才算必要条件。

**第 4 层：量化。** 在写指令处读目的地址得到缓冲区起点，在栈中定位返回地址/SEH 句柄，两者相减得到精确覆盖长度；有路径前缀、拼接或 ASCII→Unicode 转换时先扣除前缀、按内存实际字节数重算。

**第 5 层：条件化与交接。** 回到漏洞函数序言读"缓冲区多大、何时申请、前置检查是什么、循环初值是否越界"，把触发写成"一条充分条件 + 若干必要条件"，每条对应 POC 的一个字段；同时记录返回瞬间哪个寄存器稳定指向可控缓冲区，作为跳板选择的输入。

贯穿全程的纪律：**崩溃点是受害者，不是凶手**；不要停在"漏洞叫什么、用了哪个对象"这一层。PoC 恰好用到的对象名往往只是巧合，要区分"触发漏洞的偶然表象"与"导致漏洞的必要条件"。

## A1 — 书中的应用 (Past Application)

### 案例 1: CVE-2012-1876（MSHTML 表格堆溢出）— 逐层上推值的来源
- **来源**: 《漏洞战争》第 3 章 3.2 / 3.5.5。
- **问题**: 崩溃点 `CTableColCalc::AdjustForCol` 用到的 `edi` 在本函数内找不到初始化代码。
- **方法的使用**: `kb` 打印调用栈 → 发现 `edi` 来源于 `esi` → 继续上溯到 `CTableLayout::CalculateMinMax` 中的 `ebx+54h`（span 属性）。
- **结论/结果**: 真正决定越界的是 span 被设成异常值，而非崩溃函数本身；由此定位到漏洞函数并解释了"为什么崩在下游"。

### 案例 2: CVE-2012-0774（Adobe TrueType 整数溢出）— 记录断点还原虚拟指令
- **来源**: 《漏洞战争》第 4 章 4.3.2。
- **问题**: 崩溃发生在按索引分发的虚拟指令处理函数上，直接下断会被轮流调用上千次淹没。
- **方法的使用**: 在分发函数上设条件记录断点，记录每次的指令索引与虚拟栈顶 `vm_esp` 的前后值，再与 TTF 字节码对齐。
- **结论/结果**: 异常值 `0x40000001` 由 `NPUSHW / MUL / ADD / JROT` 一串指令循环累加而来；在不理解整张指令表的前提下还原了运算路径。

### 案例 3: MS08-067（NetpwPathCanonicalize）— 排除法、地址差偏移与三段式条件
- **来源**: 《0day安全》第 31 章 31.3。
- **问题**: 同一函数在两年前已被 MS06-040 修过，旧"拼接处溢出"假设失效；循环体里有边界检查，却仍能溢出。
- **方法的使用**: 静态分析定位到 `RemoveLegacyFolder`；用排除法确认问题在该调用内；以 `wcscpy` 返回地址与 `prefix_slash` 的差值 `0x12F634 - 0x12F54E = 230` 实测覆盖长度；把成功触发写成"前向搜索越过 `Buff_OF` 起点"一条充分条件 + "至少两个连续 `..\`""第二个 `..\` 后有足够字符"两条必要条件。
- **结论/结果**: 根因是循环初始化 `lea eax,[edi-2]` 越界，循环体内的检查已失去意义；最小 POC 只验证条件，加长后才覆盖返回地址，最终绕过 XP SP2 的 GS。

### 案例 4: 超长 URL（绿坝）— 受控崩溃 + 硬件写断点量出 1032 字节
- **来源**: 《0day安全》第 32 章。
- **问题**: 完整 POC 会把控制流交给 .NET 控件，崩溃现场被 shellcode 执行污染，读不出覆盖模式。
- **方法的使用**: 先做减法去掉 `<object>` 控件，只留超长 URL，让程序跳向 `0x24242424` 并据 EBP/ESP 判定栈溢出；回溯可疑地址 `0x02852B4A` 换算为 `SurfGd.dll + 0x2B4A`，确认 CALL 后找到入口下断；再在 `SUB ESP,0x404` 后对栈顶下内存写断点，命中 `MOV BYTE PTR DS:[EDX],CL`。
- **结论/结果**: EDX=`0x03E3EC68` 为缓冲区起点、返回地址=`0x03E3F06C`，差值 `0x408 = 1032` 即精确覆盖长度；复制循环只处理 `%` 转义、从未检查容量。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 有可复现样本，崩溃了，但不知道漏洞在哪个函数；EIP/SEH 被 `0x41414141`/`0x0c0c0c0c` 覆盖。
2. 崩溃发生在系统 DLL/运行时库（`ntdll!RtlpFreeHeap`、`jscript.dll`、`libc`），Call Stack 全是非法地址，不知如何回到自己的代码。
3. 断点设了不生效，或一设就被成百上千次调用淹没；重载进程后断点全部失效。
4. 已定位到可疑函数，但回答不了"缓冲区多大、到返回地址多少字节、触发要满足哪些条件"。
5. 崩溃表达式由多个变量共同决定，无法判断哪个分量失控；或顺着崩溃点跟了很久没有产出。
6. 栈已被破坏、栈回溯不可信，需要替代切入点（ROP 常量、硬件写断点）。
7. 同一函数旧系统能打、新系统失效，想判断"旧点被堵"还是"出现新根因"；或本地与远程结果不一致。

### 语言信号 (用户的话里出现这些就应激活)

- "从崩溃怎么找到漏洞函数 / crash to root cause / find the vulnerable function"
- "崩在 ntdll 里怎么办 / 崩在系统库里 / 栈回溯全是垃圾值"
- "EIP 被 41414141 覆盖了，漏洞函数到底在哪"
- "断点为什么没生效 / 一设断点就被不停断下"
- "怎么量覆盖长度 / 到返回地址偏移多少 / 缓冲区多大"
- "这个根因到底在哪，跟了很久没进展 / 十次里只崩一次"

### 与相邻 skill 的区分

- 与 `vuln-analysis-strategy`: 后者做"选哪条路"的前置判断；本 skill 是执行体，默认已经决定"要定位根因"。
- 与 `heap-vulnerability-locating`: 破坏对象是堆块头、空闲链表、页堆分配记录时走后者；本 skill 处理通用崩溃（栈、SEH、脚本引擎、UAF 等）。
- 与 `patch-diff-and-source-analysis`: 手上已有补丁/新版本/源码时优先后者，从修复反推比从崩溃逆推快得多。
- 与 `locate-by-known-anchor`: 后者用字符串/符号名/导出表**跳步**落到函数；本 skill 在没有锚点、只能从现场逆推时使用，二者可在锚点到达后用断点与偏移测量接续。
- 与 `vuln-debugging-and-breakpoints`: 后者回答"怎么停、怎么看"；本 skill 回答"看到什么算定位成功"。
- 与 `reverse-driver-and-unknown-structure`: 内核驱动与无文档结构逆向走后者。
- 与 `win-stack-overflow-exploit`: 本 skill 的终点是漏洞函数 + 写指令 + 偏移 + 触发条件；"怎么布置 payload 控 EIP"转后者。

## E — 可执行步骤 (Execution)

1. **固定环境并造受控崩溃**
   - 记录目标版本/补丁级别、输入形式、模块基址；去掉 shellcode 容器，用可识别字节填充。
   - 完成标准: 同一输入重复运行，崩溃点与异常类型稳定，寄存器/栈中至少一项呈现输入指纹。
   - 判停条件: 若依赖网络时序或缓存导致偶发，先消除环境变量；仍不稳定则停止定位，转复现工程，**不能用偶发崩溃算偏移**。

2. **读崩溃指纹并分类**
   - 观察 EIP/EBP/ESP、SEH 链、栈顶内容与目标模块保护状态。
   - 完成标准: 能用一句话定性，如"栈溢出覆盖了返回地址"或"SEH 处理函数指针为 `0x0c0c0c0c`"。
   - 判停条件: 若破坏对象是堆块头、空闲链表、虚表或内核对象 → 停止本流程，转 `heap-vulnerability-locating` 或对应内核/堆利用 skill。

3. **争取破坏发生前的第一次有效中断**
   - 已知候选函数：先加载目标模块再 attach，在入口下断；不知道函数：用非法 RetAddr 制造畸形崩溃；仍停不住：在可疑缓冲区下硬件写断点。
   - 完成标准: 断点命中时栈帧仍可读，能定位当前函数/调用点，而不是只看到跑飞的 EIP。
   - 判停条件: 若只能在崩溃后 attach、栈已完全破坏，不要相信自动 Call Stack；改用畸形 RetAddr 或直接进步骤 6。

4. **栈回溯，把"系统崩溃"翻译成"被测代码"**
   - `kb`/`kv` 打印调用栈，向上找最近的、落在目标模块代码段的返回地址，换算"基址+偏移"，确认其前是 CALL，再找到函数入口并下断；记录每层参数。
   - 完成标准: 得到"返回地址 → CALL → 函数入口 → 参数"的可核对链，且入口断点能在溢出前命中。
   - 判停条件: 若栈帧明显被破坏（地址非规范、帧链断裂）→ 走步骤 6 的硬件写断点或样本中硬编码 ROP 地址反向追踪。

5. **沿帧上推值来源 / 用排除法收敛**
   - 检查崩溃指令用到的寄存器/内存在本函数内有无初始化；没有则回上一层。单函数内多变量纠缠时先消元：标出"来源已知且稳定"的分量，只追来源不明者，画"输入字节 → 异常值 → 崩溃指令"的传播图。
   - 对候选 CALL 逐个执行前后对照 SEH 链、返回地址、关键指针；入口处正常不能排除函数，必须看调用后的状态。
   - 完成标准: 能指出"执行完地址 X 的 CALL 后，状态 Y 从正常变为被覆盖"，或画出完整传播链。
   - 判停条件: 若单步成本过高、调用链太深，停止逐层跟进，转步骤 6。

6. **用硬件写断点直达写指令并实测覆盖长度**
   - 在 `SUB ESP,...`/分配之后对缓冲区附近下写断点；读写指令目的地址得到缓冲区起点，再在栈中定位返回地址/SEH 句柄，两者相减。
   - 有前缀、拼接、宽字符转换时先扣前缀并按内存实际字节数重算。
   - 完成标准: 同时拿到"写指令地址 + 缓冲区起点 + 目标结构地址 + 精确字节差"，且用该长度填充能准确覆盖目标。
   - 判停条件: 若文件字节数与调试中的缓冲区位置对不上，先查编码转换点；写点不止一处则分别测量，选最近且可控的目标。

7. **用条件记录断点处理"高频/分发"场景**
   - 在分发函数或虚表项上设条件记录断点，记录指令索引、虚拟栈顶、对象地址等关键参数；取日志最后一次记录与输入字节对齐。
   - 完成标准: 能说明"是哪一次调用/哪条虚拟指令算出了异常值"。
   - 判停条件: 若日志无法与输入字段对应，回到步骤 5 补传播图，不要继续盲设断点。

8. **用增删对照确认必要条件，写成条件式**
   - 对怀疑语句做增删，重跑并对比内存/对象结构；删掉即不崩、结构不残留，才判定为必要条件。回到函数序言读栈申请、前置检查、循环初始化与拷贝终止条件。
   - 完成标准: 得到"一条充分条件 + 若干必要条件"，每条都能映射到 POC 的一个字段并单独验证；结论写根因，不写"漏洞叫什么名字"。
   - 判停条件: 若无法把崩溃解释成某个长度/指针/单位错配，说明还在现象层，不要写 exploit。

9. **处理跨版本与本地/远程差异**
   - 同一函数并排比较两版的检查逻辑，判断旧点是否被堵、是否出现新数据流；按失败成本排序：本地先敲定栈布局与偏移，再上远程验证协议封装。
   - 完成标准: 能解释"为什么旧 POC 失效/新 POC 成立"；远程与本地差异被归因到参数、编码或栈操作。
   - 判停条件: 若远程始终不一致且无法归因，停止调填充，回到步骤 3 重建现场。

10. **复跑验证并交接利用阶段**
    - 恢复原始 POC，在干净进程中复跑；在返回指令处记录寄存器，找出稳定指向可控缓冲区的寄存器并搜索 `jmp reg`/`call reg`；整理函数、写指令、偏移、条件、跳板候选。
    - 完成标准: 不依赖调试器也能复现；偏移表、触发条件、返回时寄存器状态均有实测记录。
    - 判停条件: 只有"程序崩溃"没有预期载荷执行，判定定位/覆盖未完成；偏移已确认但需布局与保护绕过 → 转 `win-stack-overflow-exploit` / `exploit-chain-construction`。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **崩溃无法复现** → 先解决复现问题（可能需改造样本或消除环境变量），否则偏移与根因都无从谈起。
- **漏洞类型未知且不是内存破坏** → 逻辑缺陷、权限绕过、配置错误没有"崩溃点"，先走 `vuln-analysis-strategy` / `non-memory-vulnerability-analysis`。
- **破坏对象是堆元数据且需要系统化定位** → 走 `heap-vulnerability-locating`（页堆 + 分配记录），不要用栈回溯硬套。
- **已有补丁/新版本/源码** → 走 `patch-diff-and-source-analysis`，比从崩溃逆推快得多。
- **根因与偏移已确认，只差写 exploit** → 走 `win-stack-overflow-exploit`（栈布局/跳板）或 `exploit-chain-construction`（leak/保护绕过）。
- **生产服务、不可暂停进程、强反调试/加壳/EDR 目标** → attach 与断点会改变时序并可能被检测；优先崩溃转储、日志、ETW/eBPF 与离线复现，未脱壳前偏移结论不可信。
- **x64/ARM64 或跨架构目标** → 返回地址保存、寄存器传参、栈帧与异常展开不同，不能照搬 32 位 x86 的"EBP+返回地址"模型。

### 作者在书中警告的失败模式

- **盲信栈回溯**：它未必是触发漏洞的第一现场；栈被溢出改写后，Call Stack 只能当线索（g05-ce03）。
- **把 PoC 所用对象的命名当根因**：CGenericElement/CTextBlock 只是 PoC 恰好用到的对象（g06-ce03）。
- **把 PoC 里全部代码都当漏洞关键**，不做逐句增删验证（g09b-ce01）。
- **等栈被破坏后才想起回溯**：此时 EBP/返回地址/局部变量都已被改写，只能靠 ESP 推算或启发式猜测（第 25 章 25.3.1）。
- **在漏洞函数入口直接 F8**：F8 会执行完整个函数包括溢出写，回来时程序已跑飞；应 F7 跟入（第 31 章 31.3）。
- **用绝对地址下断/照抄书上的跳板与入口**：堆地址、模块基址、DLL 版本一变即失效（g06-ce02、g04-ce06）。
- **只在函数入口看一次状态就排除**：入口正常只证明"尚未发生"，必须看到候选 CALL 之后的状态。
- **把递归造成的重复命中当断点失效**：要记录命中次数，异常可能只在第二轮/某一层递归出现。
- **把"远程成功、本地失败"当噪声**：两次远程调用间的额外栈操作可能解释精确覆盖与 `maxbuf` 约束。
- **看到 `strncpy` 就认定安全**：长度取源串长度时它等价于 `strcpy`，必须追长度来源并比较目标容量。
- **把"程序崩溃"当成"利用成功"**：崩溃只证明输入造成了破坏，不证明控制流被精确劫持。
- **认为"同一函数修过就不会再出漏洞"**：MS06-040 与 MS08-067 就是同函数、隔两年的两个根因。
- **只检查循环体、不看循环初始化**：初值由 `lea eax,[edi-2]` 直接算出且未校验时，循环体内的 `cmp` 已失去意义。
- **覆盖返回地址时忽略形参副作用**：函数返回前若解引用被覆盖的输出缓冲指针，会先触发访问异常，永远走不到 `ret`；必须保留一个合法可写的输出地址。

### 作者的盲点 / 时代局限

- **完全缺席自动化 triage**：两本书的定位都靠人工读栈与断点；现代"fuzzer 产出崩溃 → 聚类去重 → 符号化栈回溯 → 二分定位"往往先于手工调试，本 skill 更适合作为自动化 triage 之后的根因确认。
- **假设栈信息可用**：CFG/CET、优化编译的 FPO、堆隔离会让栈回溯与堆布局比书中年代更不可靠，"首选栈回溯"在部分目标上会退化为备选。
- **平台与工具停留在 2011—2016 年的 32 位 Windows 用户态**：OllyDbg 1.1 / WinDbg 6.x、手工配置符号；函数地址、偏移和跳板都是特定版本实测值，不能跨版本复用。
- **缺少现代运行时观测**：没有 ETW/eBPF/perf、时间旅行调试、ASAN/CFI 崩溃分类、崩溃快照回放；指令追踪依赖 Paimei + IDA + MySQL + Python 2.4，遇到多线程、异步、JIT、加壳样本容易失真。
- **默认"有 POC、可本地加载漏洞 DLL、可 attach 目标进程"**：现代服务常运行在 `svchost`、受保护进程或容器中，远程 attach 往往不可行。
- **只覆盖 x86 32 位**：x64 影子空间/寄存器传参、ARM 的 LR、内核与虚拟化层差异没有进入模型。
- **重手工、轻规模化**：缺少崩溃聚类、覆盖反馈与样本最小化，面对大量 fuzz 产出时效率与可重复性有限。

### 容易混淆的邻近方法论

- **"单步跟踪"≠本方法**：本 skill 主张先缩小范围再单步（回溯/消元/日志/写断点），而不是从入口一路 F8。
- **`heap-vulnerability-locating`**：用页堆、堆尾检查、分配记录定位堆块破坏；本 skill 用栈帧、SEH、返回地址与栈写入指令定位。崩溃在堆管理代码时不要混用。
- **`patch-diff-and-source-analysis`**：从补丁前后文件或源码差异产生候选漏洞点，给"可能在哪"；本 skill 用运行时证据给"确实在哪、偏移多少"。
- **`locate-by-known-anchor`**：用字符串/导出/符号直接到达函数；本 skill 在缺少锚点时从崩溃反推，二者可接力。
- **`vuln-debugging-and-breakpoints`**：讲断点类型、条件/记录断点、回溯与指令追踪的工具方法论；本 skill 讲完整判据与流程。
- **`win-stack-overflow-exploit`**：从"偏移已量出"开始做跳板、布局与 shellcode 放置；本 skill 在它之前。
