# 逆向无文档驱动与内存结构

## R — 原文 (Reading)

> "通常，在分析漏洞时是没有源码的，因此这里笔者就以此 exploitme.sys 为例讲解在闭源情况下，针对此类漏洞的分析与利用技巧。"
>
> — 林桠泉，《漏洞战争：软件漏洞分析精要》第 9 章 9.3

> "CElement + 0x14 => CTreeNode；CTreeNode + 0x0 => CElement；CTreeNode + 0x44 => CTextBlock；CTextBlock + 0x58 => element_array"

## I — 方法论骨架 (Interpretation)

真实工作中绝大多数目标**没有源码**，作者刻意选闭源驱动做教材，主张把"读汇编、下断点、验证假设"当作默认技能，而不是等源码。两个方向共用同一套纪律：**先建立可验证的入口，再逐层扩展，每一步都要有动态证据**。

### 方向一：从 ring3 到 ring0 的驱动漏洞追踪

1. **先固定入口编号**：分析 IOCTL 型驱动永远从"拿到 `IoControlCode` 数值"开始。方法链：`!drvobj <驱动名>` 取分发例程地址 → 反汇编 → 找 `cmp` 比对的常量 → 跟 `je` 跳到处理例程。
2. **DLL → 驱动的桥**：当只看到一份 ring3 DLL 且不知它调了哪个内核函数时，用 IDA 交叉引用（Xrefs）验证而非猜测。例：`dword_1000EE88` 看似数据，Xrefs 后确认它实际是 `NtDeviceIoControlFile` 的调用点——于是该处就是控制码的分发入口。
3. **审查处理例程的三件事**：输入缓冲区长度是否校验、缓冲区内容是否被当作指针/大小直接使用（未校验即"任意写"）、调用者身份是否被验证（"内核代理功能未鉴权"是提权根因）。
4. **从前置条件反推利用可行性**：把"要成功利用需要满足什么"列成清单（地址是否可知、缓冲区内容是否可控、是否能无交互触发），清单缺项即为利用障碍。

### 方向二：无文档内存结构的逆向

1. **从已知入口对象出发**：找一个已知语义的对象（如 `CElement`）作为坐标系原点。
2. **用条件记录断点 + 读写断点采点**：记录某偏移被写入/读取时的调用上下文、以及伴随出现的相邻字段值，逐步推导出"偏移 → 字段语义"与"指针关系图"。
3. **交叉验证**：用旧版本公开源码（如 IE5 的类定义）或名字相近的公开结构做对照，确认字段猜测。
4. **产出结构定义表**：把推导结果写成 `+ 偏移 => 类型/语义` 的清单，并可在 IDA 中定义结构体以提升后续可读性。
5. **从反编译代码反推结构**：反编译里大量出现的 `[reg+0xNN]` 偏移访问本身就是结构体的证据，可据此补齐字段宽度与对齐。

**共同纪律**：不迷信工具输出。IDA 的 F5 反编译结果可能把偏移显示错；符号表缺失时某些函数无法被正确识别（如 `CElement::Clone`）。所有结论都要有"下断点命中"这一动态证据。

## A1 — 书中的应用 (Past Application)

### 案例 1: exploitme.sys — 闭源驱动的完整分析
- **问题**: 只有一个 .sys 二进制，没有任何文档，要找出可提权的漏洞。
- **方法论的使用**: `!drvobj` 取分发例程 → 反汇编找控制码常量 → 跟分支到处理例程 → 审查用户缓冲区长度与内容处理。
- **结论**: 用户可控缓冲区未做校验，导致"任意写"，可提权。
- **结果**: 完成从入口编号到漏洞成因的完整闭环，并据此写出 ring0 Shellcode 提权模板。

### 案例 2: 360 bregdrv.sys — Xrefs 串接 DLL 到驱动
- **问题**: 只有 ring3 DLL 的调用片段，不知道它最终调用了哪个内核接口，也不知道控制码。
- **方法论的使用**: 用 IDA Xrefs 追 `dword_1000EE88`，发现它实际是 `NtDeviceIoControlFile` 的调用点；再反追驱动侧的分发例程。
- **结论**: 该驱动把"操作注册表的底层接口"暴露给任意 ring3 调用者，且**未对调用者做严格验证** → 任意程序可执行内核级注册表篡改。
- **结果**: 定性为"调用者校验缺失即漏洞根因"，并解释了"Shift 后门"利用工具的原理。

### 案例 3: CVE-2013-1347（MSHTML）— 无符号推导内存结构
- **问题**: `mshtml` 内部的 `CTreeNode` / `CTextBlock` 没有符号、没有文档，但漏洞链路要经过它们。
- **方法论的使用**: 从 `CElement` 出发，用条件记录断点 + 内存读写断点记录字段被读写的位置；配合 IE5 旧源码交叉验证。
- **结论**: 推导出 `CElement+0x14 => CTreeNode`、`CTreeNode+0x44 => CTextBlock`、`CTextBlock+0x58 => element_array` 等一整套布局。
- **结果**: 能正确定位 `element_array` 中残留的已释放对象引用，解释了 UAF 的形成。

### 案例 4: CVE-2013-3660（win32k EPATHOBJ）— 用结构体定义辅助内核分析
- **问题**: `win32k.sys` 里对 EPATHOBJ 的操作难以读通。
- **方法论的使用**: 在 IDA 中为 EPATHOBJ 定义结构体，把偏移访问还原为字段名；再对未初始化内存路径下断。
- **结论**: 从"未初始化内存"推到"任意地址写"。
- **结果**: 构造出覆盖 `HalDispatchTable` 的提权链。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 某驱动/内核模块被曝本地提权，手上只有一份 ring3 PoC 调用片段或一份 .sys。
2. 分析闭源软件，Ctrl+N 里全是 `sub_XXXX`，需要把控制码/接口入口先固定下来。
3. 调试时遇到 `[eax+0x5c]`、`[esi+0x44]` 这类偏移，完全不知道字段语义。
4. 需要判断某个"内核代理功能"是否缺少调用者鉴权。
5. 要为一个无文档结构产出可复用的结构定义（供后续 IDA 分析）。

### 语言信号 (用户的话里出现这些就应激活)

- "驱动逆向 / 提权驱动 / .sys 怎么分析"
- "IOCTL / DeviceIoControl 控制码是多少"
- "只有 DLL，不知道它调了哪个内核函数"
- "这个结构体偏移是什么 / 没符号怎么读结构"
- "没有源码怎么分析 / reverse driver / undocumented structure"

### 与相邻 skill 的区分

- 与 `crash-to-root-cause` 的区别: 后者从**崩溃**出发；本 skill 从**接口/结构入口**出发，常常还没有可复现崩溃。
- 与 `locate-by-known-anchor` 的区别: 本 skill 的 Xrefs/控制码属于"入口建立"，而锚点法侧重"搜到函数"；两者可串联（本 skill 建入口 → 锚点法落函数）。
- 与 `kernel-exploitation` 的区别: 本 skill 只到"找到漏洞与前置条件"；一旦进入提权链构造，走后者。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

**方向一（驱动）**：

1. **取驱动对象与分发例程**
   - 方法: `!drvobj <驱动名> 2`（或 IDA 中找 `DriverEntry` 的 MajorFunction 表）。
   - 完成标准: 拿到 IRP_MJ_DEVICE_CONTROL 的处理例程地址。

2. **固定 IOCTL 控制码**
   - 方法: 反汇编处理例程，找 `cmp`/`sub` 出的控制码常量；无 PoC 时，也可从 ring3 侧调用点的第二参数取。
   - 完成标准: 得到一个或多个具体控制码数值。
   - 判停条件: 若控制码由多层运算得出 → 用条件记录断点记录其运行时值。

3. **定位目标分支并审查处理逻辑**
   - 审查三件事: ① 输入缓冲区长度是否校验；② 缓冲区内容是否被当作指针/长度直接使用；③ 是否验证调用者身份/权限。
   - 完成标准: 明确指出"缺失了哪一个检查"，即漏洞根因（调用者校验缺失 = 提权根因）。

4. **建立利用前置条件清单**
   - 完成标准: 列出"地址是否可知 / 内容是否可控 / 能否无交互触发 / 目标版本限制"，标出缺项与对应障碍。

**方向二（结构）**：

5. **选一个已知入口对象，建立坐标系**
   - 完成标准: 明确"从哪个对象的哪个偏移开始推导"。

6. **采点：条件记录断点 + 读写断点**
   - 方法: 对候选偏移下 `ba r/w` 断点，记录访问时的调用上下文与伴随字段；对高频路径用条件记录断点（不中断、只记录）以免丢失节奏。
   - 完成标准: 每个候选偏移至少有一条"访问时机 + 上下文"证据。

7. **交叉验证并产出结构定义表**
   - 方法: 用旧版本公开源码 / 相似公开结构对照；在 IDA 中定义结构体以验证偏移自洽（无重叠、对齐合理）。
   - 完成标准: 输出 `+偏移 => 类型/语义` 清单，并能在 IDA 中定义通过。
   - 判停条件: 若两个字段的偏移互相矛盾 → 回到步骤 6 补采点，不要强行下结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **有源码或补丁** → 走 `patch-diff-and-source-analysis`，成本低得多。
- **已有可复现崩溃且属应用层** → 走 `crash-to-root-cause`。
- **目标是云/容器侧接口** → 本 skill 的 Windows 驱动模型与内存结构推导不适用。

### 作者在书中警告的失败模式

- 盲信 IDA F5 反编译结果（偏移被错误显示）（g08a-ce02）。
- 内核 Shellcode 硬编码 KPCR 地址导致不通用（g08a-ce01）。
- 内核代理功能未鉴权——把低权限接口暴露给任意调用者（g08a-ce03）。
- 检测条件不完善——仅在非零分支校验指针有效性（g08a-ce04）。
- 内核漏洞调试的成本陷阱（一蓝屏就得重启从头再来）（g08b-ce03）。

### 作者的盲点 / 时代局限

- **Windows 中心**：IOCTL/IRP/DRIVER_OBJECT 模型是 Windows 专有；Linux 侧的 ioctl 编号、io_uring、以及 eBPF 攻击面均未涉及。
- **假设驱动能被自由加载调试**：现代 Windows 有驱动签名强制（DSE）、HVCI、内核 CFG，书中"加载 exploitme.sys 直接调"的教学路径在新系统上会被拦；作者提到的"先学驱动开发"（g08b-p01）是必要但不充分的前置。
- **结构推导全靠人工**：今天可用调试器脚本、DWARF/PDB 提取、以及反编译器的结构自动重建，作者未涉及自动化。
- **未涉及内核缓解**：KASLR、SMEP/SMAP、PatchGuard 之后的利用路径与书中差异巨大。

### 容易混淆的邻近方法论

- "把驱动整个反汇编读完" 是低效直觉；本 skill 的差异点是**先固定入口编号（IOCTL 码/导出函数），再由 Xrefs 与动态命中收口**。
