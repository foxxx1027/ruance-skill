# 浏览器堆喷射与 UAF 利用

## R — 原文 (Reading)

> 浏览器攻击过程中的三个主要步骤如下所示：(1）将shellcode加载到内存中的可预测地址。(2）强制释放一个对象，并使用另一个对象重写该对象，所使用的对象包含一个VPTR，指向一个伪造的vtable，这个vtable指向步骤1中加载的shellcode。
>
> — 《灰帽黑客 第4版》第16章 16.2

> 对于每个AddRef，必须有一个对应的Release调用。如果多了一个没有对应的AddRef的Release调用，对象引用计数可能被设为O，导致从内存中删除该对象，但是其引用不会从活动对象列表中删除。
>
> — 《灰帽黑客 第4版》第17章 17.2

---

## I — 方法论骨架 (Interpretation)

1. **一句话**：浏览器 UAF 利用是三段闭环——先把 payload 放到可预测地址，再让被释放对象的位置被伪造对象重占，最后触发对旧引用的访问；任一环缺失都只剩普通崩溃。
2. **阶段一 布置可预测地址**：用 canvas、DEPS、HeapLib2、Flash ByteArray 或整数向量做大量同尺寸分配，把 shellcode/ROP 链铺进堆；载体由目标浏览器版本与分配器行为决定，不是越新越好。
3. **阶段一的验收**：目标堆中同一尺寸块应占总忙字节 70% 以上（越接近 100% 越好），并在目标地址 dump 到标记或 payload。
4. **阶段二 等大重占**：先测出被释放对象的真实大小，再用同尺寸对象占回；LFH 需至少 18 次同尺寸连续分配激活，且只服务小于 16KB 的块，遵循“最后释放、首先分配”。
5. **阶段二的关键字段**：伪造对象首部的 VPTR 指向伪 vtable，伪 vtable 表项再指向阶段一的落点；这是两级间接，偏移必须按对象布局计算。
6. **阶段三 触发引用**：让业务代码访问那个已被释放、却仍留在活动对象列表中的引用，虚调用便沿 VPTR → 伪 vtable → shellcode 走。
7. **根因验证**：对 AddRef、Release、RtlFreeHeap 分别下“参数等于目标对象地址”的条件断点，命中时打印对象结构，否则继续。
8. **判据**：AddRef 与 Release 必须一一配对；净多一次 Release 会把计数归零、释放对象却不删引用，这才是可重占、可利用的 UAF。
9. **分析顺序**：崩溃函数 → 对象类型 → 对象地址 → 释放方式 → 重占方式 → 引用计数为何失衡，六步缺一不可。
10. **判停**：喷射占比不达标先换载体或调块大小；崩溃但 AddRef/Release 次数匹配，说明还没找到真正的释放路径，回到根因。
11. **成立前提**：32 位地址空间、可预测的分配器行为、对象使用虚表分派，三者同时具备时这套流水线才成立。
12. **结论口径**：地址不可复制而流程必须可复现；报告要指出受影响函数、根因与修复点，不能停在“能崩”。

## A1 — 书中的应用 (Past Application)

### 案例 1: 三种喷射载体的落地验证（实验16-1 / 16-2 / 16-3）
- **问题**: 在 IE9–11 上要确认“把 payload 放到可预测地址”这一步哪种载体真的可用；旧的 BSTR 字符串方法已不再稳定。
- **方法论的使用**: canvas 用 256×256 画布、`createImageData` 生成 262144 字节像素数组、保存 2000 张；DEPS 把 junk+ROP+shellcode 放进 DOM 元素属性，title 与 fontFamily 各约 0x40000 字节、循环 0x250 次；HeapLib2 先按 32/64/256/32768 四类箱各填 6 个最大尺寸块耗尽缓存，再用随机命名的 DOM 属性承载 payload。三者都用 `!heap -stat` 与 Memory 窗口核对落点。
- **结论**: 载体必须匹配目标浏览器的分配路径；缓存箱没耗尽时 payload 会复用旧块，看似喷满、地址却不可控。
- **结果**: canvas 所在堆 99.67% 为 0x40000 块；DEPS 在 0x20302228 看到 GRAYHATHACKING4TH；HeapLib2 某堆 99.22% 为 0x50010 块；但 canvas 太慢，受害者容易察觉并关闭页面。

### 案例 2: CVE-2014-0322 —— LFH 重占与整数向量落点
- **问题**: Windows 7 SP1 + IE10 上的 IE 零日，公开攻击 HTML 需要改造成可控重占；同时要解决“重占对象该多大、payload 落在哪”。
- **方法论的使用**: 取公开攻击 HTML，改为通过 LFH 分配 0x340 大小的对象重占被释放的 CMarkup，用 0x1a1b1ff0 等值填充伪造 VPTR，并加入 EMET 存在性探测；喷射侧用 Flash 整数向量——外层 98688 个元素，每个是长度 0x3FE 的 `Vector.<uint>`，与 0x3FE 的 CMarkup 同尺寸，在 0x1a1b2000 附近重复出现。
- **结论**: 重占能否成立由“对象大小 + 释放顺序 + LFH 是否激活”共同决定；整数向量不只铺数据，后续还可用对相邻向量长度的递增指令换取越界读写。
- **结果**: 在 UpdateMarkupContentsVersion 断下并观察到受控 EAX，成功复现崩溃，并继续完成对象类型、地址、释放路径与重写过程的完整分析。

### 案例 3: 实验17-1 —— 用 AddRef/Release 次数证明根因
- **问题**: 已能复现崩溃，但仍需回答“对象为什么被提前释放、引用为什么还留在活动对象列表”。
- **方法论的使用**: 在 InsertSingleElement、InjectHtmlStream、CMarkup::AddRef、CMarkup::Release、RtlFreeHeap 上按目标对象地址 081d8898 下条件断点，命中打印对象结构，否则继续执行。
- **结论**: 计数差就是根因证据；只盯 RtlFreeHeap 只能证明“释放了”，同时统计两个入口才能证明“多了一次 Release”。
- **结果**: AddRef 调用 2 次、Release 调用 3 次，最后一次 Release 把计数归零并进入 RtlFreeHeap，而引用仍完整留在活动对象列表，UAF 成立。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 手上有 IE9–11/旧 Flash 环境的浏览器崩溃样本，问如何把“一个崩溃”推进到可控执行。
2. 已经在做堆喷射，但目标地址 dump 不到 payload、同尺寸占比只有十几个百分点，需要判断换载体还是调块大小。
3. 拿到一个 UAF 崩溃，需要判断对象是否真的被释放、能否被重占、重占对象该多大、LFH 是否已激活。
4. 需要验证根因是否“多了一次 Release”，或要在报告里写清受影响函数与修复点。
5. 要在 canvas、DEPS、HeapLib2、Flash ByteArray、整数向量之间选喷射载体，或判断 VTGuard/IsolatedHeap 是否挡住本次重占。

### 语言信号 (用户的话里出现这些就应激活)

- “UAF / use-after-free 怎么利用”
- “堆喷射 / heap spray 为什么打不中地址”
- “LFH / 低碎片堆 / 18 次分配 / 后进先出”
- “VPTR / vtable / 虚表被改写”
- “AddRef 和 Release 对不上 / 引用计数归零了但还在用”
- “IE 漏洞 / mshtml / CMarkup / 0x0c0c0c0c 可预测地址”

### 与相邻 skill 的区分


- **composes-with** `windows-exploit-and-mitigation-bypass`：本 skill 只做浏览器堆喷射、重占与 UAF 根因；系统层保护矩阵与通用利用流水线由它给出。
- **composes-with** `shellcode-payload-shape-selection`：本 skill 确定喷射落点与可控对象；落点之后投什么载荷、网络方向是否可达，由它决定。
- 与第 1 本 `heap-exploitation` 的区别: 它讲通用堆原语（占坑、UAF 占位、double free），默认通用 Windows 堆与普通进程；本 skill 只处理浏览器对象，多了“喷射落点验证”和“引用计数根因”两段，并要求 LFH 激活、缓存箱耗尽、等大对象与虚表两级间接。
- 与 `exploit-chain-construction` 的区别: 它提供“触发 → 信息泄露 → 绕保护 → 控流”的四段体检表，面向任意目标；本 skill 是浏览器内的具体流水线，负责喷射、重占与根因证明，需要泄露基址或写 ROP 时转交它。
- 与第 3 本 `mitigation-evolution-mapping` 的区别: 后者横向梳理保护演化与覆盖缝隙；本 skill 只回答“VTGuard/IsolatedHeap 会不会让这次重占失效”，不展开保护谱系。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **确认授权与实验环境**
   - 完成标准: 有明确授权与隔离虚拟机；确认是 32 位 IE9–11/Flash 目标，保存快照，WinDbg 符号可用。
   - 判停条件: 若目标是 64 位现代浏览器或已退役组件之外的新架构，退出本 skill。

2. **定位崩溃点与对象类型**
   - 完成标准: `kb` 打印的调用栈能指出崩溃函数，`RetAddr` 可逐层回溯，`Args to Child` 能看到同一对象指针的状态。
   - 判停条件: 若连稳定复现都做不到，先走崩溃定位流程。

3. **测对象大小、地址与释放路径**
   - 完成标准: 用 `!heap -p -a` 取得对象所属堆块与分配记录，找到栈上“已释放/未释放”状态翻转的那一层调用。
   - 判停条件: 若开启了完整 PageHeap 导致提前崩溃，关闭 gflags 后重试。

4. **选喷射载体并验证落点**
   - 完成标准: 同尺寸块占总忙字节 ≥70%，目标地址 dump 到 payload 标记。
   - 判停条件: 若占比 <70%，换载体或调整块大小/循环次数并重算偏移，不要继续拼利用。

5. **激活 LFH 并现场标定次数**
   - 完成标准: 至少 18 次同尺寸连续分配后，`!heap` 显示走 LowFrag 路径，释放后同尺寸分配能拿回原地址。
   - 判停条件: 若 GFlags/Application Verifier 的堆调试正在运行（会禁用 LFH），换干净环境重新标定。

6. **等大对象重占并伪造 VPTR**
   - 完成标准: 释放目标后立即申请同尺寸对象，dump 原地址能看到伪造结构，首部 VPTR 指向可读的伪 vtable。
   - 判停条件: 若原地址未被复用，回到步骤 3 复核大小、释放顺序与 LFH 状态。

7. **核对引用计数根因**
   - 完成标准: AddRef 与 Release 的次数差可解释；净多一次 Release 且对象仍留在活动对象列表。
   - 判停条件: 若计数匹配，说明释放路径找错，回到步骤 3 重新取证。

8. **触发重用并确认控流**
   - 完成标准: 断在虚调用处，寄存器指向伪造对象，单步后 EIP 进入阶段一的落点或伪 vtable 表项。

9. **把弱原语升级为越界读写**
   - 完成标准: 若崩溃指令只是 inc/dec 或受控写，单步对比前后内存，确认能篡改相邻 Vector 长度并读出越界数据。

10. **需要时移交保护绕过**
    - 完成标准: 若必须泄露模块基址、定位 VirtualProtect、构造 ROP 链，明确移交 `exploit-chain-construction`，并保留已确认的喷射与重占现场。

11. **失败分类后再迭代**
    - 完成标准: 每轮失败归入未喷到位、未释放、未重占、未重用、被缓解拦截之一；每轮只改一个变量。

12. **复原环境并输出报告**
    - 完成标准: 恢复快照、清理样本；报告写清受影响函数、根因（引用计数失衡）、重占条件与修复建议，并注明缓解覆盖情况。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **64 位浏览器或大地址空间目标**：地址空间显著增大，大规模同尺寸喷射的覆盖比例骤降，书中的固定地址赌法不成立；应改用确定性布局或现代利用方法。
- **启用现代 CFG/ACG/CIG/PartitionAlloc 的目标**：Chromium 的分区分配器、Windows 的 CFG/ACG 会分别破坏“等大重占”和“伪造 VPTR”两个前提；IE 已退役，书中的 mshtml 对象模型不再适用。
- **已修补版本**：CVE-2014-0322 一类漏洞的引用计数已配对，堆布局也已变化；不要对已打补丁目标套用旧 PoC。
- **漏洞尚未定位或只有一条崩溃栈**：本 skill 从“已能触发 UAF/已确认需要喷射”开始，前置工作应走崩溃定位与根因分析。
- **无授权、面向真实第三方站点或生产浏览器**：仅限隔离实验与授权测试，不得用于未授权入侵。
- **只想理解堆喷射概念或写检测规则**：不需要本流水线，检测视角应分析同质分配模式而非复现利用。

### 作者在书中警告的失败模式

- **ce110**：在 IE9/10+ 上沿用 BSTR 字符串老喷射，分配不再稳定地落在同一尺寸与区域，应改用 DEPS。
- **ce111**：canvas 喷射要保存 2000 张图，浏览器长时间无响应，受害者主动关闭标签，攻击链在触发前中断。
- **ce112**：只看某堆 Committed 接近 Reserved 就认定是喷射堆，实际最高尺寸仅占 14.17%，必须换堆再按同尺寸占比筛选。
- **ce113**：把“payload 落到可预测地址”当成“已绕过堆保护”，实验用的是无害标记，根本没有触发 Nozzle 等检测。
- **ce114**：在 64 位环境照搬 32 位喷射，覆盖比例变小、命中预设地址的概率骤降。
- **ce115**：在 GFlags/Application Verifier 的堆调试下测试 LFH，工具会禁用 LFH，LIFO 复用行为根本不存在。
- **ce116**：为了跑通而随手改 offset、块大小或循环次数，喷射仍成功，但 payload 已不在预期地址。
- **ce117**：用 as3compile 编译含 `Vector` 的代码，编译器不支持而报错，应改用 Flex SDK 的 mxmlc。
- **ce118**：为“看得更清楚”启用完整 PageHeap 复现 UAF，结果在到达漏洞函数前就崩溃，重占时序被破坏。
- **ce119**：只追到“EAX 受控、在 [eax+0x10] 崩溃”就收工，解释不了对象为何被释放、引用为何还在。
- **ce122**：喷射成功但未触发 UAF，或触发后对象未指向喷射区，结果仍是无 shell 的普通崩溃。

### 作者的盲点 / 时代局限

- **2014–2015 年技术快照**：IE9–11、Flash、EMET 5、Windows 7/8；IE 于 2022 年退役、Flash 于 2020 年终止、EMET 于 2018 年停止支持，工具链与命令大量失效。
- **32 位地址空间前提**：0x0c0c0c0c、0x20302228、0x1a1b2000 等都是示例；LFH 激活次数也要现场标定（书中见过 16 次的情形），不能硬编码 18。
- **缓解覆盖不全**：VTGuard 只保护 mshtml.dll 中部分类，IsolatedHeap 只针对重占环节，书中都只点到为止；CFG/ACG/PartitionAlloc 未涉及。
- **实验隐含条件**：host-only 网络、可反复重启的虚拟机、可关闭或规避的堆调试，结论不能外推到生产环境。

### 容易混淆的邻近方法论

- **堆喷射 ≠ 堆溢出/UAF 本身**：它只负责把数据铺到可预测地址，不触发漏洞。
- **释放 ≠ UAF**：必须同时满足“对象被释放”“引用仍可达”“攻击者能等大重占”。
- **LFH ≠ 所有小分配都走**：需先激活且块小于 16KB；堆调试工具会禁用 LFH。
- **等大 ≠ 字节数相同即可**：还要求落在同一尺寸桶并按 LIFO 顺序复用。
- **改写 VPTR ≠ 直接写函数指针**：是 VPTR → 伪 vtable → shellcode 的两级间接，伪 vtable 必须位于可读地址。
- **复现崩溃 ≠ 完成利用**：报告要给出受影响代码与修复点，不能只交 PoC。
