# 内存与资源安全

## R — 原文

> a） 保持一致的内存管理约定：使用同样的模式分配和释放内存……分配和释放应配对。b） 谨慎操作缓冲区：对缓冲区的读写操作进行边界检查，避免向指定的缓冲区外读取或者写入数据……e） 及时释放内存，避免依赖垃圾回收机制。
>
> — GB/T 38674—2020，7.2 a) b) e)；另见 7.1 d) e) f) g) h)、7.2 c) d) f) g)、6.5 a)–e)

## I — 方法论骨架

把内存、缓冲区、文件句柄、数据库连接、游标、锁、线程、临时文件看成同一种东西：有出生、有引用、有死亡。审查时按三层走，不要一上来就找 free。

第一层是约定层：同一模块、同一抽象层次内用同一种模式申请与释放，申请点和释放点必须成对。配对不成立时先怀疑设计，而不是先补一行释放。

第二层是状态层：使用前必须初始化成功，初始化失败要能安全退出；引用计数准确；及时释放，不把生命周期押给垃圾回收；同一资源不得释放两次，已释放的不得再使用；释放前先清掉敏感内容，临时文件与辅助资源一起清理。

第三层是容量层：数量、权限、有效时间都要有上限；递归要有终止条件与深度上限；循环要有次数上限；资源池按峰值规划；外部来的文件先验来源与完整性。

缓冲区是这套模型里最容易被写坏的一种资源：每次读写前核对剩余空间与本次长度，字符串同时校验长度与终止符并预留终止符空间，循环内每轮重新核对容量，而不是只在进入循环前算一次。

到 C/C++ 还要再加一层平台约束：指针先验有效性、类型兼容，只在数组内做指针运算，不用指针差值推算内存大小，不赋固定地址，偏移不越界；开启堆完整性检测与非可执行堆栈；避免 printf、strcat、strcpy 这类不检查自变量的函数。

判断标准只有一句：每个资源在每条退出路径上都有且只有一次归还，且归还之前没有被越界碰过。

## A1 — 书中的应用

### 案例 1: 指针回退 8 字节后拷贝造成堆上溢（附录 A.4.2.16，对应 7.2 b)）

- **问题**: 分配 100 字节缓冲区后，把数据指针改成缓冲区首地址之前 8 字节，再向该指针拷贝 100 字节。
- **方法论的使用**: 先算写入区间与分配区间是否重合——写入起点已落在分配块之外，长度又等于整块容量，两者相加必然越过上边界；同时指针运算发生在非数组对象上。
- **结论**: 写入范围必须与分配范围一致，拷贝长度不得直接取自外部输入，指针只能指向合法对象内部。
- **结果（防住什么）**: 不修则覆盖相邻堆元数据或对象，可导致崩溃或任意代码执行；修正后越界写消失。

### 案例 2: I/O 流与数据库连接不在 finally 释放（附录 A.4.1.2、A.4.3.2，对应 7.1 d)、7.3 j)）

- **问题**: 文件流与数据库连接只在成功路径上使用，异常或提前返回时都不关闭，指望虚拟机回收。
- **方法论的使用**: 按生命周期模型逐个资源列出所有退出路径；文件句柄与连接是有限的操作系统资源，回收时机不确定，必须每条路径显式归还。
- **结论**: 资源变量先置空，在 finally 中判空逐个关闭，关闭动作自身再单独捕获；或使用自动关闭语法。
- **结果（防住什么）**: 不修则并发请求把句柄池或连接池耗尽，形成拒绝服务；修正后池容量在高负载下保持稳定。

### 案例 3: 不设上限解压 zip 耗尽资源（附录 A.2.1.1.3，对应 7.1 f)、7.2 f)）

- **问题**: 逐条读取压缩条目直接写盘，不限单条与累计大小、不限条目数，还按条目自报的大小做判断。
- **方法论的使用**: 容量层要求给数量与时长设限；条目自报大小由攻击者构造，只能以实际写出的字节累计。
- **结论**: 累计解压量、条目数、耗时都要有硬上限，超限立即中止；条目路径先规范化再限制在目标目录内。
- **结果（防住什么）**: 不修则几 KB 的压缩包可撑满磁盘或内存；修正后解压被约束在配额内。

## A2 — 触发场景

### 用户会在什么情境下需要这个 skill?

1. 代码评审读到 malloc/new、数组拷贝、字符串拼接，需要判断会不会越界、会不会漏释放。
2. 线上服务在压测或高峰期出现连接池耗尽、句柄数飙升、内存缓慢上涨，怀疑泄漏。
3. 新增上传解压、文档解析、反序列化、图片处理等吃外部数据的入口，需要设资源上限。
4. 团队用 Go/Java 并认为有 GC 就不用管释放，但 socket、文件、游标仍然泄漏。
5. 递归或循环边界由外部数据决定（嵌套 JSON、树形结构、目录遍历），担心爆栈或死循环。

### 语言信号

- "这里要不要 free / close"（do I need to free or close this）
- "内存一直涨 / 句柄数下不来 / 连接池打满"（memory keeps growing / handle leak / connection pool exhausted）
- "这个拷贝会不会溢出"（can this copy overflow the buffer）
- "解压或解析把内存吃光了"（decompression eats all memory）
- "有 GC 了还需要手动释放吗"（is manual release still needed with GC）
- memory leak, buffer overflow, double free, use-after-free, resource exhaustion, handle leak

### 与相邻 skill 的区分

- 与 `function-and-exception-safety` 的区别：后者管异常这条第二执行路径怎么走、参数与返回值怎么验，本 skill 管资源在每条路径上是否恰好归还一次；异常处理只是释放动作最常被漏掉的位置。
- 与 `file-and-upload-safety` 的区别：后者关心路径与文件类型是否可信，本 skill 关心文件句柄、流与临时文件的生命周期与容量。
- 与 `concurrency-safety` 的区别：本 skill 不判断锁顺序与可见性，只在资源被多线程共享、引用计数这一层与它相邻。

## E — 可执行步骤

1. **建资源清单**
   - 动作：把改动范围内的内存块、缓冲区、文件句柄、流、连接、游标、锁、线程、临时文件逐项列出，标出申请点、释放点、持有者。
   - 完成标准：每个资源至少有一个申请点，且所有退出路径（正常、异常、提前返回、超时）都有对应释放动作或明确的所有权转移。
   - 判停条件：若项目完全没有显式资源（纯托管且无外部句柄），跳到步骤 3。

2. **核对配对约定**
   - 动作：对每个资源检查是否同模块、同抽象层次、同模式地申请与释放。
   - 完成标准：三项各有成立或不成立的结论；不成立的项写出具体的跨层点或跨模式点。

3. **核算边界与容量**
   - 动作：对每个读写缓冲区写出容量、本次长度、剩余空间；检查字符串终止符；检查循环内是否重算；给递归深度、循环次数、解压与反序列化总量、连接数、超时设具体数值。
   - 完成标准：每个写入点都能指出上界来源（常量、分配大小或校验过的长度），每个容量限制都有具体数值与触发后的中止动作。

4. **排查生命周期危险点**
   - 动作：逐项核对二次释放、释放后使用、过期句柄、引用计数、敏感信息擦除、初始化失败退出。
   - 完成标准：六项各有存在 / 不存在 / 已加防护的结论，存在项附修复位置。

5. **用工具或替代证据收口**
   - 动作：对改动路径至少跑一次动态检查（地址与内存检测、泄漏检测）或静态规则扫描；C/C++ 确认堆完整性检测与非可执行堆栈的编译选项。
   - 完成标准：有工具输出，或有书面说明为何当前环境无法运行并列出残余风险。
   - 判停条件：若工具不可用且风险涉及外部可控长度，标记为未验证，不得宣称已修复。

## B — 边界

### 不要在以下情况使用此 skill

- 问题出在业务状态而不是资源生命周期，例如重复下单、金额篡改、审批流跳过；这些要靠业务不变量与状态机，本 skill 只能告诉你没有泄漏。
- 你要决定谁能读这个文件；那是授权与路径校验问题，交给 `file-and-upload-safety` 与 `authorization-and-least-privilege`。
- 你在做 JVM/Go 的堆大小、GC 参数与容量规划；那是性能工程，不是安全编码。
- 目标平台的编译器或运行时不支持堆完整性检测与不可执行栈（老式嵌入式、特定实时系统），此时不能把条目当作已验证的防护。
- 存量系统补异常路径释放需要大改结构：本 skill 给的是审计靶点与优先级，不提供渐进迁移方案。

### 作者在书中警告的失败模式

- **ce08 不设资源上限**：解压或解析不限总量、条目数与耗时，还用条目自报大小作为限额依据；几 KB 输入即可撑满磁盘或内存，元数据可伪造使看起来有校验的限额失效。
- **ce13 依赖垃圾回收或退出钩子**：句柄、连接、临时文件指望 finalize 或退出时删除；回收时机不确定，少量并发即可耗尽池；进程被强杀时临时文件残留，还可能转为信息泄露。
- **ce20 吞掉异常与忽略返回值**：close、delete、设置权限的返回值被丢弃，失败被当成成功继续走，泄漏与未受保护状态长期潜伏。

### 作者的盲点 / 时代局限

- 标准默认 C/C++/Java：指针、堆、手动释放等条目在 Rust/Go 中要改写为逻辑边界与显式归还，照搬会得到一堆不适用的检查项。
- 只要求做边界检查，却不给验证手段：没有 ASan、Valgrind、模糊测试或静态分析的建议，读者无法证明检查过了，也无法判断泄漏与溢出哪个先修。
- 对异步与池化模型缺位：事件循环、协程、连接池的借出与归还语义并不等于申请与释放，标准没有给出映射。

### 容易混淆的邻近方法论

- 并发安全：两者都谈共享与竞态，但并发安全回答同一时刻谁能改，本 skill 回答这个资源什么时候死。
- 异常路径独立审视：它提供出错后世界的走查方法，是执行本 skill 步骤 2 的手段之一，不是替代品。
