# 四类程序分析技术的选型与组合

## R — 原文 (Reading)

> 现有模糊测试都会在解决某些特定问题时存在一些不足。大多数改进技术通常以一定的性能损耗为代价来换取测试效率的提升。现有的研究成果在效果评估方面都取得了一定进展，但其中部分改进技术仍存在一定的局限性，有待进一步改进提高。
>
> — 魏强、武泽慧，第7章 7.6.1 局限性和面临问题

---

## I — 方法论骨架 (Interpretation)

1. 选型不是选"最强"的技术，而是先看五个硬约束：源码/中间表示是否可得、目标规模、输入通道是否可达、是否已有崩溃样本、是否允许插桩。任何一项不满足，就删掉依赖它的技术。
2. 数据流分析不运行程序，能做全程序上近似，适合回答"值从哪来、变量状态是否违反规则"；硬边界是精度依赖建模——流敏感不判路径可行性，路径敏感又回到路径爆炸，报告天然带误报。
3. 污点分析在 source/sink 明确时最省力，能把海量代码缩成少量可疑数据流；硬边界是隐式流、净化函数和库调用建模，静态版混入不可达路径，动态版只覆盖跑过的代码。
4. 符号执行能把"是否可达"变成约束可满足性并给出具体输入，正向适合系统铺开、逆向适合从危险点收敛；硬边界是路径数随分支和循环指数增长，外部调用、指针、浮点与求解能力会迅速吃掉预算。
5. 模糊测试真实执行、误报低、吞吐高，适合有稳定输入通道和崩溃 oracle 的内存破坏类目标；硬边界是覆盖上限、格式与校验门槛、逻辑漏洞不崩溃、覆盖率不等于漏洞概率。
6. 组合的默认顺序是：静态数据流/污点先定位 sink 与可疑路径 → 符号执行判断关键条件是否可满足 → 模糊测试在真实执行中扩大战果并拿崩溃 → 覆盖率停滞时用 concolic 定向啃分支。
7. 每一段都必须有交付物和止损点：sink 清单、候选种子、可满足输入、去重后的崩溃集。任一段超预算，就把它的输出降级为"线索"，交给下一段或人工。
8. 最终结论要写清"用了什么、为什么、没覆盖什么"；四类技术都只能提供存在性证据，不能证明目标无漏洞。

## A1 — 书中的应用 (Past Application)

### 案例 1: 同一类目标（找出程序中的内存安全缺陷）的三条路线对照

把书中三个案例放在同一个问题下重组：目标都是"给定一个程序，找出内存安全缺陷"，但可用信息、缺陷形态与交付物不同，因而适合的路线不同。

| 路线 | 书中案例与出处 | 适合的目标形态 | 强项 | 硬边界 | 交付物 |
|---|---|---|---|---|---|
| 数据流 + 状态自动机 | **cB05**，第4章 4.4.2 检测程序漏洞 | 源码或中间表示可得；缺陷是变量生命周期/状态违规，如 Double Free、UAF | 不需要运行即可做全程序扫描；状态规则可解释、可复核 | 需人工建 CFG、调用图和状态规则；结论只是"可能"，不判路径可行性 | 可疑行号 + 状态序列 |
| 正向/逆向符号执行 | **cB12**，第6章 6.4.1 检测缓冲区溢出漏洞 | 程序较小；下标、长度、分支条件可用算术约束表达；目标是判定可达并给触发值 | 路径条件精确；能给出 `i=10` 这样的具体输入，也能用 unsat 排除路径 | 分支与循环导致路径爆炸；外部调用、指针、浮点和求解成本高 | 可满足输入，或不可行证明 |
| 覆盖率引导模糊测试 | **c-C09**，第7章 7.4.6 案例分析 | 有真实输入通道与合法种子；可插桩；缺陷会以崩溃暴露 | 真实执行、低误报、吞吐高；直接产出崩溃样本 | 覆盖有上限；格式/校验门槛会挡住变异；逻辑漏洞不崩溃；约 12 小时得到 28 个崩溃后仍需去重分类 | 种子库 + 去重后的崩溃集 |

- **选型结论**: 有源码/IR 且缺陷是生命周期规则时，先走 cB05 的数据流路线；程序小、条件可算术化且需要触发值时，走 cB12 的符号执行；目标是真实解析器、有输入通道和崩溃 oracle 时，走 c-C09 的覆盖率引导 fuzz。
- **组合结论**: 若只有一个闭源二进制且时间有限，书中三条路线都不应单独全程使用——先用静态手段定位危险汇点，再用结构化种子跑 fuzz，卡在复杂条件时用 concolic 定向求解，这与第7章 7.5.1 Driller 的"fuzz 打底、覆盖停滞时切选择性 concolic"一致。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 手上只有一个二进制或一份源码，时间只有 24–72 小时，用户问"先做静态分析还是直接 fuzz"。
2. 团队只会跑 fuzz，但目标有强格式校验、魔数或加密入口，覆盖率长期不涨，需要判断该补什么技术。
3. 扫描器报了几百条告警，用户要排序、分诊，决定哪些值得动态验证、哪些只需人工复核。
4. 要在报告或评审里解释"为什么选这种方法、为什么不用符号执行/为什么不全量 fuzz"。
5. 需要把两种以上技术组合成流水线，例如静态定位汇点 + 污点缩小范围 + fuzz 验证 + concolic 补分支。

### 语言信号 (用户的话里出现这些就应激活)

- "只有一个二进制、时间有限，先静态还是先 fuzz / one binary, limited time, static or fuzz"
- "团队只会 fuzz，但目标进不了深路径 / coverage plateau at a magic-byte check"
- "扫描器报了几百条，怎么排序 / how to triage hundreds of scanner findings"
- "报告里怎么解释选型 / justify why this analysis technique was chosen"
- "能不能把静态分析和 fuzz 组合起来 / combine static analysis with fuzzing"
- "为什么不用符号执行 / why not symbolic execution / which analysis technique should I use"

### 与相邻 skill 的区分

- 与 `vuln-analysis-strategy` 的区别: 后者处理"已有崩溃/已有补丁之后怎么取证"；本 skill 处理"还没有线索时，如何在四类技术之间分配预算"，不展开任何单技术的内部流程。
- 与 `coverage-guided-fuzzing` 的区别: 后者是在已经决定用 fuzz 之后，配置种子、边覆盖、调度与停止条件；本 skill 只决定 fuzz 是否值得占预算、它向其他阶段交付什么。
- 与 `symbolic-execution` 的区别: 后者讲符号化、路径条件、约束求解与路径爆炸的处理；本 skill 只把符号执行当作一个预算项，决定何时投入、投给哪个分支。
- 与 `dataflow-analysis-and-code-modeling` 的区别: 后者教如何建基本块、CFG、SSA、数据流方程并迭代到不动点；本 skill 只消费它的输出作为候选汇点与可疑路径，不教建模细节。
- 与 `taint-analysis` 的区别: 后者负责 source/sink、传播规则、净化函数与误报漏报的判定；本 skill 只判断目标是否具备"source/sink 足够明确"这一选型前提。

## E — 可执行步骤 (Execution)

1. **明确目标与交付物**
   - 写清要的是崩溃样本、可复现 PoC、根因定位、某类漏洞的排除结论，还是一份方法论证。
   - 完成标准: 一句话目标 + 可验收的交付物 + 截止时间；若目标是"已有崩溃的根因"，直接转 `crash-to-root-cause`，不进入本流程。

2. **盘点五个选型约束**
   - 逐项确认：源码/IR 是否可得、目标规模（LOC/二进制大小/函数数）、输入通道与合法种子、是否已有崩溃样本与异常 oracle、是否允许插桩/仿真，以及人力与算力预算。
   - 完成标准: 得到一张"是/否/未知"的约束表，每项附证据（例如"有源码，可编译 ASan 版本"）。

3. **排除不可用技术**
   - 无源码/IR 且反汇编不可用时，排除静态数据流与静态污点；无外部输入通道时，排除 fuzz 与动态污点；无崩溃 oracle 或目标是逻辑漏洞时，排除以崩溃为信号的 fuzz；无法插桩且无仿真器时，排除动态污点与动态符号执行；目标巨大且循环密集时，排除朴素全路径符号执行。
   - 完成标准: 四类技术逐项标注"可用/排除 + 理由"，至少保留一条可用路线。
   - 判停条件: 若四类技术全部被排除，停止选型，输出"能力缺口 + 需先解决的前提（脱壳、输入通道、插桩环境）"，转为人工逆向。

4. **给剩余技术排优先级**
   - 按"预期信息增益 × 成功概率 ÷ 成本"排序。默认启发：汇点或生命周期规则明确 → 数据流/污点优先；条件可算术化且范围小 → 符号执行；真实输入 + 崩溃 oracle + 合法种子 → fuzz 优先。
   - 完成标准: 给出排序表，每项写明第一动作、预期产物与预算上限（人时/机时）。

5. **设计组合流水线**
   - 默认链路：静态定位危险汇点 → 污点缩小候选流 → 符号执行/concolic 求解卡住的条件 → fuzz 在真实执行中验证并扩展 → 崩溃去重与根因分析。明确每一段的输入、输出和交接格式。
   - 完成标准: 画出流水线图，标出每段消费谁的产物（sink 清单、候选种子、可满足输入、crash 集），并指定回灌路径。

6. **设置止损点**
   - 为每段预设时间/状态上限与可观测指标：新增 sink 数、新增边数、可满足输入数、唯一崩溃数。
   - 完成标准: 写出带数字阈值的停止规则和 fallback，而不是"再看看"。
   - 判停条件: 若 24 小时内 fuzz 无崩溃且静态无明确汇点，转为纯静态审计、扩大目标范围或更换输入通道；若符号执行状态数指数增长或 1 小时内无新可满足输入，停止全路径探索，改为选择性符号执行/concolic 单分支；若静态报告数百条且抽样均不可达，把静态结果降级为线索，先补路径可行性验证或转动态。

7. **执行并记录证据链**
   - 每个结论记录：所用技术、工具与参数、产物位置、置信度、覆盖范围与未覆盖部分。
   - 完成标准: 任一发现都能追溯到具体输入、路径或状态序列，报告中不出现"工具说存在"这种无证据结论。

8. **复盘并替换路线**
   - 对比各段"实际产出/投入"，若某路线连续两倍预算仍无产出，或瓶颈已转移到另一约束，就替换它并更新选型备忘录。
   - 完成标准: 产出一页复盘：保留什么、替换什么、下一轮预算如何调整，以及本轮"没有证明什么"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **只做单点语法检查**: 例如只查 `strcpy` 调用点或某个常量，模式匹配成本更低，做四类技术选型是过度工程。
- **已有明确崩溃，只需根因定位**: 应直接走 `crash-to-root-cause`；本 skill 解决的是"还没有线索时怎么分配预算"。
- **合规、客户或流程指定了必须使用的工具**: 选型空间已被外部约束封死，本 skill 的预算分配没有意义，只需按指定工具执行并记录其局限。
- **目标不可执行且无可用中间表示**: 既不能跑也不能建模，应先解决脱壳、反混淆、输入通道或插桩前提，而不是比较分析技术。
- **目标是纯逻辑漏洞且没有任何语义 oracle**: 四类技术都看不到"权限绕过/业务规则错误"，应转人工审计或业务语义测试；选型只会制造"已覆盖"的假象。

### 作者在书中警告的失败模式

- **ce-A03 认为已有检测方法能发现未知类型的漏洞**: 选型时若把某条路线当成"全覆盖"，就会把"工具没报"误当成"目标安全"；未知类型的触发条件尚未进入规则或模型，必须显式标注盲区并保留人工审计。
- **ce-B09 把静态污点分析报告直接当作已确认漏洞**: 若预算只分配到静态污点、不安排动态验证，不可达路径与不可能数据流会被当成真实漏洞上报；静态输出必须降级为候选清单。
- **ce-B12 把符号执行的理论路径完备性当成工程可用性**: 对大型或含循环的目标仍按"遍历所有路径"分配预算，会直接耗尽内存与时间；选型时必须先设状态数与时限，并准备切片、摘要或 concolic 替代。
- **ce-C03 把覆盖率当成漏洞概率或测试完成标准**: 把覆盖率数字当作 fuzz 阶段的验收标准，会在危险状态不可达时提前收工；fuzz 的交付物应是崩溃证据与可达性证据，而不是覆盖率本身。

### 作者的盲点 / 时代局限

- **低估工程成本**: 书中把四类技术讲成清晰流水线，但真实工作里的 harness 编写、IR 提升、别名与外部调用建模、规则维护、误报 triage 往往比算法本身更耗时；选型时必须把这些人时计入预算。
- **案例规模偏小**: cB05、cB12 是可手算的小程序，c-C09 是约 12 小时的 gif2png 实验；这些结果不能直接外推到大型闭源软件、浏览器或内核目标。
- **静态分析乐观**: 作者假设分析者能获得可用中间表示或插桩能力，对加壳、反调试、JIT、动态生成代码以及静态误报率讨论不足；这些前提不成立时，静态路线应被排除而不是硬套。
- **工具与平台偏旧**: 成书于 2022 年，示例以 32 位 x86 和 BAP/KLEE/AFL 为主；今天更常见 sanitizer 引导 fuzz、AFL++、混合 fuzz 与 ARM64 目标，具体工具选型需重新校准。
- **假设单一根因**: 书中案例默认漏洞可由一条数据流、一条路径或一个崩溃解释；真实漏洞常涉及多线程竞争、跨请求状态与环境组合，选型时应为这类目标额外保留人工分析与差分手段。

### 容易混淆的邻近方法论

- `vuln-analysis-strategy`: 已有崩溃/补丁后的取证路线；本 skill 是无线索时的技术预算分配，两者是"选方法"与"用方法"的关系。
- `coverage-guided-fuzzing`: 已选定 fuzz 后的闭环参数与停止条件；本 skill 决定 fuzz 是否入选以及它在流水线中的位置。
- `symbolic-execution`: 符号执行内部的建模、求解与路径爆炸处理；本 skill 只决定何时投入以及投给哪个分支。
- `dataflow-analysis-and-code-modeling`: 如何构建 CFG/SSA、写方程并求不动点；本 skill 只把其输出当作候选汇点。
- `taint-analysis`: source/sink 与传播/净化规则的配置；本 skill 只判断目标是否满足"source/sink 明确"这一前提。
