# 信任边界与不可信数据追踪

## R — 原文 (Reading)

> "在程序中定义清晰的信任边界，将可信和不可信数据（比如：数据库，文件流）分别存储。当数据要从不可信的一侧传输到可信一侧的时候，使用验证逻辑进行判断。"
>
> — GB/T 38674-2020, 5.1.1 i)

---

## I — 方法论骨架 (Interpretation)

边界不是架构图上那条框线，而是代码里"某个值第一次被当成可信"的那一行。要画的不是系统图，是数据控制权的地图。

判断边界的位置只有一条规则：谁能让这个值变成别的样子？数据控制权每转移一次，就多一条边界。HTTP 入口、消息队列消费、定时拉取与第三方回调、数据库读出口、缓存读出口、文件系统、子进程调用、配置与环境变量——每一处都是独立的新边界，不是一个总边界的不同侧面。

闸门应当是单向且唯一的：不可信侧的值只能经一个明确的验证点进入可信侧；可信副本与不可信副本分开存储，不共用同一个变量、容器或对象引用。混放的结果是后续代码分不清手里这一份到底验过没有。

"上游已经验过"不是通行证。A 验过的数据进入 B 之后仍是不可信输入，因为 B 的信任域与 A 不同，而消息、缓存、共享库还可能被第三个写入者污染。

每个安全关键动作（验证、编码、鉴别、加密、授权、写日志）都要先回答一个定位问题：这段代码跑在攻击者能改的那一侧，还是我能控制的那一侧？跑在客户端的一律降级为体验优化，判定要在服务端重做。

对边界外的值，内容、长度、类型、来源四项都不可假设。最常见的两类错位是把校验做在了错误的语义层（字符串前缀 vs 规范化后的路径），和把校验交给了错误的角色（浏览器 vs 服务端）。

## A1 — 书中的应用 (Past Application)

### 案例 1: XML 外部实体让解析器变成第二条取数通道（附录 A.2.1.1.7）

- **问题**: XML 从请求流进入，解析器使用默认配置直接解析。
- **方法论的使用**: 沿控制权走一遍——HTTP 入口是第一道边界，XML 文本本身不可信；解析器遇到 SYSTEM 标识时会代替调用方去读取本地 URI，控制权在这一刻第二次转移，从"解析数据"变成"发起 I/O"，而这一步前面没有闸门。
- **结论**: 边界必须画在"解析器主动取数"这个动作上，而不只是"参数有没有校验"；用实体解析器做白名单，白名单之外的实体返回空输入源。
- **结果（防住什么）**: 不修时，构造一个极小 XML 指向终端设备文件即可让服务线程阻塞，指向本地文件即可读出内容；白名单后非授权实体解析失败，越界取数被挡在解析层。

### 案例 2: 路径前缀检查被 `../` 绕过（附录 A.4.4.5）

- **问题**: 用户提交 path，代码只判断字符串是否以安全目录前缀开头，通过就执行删除。
- **方法论的使用**: 控制权在文件 API 处再次转移——在应用层它是普通字符串，到文件系统层会被重新解释（`../`、绝对路径、符号链接）。在字符串层做的验证保护不了下一层的语义，等于把闸门装在了河的另一边。
- **结论**: 先在目标层的语义上标准化（取规范路径），再校验结果是否仍落在安全根目录内，并且验证与使用必须是同一个对象；更稳的是维护合法资源名白名单，让路径不由输入直接决定。
- **结果（防住什么）**: 不修时 `/safe_dir/../important.dat` 通过前缀检查后删掉受保护文件；规范化后越界路径被拒绝，读写都被限制在安全根内。

### 案例 3: 隐藏字段被当成可信来源（附录 A.2.1.1.5）

- **问题**: 同一个请求里 visible 参数做了净化，hidden 参数原样输出到页面，理由是"用户改不了隐藏字段"。
- **方法论的使用**: hidden 只是浏览器的呈现属性，提交上来就是一个普通 HTTP 参数，与 visible 处在边界外的同一侧；把"界面上看不到"当成边界，等于把验证点画进了客户端。
- **结论**: 同一入口进来的所有参数同权处理，来源相同则信任级别相同。
- **结果（防住什么）**: 不修时在 URL 里直接给 hidden 赋值即可注入 HTML 与脚本，并可进一步窃取会话；同等净化后注入内容被转义。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 调用链变长：服务 A 用 HTTP 调 B，B 又消费消息队列再写缓存，需要回答"这条链上边界在哪、哪几处必须重新验证"。
2. 有人拿"前端已经校验了""网关已经鉴权了""这是内网调用"来论证后端可以不查。
3. 新接一类入口：第三方支付回调、文件导入、消息消费者、定时任务从外部接口拉数据、插件加载。
4. 复盘一个已经发生的问题："校验明明加了，为什么还能注入/越权"，需要定位校验装错了层或装错了侧。
5. 评审把模型输出、OCR 结果、第三方接口返回直接拼进查询或页面的功能。

### 语言信号 (用户的话里出现这些就应激活)

- "这个参数要不要校验 / 这个字段能不能信"（should I validate this parameter / can I trust this field）
- "上游已经校验过了 / 网关已经鉴权了"（already validated upstream / gateway already authenticated）
- "内网调用不用管吧 / 内部接口"（internal only, behind the gateway）
- "隐藏字段用户改不了 / 前端已经限制了"（hidden field is not editable / front-end already restricts it）
- "边界在哪 / 帮我画一下信任边界"（where is the trust boundary / trust boundary mapping）

### 与相邻 skill 的区分

- 与 `input-validation-output-encoding` 的区别：本 skill 决定"在哪里设闸门、闸门两侧各是谁"，后者决定"闸门里放什么规则、出口用哪套编码"。先定边界，再选规则。
- 与 `authorization-and-least-privilege` 的区别：本 skill 问数据能否被信，后者问主体能否操作这个对象。对象级越权常被误当成输入校验问题。
- 与 `sensitive-data-lifecycle` 的区别：后者管"敏感数据不许跨界"，本 skill 提供"跨界点在哪里"的清单，是其前置。

## E — 可执行步骤 (Execution)

1. **列数据入口与控制权转移点**
   - 完成标准: 产出一张清单，至少覆盖 HTTP 入口、消息消费、第三方回调与定时拉取、数据库读出口、缓存读出口、文件系统、子进程、配置与环境变量八类；每一项标注"谁可以写这个值"。
   - 判停条件: 若某一项无法确定谁能写，直接标记为不可信，跳到步骤 3 按不可信处理，不得默认可信。

2. **标出"第一次信任该值"的那一行**
   - 完成标准: 每个入口都能指到具体函数或代码行；同一个值在链路上被多次信任时，每次都要标出（不是只标第一次）。

3. **在每个跨界点装闸门并把两侧分开**
   - 完成标准: 跨界处存在明确的验证或编码调用；可信副本与不可信副本不共用同一变量或容器；验证失败的分支是拒绝，不是改写后继续。

4. **复核所有"上游已验证"的传递假设**
   - 完成标准: 每个下游要么有自己的验证点，要么有一条书面理由，且该理由与两者是否同处一个信任域一致。
   - 判停条件: 若上下游跨服务、跨进程或经消息队列/缓存中转，跳到步骤 3 为下游重新加闸门。

5. **逐项定位安全关键动作的执行侧**
   - 完成标准: 验证、编码、鉴别、加密、授权、日志六类动作各有一行"执行位置"结论；落在客户端的已标注为体验优化，并在服务端找到对应实现。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单进程、单入口、无外部输入的离线计算或数据迁移脚本：边界只有一处，画图收益接近零，直接按输入校验做即可。
- 纯密码学算法与参数选型：问题出在算法、模式、密钥长度或 IV，不在边界位置。
- 边界已经确认、只差"该转义成什么"：属于输出编码规则问题，用 `input-validation-output-encoding` 更直接。
- 内存破坏、并发竞态、资源泄漏的定位：边界画得再准也挡不住越界写与 TOCTOU，应转内存与并发类方法论。

### 作者在书中警告的失败模式

- **ce06 信任隐藏字段与客户端状态**：hidden、readonly、前端路由守卫都只是 UI 约定，攻击者改包或直接构造请求即可绕过；把"界面上看不到"当边界，等于把授权与计价交给攻击者。
- **ce01 对验证失败的数据做"修复"**：闸门一旦允许"修一下再放行"，下游拿到的就不是当初被验证过的那个值；修复分支提前返回还会截断后续校验，闸门形同虚设。
- **ce12 以为集中化就等于没有遗漏**：统一验证器只覆盖经过它的入口，文件导入、消息消费、内部 RPC、老接口会形成影子入口；团队看到"框架已统一"便停止追问，单点缺陷被放大到全系统。

### 作者的盲点 / 时代局限

- 标准假设信任边界可以清晰画出。在微服务、消息队列、插件化架构里，边界是动态且重叠的：一条消息的写入者可能是任意服务，一份缓存可能被多个域读写，"上游是谁"本身就不确定。此时边界清单必须按"最后写入者"而非"调用方"来定。
- 框架完全缺位 LLM 应用：模型输出、检索召回内容、工具调用返回值都应视为边界外数据，而标准里没有这一类边界；把它当可信等于把提示注入与间接注入直接放进可信侧。

### 容易混淆的邻近方法论

- 输入验证与输出编码：本 skill 决定闸门位置与两侧归属，后者决定闸门内的规则与出口编码，二者串联而非替代。
- 授权与最小权限：数据可信 ≠ 有权访问，两套判定必须分别做，缺一都会留下越权面。
