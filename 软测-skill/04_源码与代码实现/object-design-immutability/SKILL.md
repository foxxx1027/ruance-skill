# 面向对象安全设计：不变量与防御性复制

## R — 原文 (Reading)

> 对基类的扩展，应保持由基类提供的不变性。……数据成员需要声明为私有。……禁止返回类的私有可变成员的引用。可返回一个指向内部可变成员的防御性副本的引用，从而保护内部状态不会被非预期地修改。……如果程序逻辑对可变变量进行验证和安全检查后，该变量的值被篡改，就会发生TOCTOU漏洞。
>
> — GB/T 38674-2020, 6.1 a) c) f) g)

---

## I — 方法论骨架 (Interpretation)

类的不变量就是它的安全属性："金额不为负""权限只增不减""构造完成后字段不再变"——这些一旦被外部改掉，所有依赖它们的校验同时失效。

所以第一个动作是把不变量写出来，再决定谁能改：数据成员私有；要读就返回副本；要写就走封装器，并在封装器里重新检查。

继承是第二条破坏路径：子类可以重写安全检查方法，基类改动也可以让子类处于非法状态。安全关键方法要 final 或 private，关键基类只对受信子类开放。

可变状态还制造时间窗口：校验时读到的值与使用时读到的值可以不同（TOCTOU）。依赖可变值的判断必须先取快照或复制，而不是"再检查一遍"。

序列化与复制是第三条：含秘密的类不应可复制、可序列化；半初始化对象不得逸出；嵌套类不能成为外部类私有成员的旁路。

判断一个类是否"设计安全"，只需问四句：不变量是什么？谁能改？跨边界给的是引用还是副本？有没有一条不经过封装器的旁路？

## A1 — 书中的应用 (Past Application)

### 案例 1: public static final 数组泄露内部可变状态（附录 A.3.1.3）
- **问题**: 类把配置数组声明为 public static final 直接暴露，作者的理由是"final 了，改不了"。
- **方法论的使用**: 按 6.1 c) f) 拆开"引用不可变"与"内容不可变"：final 只固定引用，数组元素仍可被任意持有者改写；再检查是否有封装器。
- **结论**: 客户端代码可以替换数组内容，之后所有基于该数组的安全判断都读到被污染的数据。规范做法是改为 private static final，并让访问器返回 clone 出的副本（附录 A.3.1.3）。
- **后果/防住什么**: 不修则共享状态被外部改写且难以复现；修后外部只拿到副本，类的不变量重新成立。

### 案例 2: 构造方法中调用可覆写方法（附录 A.3.1.4）
- **问题**: 基类构造函数里调用一个 public 的 doLogic()，子类重写了它并在其中使用自己的字段。
- **方法论的使用**: 用 6.1 a) l) 检查"构造未完成时对象是否对外可见"：构造期调用可覆写方法会把 this 提前交给子类代码，此时子类字段仍是默认值。
- **结论**: 创建子类实例时，doLogic() 打印出的 color 是 null 而不是构造器随后赋的 "Red"。规范做法是把该方法声明为 final 或 private，使构造期只执行基类自己的逻辑（附录 A.3.1.4）。
- **后果/防住什么**: 不修则读到未初始化数据、产生预期外行为，并把半成品对象暴露给其他线程；修后构造期不再有可覆写入口。

### 案例 3: 做安全检测的方法没有封住覆写（附录 A.3.1.5、A.3.1.6）
- **问题**: readSensitiveFile() 内部先请求 SecurityManager 检查读权限，但方法本身是 public 且非 final。
- **方法论的使用**: 按 6.1 a) i) 追问"子类能否推翻这条安全假设"：恶意子类只要重写该方法并省略检查，就能直接读文件。
- **结论**: 安全检测方法必须声明为 private 或 final；同样，覆写时不得扩大被覆写方法的可访问性（附录 A.3.1.5、A.3.1.6）。
- **后果/防住什么**: 不修则继承体系成为绕过授权的官方通道；修后检测逻辑不可被替换，扩展不再削弱安全性。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计对外 SDK、领域对象、配置对象或缓存对象，需要决定 getter 返回引用还是副本。
2. 代码里出现 public 字段、可变的 static 集合、Date/数组/List 直接透出，评审时说不清风险。
3. 出现"校验通过了但值还是被改了"的偶发问题，怀疑 TOCTOU。
4. 类里含密钥、口令、令牌，却在实现 Cloneable、Serializable 或使用深度拷贝框架。
5. 使用继承扩展基类，或要修改一个被大量子类继承的基类。

### 语言信号 (用户的话里出现这些就应激活)

- "不可变 / immutable / 只读视图 / unmodifiable"
- "防御性复制 / defensive copy / 返回副本还是引用"
- "不变量 / invariant / 封装被绕过"
- "final 了为什么还能改"
- "TOCTOU / 校验之后被改 / 检查和使用的间隙"
- "这个类能不能序列化 / 能不能 clone"

### 与相邻 skill 的区分

- 与 `concurrency-safety` 的区别: 后者解决"多线程同时访问共享可变数据"的同步与可见性；本 skill 解决"外部代码本来就不该拿到可写入口"的结构问题，两者常叠加但不等价。
- 与 `sensitive-data-lifecycle` 的区别: 后者关心字段是否敏感、如何加密与清理；本 skill 关心含秘密的类是否可被复制/序列化而扩散。
- 与 `function-and-exception-safety` 的区别: 后者管函数入参与返回值校验；本 skill 管类边界上"给出去的是本体还是副本"。

## E — 可执行步骤 (Execution)

1. **写出这个类的不变量**
   - 完成标准: 用三到五条可判定的句子描述"任何时候都必须为真"的属性（如金额≥0、状态只能单向流转、密钥构造后不可读），并指出哪条是安全属性。
   - 判停条件: 若写不出任何不变量（纯数据袋且不跨信任边界），跳到步骤 4 只做引用泄露检查。

2. **封住写入路径**
   - 完成标准: 所有数据成员私有；写操作只经封装器且封装器内重做校验；安全关键方法为 final/private；关键基类不可被任意子类扩展。
   - 判停条件: 若框架强制要求公开 setter（如某些 ORM），记录该例外并改为在持久化回调中恢复不变量。

3. **封住读出路径**
   - 完成标准: 返回可变成员（集合、数组、Date、可变领域对象）时一律返回副本或不可变视图；getter 列表逐个核对，无一处返回内部引用。
   - 判停条件: 若返回的是不可变对象或值类型，可标注"无需复制"并说明依据。

4. **处理复制与序列化**
   - 完成标准: 含秘密的类显式禁用 clone/序列化（或自定义 writeObject 时剔除字段）；不可序列化对象不落盘；半初始化对象不在构造期逸出（构造器不调用可覆写方法、不注册监听、不启动线程）。
   - 判停条件: 若序列化仅用于同进程缓存且不落盘，可降级为"确认不写出敏感字段"。

5. **用攻击视角回放**
   - 完成标准: 写一个"恶意调用方"测试：尝试改返回的集合/数组、尝试用子类重写检查方法、尝试反序列化含秘密的对象，三者都应失败或被安全处理。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 一次性脚本、本地数据转换、无外部调用方的内部 DTO：防御性复制只增加分配与噪音，收益接近于零。
- 语言与运行时已保证值语义或默认不可变（如 Rust 所有权、Haskell、Swift 结构体、Java record 的浅不可变）：不要照搬 Java 写法，应改写为"深不可变"与内部可变性检查。
- 极致性能的数值/批处理路径：每字段复制会改变复杂度，需先量化开销，再决定用不可变视图、冻结对象或所有权转移替代。
- 只读配置在启动期构造、之后无写入：不必每次访问都复制，但仍须禁止外部持有可变引用。
- 需要解决的是多线程同步与可见性：那是锁与内存序问题，给对象加副本不会消除数据竞争。

### 作者在书中警告的失败模式

- **ce16 共享可变状态**：校验与使用之间重新读取同一个可变变量，或把用户数据放进单例的实例字段，A 用户的数据会出现在 B 用户的响应里；返回内部集合引用等于把不变量交给调用方。
- **ce17 看似正确的并发优化**：双重检查锁定中实例字段未加 volatile，对象先被赋值、后完成初始化，其他线程看到非 null 就使用半成品——正是 6.1 l) 所说"未完全初始化的对象不得对外可见"。
- **ce06 把"界面上看不到"当成"不可修改"**：与把 final 当不可变同构，隐藏、只读、final 都只是约定，真正的边界在"是否给出可写入口"。

### 作者的盲点 / 时代局限

- 默认 Java 语境：public/private、Cloneable、Serializable、final 都是 Java 机制；对 Kotlin data class、Swift struct、Go 值拷贝、Python 无真私有，需要重新映射为"能否取得可变引用"这一本质问题。
- 未讨论自动生成代码绕过封装：Lombok 的 @Data/@Setter、Kotlin data class 的 copy()/componentN()、Jackson 的字段反射注入，都能在不经过封装器的情况下改写"私有"字段。
- 未讨论不可变集合的浅层性：List.copyOf 只冻结容器，元素本身仍可变；深不可变需要逐层处理，标准没有给出层次划分。
- 未涉及模块系统与反射（JPMS、setAccessible）下的封装失效，也未讨论内存模型对 final 字段安全发布的保证。

### 容易混淆的邻近方法论

- `concurrency-safety` 的锁与可见性规则：本 skill 消除的是"可写入口"，不是"并发写冲突"；有副本也不代表可以不同步。
- `sensitive-data-lifecycle` 的"少存、短存、不落客户端"：本 skill 只阻止秘密通过复制/序列化扩散，是否该存在由前者决定。
