# SSRF、XXE、模板注入与 NoSQL/命令注入（工程检查清单）

## R — 原文 (Reading)

> SQL 注入、NoSQL 注入、命令注入
>
> XSS、模板注入、XXE
>
> SSRF、路径遍历、文件上传/包含
>
> 反序列化、表达式注入、缓冲区溢出
>
> — 用户，《漏洞筛查覆盖框架》第 1 类「输入验证与输出处理」，2026-10-19

本 skill 只承接其中 NoSQL 注入、命令注入、模板注入、XXE、SSRF；SQLi/XSS/路径遍历/文件上传/反序列化/缓冲区溢出由相邻 skill 负责（见 A2「与相邻 skill 的区分」）。

## I — 方法论骨架 (Interpretation)

1. **先判输入进入哪一种解释器，而不是先套 payload。** 把所有外部可控输入（查询串、JSON/XML 请求体、表单、Header、Cookie、文件名、URL 参数、WebSocket 消息）列出来，标出它最终被谁解释：URL 客户端（SSRF）、XML 解析器（XXE）、模板引擎（SSTI）、NoSQL 查询构造器、系统 shell（命令注入）。同一个参数可能同时进入多层解释器，例如“URL 先被白名单正则检查，再被 HTTP 客户端解析，最后被下游服务二次解析”。设计缺陷是“把用户输入直接当语法或目标地址”，实现缺陷是“检查与执行对同一字符串理解不同”，配置问题则是“解析器默认开启危险能力或服务账号权限过大”；三者要分开记录，修复落点完全不同。

2. **URL 客户端（SSRF）先看可达性，再做最小对照。** 先只读核查：服务端是否允许访问任意目标、是否有出站白名单/网段限制、是否禁跳转、是否限制协议与端口、能否访问云元数据地址。再做最小对照：把 URL 指向自己控制的监听端（域名与端口均自控），观察是否收到请求、请求头与源地址是什么；合法外部地址与内网地址的结果差异只是辅助，不能替代自控监听。最易漏的是 URL 解析歧义（`@`、反斜杠、大小写、编码、IPv6、十进制 IP）、302 跳转后的二次请求、DNS rebinding（第一次解析到允许地址、第二次解析到内网）、以及“只校验前缀域名”被 `evil.example.com.attacker.tld` 一类构造绕过。设计缺陷是没有出站策略，实现缺陷是校验函数与实际 HTTP 客户端解析不一致，配置问题是网络层允许访问元数据或管理网段。

3. **XML 解析器（XXE）先确认 DTD 与实体能力。** 先只读核查解析器配置：是否允许 DOCTYPE、是否解析外部实体、是否允许参数实体与外部 DTD、是否开启 XInclude，以及解析失败时是否回显错误。再做最小对照：内部实体与外部实体各一组，外部实体指向自己控制的 HTTP/FTP 监听，观察是否回连；有回显时验证本地文件读取，无回显时用带外信道。常见误判是“关掉了外部实体就安全”，却仍允许 DTD、参数实体或 XInclude；另一个盲区是只测 SOAP/XML 接口，漏掉 SVG、Office 文档、SAML、RSS、配置导入等隐藏解析入口。设计缺陷是把不可信 XML 交给默认开启 DTD 的解析器，实现缺陷是禁用项不完整，配置问题则是解析器版本/默认值不安全。

4. **模板引擎（SSTI）先识别引擎与上下文，再做表达式对照。** 先确认模板语言（服务端模板、前端模板、邮件模板、报表模板）、输入落在文本/属性/JS/代码哪个上下文，以及是否经过沙箱。最小对照用无害表达式与字面量比较，例如同一位置分别传入普通字符串与引擎的算术表达式，观察是否被求值；不要一上来就用系统命令。设计缺陷是“把用户输入当模板源码编译”，实现缺陷是“拼接模板字符串且转义只覆盖 HTML 上下文”，配置问题可能是调试模式暴露了模板错误与上下文。最易漏的是只测一种分隔符、只测主模板漏掉邮件/通知模板、把 HTML 转义误当成模板沙箱，以及沙箱版本已知的逃逸链未核对。

5. **NoSQL 查询先看类型与操作符，而不是只看字符串拼接。** 先确认请求体如何进入查询：是字符串拼接、对象直接传入，还是经过 schema 校验。最小对照围绕类型混淆与操作符展开：同一字段分别传字符串与对象、传 `$ne`/`$gt`/`$regex`/`$where` 等操作符，观察认证或查询结果是否改变；用自有测试账号，不碰真实用户。常见误判是“用了 ORM 就没有注入”，但把整个请求体传入 `find()`、把查询条件从 JSON 直接反序列化、或在 `$where` 中拼接字符串仍然危险。设计缺陷是查询构造器接受任意操作符，实现缺陷是只校验字段值不校验类型，配置问题是无认证或高权限数据库账号放大了影响。

6. **系统 shell 先看调用方式，再测参数边界。** 先确认代码是否用 shell 解释器执行字符串、是否拼接用户输入、是否只做黑名单、是否把用户输入当参数而非命令。最小对照优先用无破坏性的时间差或自控带外请求，比较普通参数与含分隔符/换行/引号/编码变体的参数；同时检查“参数注入”（用户控制以 `-`/`--` 开头的参数，改变程序行为）而不只是 `;`、`|`、`&&`。设计缺陷是把不可信输入交给 shell，实现缺陷是黑名单遗漏或转义不完整，配置问题则是服务以高权限账号运行、可写系统目录。最易漏的是换行、制表符、环境变量展开、Windows 命令行解析差异，以及只测一个参数漏掉数组型参数或文件名参数。

7. **最后统一处理“过滤/解析差异”，再用回显或带外信道确认。** 把每个候选的链路写成“输入 → 解码/规范化 → 校验 → 解释器解析 → 二次请求/执行”，标出校验器与执行器理解不一致的位置：URL 解析器差异、重定向与 DNS rebinding、XML 实体展开与 DTD、模板沙箱边界、NoSQL 类型强制、shell 元字符与参数解析。验证顺序是：先无害回显，再自控带外（DNS/HTTP），最后才考虑时间盲与影响验证；所有带外请求只打自己控制的域名，所有主动测试仅在授权范围内。若两种独立构造都不能产生可解释的差异，应记录“未证实”，不要用无穷变体硬碰。

## A1 — 书中的应用 (Past Application)

> 本 skill 为工程清单型，没有单一书籍案例；以下为公开标准条款映射，不虚构事件细节。

### 标准映射 1: OWASP A03:2021 Injection
- **条款**: OWASP Top 10 2021 A03:2021 Injection。
- **对应检查**: 真实系统里通常表现为：用户输入被拼进模板源码并被引擎求值、请求体对象直接进入 NoSQL 查询构造器、命令字符串被交给 shell 解释；同一输入在过滤层被当作数据、在执行层被当作语法。
- **落到本 skill**: 用 I 段第 4、5、6 模块分别建立模板、NoSQL、shell 的“输入—校验—解释器”链路，再按 E 段第 5–7 步做无害对照，产出请求、响应、时间差或带外回连证据。

### 标准映射 2: OWASP A10:2021 Server-Side Request Forgery (SSRF)
- **条款**: OWASP Top 10 2021 A10:2021 Server-Side Request Forgery (SSRF)。
- **对应检查**: 真实系统里通常表现为：服务端根据用户提供的 URL 发起请求，未限制目标网段、协议、端口与跳转，导致可访问内网服务或云元数据；XXE 的外部实体也会形成同类出站请求。
- **落到本 skill**: 用 I 段第 2、3 模块核查出站策略与 XML 外部实体能力，再按 E 段第 3–4 步把自己的监听端作为唯一目标，记录回连来源、请求内容与跳转/DNS 行为作为证据。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 图片抓取、URL 预览、Webhook、PDF 渲染、代理下载等功能接收完整 URL，怀疑服务端可以访问内网或云元数据。
2. 接口接收 XML、SOAP、SVG、SAML 或 Office 文档，解析时报错或能回显文件内容，想确认是否存在 XXE。
3. 页面或邮件模板里渲染用户昵称、签名、报表字段，输入算术表达式后页面出现计算结果，怀疑模板注入。
4. 登录或查询接口使用 MongoDB 等 NoSQL 数据库，把请求体对象直接传入查询，怀疑可以用操作符绕过认证或拖数据。
5. 运维工具、定时任务、文件转换服务把用户参数拼进系统命令，出现延迟、报错或异常进程，想确认命令注入。
6. 已经有一个可疑参数，但不确定它进入的是 URL 客户端、XML 解析器、模板引擎、NoSQL 查询还是 shell，需要先选对验证路线。

### 语言信号 (用户的话里出现这些就应激活)

- “这个参数是完整 URL，服务端会去请求它”
- “填自己服务器的地址能看到回连，能不能读内网”
- “只允许 http/https，也禁了内网 IP，还有没有别的办法”
- “XML 里加 DOCTYPE 会报错，是不是就不能 XXE 了”
- “响应里把文件内容带出来了，但看不到报错”
- “模板里输入 {{7*7}} 页面显示 49”
- “用户昵称在邮件模板里也会渲染”
- “Mongo 登录把 password 改成对象就进去了”
- “命令里带分号没反应，带换行好像会延迟”
- “这个参数会拼到 shell 里，但过滤了特殊字符”

英文关键词：SSRF、XXE、SSTI、NoSQL injection、command injection。

### 与相邻 skill 的区分

- 与 `non-memory-vulnerability-analysis` 的区别：后者处理 SQLi、盲注、XSS、路径遍历、格式化串与编码绕过；本 skill 只处理 URL 客户端、XML 解析器、模板引擎、NoSQL 查询与系统 shell 这五类解释器。参数拼进 SQL 走前者；参数拼进 Mongo 查询、模板或 shell 走本 skill。
- 与 `upload-parser-bypass-audit` 的区别：后者专攻上传后的扩展名、MIME、魔术字节与解析器判定绕过；本 skill 只在“上传的 XML/SVG/文档进入 XML 解析器并触发 XXE”这一交叉点接手，文件类型判定本身仍归后者。
- 与 `java-deserialization-entry-enumeration` 的区别：后者枚举 Java 反序列化入口与 gadget 链；本 skill 不处理序列化数据，只处理文本/结构化输入进入解释器的路径。看到 `rO0AB`、`aced` 一类序列化标记，走前者。
- 与 `crash-to-root-cause` 的区别：本 skill 不做内存破坏定位；一旦解析器崩溃表现为越界读写、返回地址被覆盖或堆元数据异常，转后者。
- 与 `api-and-interface-security` 的区别：后者按接口检查认证、授权、限流、批量赋值与文档暴露；本 skill 只深入“接口参数进入哪种解释器、如何验证”。接口本身缺少鉴权，走前者；接口参数能触发 SSRF/SSTI，走本 skill。
- 与 `appsec-tooling-and-threat-modeling` 的区别：后者负责扫描工具编排、结果分诊与威胁建模；本 skill 是在已锁定可疑参数后的手工验证流程。扫描器报了一个“可能的 SSRF”，需要确认是否真实，走本 skill。
- 与 `web-minimal-exposure` 的区别：后者看对外暴露面与最小化；本 skill 看已暴露功能内部的解释器边界。

## E — 可执行步骤 (Execution)

1. **建“输入点 × 解释器”矩阵**
   - 动作: 列出所有外部可控输入及其最终消费点，标注进入的是 URL 客户端、XML 解析器、模板引擎、NoSQL 查询还是系统 shell；同时标出中间的解码、规范化、白名单与二次请求。
   - 完成标准: 每个输入点都有明确的解释器归属和验证目标，交叉点（如 XML 里的 URL、模板里的对象）单独标注。
   - 判停条件: 若输入点或解释器归属无法确认，先停在清单阶段补代码/流量证据，不进入 payload 构造。

2. **只读核查解释器与出站配置**
   - 动作: 核查服务端出站策略、HTTP 客户端是否跟随跳转、是否限制协议/端口/网段；XML 是否允许 DTD/外部实体/XInclude；模板引擎类型与沙箱；NoSQL 查询构造方式与数据库账号权限；命令调用是否经过 shell 及服务账号权限。
   - 完成标准: 形成“解释器 × 危险能力 × 当前配置 × 证据位置”表，能指出至少一个可疑能力或明确排除。
   - 判停条件: 若配置显示危险能力已完整关闭（如 DTD 禁用且无 XInclude、模板不接受用户源码、查询强制 schema），记录“已防护”，转向其他输入点。

3. **SSRF 最小对照（仅授权范围）**
   - 动作: 把目标 URL 指向自己控制的监听端，观察是否回连、请求头、源地址与跳转行为；再测试 URL 解析变体（`@`、反斜杠、编码、IPv6、十进制 IP）、302 跳转与 DNS rebinding 的自控域名。禁止把内网或第三方地址作为主动探测目标。
   - 完成标准: 能证明“服务端确实按用户提供的目标发起请求”，并记录哪些变体绕过了校验。
   - 判停条件: 若出站被网络层完全阻断且无任何回连/错误差异，停止加码，记录“网络层已封堵，残余风险为 X”。

4. **XXE 最小对照（仅授权范围）**
   - 动作: 分别提交内部实体与外部实体，外部实体只指向自己控制的 HTTP/FTP 监听；有回显时用无害本地文件验证读取，无回显时观察带外回连；再检查参数实体、外部 DTD 与 XInclude。
   - 完成标准: 能区分“解析器拒绝 DTD”“允许内部实体但不解析外部实体”“外部实体可回连”三种状态，并有原始响应或带外日志。
   - 判停条件: 若解析器完全禁用 DTD/外部实体且无其他实体入口，记录“已防护”，不要用超大实体做拒绝服务验证。

5. **SSTI 最小对照（仅授权范围）**
   - 动作: 先识别引擎与上下文，再用无害算术/字符串表达式与字面量做对照；确认求值后，检查沙箱与对象访问边界。不要直接执行系统命令或读写生产文件。
   - 完成标准: 能证明“用户输入被模板引擎当表达式求值”，并记录引擎、上下文、分隔符与沙箱状态。
   - 判停条件: 若输入只被当作纯文本且所有模板都使用固定模板+参数绑定，记录“已防护”，转向其他解释器。

6. **NoSQL 最小对照（仅授权范围）**
   - 动作: 使用自有测试账号，比较字符串值与对象值、普通值与操作符（`$ne`/`$gt`/`$regex`/`$where`）的查询/认证结果；检查请求体是否被整体传入查询构造器。
   - 完成标准: 能证明类型混淆或操作符注入改变了查询语义，并记录请求体、响应差异与受影响的数据范围。
   - 判停条件: 若服务端对每个字段做严格类型与枚举校验，且查询不接受任意操作符，记录“已防护”。

7. **命令注入最小对照（仅授权范围）**
   - 动作: 优先用时间差或自控带外请求做无害对照，比较普通参数与含分隔符、换行、引号、编码变体、`-`/`--` 参数的差异；检查是否存在参数注入而非仅 shell 元字符注入。
   - 完成标准: 能证明用户输入改变了被执行命令或参数语义，并记录时间差、回连或输出差异。
   - 判停条件: 若命令使用参数数组且不做 shell 解释、输入经过严格白名单，记录“已防护”；任何可能破坏数据的命令一律不做。

8. **建立回显与带外信道**
   - 动作: 为每次验证使用唯一标识（子域名、路径、请求头），把 DNS/HTTP 回连、响应回显、错误差异与时间差分别记录；带外目标只能是自控基础设施。
   - 完成标准: 每次成功/失败都能归因到具体请求与具体变体，能排除缓存、CDN、健康检查造成的噪声。
   - 判停条件: 若带外平台不可用且目标无回显，只能输出“待验证”，不能凭盲猜定性。

9. **排除假阳性并判定影响**
   - 动作: 用至少两种独立构造复现同一结论，复查 WAF、缓存、代理、重定向与前端假象；按“可达目标（内网/元数据/文件/命令）—所需权限—数据范围—是否可组合”评估影响。
   - 完成标准: 每条结论有两条独立证据，能解释为何另一种构造不成立，并给出影响边界而非只说“存在漏洞”。
   - 判停条件: 若所有构造都依赖同一已修补的解析差异，停止加码，记录“该路径已封堵，残余风险为 X”。

10. **给出证据与修复建议**
    - 动作: 记录环境、输入点、完整请求、解析链、预期/实际结果与授权依据；修复建议落到根因：出站白名单与禁跳转、禁用 DTD/外部实体、模板固定+参数绑定、查询 schema 与类型校验、命令参数数组与最小权限。
    - 完成标准: 第三方可按记录独立复现；修复建议能对应到具体解释器与代码位置，并附复测用例。
    - 判停条件: 无，结束。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 参数拼进 SQL、页面回显导致 XSS、路径遍历、格式化串或编码绕过：走 `non-memory-vulnerability-analysis`；本 skill 不重复这些判据。
- 上传文件的扩展名、MIME、魔术字节或解析器类型判定被绕过：走 `upload-parser-bypass-audit`；本 skill 只在 XML/SVG 等内容进入 XML 解析器时接管 XXE 部分。
- 输入是 Java 序列化数据、需要枚举反序列化入口与 gadget：走 `java-deserialization-entry-enumeration`；本 skill 不处理序列化流。
- 解析器崩溃表现为内存破坏、越界读写或可利用的堆布局：走 `crash-to-root-cause`；本 skill 不做内存取证。
- 需要的是扫描器编排、规则调优与结果分诊：走 `appsec-tooling-and-threat-modeling`；本 skill 只做已锁定目标的手工验证。
- 未取得书面授权，或验证需要请求内网、第三方系统、云元数据地址：不得执行；SSRF/XXE 的带外目标必须是自己控制的基础设施。
- 需要执行破坏性命令、写文件、删数据、发起拒绝服务或大实体展开：不得执行。
- 目标是绕过他人系统的出站限制、读取他人数据或获取未授权 shell：不属于防御性审查范围。

### 作者在书中警告的失败模式

- 本清单未覆盖“只校验 URL 前缀就安全”的失败：后缀域名、`@`、反斜杠、编码与重定向都能让校验器和 HTTP 客户端看到不同目标。
- 本清单未覆盖“禁了内网 IP 就挡住 SSRF”的失败：DNS rebinding、302 跳转、IPv6/十进制表示与下游二次解析仍可能到达内网。
- 本清单未覆盖“关闭外部实体就完成 XXE 防护”的失败：DTD、参数实体、外部 DTD 与 XInclude 是不同开关，需逐项确认。
- 本清单未覆盖“模板里做了 HTML 转义就不会被求值”的失败：HTML 上下文编码与模板表达式求值是两套机制。
- 本清单未覆盖“过滤了 `;` 就没有命令注入”的失败：换行、管道、命令替换、参数注入与 Windows 解析差异都可能绕过黑名单。
- 本清单未覆盖“用了 ORM/驱动就没有 NoSQL 注入”的失败：把请求体对象整体传入查询、允许任意操作符或在 `$where` 拼接字符串仍然危险。
- 本清单未覆盖“有回显才算漏洞”的失败：SSRF、盲 XXE、盲命令注入与盲 SSTI 都可能只通过带外或时间差体现。

### 作者的盲点 / 时代局限

- 本清单未覆盖不同语言 HTTP 客户端与 URL 解析器之间的具体差异，实际绕过需按目标运行时逐项验证。
- 本清单未覆盖云环境元数据地址、容器网络、服务网格与出口代理的具体行为，网络层封堵效果需结合部署架构确认。
- 本清单未覆盖 XML 解析器的版本差异与安全默认值变化，禁用项名称与生效范围应以目标版本文档为准。
- 本清单未覆盖各模板引擎沙箱的完整逃逸面，也未覆盖服务端渲染、客户端渲染与邮件模板之间的上下文差异。
- 本清单未覆盖 NoSQL 各数据库/驱动对操作符与类型强制的不同语义，具体行为需按目标产品验证。
- 本清单未覆盖命令注入在容器、Windows、PowerShell、CI Runner 等环境下的解析差异。
- 本清单未覆盖 GraphQL、gRPC、消息队列等协议特有的注入形态，这些应结合接口与协议类 skill 使用。

### 容易混淆的邻近方法论

- `non-memory-vulnerability-analysis`：SQL/HTML/路径/格式化串注入；本 skill 是 URL/XML/模板/NoSQL/shell 五类解释器。
- `upload-parser-bypass-audit`：文件类型判定与解析器绕过；本 skill 只接管 XML 类内容的实体解析。
- `java-deserialization-entry-enumeration`：序列化流与 gadget；本 skill 是文本/结构化输入的语法注入。
- `crash-to-root-cause`：崩溃后的内存根因定位；本 skill 是输入语义与解释器行为验证。
- `api-and-interface-security`：接口鉴权、限流与批量赋值；本 skill 是接口参数进入解释器后的注入判据。
- `appsec-tooling-and-threat-modeling`：工具编排与告警分诊；本 skill 是人工最小对照与证据固化。
- `web-minimal-exposure`：暴露面收敛；本 skill 是已暴露功能内部的解释器边界。
