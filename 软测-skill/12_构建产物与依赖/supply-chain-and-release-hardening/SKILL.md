# 供应链与交付加固

## R — 原文

> a） 搭建并维护统一的第三方软件仓库，并仅能从内部搭建的组件仓库获取第三方软件，不允许自行下载组件进行使用……c） 对第三方软件进行完整性验证测试，确保所用第三方软件未被篡改。……g） 关闭服务器上不需要的服务。h） 建议禁止自动目录列表功能。
>
> — GB/T 38674—2020，8.1 a) c)、8.3 g) h)；另见 8.1 d)–h)、8.2 a)–d)、8.3 a)–i)、6.6 a)–l)

## I — 方法论骨架

交付安全是一条链：依赖从哪来、构建怎么做、开发环境是否干净、产物里剩了什么、运行时开了什么。只审源码，等于只看了链条中间的一小段。

组件固定问四件事：来源（内部仓库或官方渠道，不随手下载）、完整性（哈希或签名，确认未被篡改）、时效（持续检测已知漏洞并及时升级）、许可（真实有效且不冲突）。四问分别对应投毒、篡改、过期版本、法律风险，缺一个就有一个盲区。用了私有镜像只解决了第一问。

构建链也要当成安全边界：判断依赖库版本，对加密与通信等关键库做哈希校验，宏定义不冲突，同一工程 Release/Debug 统一，版本信息不靠编译参数注入，头文件搜索路径受控且无歧义，多仓库源码配统一版本脚本，中间产物放在源码目录之外，谨慎使用自动生成的代码。

开发环境决定产物起点：编译器从官方渠道获取并打齐补丁，去掉调试等不必要的编译功能，开启安全编译选项；源码按权限存储、用变更管理记录改动；开发、测试、生产环境隔离，只对授权团队开放。

发布面是攻击者的第一手资料：清除调试与测试残留，配置信息可审计且受保护，删除用户可见的注释，客户端产物做混淆、签名与加固，删除不需要的文档与应用，关闭不需要的服务，禁止自动目录列表，系统组件保持已打补丁的稳定版本。

最小功能面贯穿资源层与环境层：判断标准不是关掉会不会出问题，而是开着它带来了什么攻击面、又换来了什么业务价值。数据库不必要的存储过程、服务与安装项同理。

一句话：包是真的、版本是对的，也不代表安全；必须能证明跑起来的产物就是审过的那份代码。

## A1 — 书中的应用

### 案例 1: Struts2 插件启用导致远程命令执行（附录 A.5.1.2，对应 8.1 b) d) f)）

- **问题**: 使用带 Struts1 插件的 Struts 2.3.x，把用户可控字符串拼进 ActionMessage，并保留了示例应用包。
- **方法论的使用**: 先用组件四问问时效与最小功能面——该插件已知有高危漏洞且业务并不需要；再把用户输入进入表达式求值视为组件配置放大了攻击面。
- **结论**: 不启用该插件、不部署示例应用；消息改用资源键，不把原始消息拼进 ActionMessage。
- **结果（防住什么）**: 不修时一个恶意字段值即可触发表达式求值并执行任意命令、取得主机权限；修正后注入面被关闭。

### 案例 2: 解析特数值导致线程挂起（附录 A.5.2.2，对应 8.2 a)）

- **问题**: 直接把请求参数交给浮点解析，运行在未打补丁的旧 JDK 上；特定区间的数值会让线程长时间挂起。
- **方法论的使用**: 环境安全要求运行组件为已打补丁的稳定版本；这类问题不是业务代码写错，而是开发与运行环境的组件版本落后，同时输入侧缺少范围校验。
- **结论**: 升级到修复该缺陷的 JDK 版本，并在解析前校验长度、字符与范围，对解析类操作设置超时或隔离。
- **结果（防住什么）**: 不修时少量特制请求即可挂起工作线程，形成拒绝服务；修正后非法数值被拒，组件缺陷已修复。

## A2 — 触发场景

### 用户会在什么情境下需要这个 skill?

1. 引入新依赖或升级大版本，需要确认这个包从哪来、是不是原版、能不能被锁定。
2. CI 构建出现多仓库版本漂移、头文件被同名文件劫持、Release 与 Debug 配置混用。
3. 发版或打镜像前做收口，检查调试接口、源码注释、示例应用、目录列表是否还在。
4. 团队已有私有镜像与内部仓库，认为供应链安全已经解决。
5. 安全评审发现组件带已知高危漏洞且业务不肯升级，需要判断发布产物与运行面还能怎么收口。

### 语言信号

- "这个包是不是官方原版 / 内部仓库能不能证明没被换过"（is this package the official one / can we prove the registry copy was not swapped）
- "私有镜像已经配了，供应链是不是就安全了"（private registry is configured, is supply chain solved）
- "发版前还要检查什么"（what to check before release）
- "构建产物和源码不一致"（build artifact does not match source）
- "镜像里还留着调试接口和示例应用"（debug endpoints and sample apps are still in the image）
- build hardening, release hardening, reproducible build, build chain

### 与相邻 skill 的区分

- 与 `supply-chain-and-dependency-security` 的区别：后者从"用了哪些依赖、有没有已知漏洞、要不要出 SBOM"入手，产出漏洞清单与修复优先级；本 skill 从"交付出去的这份产物是否可信"入手，产出构建链与发布面的核对结论。同一个组件漏洞，问"该不该紧急升级、怎么排优先级"归前者，问"能否证明发布的就是审过的那份代码、产物里还残留什么"归后者。
- 与 `sensitive-data-lifecycle` 的区别：后者管密钥、口令与敏感字段本身怎么存怎么清；本 skill 管组件来源、构建链与发布产物里的配置与残留。
- 与 `file-and-upload-safety` 的区别：后者处理运行期用户上传的文件；本 skill 处理随软件一起交付的组件、产物与运行环境。
- 与 `input-validation-output-encoding` 的区别：本 skill 可能顺带要求输入校验，但根因在组件版本或环境配置时，补校验只是补偿控制。

## E — 可执行步骤

1. **建组件与工具链台账**
   - 动作：列出直接与间接依赖、基础镜像、运行时、构建工具，标注来源、版本、锁定方式、许可证。
   - 完成标准：每个组件四项齐全；浮动版本范围、无锁文件、无法说明来源的项被标红。
   - 判停条件：若组件由平台统一提供且版本不可见，记为外部假设并写入残余风险，继续步骤 2。

2. **过组件四问**
   - 动作：逐项核对来源是否内部仓库或官方渠道、完整性是否有哈希或签名、时效是否有近期检测结果与高危漏洞、许可是否有效且不冲突。
   - 完成标准：每项有证据或明确缺口；存在可利用高危且无缓解的组件进入阻断清单。

3. **检查构建链**
   - 动作：核对依赖版本判断、关键库哈希、宏冲突、Release/Debug 统一、版本信息不靠编译参数、头文件路径受控且无歧义、多仓库版本脚本、中间产物与源码分离。
   - 完成标准：八项各有符合 / 不符合 / 不适用的结论；不符合项写明影响的产物范围。

4. **检查开发环境**
   - 动作：核对编译器来源与补丁、调试开关、安全编译选项、源码权限、变更管理、环境隔离。
   - 完成标准：六项各有证据；开发环境能直连生产或源码目录对全员可写即为阻断项。

5. **发布前收口**
   - 动作：检查调试与测试残留、配置保护与可审计、用户可见注释、客户端混淆签名加固、无用文档与服务、目录列表、系统组件补丁、数据库不必要功能。
   - 完成标准：抽查产物与运行环境，每项有已清 / 已关 / 有业务理由的结论；存在默认示例应用、调试接口或目录列表即为阻断项。

## B — 边界

### 不要在以下情况使用此 skill

- 问题在单个接口的越权、注入或会话设计：本 skill 只能提供环境与组件侧的兜底，不能替代对应的方法论。
- 需要判断某个已知 CVE 的利用条件、修复优先级，或要出 SBOM、排查依赖投毒：转 `supply-chain-and-dependency-security`；本 skill 只核对交付前的来源、完整性与发布面。
- 已经失陷后的入侵排查、取证与应急响应：本 skill 管交付前，不管运行期事件。
- 需要判定某许可证能否商用、是否构成侵权：本 skill 只标记冲突与缺口，不给法律结论。
- 需要设计 SBOM 格式、SLSA 等级、可复现构建的具体工程方案：标准未覆盖，本 skill 只能指出缺口，不能假装给出方法。
- EOL 平台无法升级组件：本 skill 只能给补偿控制与残余风险，不能给出合规结论。

### 作者在书中警告的失败模式

- **ce03 硬编码密钥与连接串**：密钥写进源码就等于进入每个开发者机器、每次构建产物和每份反编译结果；轮换还要重新发版，现实中就变成永不轮换，发布加固里的配置保护必须包含密钥外置与轮换。
- **ce23 供应链只做到可信仓库加 SCA**：认为内部仓库加一次扫描就够；现代攻击发生在包是真的、版本是对的前提下，抢注相似包名、劫持维护者账号、在安装脚本中执行代码、污染构建缓存，仅比对包名版本或扫已知漏洞都发现不了。
- **ce24 把标准当合规检查表**：逐条打勾会给出没有已知问题的错觉，业务逻辑绕过与架构级信任错配不在任何单条编码规则里，交付清单只能兜底。
- **ce22 密码学要求停留在用了安全算法**：只查是否调用加密接口，不查算法、模式、IV 与密钥来源，形式合规挡不住用了加密但仍可破。

### 作者的盲点 / 时代局限

- 供应链条目偏薄，未覆盖 SBOM、SLSA、可复现构建、依赖投毒与相似包名抢注，也未讨论 CI/CD 凭证泄露与构建缓存污染。
- 把发布加固写成一次性清单，没有流水线门禁、产物签名与溯源，无法证明跑起来的就是审过的那份代码。
- 条目并列却不给优先级与成本：升级组件与冻结版本冲突时没有取舍方法，中小团队无法判断先做哪几件。

### 容易混淆的邻近方法论

- 敏感数据生命周期与加密：它回答密钥和敏感字段怎么管，本 skill 回答这些配置在交付产物里有没有被保护与清理。
- 威胁建模：交付加固处理已知的组件与配置风险，威胁建模处理本系统特有的攻击路径，二者不能互相替代。
