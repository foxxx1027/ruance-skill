# 日志完整性与证据保全

## R — 原文 (Reading)

> "删除日志前必须先停止相应的服务，再进行删除即可。日志删除后务必要记得再打开相应的服务。"
>
> — 网络安全技术联盟 主编，第15章 15.3 清除服务器入侵日志（PAGE 288）

---

## I — 方法论骨架 (Interpretation)

日志不是默认存在、默认可信的：它可能没开、保留期太短、被轮转覆盖，或被管理员/攻击者改到别处。
第一步是盘点资产：安全/系统/应用程序三类 Eventlog、注册表 Eventlog 子表与实际路径、IIS 每日 WWW/FTP 日志、Scheduler 日志，以及保留期与时钟。
第二步是先保全再分析：把现有日志连同“显示信息”导出，记录来源、时间、操作者与完整性信息，再在副本上分析。
第三步是从攻击者的机械约束反推检测点：删 WWW/FTP 日志要先停服务、当天文件被占用删不掉、删完还要重启服务。
因此服务停止/启动事件、日志文件缺失或时间断档、目录内批量删除、日志路径变更，都比“日志内容”更难完全隐藏。
第四步是多源交叉：单条日志可被删除或伪造，安全、系统、应用、IIS、Scheduler 与网络/账户记录的时间线要互相印证。
空日志不是清白证明，反而可能是清理痕迹；只查事件查看器会漏掉 IIS 与 Scheduler。
集中收集、哈希、只读/WORM 是本书没有的补强，必须明确标注为编者建议，不能冒充原文。
核心判断：先固定证据，再解释缺口；不能解释的断档按疑似篡改处理。

## A1 — 书中的应用 (Past Application)

### 案例 1: 清 WWW/FTP 日志的固定顺序（c31）

- **问题**: 作者要说明入侵后如何清除服务器日志；日志按天生成，当天的文件仍被对应服务占用。
- **方法论的使用**: 书中先给出 WWW/FTP 日志的默认目录与“每天一个文件”的规律，再演示：直接删除当天文件会失败，必须先停止对应服务、删除文件、再重新启动服务。这里不关注删除动作本身，而关注它被迫留下的顺序。
- **结论**: 清理日志不是无痕操作；服务停止/启动、日志文件缺失、当天记录断档，都是可检测的副作用。防御侧应监控服务状态与日志连续性，而不是只读日志内容。
- **结果**: 日志文件被删除、服务恢复运行（PAGE 288–289）；书中这个“必须停服务”的约束，正好反转为服务事件与日志断档两个检测点。

### 案例 2: 批处理 + 远程执行跨主机清日志（c32）

- **问题**: 单机手工清理效率低，攻击者需要在多台主机上批量清除日志。
- **方法论的使用**: 作者用批处理文件列出要删除的日志类型，再通过远程执行工具在目标主机运行；案例的重点不是命令写法，而是清理可以批量化、远程化。
- **结论**: 只保护本地日志目录不够；攻击者可以从另一台主机批量清除，因此防御侧需要集中留存、权限隔离与多源交叉。
- **结果**: 书中称可在远程主机清除日志文件（PAGE 289）；这反过来说明，本地日志缺失不能单独作为“没发生”的证据，必须结合网络、服务与账户记录。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 事件查看器几乎为空或关键时间段没有记录，用户问“是不是没被入侵”。
2. 发现 WWW/FTP 当天日志缺失、日志时间断档，或 IIS 服务莫名停止/重启。
3. 需要把日志导出交给运维/安全/外部分析人员，问导哪些、怎么保证换机可读。
4. 日志被管理员重定位，默认路径找不到；或多台主机日志分散，无法拼出时间线。
5. 要设计日志留存方案，问本地日志够不够、是否需要集中收集与完整性校验。

### 语言信号 (用户的话里出现这些就应激活)

- "事件查看器是空的" / "日志为空是不是没被入侵" / "日志被删了吗"
- "日志断档" / "当天日志没了" / "WWW 日志/FTP 日志缺失"
- "服务自己停了" / "IIS 重启过吗" / "日志路径被改了"
- "日志怎么导出" / "导出后换机打不开" / "日志保全/证据"
- "log cleared", "empty event log", "log gap", "log tampering", "evidence preservation", "export event log", "centralized logging"

### 与相邻 skill 的区分

- 与 `host-default-surface-convergence` 的区别：本 skill 只做日志盘点、检测与证据保全；账户、默认服务、共享等主机加固转该 skill。
- 与 `malware-triage-order` 的区别：本 skill 不负责恶意代码清除与样本处置；已失陷主机先隔离与保全，清除转该 skill。
- 与 `data-backup-recovery-discipline` 的区别：两者都涉及留存与恢复，但本 skill 的重点是证据完整性与篡改检测，不是业务数据备份策略。
- 与 SIEM/集中日志平台的区别：本 skill 给出保全要求与检测点，不负责平台选型与部署。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **盘点日志资产**
   - 完成标准: 列出安全/系统/应用程序三类 Eventlog、注册表 Eventlog 子表中的实际路径、IIS 每日 WWW/FTP 日志、Scheduler 日志，以及保留期、大小上限、审计开关与时钟状态；每项有实际路径或配置证据。
   - 判停条件: 若无权限读取注册表或日志目录，把缺口记录为“证据盲区”，不要用默认路径假设代替实际盘点。

2. **先保全再分析**
   - 完成标准: 导出时勾选“显示信息”（display information），记录来源主机、导出时间、操作者、日志范围与完整性校验值；导出文件在另一台机器上能正常打开并显示消息文本；原始文件另存只读副本。
   - 判停条件: 若导出会触发轮转或覆盖关键日志，先复制原始日志文件；若空间不足，优先保全安全/系统/应用程序与 IIS 当天日志。
   - 说明: 哈希、只读副本属于书中没有的补强，需标注为编者建议。

3. **从机械约束建立检测点**
   - 完成标准: 把“服务停止/启动、当天日志被占用、删除后必须重启、日志文件缺失或时间断档、日志路径变更、目录内批量删除”逐条映射到数据源与查询/事件类别；每条有可执行的核查方法。
   - 判停条件: 若日志已经为空，不要得出“清白”结论；跳到第 4 步做多源交叉，并明确哪些结论因证据缺失而无法成立。

4. **多源交叉**
   - 完成标准: 至少用两个独立来源（安全/系统/应用/IIS/Scheduler、网络流量、账户登录、备份任务、终端记录）对齐同一时间线；能解释的缺口标注解释，不能解释的缺口按疑似篡改处理。
   - 判停条件: 若只剩单一来源，降低结论置信度并写明局限，不把单条日志当作事实。

5. **集中留存与持续验证**
   - 完成标准: 日志实时外送到攻击者不易触及的位置，设置只读/WORM、访问控制、时钟同步、保留期与完整性校验；做一次“删除本地日志后仍能还原时间线”的演练。
   - 判停条件: 若暂时没有集中平台，至少做到异机只读副本 + 哈希 + 定期校验，并标注为补偿措施而非书中原文。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯应用报错、性能日志、业务审计指标分析：本 skill 不是日志分析工具，重点是完整性与证据保全。
- SIEM/集中日志平台选型与架构设计：本 skill 只给保全要求，不替代平台建设。
- 已失陷主机的恶意代码清除与样本处置：转 `malware-triage-order`；本 skill 只负责先保全证据与识别检测缺口。
- 司法级取证：书中的导出方法不足以满足监管链、哈希、WORM 与可采性要求；需要专业取证流程。
- 没有授权的主机：不要导出、复制或分析他人日志。
- **本 skill 只写防御侧检测与保全，不提供清日志的具体操作步骤。**

### 作者在书中警告的失败模式

- **空日志不是清白证明**：日志为空、关键时间段缺失或服务记录异常，都可能是清理痕迹，不能据此判断“没被入侵”。
- **只清事件查看器会漏 IIS/Scheduler**：Windows 事件日志之外，IIS 的 WWW/FTP 每日文件与 Scheduler 日志是独立资产；攻击者只清事件日志、或防御者只查事件查看器，都会留下盲区。
- **导出不含显示信息，换机不可读**：只导出原始记录而不带消息文本，换一台机器或缺少消息 DLL 时可能无法阅读。
- **只保护本地日志目录不够**：批处理 + 远程执行说明日志可以被跨主机批量清除，必须集中留存与权限隔离。
- **只看日志内容、不看服务状态**：清 WWW/FTP 日志必须先停服务，服务停止/启动本身就是检测点；只监控内容会漏掉删除动作。
- **默认路径假设**：管理员或攻击者可以把日志重定位到别处，只查默认目录会漏。

### 作者的盲点 / 时代局限

- 书中没有哈希、监管链、WORM、集中收集、时钟同步与保留期策略；这些只能作为编者补强，不能冒充原文。
- 书中以 2019 年 Windows 事件日志（.evt）与 IIS 日志为主，现代系统多为 .evtx、ETW、云审计与容器日志，字段与位置需要重新映射。
- 作者假设管理员拥有完全控制权、日志默认存在且可信，未讨论日志被内核级工具篡改、日志服务本身被替换等情形。
- 作者从攻击者视角演示清理，防御侧只给到“看日志/导出日志”，缺少完整性校验与证据链设计。

### 容易混淆的邻近方法论

- `data-backup-recovery-discipline`：备份关注可恢复性，证据保全关注不可篡改与可追溯；日志副本可以参考备份的异地/验证思路，但不能把“有备份”当成“证据可信”。
- `malware-triage-order`：负责恶意代码处置顺序；本 skill 负责在处置前固定日志证据并识别缺口。
- `host-default-surface-convergence`：负责账户、默认服务与共享等主机加固；本 skill 不重复这些配置，只处理日志资产与检测点。
- 日志分析/SIEM：分析回答“发生了什么”，本 skill 先回答“记录还在不在、可不可信、能不能作为证据”。

## 相关 skills（阶段 3 定稿）

- `host-default-surface-convergence`（composes-with）：账户锁定、失败登录与策略变更是否生效，要用日志验证；没有日志就无法证明加固落地。
- `remote-access-surface-audit`（composes-with）：远程入口的会话起止、来源地址与失败尝试都落在登录日志里，是本 skill 多源交叉的材料。
- `web-minimal-exposure`（composes-with）：网站侧的目录访问、错误回显与文件改动，需要 IIS 日志与文件时间线互相印证。
- `data-backup-recovery-discipline`（contrasts-with）：本 skill 关心证据是否完整、是否被篡改；业务数据的备份周期与还原演练归后者，备份任务本身只是时间线的一个来源。
