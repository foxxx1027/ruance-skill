# 02 移动端 App

这一层测的是跑在手机上的 App 与其安装包：APK、so 库、签名与加固壳，以及移动系统的漏洞面。典型被测物是一个 APK（自研的或被怀疑恶意的）、native 加密实现、重打包后的安装包。关注点是装到设备上的这坨二进制能不能被改、被调试、被打穿。

## 这一层最常见的四类问题

- 重打包后签名校验没做，改完照样安装、照样运行。
- 关键逻辑（加密、风控）藏在 so 库里，Java 层翻完什么也看不到。
- APK 申请了短信、无障碍、设备管理这类权限组合，行为像扣费马却没人判过。
- 移动端栈溢出/越界能稳定崩溃，但崩在哪一层、返回地址在哪说不清。

## 这一层的 skill

| skill | 作用 | 什么时候会用到 |
| --- | --- | --- |
| android-vulnerability-analysis | 按 APK/smali → so → 系统 Java → 系统 C/C++ → 内核分层调试，并分析签名校验机制与重打包绕过。 | 「App 一 attach 就闪退，崩在哪层」「加固壳的 so 怎么动态调」 |
| arm-mobile-overflow | 针对 WinCE/Windows Mobile 32 位 ARM 程序，重建内存地图与 ARM 调用约定后布置栈溢出 payload。 | 「手机上的 ARM 栈溢出怎么定位返回地址」「LR 和 PC 怎么用」 |
| android-malware-triage | 从 Manifest 权限、DEX 敏感 API 与模拟器行为快速判断 APK 是否恶意，并做反编译互证。 | 「这个 APK 是不是扣费木马」「权限组合看着可疑，要不要跑一下」 |

## 跨层可复用

- malware-sample-analysis（99_跨层通用方法）— APK 只是样本载体之一，载荷提取、配置解码与第一现场复现的方法通用。
- reverse-engineering-workflow（03_桌面与二进制程序）— 逆 so 库之前先定交付物、深度与起点，避免一头扎进汇编。
- vulnerability-mechanism-identification（99_跨层通用方法）— 先判是内存破坏、类型混淆还是逻辑缺陷，再决定走哪条路线。
- network-transport-and-session（09_网络与传输）— App 与服务端的证书锁定、会话与重放问题常和 App 侧一并评估。
- client-side-and-frontend-security（01_前端与浏览器端）— App 内嵌 WebView/H5 的 DOM 与跨窗口问题归 01。
- exploit-chain-construction（03_桌面与二进制程序）— 确认原语之后，移动端的控流与绕过仍按四段式体检。

## 和相邻层的分界

- 与 03 桌面与二进制：同样是逆向与利用，但 03 的对象是 PC/服务器上的 exe、dll、驱动与崩溃样本，02 的对象是随 App 分发的 APK/so 与移动系统。手法可借，对象不混。
- 与 01 前端：WebView 里的 H5 页面按 01 处理，App 原生层（Java/native/签名）按 02 处理。
- 与 99 通用方法：02 有明确的被测物（安装包/设备），99 只有方法与样本，不绑定平台。
