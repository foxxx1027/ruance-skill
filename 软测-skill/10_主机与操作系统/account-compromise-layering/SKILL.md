# 账号四层防护与止损优先

## R — 原文 (Reading)

> "当发现自己的微信账号被盗或手机丢失时，用户可以通过冻结微信号来保护账号安全。"
>
> — 网络安全技术联盟, 第7章 7.2 微信账号及密码的安全防护（PAGE 125）

---

## I — 方法论骨架 (Interpretation)

账号安全不是一个密码开关，而是四层互相兜底的资产。
凭证层决定别人能不能进来：唯一且不取自公开信息的密码、二次验证、可信的找回方式、登录设备清单。
隐私层决定进来后能看到和利用什么：聊天记录、绑定手机与邮箱、文件传输、授权应用。
支付层决定钱能不能被转走：支付密码、数字证书、钱包锁、免密支付与代充/礼品卡通道。
应急层决定发现后多快能止血：冻结、踢下线、挂失银行卡、官方申诉与解冻。
常规评估从凭证层开始，再查隐私与支付，最后确认应急路径真的走得通；但一旦正在发生损失，顺序反过来：先止损，后找回。
只改密码通常不够，因为凭据可能在输入侧被截获，或找回邮箱、已登录设备仍在攻击者手里；改密后仍被顶下线，说明别的层还开着。
结构性做法是把重要邮箱/账号与日常注册、论坛、订阅分开，降低被精准针对和撞库命中的概率。
单层修补一定会留下残余路径：密码改了但设备未清、设备清了但找回问题可猜、支付锁开了但免密或代充仍通。

## A1 — 书中的应用 (Past Application)

### 案例 1: 被盗后的止损——冻结微信与网上挂失银行卡
- **问题**: 作者的场景是“微信账号被盗或手机丢失”，账号与绑定银行卡同时暴露。
- **方法论的使用**: 把处置放在应急层，先冻结微信账号、再对银行卡办理网上挂失，而不是先尝试申诉找回或继续使用账号。
- **结论**: 发现异常后的第一目标是缩短损失窗口；冻结和挂失的入口必须提前知道，风险解除后再解冻。
- **结果**: 微信账号进入冻结状态，银行卡完成网上挂失，书中同时说明风险解除后可解冻账号（PAGE 125–126）。

### 案例 2: QQ简单盗——看不到进程不等于凭据安全
- **问题**: 作者演示用“QQ简单盗”生成木马并经 QQ 投递，目标运行后账号密码被回传。
- **方法论的使用**: 该案例说明凭据会在“输入侧”被截获，所以凭证层不能只有密码，还要有二次验证与登录设备核查；事后必须进入应急层止损，而不是只改密码。
- **结论**: 木马采用插入技术、不产生独立进程，任务管理器干净不代表凭据没被截获；密码泄露与设备失守要一起排查。
- **结果**: 测试邮箱先收到“测试发信”，木马运行后截获的账号密码被发送到攻击者指定的邮箱（PAGE 117–119）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 收到“异地登录/新设备登录”提醒，或被顶下线，不确定该先改密还是先冻结。
2. 手机丢失，微信、支付宝、网银和绑定银行卡同时暴露。
3. 游戏或社交账号被盗但没绑支付，用户问“改个密码是不是就够了”。
4. 已经改过密码，仍然被踢下线或再次被盗，怀疑设备或找回通道也失守。
5. 想把重要邮箱/账号与论坛、订阅、抽奖等日常注册分开，但不知道边界怎么划。

### 语言信号 (用户的话里出现这些就应激活)

- “账号被盗了，先改密码还是先冻结？”
- “改完密码还是被顶下线”
- “手机丢了，微信和银行卡怎么办”
- “密保问题/生日被知道了”
- "my account was hacked", "account takeover", "should I freeze or reset first", "logged out on all devices"

### 与相邻 skill 的区分

- 与 `identity-deception-detection` 的区别: 后者判断“这个网站/链接/证书是不是假的”；本 skill 处理“账号已经或可能失守后，四层怎么补、先做哪一步止损”。
- 与 `malware-triage-order` 的区别: 后者处理主机上的木马、持久化与恶意代码；本 skill 处理账号侧的凭据、隐私、支付与应急。怀疑设备被植入木马时两者应并行，但不能用改密代替清马。
- 与 `data-backup-recovery-discipline` 的区别: 后者恢复系统与数据；本 skill 恢复的是账号控制权与支付安全。
- 与 `hidden-account-hunt` 的区别: 后者是发现隐藏账户的可见性问题；本 skill 是保护现有账户并止损。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先定损：确认是否正在发生损失**
   - 检查异常登录提醒、支付/转账记录、绑定设备与代充记录。
   - 完成标准: 列出受影响账号、可疑设备/会话、已发生或可能发生的资金动作。
   - 判停条件: 若正在转账、银行卡已泄露或手机丢失，跳过其余诊断，直接进入步骤 2。

2. **先止损：执行应急层动作**
   - 冻结账号、踢出所有会话、挂失银行卡、关闭免密与代充；记录工单号与时间。
   - 完成标准: 账号处于冻结或强制下线状态，银行卡挂失已受理，支付通道已关闭。
   - 判停条件: 若找回依赖的生日/密保答案也已泄露，不要继续用知识问答自助找回，改走官方人工核验。

3. **再封堵凭证层**
   - 换用唯一且不含姓名、生日、手机号的密码；开启二次验证；移除未知登录设备与授权应用；更换可用的找回邮箱/手机。
   - 完成标准: 所有旧会话失效，二次验证生效，设备与授权列表无未知项，找回通道可用且不依赖公开信息。

4. **核查隐私层与支付层**
   - 检查聊天记录、绑定信息、文件传输与好友通知；检查支付密码、数字证书、钱包锁、自动扣费与代充。
   - 完成标准: 无未知绑定、授权或扣费，支付保护全部开启，必要时已通知可能被二次诈骗的联系人。

5. **最后找回并重建分层**
   - 通过官方申诉找回账号；把重要账号与日常注册分开；复核改密策略，避免“每月强制改密”催生可预测弱口令。
   - 完成标准: 账号已找回并可正常登录，重要/备用账号清单与找回方式已记录。
   - 判停条件: 若完整重置后仍反复失守，转 `malware-triage-order` 排查终端，必要时重装而不是继续改密。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 只是要判断一个登录页/链接/证书真假：这是身份欺骗检测问题，转 `identity-deception-detection`；在本 skill 里继续分析域名会重复且容易漏判。
- 主机上发现木马、可疑进程或持久化项：先按 `malware-triage-order` 处置终端；只做账号四层会留下再次窃取的入口。
- 系统崩溃、误删、需要还原或重装：属于 `data-backup-recovery-discipline` 的恢复半径问题。
- 用户只是想要一条强密码建议、没有任何失陷迹象：不必启动四层流程，给出最小凭证建议即可。

### 作者在书中警告的失败模式

- **只改密码不够**: QQ 木马案例说明凭据会在输入侧被截获；改密不清设备、不查找回通道，等于只换锁不赶人（PAGE 117–119）。
- **先找回后止损是错的**: 微信与网银案例都把冻结、挂失放在找回之前；先申诉会延长损失窗口（PAGE 125–126）。
- **强制频繁改密可能导致弱口令**（ce26）: 每月改密会催生月份、序号等可预测变体，生日/提示问题找回又常能从公开信息猜到，二者叠加是假安全（PAGE 231）。
- **把“看不到进程”当成安全**: 木马采用插入技术、不产生独立进程，任务管理器干净不代表凭据没被截获（PAGE 117）。

### 作者的盲点 / 时代局限

- 场景停留在 2019 年的 QQ/微信/网银客户端，冻结与挂失入口已变化；书中的数字证书更多指旧式网银证书，不等于现代的设备绑定或通行密钥。
- 未覆盖短信转移（SIM swap）、OAuth 授权令牌窃取、企业 SSO、passkey、找回邮箱被接管等当代主要接管路径。
- 对“应急路径是否真的走得通”只给操作，不给演练与回退；冻结后如何证明身份、申诉失败怎么办，书中没有展开。
- 一边建议高频改密，一边要求口令不含公开信息，未意识到强制轮换会反向制造弱口令。

### 容易混淆的邻近方法论

- `identity-deception-detection`: 判断入口真假；本 skill 处理失守后的分层止损。
- `malware-triage-order`: 终端恶意代码处置；本 skill 是账号资产处置，二者常需并行。
- `data-backup-recovery-discipline`: 数据与系统恢复；本 skill 恢复账号控制权与支付安全。
- `hidden-account-hunt`: 发现隐藏账户；本 skill 保护与止损现有账户。

## 相关 skills（阶段 3 定稿）

- `host-default-surface-convergence`（contrasts-with）：前者面向已失守账号的止损与重建，后者面向未失陷主机的默认值收敛；出现盗号迹象时顺序要反过来，先止损再加固。
- `email-trust-boundary`（composes-with）：邮箱是多数账号的找回通道；邮件入口失守或被接管后，直接转入本 skill 的应急层动作。
- `malware-triage-order`（composes-with）：凭据可能在输入侧被木马截获；只改密不清终端会再次失守，两者应并行而非互相替代。
