# 邮件信任边界与邮箱分层

## R — 原文 (Reading)

> "（1）查看附件大小……（2）查看邮件地址……（3）识别真伪退信。"
>
> — 网络安全技术联盟, 第12章 12.1.2 识别电子邮件病毒（PAGE 228）

---

## I — 方法论骨架 (Interpretation)

邮件本身不产生病毒，它只是运输工具；风险落在附件、信纸模板和邮件客户端上，所以“正文看起来正常”不能作为放行理由。
把邮件当成低信任通道：任何一封邮件都先按不可信处理，再用独立渠道核实，而不是先打开、再判断。
三查是最低成本的第一道筛：附件类型与大小是否和内容相符、是否要求启用宏或输入解压密码；发件地址（不是显示名）是否陌生、域名是否与声称的机构一致；退信是否由自己刚发过的那封信触发、是否夹带附件并催促打开。
任一项异常就隔离邮件，绝不通过“打开附件看看”来验证；验证动作本身就会执行恶意代码。
结构性措施是邮箱分层：重要邮箱只用于关键业务与找回，不对外注册、订阅、抽奖或在论坛公开；这些场景一律用可公开、可弃用的备用邮箱。
口令与找回要一起设计：唯一长口令、二次验证、找回通道不依赖生日或姓名等公开信息；避免每月强制轮换，因为它会催生可预测的变体。
垃圾邮件默认拒绝，而不是先接收再让用户自行判断；白名单与举报通道比“员工自己小心”更可靠。
这些措施把“每封邮件都要靠人判断”变成“默认不信任、少数可信通道、可快速止损”。

## A1 — 书中的应用 (Past Application)

### 案例 1: 流光字典命中——邮箱口令被猜中
- **问题**: 作者要说明邮箱密码如何被获取，目标邮箱使用 POP3。
- **方法论的使用**: 在流光中添加 POP3 主机、用户名和字典，勾选解码后开始探测；分析重点落在“字典能否由公开信息生成”，而不是传输层是否加密。
- **结论**: 邮箱口令的风险不只在复杂度，还在是否可被公开信息拼出；防御侧应使用唯一且非公开信息生成的口令，并加二次验证、减少邮箱暴露。
- **结果**: 字典选择正确时，破解出正确的邮箱密码（PAGE 229–230）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 收到自称 HR、财务、快递或平台客服的邮件，带 zip/exe/宏文档附件，问能不能打开。
2. 收到“退信”，附件写着“邮件正文”，但自己近期并没有发过那封信。
3. 发件人显示名很熟，完整地址或域名却差一个字母，或来自免费邮箱。
4. 想把重要邮箱只用于关键业务和找回，论坛、订阅、抽奖改用备用邮箱。
5. 邮箱已经出现异常登录、自动转发或垃圾邮件暴增，需要同时处理入口与结构。

### 语言信号 (用户的话里出现这些就应激活)

- “这封邮件能不能打开？”
- “附件是个 zip，说是工资表”
- “这是不是真退信？”
- “重要邮箱要不要拿来注册网站？”
- “邮箱老收到垃圾邮件，要不要先收下来再删？”
- "is this email safe to open", "suspicious attachment", "fake bounce", "important vs disposable email", "spam reject vs accept"

### 与相邻 skill 的区分

- 与 `identity-deception-detection` 的区别: 后者判断 URL、链接真实指向与证书主体；本 skill 只做“先别点、先隔离、再用独立渠道核实”，不重复其判据。
- 与 `malware-triage-order` 的区别: 后者处理附件已执行后的主机恶意代码；本 skill 侧重执行前的信任判断与执行后的第一分钟止损。
- 与 `account-compromise-layering` 的区别: 后者处理邮箱已被接管后的账号四层止损；本 skill 处理邮件入口与邮箱结构，二者在“已失守”场景衔接。
- 与 `data-backup-recovery-discipline` 的区别: 后者负责 PST/邮件备份与恢复；本 skill 把备份视为补救，不作为防护。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先隔离，不打开**
   - 不双击附件、不启用宏、不输入解压密码；把邮件移到隔离区或暂不处理。
   - 完成标准: 附件未被打开，邮件已单独标记或隔离。
   - 判停条件: 若用户已经双击或启用宏，跳过三查，直接进入步骤 4。

2. **做完三查并留证据**
   - 查附件（类型、大小、是否可执行/脚本/快捷方式、是否要求宏或密码）；查发件地址（完整地址与域名，不只看显示名）；查退信（自己是否刚发过信、收件地址是否写错、退信是否夹带附件）。
   - 完成标准: 三项各有“正常/异常/无法判断”的结论与依据。
   - 判停条件: 任一项异常，按恶意邮件处理并通知收件人，不再尝试打开验证。

3. **用独立渠道核实发件人**
   - 通过已知电话、内部通讯录或当面核实；不回复该邮件、不点邮件内链接；链接与证书真假转 `identity-deception-detection`。
   - 完成标准: 发件人已通过独立渠道确认，或仍维持不可信状态。
   - 判停条件: 无法独立核实时保持隔离，不因“看起来像官方”而放行。

4. **若已打开或执行：先止损再清理**
   - 立即断网并隔离主机，修改邮箱密码、撤销所有会话与异常转发规则、开启二次验证，通知相关联系人；PST 备份只用于事后恢复邮件，不是清除恶意代码的手段。
   - 完成标准: 主机已隔离，旧会话失效，异常转发与规则已清除。
   - 判停条件: 出现加密、横向扫描或持久化迹象，转 `malware-triage-order`。

5. **重建邮箱分层与默认拒绝**
   - 列出重要邮箱与备用邮箱；重要邮箱退出所有外部注册与订阅，备用邮箱承担论坛、抽奖和公开联系；配置垃圾邮件默认拒绝、附件类型限制与举报通道；复核口令轮换策略，取消“每月强制改密”。
   - 完成标准: 分层清单落地，重要邮箱暴露面收敛，垃圾邮件策略与举报通道可用。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 需要判断钓鱼站点、链接真实指向或证书主体：转 `identity-deception-detection`；本 skill 只做“先别点、先隔离、再核实”。
- 主机已经执行了附件、出现木马或勒索迹象：转 `malware-triage-order`；继续分析邮件会耽误终端止损。
- 需要配置 SPF/DKIM/DMARC、分析 Received 邮件头、做邮件网关选型或取证：这些在本书范围之外，本 skill 不提供相应判据。
- 需要 PST 备份、系统还原或数据恢复：属于 `data-backup-recovery-discipline`；PST 只是邮件补救，不是安全边界。
- 只是写一封正常业务邮件、没有可疑输入：不需要启动信任边界流程。

### 作者在书中警告的失败模式

- **三查不是充分条件**（ce25）: 恶意附件可以很小，例如脚本、快捷方式、宏文档或下载器；熟人账号被盗后发件地址完全可信；大附件也可能是正常业务文件（PAGE 228）。
- **SSL 不保护账号被骗**（ce24）: TLS 只保护传输，不保护弱口令、撞库、钓鱼页和键盘记录；书中随后就用字典破解邮箱口令，与“必须先攻破 SSL”的判断自相矛盾（PAGE 228–230）。
- **不要打开附件验证**: 验证动作本身就会触发宏、脚本或漏洞利用；正确做法是隔离并按恶意处理。
- **PST 备份只是补救**: 备份只能找回邮件，不能阻止再次中招，也不能清除已执行的恶意代码。
- **轻信退信**: 假冒退信会带附件并催促查看，真退信通常只回显正文；退信本身不是可信系统消息（PAGE 228）。

### 作者的盲点 / 时代局限

- 语境停留在 2019 年的 POP3、Outlook 与 PST，未覆盖云邮箱、MFA/passkey、OAuth 同意钓鱼、二维码钓鱼、同形字域名与现代邮件安全网关。
- 只给“三查”这一层用户侧判据，缺少 SPF/DKIM/DMARC、邮件头、附件沙箱、链接改写与域名信誉等服务器侧验证；这些必须标注为边界外，不能假装三查足够。
- “附件大小”作为判据本身很弱，作者没有给出附件类型白名单、宏策略或沙箱执行结果。
- 建议每月改密与“口令不含公开信息”并用，未意识到强制轮换会制造可预测弱口令；也未讨论找回邮箱被接管后的连锁接管。
- 未覆盖熟人账号被盗、鱼叉邮件、供应链邮件等“发件人可信但内容不可信”的情形。

### 容易混淆的邻近方法论

- `identity-deception-detection`: 判断 URL、证书与身份真假；本 skill 判断“邮件能不能信、附件能不能开”，并把链接真假转出去。
- `malware-triage-order`: 终端已执行后的恶意代码处置；本 skill 是执行前的隔离与执行后的第一分钟止损。
- `account-compromise-layering`: 邮箱已被接管后的账号四层止损；本 skill 侧重邮件入口与邮箱结构。
- `data-backup-recovery-discipline`: PST 与邮件备份恢复；备份是补救，不是防护。
