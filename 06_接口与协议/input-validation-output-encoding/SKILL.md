# 输入验证与输出编码

## R — 原文 (Reading)

> "对输入的数据进行过滤或标准化处理，然后进行验证。……禁止试图对验证失败的数据进行修复，自动错误恢复代码很可能改变请求的初始意图或者截断验证逻辑。……除非明确对目标编译器是安全的，否则对所有字符进行编码。"
>
> — GB/T 38674-2020, 5.1.1 d)、5.1.1 e)、5.1.2 a)

---

## I — 方法论骨架 (Interpretation)

数据要过两道闸门，且两道闸门的职责不许混。

入口闸门解决"这个值是不是我预期的形态"，顺序固定：先解码与标准化（统一字符集、统一路径与数字形式、剥掉双重编码），再按类型、长度、取值范围、边界值做白名单式验证，最后落到"通过"或"拒绝"两个结果之一。验证失败就整条拒绝，不截断、不补全、不做大小写纠正、不"尽力解析"——因为修复必须猜意图，而攻击者的输入恰好可以被改写成另一个仍然合法的请求。

出口闸门解决"这个值要去的语法环境是什么"。同一个字符串进 HTML 正文、HTML 属性、JS 字面量、CSS、URL 参数、SQL、XML、LDAP 过滤器、shell 命令、日志行，需要九套不同的处理；编码依据是落点，不是数据来源。SQL 与命令这类不允许字符级转义的地方要做语义净化（结构化 API、参数绑定、白名单），而不是删引号。

编码绑定输出点，不绑定入库点。入库只做验证与标准化，因为入库时还不知道未来有谁会读它。一个昵称被网页、CSV 导出、短信模板三处消费，就要三次编码；若在入库时统一做 HTML 编码，网页安全了，CSV 与短信却会双重转义或直接注入。

现代框架默认在模板层转义，此时最大的风险不是"没转义"，而是"重复转义导致显示错乱后有人关掉全局转义"，以及"框架管不到的落点"（拼 SQL、拼命令、写日志、跳转 URL、富文本白名单）被漏掉。要按落点逐个确认，而不是宣布"我们用了框架所以安全"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 字符串拼接的登录 SQL 被恒真条件绕过（附录 A.2.1.1.2）

- **问题**: 先用散列处理口令，再把用户名与口令拼进查询语句，交给语句对象执行。
- **方法论的使用**: 走入口闸门——用户名与口令来自请求，没有任何类型与长度校验；更要紧的是它们进入了 SQL 这个语法环境，而处理方式只是"拼接"，等于让数据与命令待在同一语法层。这里正确的做法不是补一个过滤函数，而是换掉出口机制：用参数化语句，让值只作为数据绑定。
- **结论**: 注入的根因是"数据与语法未分离"，不是"特殊字符没删"；参数化查询 + 基本长度校验才是配对答案，且增删改要同样处理。
- **结果（防住什么）**: 不修时口令传 `' OR '1'='1` 即让条件恒真，无需知道口令即可登录；参数化后注入串被当作普通字符串值，无法改变语句语义。

### 案例 2: 未净化的参数进入进程调用造成命令注入（附录 A.2.1.1.4）

- **问题**: 从运行环境读出一个目录值，拼进命令行交给进程执行接口。
- **方法论的使用**: 这是"语义净化"场景而不是"字符转义"场景——shell 会二次解释 `&`、`|`、`;`、换行。此处不该用黑名单删符号（黑名单永远落后于编码变形），而应对该参数做白名单正则（只允许字母、数字与少数必要符号），并把"一条命令"改为"参数数组"形式，杜绝 shell 参与解析。
- **结论**: 命令落点的正解是"不要让 shell 解释用户数据"；能结构化传参就不拼串，必须拼时只允许白名单字符。
- **结果（防住什么）**: 不修时把参数设为 `dummy & echo bad` 就能一条命令变两条，攻击者取得任意命令执行；白名单后分隔符被拒，追加命令失败。

### 案例 3: JSP 直接回显请求参数造成反射型 XSS（附录 A.2.1.2.2）

- **问题**: 页面把请求参数直接写进响应体，既没验证也没按 HTML 上下文编码。
- **方法论的使用**: 出口闸门看落点——这个值落在 HTML 正文，应按 HTML 实体编码；若落在属性、脚本块或 URL，则分别用对应编码。同一组防御还要覆盖存储型（从库里取出后回显）与 DOM 型（前端用字符串拼 innerHTML），因为落点相同、规则相同。
- **结论**: 编码在渲染处做，且要按具体插值位置选函数；Cookie 追加 HttpOnly 作为纵深，但不能替代编码。
- **结果（防住什么）**: 不修时任意反射参数都能执行脚本、读取会话 Cookie，并可蠕虫式传播；编码后特殊字符变成实体、脚本不执行，HttpOnly 阻断脚本取 Cookie。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 代码里出现字符串拼接的查询、shell 命令、XML 或 LDAP 过滤器，评审时被质疑"这样拼有没有问题"。
2. 页面或模板回显用户内容，需要决定"这里该用哪种转义、要不要再过滤一遍"。
3. 同一个字段被多个出口消费（网页、导出文件、短信/邮件模板、开放 API），争论"到底在入库时统一编码还是各自编码"。
4. 已经上了框架的自动转义，但仍有富文本、URL 跳转、日志写入、文件下载名等框架管不到的落点。
5. 收到一个具体 payload（`' OR 1=1`、`<img onerror>`、`$(id)`、`../../`），要判断现有校验能否挡住、挡不住该改哪一层。

### 语言信号 (用户的话里出现这些就应激活)

- "这个输入怎么过滤 / 要不要转义"（how to sanitize / should I escape this）
- "参数化查询是不是就够了 / 我用了 PreparedStatement 还安全吗"（is parameterized query enough）
- "这个 XSS payload 能过我的校验吗"（will this payload bypass my filter）
- "存库前统一编码行不行"（encode before storing / encode on input）
- "输出编码 / output encoding / context-aware escaping / 白名单校验"

### 与相邻 skill 的区分

- 与 `trust-boundary-mapping` 的区别：后者先回答"哪里要设闸门、闸门两侧是谁"，本 skill 只负责"闸门里放什么规则"。边界没画清就谈编码，容易在错误的层做正确的转义。
- 与 `authorization-and-least-privilege` 的区别：参数化能防注入但防不了越权；只按 ID 查询而不带属主条件属于授权问题，不是编码问题。
- 与 `logging-security` 的区别：日志是第九个输出上下文，写入前的过滤规则与本 skill 同源，但"记什么、不记什么、如何保完整性"归日志 skill。

## E — 可执行步骤 (Execution)

1. **为每个输入标注来源与预期形态**
   - 完成标准: 每个入参有一行"来源（表单/头/cookie/URL/消息/文件/环境）+ 预期类型 + 长度上下界 + 合法取值集合"；没有预期形态的字段被显式标为"自由文本"。
   - 判停条件: 若某字段是自由文本且会进入查询、命令或页面，先跳到步骤 3 按落点补救，不要指望入口白名单。

2. **在入口先标准化再验证，并让失败分支只有拒绝**
   - 完成标准: 代码里能看到"解码/规范化 → 校验 → 通过或拒绝"的顺序；校验函数返回布尔或抛异常，不返回"清洗后的值"；不存在截断、补全、默认取第一个之类的修复分支。

3. **列出该值的全部出口，逐个标注目标语法**
   - 完成标准: 输出清单覆盖 HTML 正文、属性、JS、CSS、URL、SQL、XML、LDAP、OS 命令、日志、响应头；每个出口写明用哪种机制（编码函数、参数绑定、结构化 API、白名单）。
   - 判停条件: 若某出口无法用结构化机制（如必须拼命令行），转入白名单字符集方案并记录允许的字符范围。

4. **把编码装到输出点，而不是入库点**
   - 完成标准: 存储层只做验证与标准化；每个渲染/拼装点各自调用对应编码；同一字段在多出口时验证"每处都有独立编码且互不影响"（导出与短信不出现 HTML 实体）。

5. **做一次绕过复核**
   - 完成标准: 用双重编码、宽字符、大小写变形、注释符、换行、超长输入各试一遍；确认框架默认转义未被关闭、未被二次转义、富文本白名单只允许预期标签与属性；每条结论落到"拒绝/编码/无害"三种之一。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 判断"用户 A 能不能看用户 B 的订单"：这是对象级授权，编码再正确也拦不住改 ID 的越权。
- 选择加密算法、密钥长度、随机数源：属于敏感数据与密码学范畴，与本 skill 无交集。
- 防御解压炸弹、递归解析、超长请求导致的资源耗尽：这类问题靠配额、超时与条目计数，不靠字符校验。
- 已经确认"数据全程不离开内存、不进入任何解释器"的内部计算：此时做输出编码是无效劳动。

### 作者在书中警告的失败模式

- **ce01 对验证失败的数据做"自动修复"**：校验不通过就截断、补全、"尽力解析"后继续，攻击者可用超长 payload 让截断后只剩合法前缀，或让"纠正"把编码后的危险字符还原；修复分支提前返回还会截断同一请求里后续的校验步骤。
- **ce02 把不可信数据拼进 SQL / 命令 / XML**：拼接之后数据与命令同处一个语法层，解析器无法区分值与语法；黑名单永远落后于 URL 编码、宽字符与注释符变形，只有参数化与结构化 API 才从根上消除改写可能。
- **ce06 信任前端校验与客户端状态**：只在浏览器里做格式校验，服务端直接入库或直接使用；前端校验只改善体验，不构成信任边界。

### 作者的盲点 / 时代局限

- 标准把"集中输入验证"当成默认最优，却没讨论集中化的失效模式：一条规则写错会打穿全部业务，且文件导入、消息消费、内部 RPC 常绕过统一验证器形成影子入口。集中化的前提是有一张入口清单和覆盖证明，否则"统一"只是"统一地漏"。
- 示例停留在 JSP 与手写转义的时代，未覆盖现代框架默认转义带来的新问题：重复编码导致显示错乱，团队于是关掉全局转义；也没有涉及 CSP、Trusted Types、富文本白名单库、LLM 提示注入与模型输出不可信这些 2020 年后的主流上下文。

### 容易混淆的邻近方法论

- 信任边界与不可信数据追踪：它决定闸门装在哪，本 skill 决定闸门里放什么；两者顺序不能反。
- 数据库访问安全中的账户权限与行级控制：与本 skill 的"参数化查询"同属数据库话题，但一个防注入、一个防越权取数。
