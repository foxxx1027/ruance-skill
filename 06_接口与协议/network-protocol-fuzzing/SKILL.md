# 网络协议与服务漏洞挖掘

## R — 原文 (Reading)

> “虽然 FTPFuzz 程序可以快速实现 FTP 协议的安全测试，但是在处理需要登录的情况时会出现一些失败的现象。在实际使用中，可以将 FTPFuzz 程序作为初步测试工具使用，之后还要结合 Python 脚本进行更加深入的 FUZZ 测试。”
>
> — 王清 等，《0day安全：软件漏洞分析技术（第二版）》第 18 章 18.2

---

## I — 方法论骨架 (Interpretation)

网络协议挖掘的对象不是“一个输入框”，而是**一个有状态的命令集合**。方法的核心是把服务的攻击面拆成“命令 × 参数 × 状态”三个维度，再按优先级逐条测试。

**第一步是画状态机、列命令清单。** 从 RFC、帮助文档和正常交互中把协议命令逐条列出：建立连接、认证、会话、功能操作、退出。每条命令都当作独立攻击面；命令后的每个参数都当作一个可变异字段。优先级通常是：认证命令（USER/PASS、login 的用户名/密码）→ 会话/状态命令（LIST、CWD、SELECT boxname）→ 功能命令（取信、下载、删除、管理）。认证参数之所以优先，是因为它是进入后续功能的门，而且登录名/密码往往被直接拿去做字符串拼接、路径拼接或内存拷贝。

**第二步是选封装层次。** 用现成库（smtplib/poplib/imaplib）能快速完成标准交互，但库把命令细节藏起来，无法发送非标准/无认证/精细定制的原始命令；要逐条命令定点测试，就用 socket 手工封包。判断标准是“可控粒度”：需要控制每一个字节、每一个命令顺序时，手工封装；只需要快速跑通常规流程时，用库。

**第三步是必须通过认证。** 通用 Fuzz 工具常常在登录环节失败，登录后的命令根本没被测到。自己写脚本时，第一步就是用 `USER`/`PASS` 或库的登录函数建立合法会话，再在认证后的状态里发畸形命令。认证本身不是测试重点，但不能被它挡住。

**第四步是黑盒定位处理函数。** 对没有源码的服务，在数据进入进程的系统调用上下断：OllyDbg 的模块窗口找 `WS2_32.dll`，在 `WSARecv`/`recv` 上按 F2，运行目标；断下后用 Ctrl+F9 执行过当前调用、F7/F8 单步，盯住堆栈/内存窗口里自己发送的字符串，沿着“数据被哪个函数消费”一路跟到处理函数。这样就把“网络包”与“漏洞函数”连了起来。

**第五步是从数据的二次用途反推漏洞类型。** 不要因为发送超长数据导致崩溃就认定是栈溢出。看清楚数据被程序拿去做了什么：拼文件路径 → 可能是路径长度/路径回溯；当数组下标 → 可能是越界访问；当长度字段 → 可能是整数溢出/越界拷贝；当格式串 → 可能是格式化串。漏洞类型由“用途”决定，不由“长度”决定。

**第六步是入口转移。** 一条输入面被封堵时，不要停手：管理通道加密，就找 GUI/配置文件/日志设置里的同一后端参数；客户端过滤了 `/` 和 `\`，就用调试器直接改写内存中即将被使用的字符串；协议端口没有溢出，就读产品文档找远程管理、日志、导入导出等额外功能面。同一后端功能往往有多个前端入口。

**第七步是工具只做初测。** FTPFuzz、SPIKE 这类工具擅长快速批量替换命令参数、发现浅层崩溃；它们不擅长登录/会话保持、加密通道和深度定向测试。工具跑出崩溃后，要接调试器确认、写 Python 脚本复现、按命令清单逐条深入。

## A1 — 书中的应用 (Past Application)

### 案例 1: MailCarrier 的 SMTP HELO 超长参数溢出（第 19 章 19.1.2）
- **问题**: MailCarrier 2.51 的 25 端口历史上存在远程缓冲区溢出；需要验证当前版本是否仍可触发，并找到处理 HELO 命令的函数。
- **方法论的使用**: 先按 SMTP 命令清单锁定 `HELO`，用原始 socket 手工封装 `HELO` + 5100 字节 buffer 发送；同时用 OllyDbg 附加负责接收 SMTP 命令的 `smtpr` 进程，观察异常。
- **结论**: 认证前的命令同样是攻击面；库函数会隐藏命令细节，要精确控制参数长度和命令格式，必须手工封包。
- **结果**: 发送超长 `HELO` 后 OllyDbg 捕获到异常，验证了该版本仍存在可触发的溢出问题。

### 案例 2: TurboMail POP3 用户名拼路径导致 DOS（第 19 章 19.2.2）
- **问题**: 用 260 字节的用户名调用 `M.user(ar)` 后 TurboMail.exe 崩溃；表面看像“用户名太长导致溢出”，但真正原因不明。
- **方法论的使用**: 先在 `WS2_32.dll` 的 `WSARecv` 上下断，确认 `USER AAA…` 被进程接收；再用 Ctrl+F9/F7/F8 单步，跟踪到程序把“邮件域名 + 用户名”拼成一个完整文件路径，去打开该用户目录下的 `account.xml`。拼接后的路径超过 Windows 260 字节限制，打开非法路径时崩溃。
- **结论**: 数据的二次用途是“拼路径”，所以漏洞类型是路径长度/非法路径导致的 DOS，而不是典型栈溢出；漏洞成因仍是缺少输入合法性校验，与溢出同源。
- **结果**: 定位到认证关键函数与路径拼接点，确认 TurboMail 4.3.0 的 POP3 用户名长度未校验。

### 案例 3: TurboMail IMAP4 的 `boxname` 超长参数溢出（第 19 章 19.3.2）
- **问题**: IMAP4 登录后可以用 `M.select(boxname)` 选择邮箱文件夹；`boxname` 是功能命令参数，是否也存在长度校验缺失？
- **方法论的使用**: 按命令清单把“认证后功能命令”列为第二优先级；构造超长 `boxname` 调用 `select`，观察服务端是否崩溃，再用调试器确认崩溃点。
- **结论**: 认证参数之外，状态/功能命令的参数同样是高价值攻击面；它们常被直接拿去做内存操作或文件操作。
- **结果**: TurboMail 在处理 IMAP4 邮箱选择命令时未限制文件夹名长度，超长 `boxname` 导致服务程序崩溃。

### 案例 4: Kerio Mailserver 管理通道的路径回溯（第 19 章 19.4.2）
- **问题**: 对 Kerio 做了一轮协议 Fuzz，没有发现溢出；管理端与服务端之间的数据还是加密的，直接改包走不通。
- **方法论的使用**: 先接受“协议端口无溢出 ≠ 产品无漏洞”，转而读帮助文档，发现“远程管理”功能面；抓包发现管理通道加密后，改从 GUI 的“日志设置”找同一后端参数；在客户端过滤 `/` 和 `\` 的情况下，用 OllyDbg 在内存中把日志文件名改成 `../../../../1.txt`，验证服务端是否真的校验。
- **结论**: 功能入口被封堵时要换另一条；客户端过滤不代表服务端过滤；同一后端功能可以通过 GUI/内存注入绕过传输层加密。
- **结果**: 成功让日志查看功能读取服务器任意文件，作者将这一 0day 上报给厂商并得到确认。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 目标是一个 FTP/SMTP/POP3/IMAP4 服务，需要系统性地枚举命令与参数，而不是只测一个登录框。
2. 通用 Fuzz 工具一跑到登录/认证就失败，或者登录后的命令完全没有被覆盖。
3. 需要判断“先测哪些命令”：登录用户名/密码、`USER`/`PASS`、`LIST`/`CWD`/`RETR`、`SELECT boxname` 等。
4. 服务端崩溃了，但不知道是哪个命令、哪个处理函数、属于溢出还是路径/权限问题。
5. 管理通道或协议数据被加密，改包走不通，需要找 GUI、配置文件、日志设置等替代入口。
6. 协议 Fuzz 没发现溢出，需要判断是否还应继续测产品的其他功能面（远程管理、日志、导入导出）。

### 语言信号 (用户的话里出现这些就应激活)

- “FTP 服务怎么挖 / FTPFuzz 怎么用 / CWD 命令能不能溢出”
- “SMTP/POP3/IMAP4 的命令清单 / 登录参数要不要测”
- “工具有登录就失败 / 怎么保持会话 / 认证后怎么 Fuzz”
- “WSARecv 下断 / recv 断点 / 怎么跟到处理函数”
- “数据包是加密的 / 改不了包 / 管理端连不上”
- “服务端没崩是不是就没漏洞 / 路径回溯怎么测 / 550 代表什么”
- “protocol fuzzing / service fuzzing / command fuzzing / authenticated fuzzing”

### 与相邻 skill 的区分

- 与 `non-memory-vulnerability-analysis` 的区别：那个 skill 处理 Web/邮件/客户端功能点里的参数注入、XSS、路径回溯与访问控制，入口是 HTTP/表单/文件路径；本 skill 处理网络协议服务的命令、状态机、认证会话与接收 API。若目标是“Web 下载接口的 `urlOfAttach` 参数”，走前者；若是“FTP 的 `CWD`/`RETR` 命令或邮件服务的 `USER`/`SELECT` 命令”，走本 skill。
- 与 `logic-and-isolation-bugs` 的区别：那个 skill 处理竞争条件、TOCTOU、类型混淆、沙箱逃逸，核心是时序与对象模型；本 skill 处理协议命令参数与状态机，核心是攻击面枚举与会话保持。若现象是“认证检查与命令执行之间有时间差”，可转前者；若只是“某条命令参数没校验”，用本 skill。
- 与 `vuln-analysis-strategy` 的区别：那个 skill 是跨范式选型（Fuzz/静态/补丁比较/逆向/调试）；本 skill 是在选定协议 Fuzz 后的具体执行流程。若还没决定是否用 Fuzz，先走前者。
- 与 `fuzzing-strategy` 的区别：那个 skill 负责 Blind/Smart、样本/模型、工具与变异策略；本 skill 负责协议命令清单、登录会话、接收 API 下断与入口转移。两者组合使用：先用本 skill 画攻击面，再用 `fuzzing-strategy` 选用例生成方式。
- 与 `file-format-vulnerability-reversing` 的区别：本 skill 的输入是网络字节流与协议状态；文件格式解析走后者。
- 与 `kernel-driver-fuzzing` 的区别：本 skill 是用户态网络服务；驱动设备名/IOCTL 走后者。

## E — 可执行步骤 (Execution)

1. **画协议状态机与命令清单**
   - 从 RFC、帮助文档、正常客户端抓包中列出：连接/握手、认证、会话、功能、退出各阶段的命令与参数；标出哪些命令需要登录后才能用。
   - 完成标准: 得到一张“状态 → 命令 → 参数 → 预期响应”的清单，认证前后的命令分开。
   - 判停条件: 若协议是私有/加密且命令语义完全未知，先做协议逆向或找客户端库，不要盲目发包。

2. **排优先级：认证参数优先**
   - 把 `USER`/`PASS`、`login` 的用户名/密码放在第一优先级；其次是 `LIST`/`CWD`/`RETR`、`SELECT boxname`、`MAIL FROM`/`RCPT TO` 等功能参数。
   - 完成标准: 每条命令都有明确的“先测什么参数、用什么畸形值”的计划。
   - 判停条件: 若目标没有认证，直接从功能命令开始；不要因为没有登录环节就跳过命令清单。

3. **选择封装方式并建立合法会话**
   - 需要快速跑标准流程时用库（smtplib/poplib/imaplib）；需要控制原始命令、无认证模式或精细变异时用 socket 手工封包。脚本第一步完成登录并保存会话状态。
   - 完成标准: 脚本能稳定登录、执行一条正常功能命令并读到预期响应。
   - 判停条件: 若登录失败，先解决凭据/加密/验证码/多步握手，不要在没有会话的情况下测功能命令。

4. **建立正常基线并逐条变异**
   - 先记录每条命令在正常参数下的响应码/响应内容；再每次只对一条命令的一个参数做变异：超长字符串、格式串、路径回溯、特殊字符、边界数值。
   - 完成标准: 每个用例都能对应到“哪条命令、哪个参数、什么畸形值”，并能区分正常响应与异常响应。
   - 判停条件: 若服务端返回统一的错误页/直接断开，先确认是否是协议格式错误或前置校验，不要误判为“无漏洞”。

5. **接调试器，在接收 API 下断**
   - 附加目标进程，在 `WS2_32.dll` 的 `WSARecv`/`recv` 上下断；断下后用 Ctrl+F9 执行过当前调用、F7/F8 单步，盯住堆栈/内存中的攻击者数据，跟到处理函数。
   - 完成标准: 能指出“这条命令的数据在哪个函数、哪一行被消费”，而不是只知道服务端崩了。
   - 判停条件: 若目标有反调试/崩溃保护，先换调试方式或转本地复现，不要在没有现场的情况下猜根因。

6. **按数据二次用途判断漏洞类型**
   - 看数据被拿去做什么：拼路径 → 路径长度/路径回溯；当数组下标 → 越界；当长度 → 整数溢出/越界拷贝；当格式串 → 格式化串；当 SQL/命令 → 注入。
   - 完成标准: 能说出“漏洞类型 + 触发条件 + 关键字段”，并解释为什么不是其他类型。
   - 判停条件: 若数据用途仍不清楚，继续单步跟踪到消费点，不要用“超长导致崩溃”直接下结论。

7. **入口被封堵时换另一条**
   - 管理通道加密 → 找 GUI/配置文件/日志设置/导入导出；客户端过滤 → 用调试器改写内存参数；协议端口无溢出 → 读产品文档找远程管理、附加服务、Web 接口。
   - 完成标准: 至少验证一条替代入口能到达同一后端功能，并确认服务端是否校验。
   - 判停条件: 若所有入口都需要高权限且无法获得，记录为“受权限限制”，不要伪造结论。

8. **从工具初测升级到脚本深入**
   - 工具（FTPFuzz/SPIKE 等）只用于快速枚举命令和浅层崩溃；对可疑点写 Python 脚本复现、按命令清单逐条深入、保存每个用例的请求/响应/崩溃现场。
   - 完成标准: 形成可复现的最小 PoC 与命令清单覆盖表；明确哪些命令已测、哪些未测、哪些因登录/加密未覆盖。
   - 判停条件: 若需要 exploit 构造，转 `exploit-chain-construction`；若需要从崩溃回溯根因，转 `crash-to-root-cause`。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **目标是 Web 应用的 HTTP 参数注入/XSS/越权**：应走 `non-memory-vulnerability-analysis`；本 skill 的命令清单与接收 API 下断不适用于 HTTP 业务参数。
- **目标是文件解析器**：畸形文件进入 Office/PDF/图片解析器的问题走 `file-format-vulnerability-reversing`；协议服务与文件格式的输入通道不同。
- **目标是内核驱动/IOCTL**：设备名、控制码、MITM 调用链走 `kernel-driver-fuzzing`；不要在用户态 socket 层套用。
- **已经拿到崩溃、只需要构造 exploit**：本 skill 只到“定位处理函数/判断类型”，利用构造走 `exploit-chain-construction`。
- **协议完全私有且加密，且没有客户端/文档可借**：先做协议逆向；在命令语义未知时发包，响应无法解释，Fuzz 只会产生噪声。
- **生产环境或没有崩溃隔离的环境**：协议 Fuzz 会导致服务崩溃/连接耗尽；必须在隔离环境或获得明确授权后进行。

### 作者在书中警告的失败模式

- **通用 Fuzz 工具在登录场景失败**：FTPFuzz 处理需要登录的情况会出现失败，登录后的命令根本没被测到；工具只能作初测，之后要用 Python 脚本（第 18 章 18.2）。
- **只 Fuzz 协议端口，漏掉产品其他功能面**：Kerio 协议 Fuzz 没有发现溢出，但帮助文档里的“远程管理”藏着路径回溯；没测出溢出 ≠ 没有漏洞（第 19 章 19.4.2）。
- **看到加密就放弃**：管理通道数据全是“乱码”只说明传输加密，不代表 GUI/内存中的参数不可改；作者改从日志设置和内存注入完成了利用（第 19 章 19.4.2）。
- **把客户端过滤当成服务端过滤**：界面过滤了 `/` 和 `\`，服务端未必过滤；用调试器直接改写内存字符串即可验证（第 19 章 19.4.2）。
- **只测认证、不测功能命令**：认证是入口，但 `boxname`、`CWD`、`LIST` 等功能参数同样可能溢出或路径回溯（第 19 章 19.3.2）。
- **路径回溯只校验前缀**：只判断 `/maildata/` 开头，追加 `/../` 即可绕过；必须在范式化后做访问控制（第 19 章 19.4.1）。
- **把“服务端没崩”当成“没有漏洞”**：路径回溯、越权、任意文件读写不会让服务崩溃；测试计划必须包含非内存类检查（第 19 章 19.4.1）。
- **把超长导致的崩溃一律当栈溢出**：TurboMail 的 POP3 用户名崩溃实际是拼路径超过 260 字节；要先看数据的二次用途（第 19 章 19.2.2）。

### 作者的盲点 / 时代局限

- **2011 年的明文协议环境**：书中 FTP/SMTP/POP3/IMAP4 默认明文、无 TLS/STARTTLS、无 MFA/速率限制；现代服务普遍加密、有认证锁定与 WAF，直接照搬命令与 payload 会被传输层挡住。
- **工具与平台绑定旧版本**：FTPFuzz 1.0、OllyDbg、Windows XP/2003、旧版 Quick 'n Easy/TurboMail/Kerio；现代服务版本、64 位进程、ASLR/DEP 与日志审计会让地址与崩溃行为不同。
- **命令清单偏 RFC 基础集**：未覆盖现代协议扩展（SMTP AUTH、IMAP IDLE/UTF-8、FTP over TLS、HTTP/2 等），也缺少对 API/JSON/gRPC 等现代服务接口的映射。
- **依赖人工单步与手工脚本**：没有 coverage feedback、协议状态自动推断、语料调度与自动 triage；面对复杂状态机时覆盖高度依赖测试者经验。
- **“崩溃=漏洞”的倾向**：书中以调试器捕获异常为主，未系统区分 DoS、信息泄露与可 RCE 的崩溃；现代测试需要可利用性评估与去重。

### 容易混淆的邻近方法论

- **`non-memory-vulnerability-analysis`**：Web/客户端参数注入、XSS、路径回溯、访问控制；本 skill 是网络协议服务的命令/会话层。路径回溯在两者都出现，区别在入口：HTTP 参数走前者，FTP/邮件命令走本 skill。
- **`fuzzing-strategy`**：通用 Fuzz 范式与 Smart Fuzz 用例生成；本 skill 是协议攻击面枚举与会话保持。先画命令清单，再选用例生成策略。
- **`logic-and-isolation-bugs`**：竞争/TOCTOU/类型混淆/沙箱逃逸；本 skill 不分析时序窗口与类型布局，只做命令参数与状态机。
- **`vuln-analysis-strategy`**：跨范式选型；本 skill 是协议 Fuzz 的具体执行。
- **`file-format-vulnerability-reversing`**：文件解析器；本 skill 是网络字节流。
- **`kernel-driver-fuzzing`**：内核 IOCTL/MITM；本 skill 是用户态服务。
